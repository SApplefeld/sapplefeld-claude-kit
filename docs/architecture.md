# Kit Architecture

The kit is a Claude Code plugin plus the repo material that maintains it. Almost all of it is prose: skills the model loads on demand, agent definitions, an output style the harness applies to every main-thread session, and a doctrine file that ships to the user's home directory. The exceptions are the pieces with real runtime behavior: the Node hooks wired to session and tool events, the `memq` CLI over the memory store, the status line's two files, the repo-only size reader `kit-size.js` that measures the corpus against a committed budget, and the repo-only scenario-probe runner that reads that prose back through a cold model. The set is named rather than counted, because a count of it restated here is an invariant nothing checks.

That split is the thing to hold onto when changing anything here. Prose surfaces are behavior-shaping text whose general gate is the writing-skills RED/GREEN check; the code surfaces have a real gate under `test/`. One gate reaches both corpora, and it measures rather than judges: the size ratchet the next paragraph describes. The exceptions are the prose surfaces that carry a copy of text whose source is elsewhere: the home doctrine mirrors the doctrine whole, the output style copies its register core, and the two code-reviewer charters copy executing-work's behavior-or-claim class definition, so `test/doctrine-parity.test.js`, `test/output-style-parity.test.js` and `test/claim-class-parity.test.js` hold those copies byte-identical to their sources. Identity is not presence, and the doctrine gate covers both: its tests are one whole-body comparison plus a set of presence pins: assertions pinning individual rules present and the far ends they route to, a group holding one drift class where an amendment falsifies an unchanged sentence elsewhere, the pointer pairs naming the coordinator skill and the role skill, whose near ends are the repo README's payload map and the peer-sessions Roles section rather than any doctrine bullet, a group holding a deliberate duplication in step, where one rule is stated in full in the doctrine and again at the point of action and only a pin keeps the two statements saying the same thing, and a group over the seats' own contracts, the coordinator's function enumeration held against the count that enumeration states, the standing-delegation model's exclusions and the three refusal rules it composes with, the reciprocal kaizen routing duty, and the coordinator board's routing and homing claims, which are held on the skill and on the surfaces that restate them, the two curated indexes and the audit artifact's coordinator section, since a claim restated on a sibling surface is an invariant nothing checks and one dropped destination reddens nothing on its own. Some of the pins are structural rather than a list of sites, and they are the shape the gate cadence earned: one sweeps every shipped kit document plus the doctrine mirror and the repo and docs indexes for any prose describing the trunk property the pre-push gate keys on, and requires each hit to be a listed carrier stating that condition in one shared wording, so a reword reaching some surfaces and not others reddens; another sweeps every skill file for a paragraph performing a git integration and requires that paragraph to name the lane its action takes or to carry an anchored exemption with the rule behind it, each exemption asserted to still match something so a stale entry reddens rather than quietly widening the sweep's silence; and another sweeps every tracked file, the owner of those classes, the pin's own file and every archived document exempt by name, for a paragraph naming enough of the classes that retire a test to be enumerating them rather than using one of the names in passing, and requires each such paragraph to name the skill those classes live with rather than to state its own definition of them, so a class amended at its owner and left standing in a carrier nobody thought to re-read reddens wherever that carrier still spells the class the owner's way, a class renamed or dropped at the owner being the amendment the sweep cannot see, since the carrier then matches on the heads that did not change and passes every leg, with the append-only Chapters of a live plan document cut out of its reach for the same reason the archive is exempt whole, because history quotes a retired wording as its subject. That set is described here rather than counted, and deliberately so: it grows with every surface it comes to guard, and a count restated on a second surface is an invariant nothing checks, which is the defect class several of these pins exist to catch. What earns a rule its own pin is deferral. A bullet whose content is all its own fails loudly when it is deleted, so a pin adds nothing. A bullet that defers a rule to a skill is the case a pin earns, and it earns one whether the pointer is all that is left or sits beside substantial content of its own, because the deferring sentence alone can be deleted from both copies at once, pass the identity check, and leave the always-on layer naming no owner for the rule it defers. The bullets meeting that test today are the memory-extension pointer, the standing-dispatch grant, the chapter-close checkpoint sentence, the two liveness bullets, the peer-sessions pointer, the outline bullet, the test-earning bullet that routes the retire classes to `testing-discipline`, the document-length bullet that routes the sentence-shape bars to `writing-skills`, the gate and test-authoring bullets that route the lanes, the cost shapes and the red protocol to that same testing skill, and the box-check bullet that routes the claim protocol to the role skill. The set is named rather than counted, for the reason the pin set above is: a count restated on a second surface is an invariant nothing checks. Some of those pins reach the far end as well, which is the half a presence check otherwise leaves open: the outline bullet's asserts that the style skills it routes to still carry a recipe and that the four surfaces restating the rule still say so, and the peer-sessions bullet's asserts that the bullet still names its skill, that the skill is on disk carrying the three sections the bullet defers to (its contracts, sanctioned patterns, and etiquette) plus the Naming section the coordinator skill defers to from the other direction, which rides in this pin rather than one of its own because it is the same defect class against the same file, and that the skill's file is tracked in git's index, so deleting the skill, emptying it to a stub, or committing without the new directory cannot leave the pointer aiming at nothing with the suite green. The document-length bullet's asserts that `writing-skills` still carries the sentence-shape section it routes to, with its named bars inside it. Two far ends hang off no doctrine bullet at all, beside the coordinator and role pointer pairs above, and both are Chapter-template fields naming a repo-only tool a session is told to run. The `Delta:` field names a size reader by path and verb, so that pin holds the script on disk and in the index and holds it to the verb and the flags the field spells, a shipped invocation that throws being the failure a path-only check leaves open. The `Gate:` field's slot for the probe reading is the second: the two skills that spell a `tools/probe-corpus/run.mjs` command quote flags that runner has to still take and output prefixes it has to still emit, so that pin reads every flag inside a `run.mjs` command span in `writing-skills` and `finishing-work` against the runner's own `KNOWN_FLAGS` array, holds each skill to the flags it needs (`--only` and `--before` in the first, those two plus `--shape` in the second), checks the summary and warning prefixes the Chapter template quotes against the literals `run.mjs` emits, and pins both pointer pairs between the skills and the template on stable tokens rather than on the sentences around them, so a rename reds the parity lane while the wording stays free to move. The testing pointers' far end is asserted the same way and across more surfaces, because they reach past the doctrine: the skill on disk still carries the sections those pointers route to and the named leads inside them, the five surfaces that point at the skill rather than restating it still carry their pointer clause, and the adversarial reviewer's charter still judges test-worthiness by that litmus rather than by a list of its own.

**The size ratchet holds every curated file and every test file to a committed per-file cap, so growth is a deliberate edit rather than drift.** `test/size-budget.json` carries one cap per file and `test/size-ratchet.test.js` is the gate: it fails a file over its cap, a curated or test file with no budget entry, and a tracked file under a measured root that the classifier does not reach, that last one being the control that keeps the ratchet from greening on a corpus it never measured. The reading comes from `plugins/claude-kit/scripts/kit-size.js`, which classifies by path (words for the skills, their references, the agent charters and the output styles, plus the markdown directly under `home/` and the probe files directly under `test/probes/`; lines for `test/*.test.js`, with a test count riding the reading and capped by nothing, since the retire classes exist to make that count fall). Sizes are read from worktree content rather than from HEAD, so an uncommitted edit anywhere in the corpus moves the reading for every session sharing the checkout, and an over-cap failure says so and says whether the path differs from HEAD. A cap is a ledger entry rather than a ceiling: a file that grows raises its cap in the same change and one that shrinks lowers it, both through `sync`, and `writing-skills` (The size budget is a ledger rather than a ceiling) owns that moment. `check` is the reading the gate runs, and it distinguishes its failures by reason rather than reporting one, because an over-cap file wants a budget edit while an unclassified one wants a classifier fix. `report` opens with a subject line naming the repository by its top-level directory name, then prints one line per file whose size moved against HEAD with its cap and delta, the totals, every untracked file under a measured root, and how many changed paths fell outside the measured roots, which is the output a Chapter's `Delta:` field quotes verbatim. `init` writes a budget from current sizes and refuses an existing one. `sync` rewrites the caps of the paths named after it to their current sizes, adds a first cap for a named path the budget lacks, and with no paths moves every cap, refusing where the budget file, or any file whose cap would move, differs from HEAD or is not yet added to git. `sync` writes by rename from a sibling temporary file under `test/`, and `.gitignore` carries `test/size-budget.json.*.tmp` because a stray one committed there is a tracked path under a measured root that no shape classifies, which reds the coverage control rather than the file it came from. The blind spots are stated rather than closed, and the script's own header states them: a whole curated directory under no root in that classifier ships unmeasured, and an untracked file no cap names greens `check` and is only named by `report`.

**The scenario-probe corpus is the regression instrument over the prose the ratchet only measures: a cold reader answers a governed moment from a fixed document set, and the answer either held or moved.** `test/probes/*.md` carries one file per moment, its frontmatter naming the moment, the reader's tier, a closed option list of four to six slugs, one or more context shapes as file lists under `plugins/claude-kit/` and `home/`, and the answer the operator ruled; its body is the scenario the reader receives verbatim, carrying no account of what the documents were meant to say, because a reader handed the intent confirms the intent. `tools/probe-corpus/run.mjs` runs the set: it copies each shape's files into a scratch directory, spawns the Claude Code CLI headless once per probe and shape at the probe's tier with the shape's files inside the prompt, parses the verdict line out of the reply, and diffs it against the ruling, writing `report.md` and `report.json` under `.kit/probe-runs/<UTC stamp>/` with each reading's cited passages kept whole so a mismatch is re-locatable by content. `--before <ref>` reads a shape's files out of a git ref instead of the worktree, which makes a before-and-after pair two invocations and no hand copying. The exit code is the count of mismatches on probes whose ruling state is `ruled`, capped at 100; a mismatch on a `proposed` probe, a shape the probe marks `designed-mismatch:` reading against the answer as it was built to, and an error each count on their own and stay out of that code, because a probe's reading is model output and a gate that flaked on a doctrine edit would train authors around it. `tools/probe-corpus/README.md` owns the runner's mechanics and `test/probes/README.md` the discipline an answer is frozen under, this document neither restating them nor being the place they change. Three skills hold the hook-ins: `writing-skills` runs the before-and-after pair as the RED and GREEN for a change touching, in a shape-named file, a passage a probe's scenario turns on; `finishing-work`'s step 5 runs the whole set ahead of the whole gate under the box claim and disposes each row; and `executing-work`'s Chapter template holds the `Gate:` and `Decisions / Surprises` slots those two readings land in, so neither hook-in defines a Chapter field from outside its owner. Every ruling in the set is `proposed` until the operator answers the batched rulings brief, so both skills' ruled branches wait on that answer and a run today spends its paid readers on rulings evidence.

## Repo layout

- **`plugins/claude-kit/`** is the installable payload, and the only zone an installed plugin loads. It holds `skills/` (each a `SKILL.md` plus optional `references/`), `agents/` (three code reviewers, two document reviewers and a plan reviewer, implementers by model tier, the QA verifier, the docs curator, the design facilitator, the council member, the consultant, the scope adjudicator; frontmatter pins a model where the role fixes one, and pins effort on thirteen: `effort: medium` on implementer-sonnet, implementer-opus, the QA verifier and the docs curator, `effort: high` on implementer-fable, the consultant and the scope adjudicator, and on the per-section reviewers `effort: low` (adversarial-reviewer, blind-reviewer, blind-reader, prose-reviewer, plan-reviewer) or `effort: medium` (security-reviewer), since judgment-heavy work is where deeper effort converts into signal, plan-following work is where it converts into tangents, and a per-section lens reads a bounded diff while the finishing pass, a per-section reviewer below Fable, and any reviewer re-aimed after its tier was ruled out climb to `high` per dispatch. Effort above a pinned default is chosen per dispatch, and the executing-work skill's reviewer-effort table owns that rule), `hooks/` (Node scripts plus `hooks.json`), `output-styles/` (one file, `kit.md`, the `Kit` style described under the always-on boundary below), `scripts/` (the `memq` CLI, its shim, `memory-index.js`, which owns the optional embedding stack and the semantic index, `kit-endpoint-lib.js`, the shared client for the model endpoint named by a machine-local config file, which on this fleet is not on this machine at all: it runs on the virtualization host, reached across the virtual switch over plain HTTP, and both `memq find` and the judge daemon reach it through this one client, `prompts/`, holding the versioned prompt that client is sent, the size reader `kit-size.js`, which measures the payload's curated prose (the skills, their references, the agent charters and the output styles), the `home/` files that land in the user's home directory, and every `test/*.test.js` in lines, and whose `check` verb is the reading the size ratchet gates on while the script itself is a repo-only tool an installed session never runs, and the status line's two files, `kit-statusline.js` and `kit-goal-statusline.js`, described under Status line below), and `doctor/` (the Windows first-run and repair tool, whose installers sit beside it one per repair; it has no destructive action, so `-Fix` never deletes).
- **`home/`** holds the two files that land in the user's home directory rather than loading from the plugin: `CLAUDE.md`, an import stub that pulls the doctrine in and carries any machine-local pointers, and `claude-kit-doctrine.md`, the doctrine body itself. The doctrine's single source is the `operating-instructions` skill: `doctrine-refresh.js` strips that skill's frontmatter and writes the body to `~/.claude/claude-kit-doctrine.md` each session, so the copy here must stay byte-identical to the skill's body or a session loads doctrine the repo does not show. What earns a place in that body is a separate question, answered by the always-on boundary below.
- **`docs/`** is the working library: about-the-solution documents at the root, active plans in `plans/`, finished history in `archive/`. It is not part of the payload.
- **`kaizen/`** is the kit's self-improvement inbox, one note per piece of observed kit friction.
- **`settings/settings.recommended.json`** is the recommended user settings shape.
- **`sidecar/`** is the judgment sidecar: a daemon and its modules, run from the working clone rather than shipped in the payload. `daemon.js` consumes the capture hook's spool, asks a local model whether each tool call did what its stated intent required, and asks a second question against the project's memory index, writing verdict logs, recognition logs, a findings file, and the delivery inbox the capture hook reads back; an entry older than a freshness horizon (default 15 minutes, overridable with `--stale-horizon-minutes`) when the drain reaches it is skipped whole rather than judged, counted as `stale`, and recorded per contiguous stretch as a dated, session-attributed stale record in the session log and the findings file, so a drained backlog stays distinguishable from a quiet fleet; a stale entry counts inside `parsed` and never as `judged`, and every parsed call is accounted for by `parsed` = `judged` + `stale` + `gapped`. The daemon also says out loud that it is running, because a stopped daemon and an idle fleet produce the same silence on every other surface: it stamps `logs/heartbeat.json` with `{ v, ts, pid }` at startup, at each `--once` pass, and at most once a minute from the drain, checked once per entry rather than once per pass so a long backlog cannot let the stamp go stale, and every line it reports to stderr opens with the UTC instant it was written. A failed stamp is counted in its own persisted counter, `heartbeatFailures`, never in `writeFailures`, because it costs a reader the daemon's liveness and loses no record; the rollup renders it as its own clause and the battery excludes it from the lost-records reading. The scheduled-task wrapper `daemon-task.ps1` completes that signal from outside: when it finds a daemon already running it stands down and writes one timestamped line naming the pids it found and the heartbeat's instant and age, into its own log `daemon-task.log` rather than `daemon.log`, which the wrapper's own output redirection holds locked for the daemon's whole life. `rollup.js` is the audit surface over those logs: `node sidecar/rollup.js [--state-dir <path>]` prints per-session and per-day counts, gap ranges, stale-skip stretches and delivered-pointer counts as plain text a status round can quote, and prints on their own lines the instrument's tool scope and the limits that make a count evidence rather than a guarantee, so neither is dropped when the numbers are quoted onward. It also splits the verdict totals by the prompt id each record carries, but only where the window it read holds more than one: a verdict is comparable only to another produced by the same prompt, so a window spanning a prompt change sums two instruments into one column unless the report says so, and one id is the ordinary state whose split line would merely repeat the totals. `battery.js` and `harvest.js` are the evaluation pair, on-demand and dev-time rather than anything the fleet runs: `node sidecar/battery.js <judgment|recognition|all>` replays a frozen battery through the real daemon, which posts every fixture command, its output and the whole frozen memory index off this machine to the model endpoint as cleartext HTTP, and scores the answers against expectations frozen under `sidecar/batteries/`, so a later prompt change tells you which case moved, and `node sidecar/harvest.js <transcript file>` extracts fresh intent, action and result triples from one named session transcript so a future battery can be frozen from real calls. The daemon's own running state lives under the user's home directory, and two pieces of this component deliberately sit outside it: `sidecar/batteries/` is committed fixture content in the repo, and a battery run builds its state root under the system temporary directory by default rather than under the home directory, or at the path `--state-dir` names when a caller supplies one. One file here runs nowhere near this repository: `sidecar/ollama-watchdog.ps1` is a standalone PowerShell rider installed on the model endpoint's own host, where a scheduled task probes the generation lane every few minutes and restarts the service after two consecutive failed probes. Two consecutive rather than one, because a busy serial lane can starve a single probe behind a long generation while total silence across two whole cycles is the wedge it keys on: a generation lane that answers nothing while the HTTP layer answers normally. It shares no state and no module with the daemon, and its strike file and log live under `%ProgramData%` behind an explicit SYSTEM-and-Administrators DACL. `sidecar/CONTRACT.md` owns the file contracts between the parts, and `docs/security-model.md` owns what all of that state holds and what leaves the machine.
- **`test/`** is the gate over every code surface, and it is the only place a runner reaches. The suite is `node --test test/*.test.js`, spelled with the glob rather than the bare directory. One flat file per surface, named `<surface>.test.js`, with no test subdirectories and no `describe` blocks, so a run reporting `suites 0` is the mechanical proof that nothing nested; the one directory under it, `test/probes/`, holds the probe corpus, curated prose the ratchet measures in words rather than test files, and the glob never reaches it. A test file living anywhere else is invoked by nothing, and its coverage exists on paper only. `testing-discipline` defines a contention lane that would sit outside that glob and run serially beside the whole gate wherever the whole gate runs, and at a section close whose delta touched the lane's subject; this repo has none, because no test here has machine-shared state as its genuine subject, so every test file under `test/` is in the main gate.
- **`tools/`** holds repo-side utilities that do not ship: `transcript-study/`, the session-corpus analysis scripts, and `probe-corpus/`, the cold-reader runner over `test/probes/`.
- **`build.ps1`, `build.sh`, `.claude-plugin/marketplace.json`** package and publish the plugin. Both builders stamp `plugins/claude-kit/.claude-plugin/build-info.json` before collecting files, so the stamp ships inside the zip: the git short hash and a dirty flag `kit-version-nudge.js` reads, plus a `hooks` map of `<filename>: <sha256>` over every file in the packaged `hooks/` directory, which the canary compares the executing cache against. The stamp carries no wall clock, so a clean rebuild of the same commit stays byte-identical, and it is gitignored, so the copy in a working tree is only as fresh as the last local build. `build.sh` fails the build rather than stamping when it cannot produce a 64-character hash for a hook, because a partial manifest would make every install read as tampered.

## Always-on boundary

The doctrine is the prose the model carries into every task, so what lives in it is an architectural decision rather than an editorial one. It holds the rules that are general (true in any repo, not just the one that taught them), earned (the harness's own system prompt and tool descriptions do not already guarantee them), and needed before any skill has been loaded. Everything else lives in the skill that owns the moment the rule applies, and the doctrine points at it. The communication register is the one part of that always-on text carried on a second surface as well, and the register surfaces below say why.
Which of those surfaces governs when two of them disagree is itself always-on text, under the doctrine's "Which text governs" section: a ranking (the harness, the operator's live word, a positional grant for its assigned scope, the doctrine for principles and for the scope of every authorization, the owning skill for mechanics, every other surface as a pointer or a whole copy), the rule that a stop met on a surface that does not own the moment is a pointer to the owner rather than a bar, the rule that authorization for an outward act is positional, and the one-owner-per-moment rule. The map of moments to owners ships beside the skill as `skills/operating-instructions/references/ownership-map.md`, and the parity suite pins the section and the map together, since the section is a pointer whose far end is the map. The map's unowned section is deliberately part of the shipped state: a moment two documents govern with no stated precedence is listed there until the operator rules, so a session that meets one declares the gap rather than resolving it silently.


Inside the doctrine the bold leads are the index, which makes where a rule sits a second architectural decision after whether it belongs there at all. A reader scanning for the rule that governs the moment they are in reads the leads, so a rule filed under a lead naming a different moment is present and unfindable, which reads from the outside exactly like a rule that was never written. The absence-check rule is the worked case: the control requirement, the withheld-control criterion, and the class-versus-named-list coverage answer stand under their own lead, "A silent check earns its silence with a withheld control", because their moment of use is authoring a silent grep while the lead they previously sat under, "Make the test earn its green", names authoring a test. That bullet keeps red-first testing, both-direction proof, the temporary repro, wire-field pinning, single-sourcing, guard siting, and the tree-mutating-probe discipline.

Orchestration mechanics are the largest thing that boundary keeps out. `brainstorming` owns the model tier bands, which session model executes an approved spec, and the scout sweep that derives a section gets, having no brief for the entries to fold into), scout banding and the scout return contract, the serialize-what-cannot-be-shared rule, the stagger rule that advances concurrent sections offset rather than in lockstep, the interim board entry a closure drought earns, the route that sends a surface found outside a section's declared files to a fold, an appended section, or out of the plan, the review round a qualifying fix delta owes and the re-open, in the closing section's own round, of a completed section's document whose described behavior that section changed, the behavior-or-claim class every finding is read at and the class-keyed condition that ends a section's review loop (the first round leaving no Critical and no owed Major unfixed, unrouted and unrecorded, over a fix delta owing no round of its own), with the recurrence split that sends a second instance of a claims class to a mechanical check or a deletion sweep rather than a `Standing re-aim reaching Fable runs at `high` where a first-aim Fable reviewer runs at `low` or `medium`. `finishing-work` owns the matching floor, and it is two states rather than one: fable at `high` by What that floor reads is set per section: a section the rule aimed below Fable, or whose round ended ungated, clears nothing for the finishing reviewers, so the whole-changeset pass reads those sections for local defects as well as for cohesion, and the Chapter's review line carries each round's model and route so the pass reads that from the record rather than deriving it. Both states dispatch through `Workflow`'s `agent()`, because `high` sits above every reviewer's frontmatter effort and `max` above every agent's, while the Agent tool carries a model override and no effort parameter at all; a session where that route is unavailable falls back to the Agent tool at fable and the frontmatter effort, which the Chapter records as a lower-effort pass rather than as compensation. The per-section rows fall back the same way and keep each row's own model rather than climbing a tier, since a climb would put Fable back on the sonnet- and haiku-tier sections the rule takes it off. It also owns the wedge hallmark, the cross-class liveness predicate that decides when a dispatch of any class may be stopped for being quiet, along with the readings that fill it and the cadence it runs on. The hallmark's middle term takes one of three readings, and the dispatch's shape picks it. A dispatch that has taken a turn is read on byte growth, against its class's growth window and its class's probe window. One that has taken none is read on the count of `"type":"assistant"` lines whose `message.model` is not the harness's `<synthetic>` error placeholder, against a five-minute first-turn window and a five-minute probe, one pair shared by every class rather than derived per class the way the growth windows are: the asymmetry that sets the long windows, that a stop discards what a live agent built, carries no weight for an agent that has built nothing. One whose transcript cannot be read at all keeps its own class's growth and probe windows, since the shape that would earn the short pair is read from the very file that is unreadable. The same transcript is the resolved-model artifact: the distribution of `message.model` across its assistant lines is what the round ran at, while the dispatch record and the `.meta.json` sidecar beside the transcript carry only what was requested, so a harness that substitutes silently is read from the difference rather than from the absence of an error. That predicate fires during execution rather than at the finish, and every surface naming it points at it rather than restating it: `executing-work` at its dispatch sites, `consult`, `brainstorming`, `standing-watch`, which writes the check into its tick order because a watch re-blocks on nothing for the cadence to fire on, the doctrine's two liveness bullets, and the README. The doctrine keeps the habit and the route (the file by path under the plugin root, the rule found by its bold lead, since finishing-work carries no heading for it) and no number of its own, because its audience includes sessions that never load that skill and a bare pointer would leave them holding a duty they cannot discharge. The hallmark leans back on the doctrine once, and the dependency runs the other way there: a zero-growth transcript reading is an absence-proving check, so it takes the positive control the doctrine's "A silent check earns its silence with a withheld control" bullet requires of any check that proves an absence through a hand-authored pattern, path, or scope, and where no control can be run the instrument is unproven rather than the agent dead. `consult` owns the fresh-context end of the escalation ladder: the trigger floor that decides when a stuck session convenes the `consultant` agent, the brief that makes a consult work, the same fable-at-`high` model rule with the same Opus-at-`max` stand-in, and the adjudication rule that treats a returned ruling as a hypothesis until the orchestrator checks it against the code. The intake gap check splits the same way and for the same reason: the doctrine states the rule, because an intake happens before any skill has loaded, while `brainstorming`, `executing-work`, and `finishing-work` own the phase mechanics described under Intake gap check below.

The same siting question decides which of the Dispatch Brief template's fields are conditional, and two hazard protections are answered as standing rather than conditional because the party that can see the hazard is not the party that acts on it. A dispatched implementer holds its brief and nothing else, so a protection the orchestrator forwards only when it remembers to reaches the implementer only that often. The whole-worktree prohibition is one: no git operation reaching past the agent's own files, and no `git checkout -- <file>` at all, since that restores to HEAD rather than to the state before the agent's own edits, which the commit-model rule leaves unstaged. It rides in every brief rather than only where a sibling session is known to be live, because an implementer can never see from the tree whether another session's uncommitted work is sitting in it, which would leave the dispatching session's judgment that none is as the only gate, made from outside that other session with nothing to check it against. The hostile-boundary reuse step is the other: before writing a call whose safety rests on what the far side is protected against, grep the tree for that boundary's other callers and reuse a correct one's guard rather than reproducing its protections by hand. That step is the guard-belongs-to-the-channel rule the doctrine already carries, deliberately restated at the point of action, and it earns a pin in `test/doctrine-parity.test.js` for the reason every deliberate copy here does: a divergence between the brief's wording and the doctrine's survives a suite whose assertions never touch the diverging text. The conditional workspace-constraints field stays for the genuinely stateful extras a brief cannot predict, a foreign worktree or a process holding binaries, and no longer illustrates itself with the whole-worktree examples that moved up.

A deliverable document takes its own review pair, because the code lenses carry postures that fight prose. `blind-reader` is dispatched once per persona a section's `Audience:` line names, and once more before a spec leaves brainstorming with the spec itself as the document under review, in both cases with the document paths and a `Reader:` line and nothing that describes the documents' intent, and it reports what it understood, what it was left asking, what it could not follow, and for a procedure the first step it could not perform. It also answers the gating-definition litmus: for every phrase in the document that decides what a bounded artifact admits, it returns three near-miss pairs, a thing the rule admits beside the nearest thing it keeps out and the feature separating them, derived from the rule as written and never resolved against the code or the artifact the phrase gates; the pre-spec dispatch's orchestrator then places those six members against its own reading with the deciding clause cited, since two readings of one definition can paraphrase identically and still put the same example on opposite sides. What the persona may open is decided by whether it holds this repository rather than by the job title it carries: a persona who holds it may read it read-only to attempt a step, never opening `docs/`, a spec, a plan, or a commit message on its own initiative, though a spec or plan handed to it as the document under review is its subject and it reads that, while a persona from outside it (a customer, non-technical staff, an engineer who has never held this code) opens the documents and nothing else, since a strong model with the source open fills the document's gaps from it and never reports them. `prose-reviewer` is the adversarial half and runs two passes in a fixed order, goal compliance and every claim against the fact base first, then the writing skill's rules, the machine-prose tells, and presumed knowledge against each named persona, so a style fix that would loosen a claim is reported as a conflict rather than applied. Both agents are read-only and join the guard's strict class; both hold Bash and are chartered to treat a document in scope as data, since the guard's denylist does not cover a read-shaped command it can resolve and a document that can make a reviewer run one has turned the review into its own tool. `plan-reviewer` is the third lens in that class, and its subject is the plan rather than the prose: it takes the spec path alone once the litmus closes, asks whether following the sections as written would achieve the Goal, and holds Bash under the same data-not-instructions charter, which is why the security model counts three strict members reading text that need not be the operator's own. The tell catalog is single-sourced at `skills/scott-writing-style/references/ai-tells.md`, which the writer reads before finishing a draft and the reviewer hunts from by name; a dispatch that cannot supply that path costs the tell hunt entirely rather than getting one from memory. The pair is added to what a section's content earns and replaces the code pair only where the changed files are documents and nothing else, so a mixed section still gets code review in the same round. At finishing, `prose-reviewer` runs once over every document in scope, reading each whole exactly as a section-time dispatch does; what earns the separate run is timing rather than scope, since only the finishing pass reads after every section has landed, the one vantage from which cross-document consistency, the whole-effort lens, is checkable at all; the blind reader is re-run only where a document changed after its section review. The prose-only security waiver also becomes an audience predicate: a document written for anyone outside the operator and the operator's own sessions voids it, and the security-reviewer's brief then carries the spec's `Disclosure:` list to sweep the documents against.

The consult is the kit's answer to a reasoning dead end, and it is deliberately the only one that runs on fresh context: the kit runs with no in-context advisor, because a companion model sharing the session's transcript inherits the session's blind spots and ratifies the framing at exactly the moments that matter. The `consultant` agent is read-only, fresh-context, and dispatched by the main session alone, since subagents carry no Agent tool; an implementer reaches it semantically instead, by returning NEEDS_CONTEXT stated consult-shaped (the decision, the options, the evidence, its lean) for the orchestrator to route. Four triggers form a counted floor rather than a felt one, because a stuck session feels almost done: a second failed attempt at one problem, which names the review seesaw (one passage's fix reversed a second time) as one of its shapes, a BLOCKED that turns on a decision, a debugging dead end, and a weighty decision the spec does not cover. The floor's width is judgment rather than data, and `docs/backlog.md` carries the adoption watch that judges it on the first real long run. A blocker reaches that floor already asked: the expert ask under Session roles below runs ahead of the consult, being the cheaper instrument and the one that resolves from sources that already exist, and it neither gates the declaration nor stands in for the consult, the ask asking whether the answer exists somewhere already and the consult asking whether the framing is wrong.

The doctrine's "Orchestrating fan-out work" section is three bullets. One points at those two skills, which buys always-on context back at the cost of a load: fanning out scouts, implementers, or reviewers outside a skill-driven run depends on that pointer actually triggering the skill load, an accepted risk rather than a guarantee. The other is the standing dispatch request, and it is the one place the always-on text carries a tool authorization rather than a rule. It covers the Agent tool for dispatch generally, and the Workflow tool for one narrow purpose, dispatching a read-only agent (a fresh-context reviewer, the consultant) at an effort the Agent tool cannot set. The covered class is a predicate the doctrine states itself (a read-only dispatch needing its effort set per call, naming an `agentType` the read-only guard governs) rather than a reference to what the skills say, because a skill that defined the class would be granting itself a permission the doctrine scopes; the skills say where and how and cannot widen it. The grant lapses on its own terms if the Agent tool ever gains a per-dispatch effort parameter. The third points at the `peer-sessions` skill, and it is the section's only outward-facing rule: the other two govern agents this session dispatches, while this one governs independent sessions it does not own, which is why it carves its own subagents back out and leaves them to executing-work and finishing-work.

One further Workflow authorization sits outside that class and outside the doctrine entirely, in `/kit-goal` arming. The arming invocation is user-typed, so it carries the operator's own request for that run: reduce wall-clock time by parallelizing whatever the sections and their gates allow, through subagent dispatch and through Workflows. Its authority is the arming act rather than any skill's text, its scope is executing the armed plan and nothing wider, and the canonical condition text `kit-goal-lib.js` composes carries the request, so it rides with the goal state across a session swap and the Stop hook restates it at the point of action.

Project-specific rules are kept out the same way. A product's honesty and privacy gates, its identity and framing constraints, and its test-suite naming live in that project's own `CLAUDE.md`, next to the gate tests that enforce them. The doctrine keeps only the general form: nothing untrue ships, and where a project defines honesty or privacy gates, a violation is a defect to sweep the whole tree for. The same rule sends .NET lessons to `csharp-style` and the capture bar to `kaizen` rather than into the always-on text.

Language-scoped knowledge splits on that seam too, and the outline-first reading rule is the sharpest instance of it. The doctrine states the principle, that a file past roughly 1,000 lines you are opening to find one thing is grepped for declarations and section labels before any range of it is read, along with the two guardrails that fail quietly (an outline never proves absence, so a symbol not found in one still earns a whole-file search, and an `<auto-generated>` header means grepping for the member by name instead). It carries no patterns. Those live in `csharp-style` and `sql-style`, each of which gained an Outlining section holding a recipe verified against a real file, because a language-agnostic surface cannot hold the house idioms a generic pattern misses: T-SQL's leading-semicolon `;ALTER PROCEDURE` deployment form and the banner comment whose label sits on the line after its border, C#'s `#region` organization and the interface whose members carry no access modifier for a member grep to anchor on. For a language no style skill covers, the bullet says to compose that language's own declaration and section markers on the spot, and no JS or TS anchors ship at all, the kit having no JS house style with the standing to own them. The trigger is the hunt rather than the size: a file whose whole content is the point is read whole, which is what keeps the rule from colliding with the two committed read-in-full mandates the kit already carries, `executing-work`'s post-compaction plan-doc read and the blind reviewer's charter.

Test discipline splits on the same seam, and what the doctrine keeps is set by what a session needs before any skill has loaded. It keeps which lane each gate moment takes (the targeted lane after every fix and at section close, whatever the delta touched, and the whole gate at finishing, which is the plan's handoff gate rather than a second one beside it, after a merge, and before a push only where that push lands on a trunk consumers install from directly with no CI gating the merge), the contention lane's own schedule beside those moments, the duty that a section's closing Chapter name the lane or lanes that gated it, the delta report against a baseline recorded on that same lane, the real exit code, green-necessary-not-sufficient, and the merge-reddens-a-suite warning. The exit-code rule is the one of those whose scope is wider than the lanes around it, and it says so in its own sentence rather than leaving a reader to infer it from the bullet's examples: it governs any command whose success or failure the session will act on, whatever that command cost to run, since the cheap probe is where the rule looks like it stops applying and does not. Two carve-outs bound it, each against a rule the doctrine states elsewhere: a command run for its output rather than for a verdict, a listing or a readiness marker, and a run whose exit code the environment refuses to hand over at all, which is the worktree-isolated session whose isolation screen refuses the marker compound that would carry the code out, where the run's own summary is the reading and is reported as the summary it is. `testing-discipline` owns the classes that retire a test already in the tree, which no doctrine copy carries, and, of what the doctrine defers rather than spelling out, the litmus for what earns a test, the shared-setup blind spot, the cost shapes and their cheaper forms, the lane mechanics, the red protocol, the comparable-contention rule, and the engine-agnostic box check. The doctrine bullets carrying that pointer each defer their operative mechanics rather than carrying them, so each earns a presence pin among those above; how many there are is that pin set's own business rather than a count restated here. The surfaces that point rather than restate: executing-work's step 2, its Dispatch Brief template's `Tests:` field, its step 3 (which points at the doctrine's gate bullet, that moment's own owner, rather than at the skill), brainstorming's `Tests:`-line paragraph, and the repo README's payload map. The adversarial reviewer's charter joins them from outside the doctrine, because that charter adjudicates every section review and a litmus restated there would outlive every deletion the fold performed. Several rules are deliberately stated in full on both surfaces rather than deferred, so a doctrine-only reader runs the right lane without loading anything, and a cross-surface loop in `test/doctrine-parity.test.js` holds each of them identical across the copies. Which rules those are is that loop's own list rather than a count restated here: a count in prose drifts silently every time the shared set grows, where the loop cannot, so the test is the authority and this paragraph names the principle. What the skill does not carry is any command: a repo's suite invocation and its lane commands are per-repo facts that live in that project's memory tier, which is what lets one skill ship kit-wide.

Mode-specific rules are kept out on the same test, and `standing-watch` is the case that names the mode. A session watching a live system it does not own, waking on a timer or an operator message, re-deriving the board, intervening, writing a ledger and sleeping again, carries failure modes no other work has, so the ledger's standing-versus-situational split, the tick order that arms the wake before it checks anything, the wake prompt that carries prohibitions and never a situation report, the ping's evidence line, and the one-way-door preflight all live in that skill and load only when a watch is running. The ledger's admission test and its default live there too, and the default faces outward: a line the keeper cannot confidently say a successor needs stays off the ledger, the default being the test's tie-break for doubt rather than a stage every line passes through, and residual to the rules of the chassis and of a consuming skill that already place content by naming a class. Three obligations on a consuming skill follow: it names by rule every class its ledger is the one record of, since an unnamed one-record class is the class the default loses; it states its own kind fork beside any override of the chassis's kinds; and where it names a member of its own carrying the exempting property below, it states that the member takes that exemption. Doubt about which kind an admitted line is falls to situational, the kind whose misfiling costs a re-measurement, with one carve-out asked first: a standing member no probe of the watched system reproduces (a prohibition or a do-not-reopen trap) falls to standing, since its loss licenses the act it exists to close off. The doctrine keeps from that same material only what is true of any session whether or not it is watching anything: probe a dispatched agent before killing it, read one heavy process at a time as a per-machine limit, take a background run's exit from a marker it wrote itself, answer "cannot measure" when the source that would answer is down, and ask, in the Before-you-send list, whether every figure or state names the source it came from and the subject it is about. That last one sits inside the register core, so it reaches the output style as well as both doctrine copies; the four bullets live in the doctrine copies alone.

### Intake gap check

Every input the kit takes in gets its gaps enumerated before anything is built on it, and the doctrine carries that rule because an intake precedes any skill load. At an intake (a prompt, a handoff, a spec, a dispatch brief) the session lists what the input does not state, then routes each gap three ways: (a) one an existing source answers (doctrine, memory, the plan doc, the code's own conventions, a house style) is resolved with the source cited; (b) a low-blast, reversible one with a conventional default is decided and declared; (c) a material one that is the operator's to make is asked, batched, with a recommendation. The first two routes produce declared assumptions and the third produces a question. Enumeration is a step rather than a habit because a model fills gaps silently and cannot see the ones it filled, which is the same reason brainstorming's self-review ends in dispatched reads, a blind read and then a plan review, rather than in a second inline pass.

A declared assumption is never left only in a document, because the operator approves plans from the recap without reading the doc. Three surfaces carry it, one per phase. During brainstorming it rides the plan sketch and every later recap the operator approves, as its own `Assumptions` block, and a recap that omits the block has not shown the plan. During execution a material gap the spec does not cover is a `BLOCKED:` on an armed run or a decision ask on an attended one. At close-out the finishing status lists every execution-time entry verbatim, which is what reaches a run the operator walked away from, since under a leash that status is the closing message the `goal-complete` event points at.

The durable record is split in two by the external engine's approval-scoped fingerprint, which covers everything above `## Chapters`. The plan doc's `## Assumptions` section holds the design-time entries and freezes at approval, because a routine mid-run append there would mutate the fingerprinted region and read as approval drift; a deliberate spec amendment above that line is still made when the design changes and is recorded in a Chapter as the drift it is. Everything execution adds rides the Chapter's own `Assumptions:` line, which is append-only and below the boundary. One line format serves both, instanced normatively in brainstorming's spec template:

`- assumed YYYY-MM-DD (<route: a source name | default>): <the assumption>; reversal: <what changing it costs>`

with `, section N` added inside the parenthetical for an execution-time entry. The close-out block is computed from the Chapters rather than by dating entries against `## Assumptions`: no approval date is recorded anywhere, the entries carry day precision, and a plan approved and run the same day is the ordinary case, so a dated filter would report `none` on exactly the walked-away run the block exists to serve. An empty block says `none`, so silence is a stated fact rather than an omission.

Three skills instance the rule at the moments it applies. `brainstorming` carries it into the design conversation: its one-question-at-a-time rule is how route (c) is asked there, its sketch and recaps carry the `Assumptions` block, its spec template holds the `## Assumptions` section (inert to the plan-doc parser and required to stay outside `## Sections of Work`, whose block any foreign `##` heading ends early), and its self-review closes by dispatching `blind-reader` on the spec itself, adjudicating each returned question three ways (answer it in the spec, declare it as an assumption, or put it to the operator with a recommendation) and recording `blind read: <n> questions, <a> answered, <b> assumed, <c> asked` in the handoff recap, beside a `gating litmus:` line whose buckets and dispositions that step owns, then by dispatching `plan-reviewer` on the spec against its own Goal, at fable and high, with the spec path alone, adjudicating its six-question findings the same three ways and recording `plan review: <n> findings, <a> fixed, <b> assumed, <c> asked` beside them. Each costs one dispatch per spec, and a trivial spec of one or two sections may skip both, saying so. `executing-work` runs the check on the plan doc: it lists what each section leaves unstated during the plan-doc read and routes after `memq recall`, since memory is one of the sources a gap routes to, so a non-material gap is resolved before its section is dispatched and the brief carries the answer rather than the gap. Its implementer-status handling reads a `DONE_WITH_CONCERNS` "spec ambiguity you resolved" concern as a route (b) assumption bound for the Chapter line, while a concern that reads as material re-routes to `NEEDS_CONTEXT`. `finishing-work` step 5 delivers the close-out block and rides the same block on the finishing Chapter, beneath the plain-language recap that opens the close-out status and rides the finishing Chapter's `Recap:` field, quoting the plan's Goal, stating what the tree now does, and listing the refinements read off the Chapters.

### Register surfaces

The communication register reaches the model on three copies of one text, and the copies exist because no single surface covers every session. `plugins/claude-kit/skills/operating-instructions/SKILL.md` is the source. `home/claude-kit-doctrine.md` is the mirror `doctrine-refresh.js` writes to the user's home directory, which the home `CLAUDE.md` imports and every subagent therefore inherits. `plugins/claude-kit/output-styles/kit.md` is the third: a Claude Code output style whose marked region carries a subset of the doctrine, the register core, byte-identical.

Coverage and lateness are the two properties no single surface has. CLAUDE.md prose reaches subagents and survives the triggers that deactivate a style (a plugin update lag, an older harness ignoring the force flag, a non-Code surface, safe mode disabling non-builtin styles, and a future deprecation of the feature itself), but it fades as a session grows. An output style rides the system prompt and is re-asserted after tool results, so it binds at turn 200 where the imported prose does not, and it reaches the session's own thread only: subagents never receive it. Holding one text on both surfaces is what buys both properties, and it is why the core is a copy rather than a pointer, since a subagent handed a pointer to style content cannot load it.

The core is seven bullets (`Skip the preamble`, `Disagree up front`, `No false certainty, no flattery`, `Teach the why; treat design as a dialog`, `Write every decision ask to the client-briefing register`, `Narrate the cadence, and close with the state`, `Close with the board when plans are pending`) plus the doctrine's whole `## Before you send` section. Bullets ride whole rather than split at the sentence, because a half-bullet on one surface and its other half on the other is paraphrase adjacency no test can pin. The style's own shell (the reader definition, the teaching posture, and the ★ Insight, ⚖ Decision, and ✎ Memory block mechanics) deliberately never enters the doctrine: subagents inherit the doctrine, and block mechanics in a worker's context would reshape the reports it returns.

Four frontmatter keys are the harness contract, and two of them are load-bearing beyond tidiness. `name: Kit` and a double-quoted `description` identify the style; `keep-coding-instructions: true` is what keeps Claude Code's built-in software-engineering instructions in a kit session, which the style otherwise silently removes; and `force-for-plugin: true` is what activates the style wherever the plugin is enabled, over a machine's own `outputStyle` setting. Rollback is removing that one flag, and safe mode is the always-available escape hatch.

`test/output-style-parity.test.js` is the gate over all of it, in 11 named tests. It pins the frontmatter as a closed set of exactly those four keys, each declared exactly once (YAML is last-key-wins, so a first-match read would accept a `true` followed by a `false`) with the two flags matched against the raw bare token `true`, since a quoted `"true"` is a string to a type-strict reader. It then locates each core bullet by its lead in both doctrine copies and in the style's region, requires exactly one hit in each, and compares bytes; compares the Before-you-send segment from its header to end of body across all three; and pins the region as a closed set, the seven bullets in spec order, then Before-you-send, then nothing but blank lines, so a paraphrased paragraph cannot sit alongside content that passes. The doctrine copies carry no markers of their own, which is why extraction is by lead, and the sync direction is skill to mirror to style core. One consequence lands on whoever edits the doctrine: a new section appended after `## Before you send` fails this test, and the fix is a deliberate call about where the core's boundary now sits rather than a widening of the compared segment.

## Hooks

`plugins/claude-kit/hooks/hooks.json` is the wiring, and every hook is a Node script invoked with the plugin root. Seven events are in use: the five below, plus `UserPromptSubmit` and `SubagentStart`, which `memory-recognition-nudge.js` alone registers on and which the PostToolUse bullet describes with the rest of that hook's reach. The events in use:

- **SessionStart** runs `session-start.js` (thirteen blocks: the compact-source re-load instruction, resume surfacing, the notice that in-progress plans sit here with no goal armed, the Ready-parked list, unarchived-plan flagging, the bounded-scan qualifier over every figure the docs/plans/ walk feeds, the kit-repo kaizen nudge, the plugin-view line, the armed-goal notice, the sibling-worktree leash hint naming each linked git worktree of this repository that holds an armed goal of its own, the backlog block described below, the shared-checkout advisory described under Dispatch authority, and the parked-handoff inventory over the project's `.kit/parked/`), `branch-reaper-nudge.js`, `kit-version-nudge.js`, `doctrine-refresh.js`, `hook-canary.js`, and `memory-session.js` (the memory index emission described under the memory store below). Matchers differ per hook: the doctrine refresh also fires on `clear`, and `branch-reaper-nudge.js` and `hook-canary.js` skip the `compact` entry, the canary because a plugin cache cannot change mid-session. `session-start.js` firing on `compact` is what makes a compacted session re-read its plan doc, so it is the recovery path the kit relies on; on that source it also leads with a re-load block, emitted whether or not a plan is in progress, because a compaction keeps the doctrine and this hook's output but drops what tool calls had loaded (skill bodies, deferred tool schemas), and a session left to run a summarized skill executes the half the summary kept. Under `KIT_EXTERNAL_ENGINE=1`, the marker an external engine sets on every worker it spawns, four of these stand down: `session-start.js` omits its drive-to-completion push (it still lists each In Progress plan's path and commit model, followed by one line stating that the engine's own directive owns scope and continuation) and suppresses both the unleashed notice and the sibling-worktree leash hint entirely, the notice because a worker starts in exactly the state it describes and a leash armed there would hold it past the section its engine assigned, the hint because a worker's sibling trees are its own engine's other workers and the block would hand each of them a reading of a fan-out none of them owns a decision about, `hook-canary.js` exits before spawning anything, and `branch-reaper-nudge.js` and `kit-version-nudge.js` emit nothing. The three nudges ask for an attended operator's action a headless worker cannot take, and the canary's sweep is serial child spawns whose report has no reader there, fleet payload integrity being the deploy's concern. `doctrine-refresh.js` and `memory-session.js` stay live: doctrine and memory wiring are wanted inside a worker.
- **PreToolUse** runs seven hooks: `docs-write-guard.js` on write-shaped tools, `memory-frontmatter-guard.js` on `Write|Edit|MultiEdit`, `pr-docs-guard.js`, `merged-pr-push-guard.js`, and `readonly-agent-guard.js` on shell tools, `memq-grant.js` on the Bash tool alone, and `memory-recognition-nudge.js` on every tool, which neither denies nor grants and is described with its PostToolUse half below. `memory-frontmatter-guard.js` is the memory store's write door and is described under the memory store below. `readonly-agent-guard.js` keys on the calling agent's type and governs two classes: the nine judgment agents (the three code reviewers, the two document reviewers, the plan reviewer, the council member, the design facilitator, and the consultant), for whom the repo tree is read-only, and `qa-verifier`, which may write and delete inside the build-output directories its suites need, and outside them may bring a fresh path into existence with `touch`, `New-Item`, or a copy, but not by any content-writing spelling. Both lose git and GitHub state changes, formatters, and the package-manager verbs that rewrite a lockfile or a tracked project file; reads, builds, and test runs stay untouched for both, and `.kit/` is writable scratch. The five guards fail open on their own malfunction and are denylists otherwise, blocking the shapes they name, with `readonly-agent-guard.js` running the other way on ambiguity it can attribute, denying command text it cannot resolve and a destructive cmdlet fed by an enumerating pipeline whose operands do not resolve, so the `git status --porcelain` comparison that executing-work and finishing-work run around each review round is the backstop for what the heuristics miss. That comparison is two porcelain readings rather than a byte comparison, so it misses an outward `gh` call as much as a merge or a `reset --hard` moving HEAD and the worktree together, and the denylist carries most of that class for exactly that reason. git's own ref, config and remote plumbing is the part it does not carry: the guard leaves `git fetch`, `git remote`, `git config`, `git notes`, `git replace` and `git reflog expire` allowed as review work, so a refspec fetch writing local refs, a remote repointed at another host, and an alias written into the global config each pass with neither control watching. An alias defined on the command line is the one member of that class the guard does take, since `git -c alias.<name>=<value>` puts the invocation's real verb in a config value and leaves the subcommand unresolvable, which is a deny under the same ambiguity rule.
- **PostToolUse** runs six hooks. `format-on-edit.js` runs CSharpier over edited `.cs` files. `memory-usage-stamp.js` records a `read` stamp when the Read tool opens a memory file of any of the three tiers. `memory-recognition-nudge.js` rides four boundaries, the two tool ones and the two lifecycle ones, and is the memory store's pull for the session that does not know to ask. It matches `triggers:` entries from all three tiers, and file anchors and `glob:` triggers from the project tier alone, against the call: at PreToolUse the `cmd`, `skill`, `agent` and `tool` types, whose subject is knowable from the request and whose nudge is worthless once a command-shaped hazard has run; at PostToolUse the `err` and `glob` types and the records' anchor paths, none of which exists until the call has returned, with the `err` types reached only where the call itself failed, so a successful command that merely wrote progress to stderr raises nothing. The two lifecycle boundaries are what carry the reach past the tool stream. At `UserPromptSubmit` the prompt's own text is matched against the `cmd`, `err`, `skill`, `agent` and `tool` types from the project tier alone, and from no tier at all while a store pin is in effect, so a record can answer a question before any tool runs, with the identifier types matched on a whole token there so that a prompt writing readme or thread does not fire `tool:Read`. The tier confinement is what the prompt boundary costs: a prompt is prose rather than a field, so every type matched against it is a guess about what words mean, where memq's authoring bars screen a pattern against a command line or a failure's output and say nothing about English, and a shared tier turns that guess into a pointer in the opening prompt of every session in every project on every machine the store reaches. Nothing is lost that was true, each shared-tier trigger keeping the channel where its match is a statement about the session rather than about prose: `cmd:` and `err:` at the tool boundaries, `skill:` and `tool:` against the field a call names, and `agent:` against the type a dispatch starts. A pin is read rather than the tier's name because a pin makes one directory serve every repository the instance works in, and confinement to one checkout is the whole of what admits a tier here; at `SubagentStart` the dispatched agent's type is matched against the `agent` type, and that is the one boundary whose nudge lands in the subagent's own context rather than the orchestrator's, a subagent inheriting no memory context by any other route, with one class of dispatch excepted: a read-only judgment seat receives nothing at all, being dispatched to hold a context that inherited nothing, on the same policy classification that refuses those seats a tree-mutating command. A prompt the harness marks machine-injected on the `loop_wakeup`, `schedule_wakeup` or `poll_event` source is not answered at all, so no nudge is spent on a turn nobody processes. A fragment type (`cmd`, `err`, `glob`) matches by containment or by a path-segment walk; an identifier type (`skill`, `agent`, `tool`) matches whole, since `tool:Bash` names Bash and not BashOutput. Every matcher is linear and constructs no regular expression, and a per-call operation budget is spent across the whole matrix, so neither one stored pattern nor a store full of them can cost a call more than a fixed amount of work. Anchors are matched on their paths with the sha ignored, drift being a different question asked by a different surface. The nudge is a pointer and never a body: the record's name, the tier it was read from, the trigger that fired, one clause of why, the `memq get` spelling carrying whichever of `--type` or `--operator` that tier needs, and, where the record scopes itself to one box, a label naming that machine, so the session opens the record itself. One further write goes elsewhere: a nudge log under the project's own gitignored `.kit/`, one line per nudge actually emitted carrying the record, the tier it was read from, the trigger and the moment, rotating past 1 MB to `.old`, which is what feeds the stamp-rate reading `memory-system/SKILL.md` describes. It reads the dispatched agent's own id at all four boundaries, on one narrow reading rather than two: at the two tool boundaries and at `UserPromptSubmit` that id is a stand-down, since a subagent shares the parent's session id and would otherwise spend the parent's dedup budget, and an `--agent` session's main thread still nudges because it carries an `agent_type` and no `agent_id`; at `SubagentStart` it is the dedup recipient, which is what lets the boundary fire into a subagent whose parent already nudged on the same record; it stands down under `KIT_EXTERNAL_ENGINE=1`; and it stands down on a network-shaped working directory or store root, because it resolves the memory directory on every call and that resolution rides a synchronous stat that hangs for the SMB timeout. Every failure is silence at exit 0 on both channels, under a fence that drops any other write to either. `chapter-boundary-nudge.js` closes the checkpoint system's one-way loop: it fires when the session holding the leash on an armed kit goal adds a `### Chapter` heading to the armed plan's own doc, matched by path rather than to any doc under `docs/plans/`, because the reminder opens by asserting that a boundary was reached and that assertion is false on a sibling plan; and it puts a fixed reminder of the executing-work boundary steps (the memory sweep, then the checkpoint open, once the section's commit model has been honored) in front of the model. Added means a Chapter number present in an edit's `new_string` and absent from its `old_string`, not a heading present anywhere in the new text: a real append anchors its `old_string` on the document's tail, which past the first boundary already carries the previous Chapter's heading, so a presence test would go silent on the one shape the hook exists to catch. A whole-file `Write` has no pre-image to diff, so any heading in its content fires it. It reaches the model through the nested `hookSpecificOutput.additionalContext` JSON form, because the top-level `additionalContext` key the hooks documentation shows is inert on this harness. It is a detector plus a directive rather than an auto-open, since the checkpoint belongs after the section's commit and an auto-open at the Chapter append would admit a compaction between the Chapter write and its commit, the mid-boundary landing the gate exists to prevent. It stands down for a subagent's tool call on the payload's agent keys, `agent_id` plus the four `agent_type` spellings the kit's sibling detectors defend, rather than on the session id, because a subagent's payload carries the parent session's own id and the leash-holder check alone would pass one; it stands down under `KIT_EXTERNAL_ENGINE=1`; and every guard and every internal error exits 0 silently, so a missed nudge degrades to the pre-hook status quo rather than to a broken edit loop. `compact-deferral-nudge.js` closes the other half of that loop, the half no edit announces: the gate's deny lands at a turn boundary where PreCompact stderr reaches the operator and never the model (an observed property of the harness the kit runs against rather than a guarantee, stated with the note it protects below), so a run can be held for hours without knowing it. This hook rides the return of the tools whose results follow a wait (`Agent`, `TaskOutput`, `Bash`, `PowerShell`), which is the first thing the model reads after a deferral, and tells it the gate is holding offers. Two sessions are held by this gate and neither can see it, so there are two directives rather than one, mutually exclusive by construction because the gate reaches its hands-on leg only for a session that does not hold the leash. The LEASHED run is held on a boundary deny under an open deferral episode, and is told how many offers are held and for how many minutes, and which boundary step ends the hold. The HANDS-ON session is held on an interactive deny, because the project's goal belongs to another session or nothing is armed here at all; it has no chapter to close and no checkpoint to open, and its only release is the role-boundary marker the checkpoint CLI's boundary verb writes, so it is told to judge whether everything it holds is durable and to declare it if so. The first directive carries exactly two integers out of the gate's state and the second carries nothing at all, its prose fixed and the one figure that decides whether it speaks compared against a floor rather than rendered, which is the same provenance bound the memory nudges hold. The guard set forks with the directives rather than running flat, and every guard fails toward a silent exit 0. Four are common: the payload must parse and name a covered tool, the external-engine marker must be absent, no truthy agent-identity key may be present (truthiness rather than key presence, deliberately and unlike its sibling: a harness version emitting a null or empty `agent_id` on a main-session payload would otherwise stand this hook down on every call and kill the feature outright), and the cwd must be a usable non-network path. The fifth reads the gate's verdict for this session and sends it down one path or the other. The episode path then takes three of its own: a goal must be armed and its leash held by this session, no matching checkpoint may already be open (an open one means the boundary is declared and the next turn lands it), and the episode's own nudge stamp must be absent or older than thirty minutes. The hold path takes three that answer to its own subject: the state's interactive-hold list must carry a record for this session, the denied decision's consumed reading must be at or above the context floor, and this session's own stamp in `compact-hold-nudge.json` must be absent or older than the same thirty minutes. The third guard above is load-bearing on its own rather than belt-and-braces, because a subagent's PostToolUse payload carries the parent session's own id, so nothing downstream of it can tell a dispatched agent's tool return from the main session's. The interval stamp is a compare-and-set against a re-read of the state, failing closed to no stamp, because a stamp landing across a valve or an illegible allow would restore an episode that allow had just cleared and hand a stale checkpoint the long freshness bound instead of the short one. Its honest rate is once per interval per tool batch rather than once per interval: parallel tool returns all read the stamp before any of them writes it. `kit-sidecar-capture.js`, on a `Bash` matcher, carries two duties for the judgment sidecar. It appends one JSON line per completed call to the spool under `~/.claude/kit-sidecar/`, so a separate daemon can ask a local model whether each call did what its stated intent required; and it reads that daemon's answers back, putting queued items in front of the session as `hookSpecificOutput.additionalContext`, the one field of a hook's response that reaches the model. The two duties have independent off switches, each dormant unless its own directory exists and neither creating it: the spool root gates capture, the `inbox/` directory beneath it gates delivery, the daemon's first run is the activation act, and deleting either directory switches that duty off while the other keeps running. Delivery stands down entirely on a subagent's call, because a subagent's payload carries the parent session's id byte-identically and would otherwise spend the parent's queue on work that session never saw. A delivered block carries at most three items, each cut to 600 bytes, in a batch budget derived from those two numbers so a full batch always fits, the remainder left queued for the next call, and it is framed as data rather than instruction, naming the machine boundary the sidecar's judgments cross and the source each pointer is unverified against. A per-session offset records what has already gone out, advanced under a claim that is attempted once and never waited on. The hook exits 0 on every path including its own internal errors and blocks on nothing, because the one thing a hook observing a session may not do is put that session on a critical path. `docs/security-model.md` carries what the spool holds and what protects it.
- **PreCompact** runs `kit-compact-gate.js` on the `auto` matcher alone, the scheduler that lands native auto-compaction at the boundaries a plan run declares instead of wherever context happens to fill. A boundary is ordinarily a section's close, and where a run goes long enough with work in flight and no section closing, it is an interim board entry written to the plan doc and put through the run's commit model, so a drought between closes still leaves the gate somewhere safe to land. `executing-work` owns both moments and the drought's trigger, and opens the checkpoint the gate reads. Nothing can raise a compaction on demand, so the gate works the only lever there is: it vetoes one. A denied auto attempt is re-offered once per assistant turn, indefinitely, which is what turns a veto into a schedule. It reaches a three-state verdict, evaluated cheapest first. Two preconditions come first and allow outright when either fails: the trigger must be `auto`, and `KIT_EXTERNAL_ENGINE=1` must be absent (an engine's workers are fresh per section and have no mid-chapter context to protect). Past those, an armed kit goal whose leash this session holds takes the **boundary-gated** path, denying while no boundary checkpoint is open, consumption read from the transcript is legibly below a safety ceiling, and no live operator-consent marker names the bound session. An armed goal no session has yet claimed is decided by the same claim proofs the leash uses, two predicates that this gate and `kit-goal-stop.js` both call: a transcript showing the user typing the arming command (one predicate in `kit-compact-lib.js`) claims the binding, and so does a session whose own id equals the arming session id the state records (one predicate in `kit-goal-lib.js`, reading no transcript at all, which is the route by which a run that armed a plan for itself reaches its own leash). Either claim takes the boundary-gated path; a session meeting neither is a bystander on the interactive path. An in-session arm binds at arm time and reaches the gate already bound, so what this claim point serves is the narrower population the arm CLI could not bind: an arm whose session id was absent or matched no transcript on this machine, and an arm run outside any session. For that population, claiming here rather than only at a stop is what makes the gate reachable on a well-behaved run, since the completion contract forbids stopping while unblocked work remains, so a run that never stops would otherwise stay unbound and ungated for its whole length. The claim's write is best-effort and the verdict does not wait on it, matching the leash's own posture that enforcement never depends on the write: a `.kit/` that refuses the write leaves the run deferring to the safety ceiling, which is where a refused checkpoint write leaves it anyway. A checkpoint opened while the goal was still unbound records no bound session, and each claim point adopts such a record for the session it binds at the moment it binds it, carrying the original opening timestamp and pending flag over verbatim so an adoption grants no freshness and an expired record stays expired. A record already naming a session is never rewritten, so a checkpoint belonging to a genuinely different session still reads as absent. An armed goal beside a payload carrying no usable session id still allows outright rather than taking either denying path, since no binding could be written from it and no comparison made with it. Every other session, meaning no goal is armed for the project or an armed one belongs to a different session, takes the **interactive** path, which asks the transcript a different question: whether a native automation instrument is driving this session. When `/goal` or `/loop` is in effect the gate allows, because an automated run is better served compacting early at the native trigger than deferring; otherwise it denies to the same safety ceiling, so a hands-on session keeps its full context through the long middle of a working stretch instead of being compacted at the early trigger the armed path needs. That deny, and the boundary-gated one above, are what the two release markers lift, and each is read only after every allow already described has declined, so a session holding no marker takes exactly the path it always did. A live role-boundary marker naming the compacting session releases the interactive deny alone: it is a goalless seat's own declaration that its context holds nothing the disk does not, which is what a leashed worker's checkpoint already says on the other path. A marker the checkpoint CLI's `boundary` verb wrote carries a declaration field and a recorded transcript position, a byte offset with a sha256 anchor over the preceding stretch, and the leg honors it only while nothing has arrived in that session's transcript past that position: the gate reads forward from the offset and refuses on any reading that cannot vouch for the moment, a replaced or unreadable transcript and an inbound message among them, with the refusal set stated at `markerMomentHolds` rather than counted here. Position rather than time is what orders those lines, so the rule reads no timestamp at all. A marker carrying no declaration field is the Stop hook's turn-end bank, rewritten every turn, and the rule does not reach it, which is what keeps an automatically banking seat banking: an offer only ever arrives inside a later turn than the turn end that opened one. A live operator-consent marker naming the session releases either deny, being the operator's word rather than the session's judgment. Either one allows, retires itself, and journals its own reason, so a marker ordinarily lands exactly one compaction, the retirement being best-effort like the checkpoint's and a failed delete costing one extra release inside the marker's own age bound rather than a wedged run; both markers age out in 4 hours, each derived from the deferral episode's own idle bound rather than restated beside it, so the three quantities bounding a session's quiet gap retune together. Neither reaches a clause that denies for an integrity reason, so consent converts a not-yet into a now and never a never into a yes. Every other state, every read error, every ambiguity allows, so a forgotten checkpoint or a misread transcript degrades to compaction landing at the native trigger, the behavior before the gate existed, and never to a wedged run.

Automation detection reads the transcript for shapes the harness writes but does not document, which is why every misread is built to land on allow. Native `/goal` is read from two surfaces: the `goal_status` attachment the goal system writes at arming and at each stop evaluation, whose `met` field distinguishes a running goal from one that completed and auto-cleared, and the user-typed command markup, whose `clear` argument retires it. `/loop` is read from its own user-typed command markup, retired by the terminating `ScheduleWakeup` whose input carries `stop: true`. Both are ordered signals and the newest match decides, so a finished goal or a stopped loop returns the session to the interactive deferral rather than leaving it classified as automated forever. The reader takes a capped head-plus-tail slice of the transcript, because `/loop` evidence sits at the head where the command was typed while goal status lands in the tail, and it excludes tool results, meta entries, compaction summaries, and sidechain rows, since the literal command markup travels freely inside quoted file content and agent output. That exclusion is load-bearing rather than defensive: this repo's own plan docs and hook sources quote the markup, so reading them plants it in the reading session's transcript. Manual `/compact` is never gated, and it is excluded in code as well as by the `hooks.json` matcher, the in-code clause allowing a non-auto trigger outright rather than refusing it, though only the matcher is ever reached: the matcher is auto-only, so the gate process never starts for a manual compaction and the in-code clause is defence against a later wiring edit rather than a live path. That has one consequence for the release markers below. A manual compaction is not a landing the gate sees, so it spends no marker; a marker live at that moment survives the compaction and is retired by its own age bound or by the session's next gated landing. The boundary signal is `.kit/compact-checkpoint.json`, written by `kit-compact-checkpoint.js` at either executing-work boundary, a section's close or an interim board entry, and recording the armed plan, the session bound to it, which is null where the goal is not yet bound, and the session that opened it; rewritten by `kit-goal-stop.js` when a queue advance moves the current plan out from under an open one; and given an owner by either claim point, in `kit-goal-stop.js` and `kit-compact-gate.js` alike, where the record it finds carries none; the gate consumes it when it allows, so one checkpoint lands exactly one compaction, and a checkpoint naming another plan or another session reads as absent so a crash-orphaned file cannot open the gate, and one whose opener is not the session it is bound to reads as absent too, so a boundary a bystander declared, or a record an older kit wrote with no opener, never lands the leash holder's compaction. The valve is the failure mode nothing else caps: sustained denial with a chapter that never closes would climb to the model's hard limit, where a session dies outright on an over-length prompt, so at or above the ceiling the gate allows regardless. One ceiling serves both denying paths, an absolute token count sized for the roughly 1,000,000-token window the models running these sessions carry, because the PreCompact payload provides no `model` field to derive the real one. That assumption is the one direction of this design that is not fail-open: on a model whose window fell between the trigger and the ceiling, the valve would never fire. It is bounded by what the gate can actually do, which is veto an offer the harness has already made, so a model whose window is too small to reach the trigger is never offered a compaction to defer. The consumption it compares against is read from the newest assistant `usage` block, taking the largest entry of that block's `iterations` array when one is present, because a multi-iteration turn's top-level cache figures are summed across iterations and describe no single request. Largest rather than last, because the two errors are not symmetric: understating consumption defers longer and walks a session toward the hard limit the valve exists to keep it away from, while overstating it only ends a deferral early. Nothing detects that state, and the doctor's auto-compaction-window check is not it. That check reads the configured window, which says nothing about the running model's real one; what it catches is the opposite and safer failure, a window configured so high that the trigger lands at or above the ceiling, where the valve allows everything and the gate defers nothing. `docs/security-model.md` carries the assumption and what does and does not cover it.

The boundary signal carries its own staleness bound, because a checkpoint that outlives its boundary is how this feature would quietly become a no-op. A boundary is often reached below the trigger, where there is no pending offer to catch, so without a bound that checkpoint would sit open and admit the next offer, which arrives mid-chapter. The gate therefore treats a stale checkpoint as absent, and it measures staleness two ways rather than one, because the two kinds of boundary are not alike. A checkpoint opened below the trigger has no offer waiting for it and takes a short window of ten minutes, which is what retires the leftover. A checkpoint opened while the gate is already holding offers takes a far longer one, because what delays its consumption is a tool call that has not returned yet, and a dispatched implementer or a whole-repo suite routinely runs past ten minutes. Which leg applies is not the caller's claim about itself: the CLI records a `pendingOffer` flag at the open, and the gate honors the long leg only when it can corroborate that flag against its own recorded state, requiring an episode still open, owned by this binding, and dated before the checkpoint it vouches for. A flag with no corroboration falls back to the short leg, which is the fail-safe direction. The predate condition is what stops the flag from minting its own licence, since without it the very denial that refuses a stale checkpoint would open the episode that corroborates the same checkpoint one turn later. The long leg's outer bound is 24 hours, a sanity cap on a hand-made or clock-skewed record rather than an operating figure; the operating bound is the episode's own life, which ends four hours after its newest denial, because a denial is recorded only at an assistant turn and a long call has none. The asymmetry that makes the short leg work is unchanged: past the trigger the harness re-offers every turn, so a checkpoint opened at a real boundary with the turn free is used within seconds, while one opened below the trigger simply ages out. The executing-work ritual also clears the checkpoint when the next section starts, where the record is that session's own boundary or nobody's, so the two guards are independent. That clear runs only at a section start, so the expiry is the sole bound on a checkpoint opened at an interim board entry, where by definition no section is closing and none is about to start. The kit summarizes nothing itself: the native summarizer runs unmodified and re-grounding afterward is the existing `session-start.js` `compact` path.

The gate also records what it decides, which is what makes any of the above measurable rather than reconstructed from scrollback. Every verdict on every path writes two files under the project's `.kit/`: `compact-gate.json`, the current state, and `compact-gate.jsonl`, an append-only journal. A third project-local file sits beside them under the same resolver, `compact-hold-nudge.json`, which the gate never writes: it is the deferral nudge's own per-session clock for a hold that owns no episode, and it exists as its own file because every gate write rebuilds the state from a fixed key set, so a stamp parked among those keys would be erased by the next verdict. One resolver in `kit-compact-lib.js` decides where that `.kit/` actually is, and it serves every writer of these files and the gate's own reader alike, which is what keeps a marker's writer and its reader agreeing on where it lives. Ordinarily it is the project directory's own `.kit/`. The exception is a project directory lying inside the memory store, which is the coordinator seat's normal state once its board lives there: dropping `.kit/` into that tree would replicate one machine's gate state to every other, so the resolver sends it to an unsynced per-machine location outside the store instead, `~/.kit/store/<store-relative-path>/`, keyed that way so two store-resident projects stay separate. The path is named here rather than left to the resolver's source because nothing else owns it: no doctor check knows about it and nothing prunes it, so a store-resident project's gate journal accretes there to its own 2 MB trim and an operator looking for it has only this line to go on. The alternative reading, a `.kit/` under the store root that the store's own exclusion would keep unsynced, was declined because it puts the file back inside the replicated tree and relies on ignore machinery to keep it out, which is the arrangement that has already failed once here. The journal carries two record classes, partitioned so a reader folding it never has to guess: a decision record carries `verdict`, and a nudge record carries `event`, which takes one of two values, `nudge` for the leashed run's own reminder and `nudge-hold` for the directive sent to a session held on the hands-on leg. A decision record holds the time, the verdict (`allow`, `deny-boundary`, `deny-interactive`), the clause that decided it, which on an allow a release marker lifted is `role-boundary` or `operator-consent` so a run's compaction history states which release landed it, the consumption figure read, the checkpoint's age and flags where one was present, and the payload's session id; a nudge record holds the time, the session, and which tool's return carried the reminder, that last field being how a run whose nudges were all consumed by dispatched agents is readable after the fact. The state additionally holds two aggregates rather than one. The first is the open deferral episode, which the corroboration leg and the deferral nudge both read: how many offers have been denied, since when, and when the run was last nudged about it. The second is a list of interactive holds, one record per session and capped at eight, each naming why that session is being held, `bystander` or `no-goal`. The two are stored differently because they belong to different things: the episode belongs to the leash, so one slot is enough for it, while a hands-on hold belongs to the session, so it needs a record per session and the list is the deferral nudge's alone to read. Both writes happen after the verdict is emitted and the exit code set, under one try that covers the state write, the trim and the append together, so a recording failure cannot change what the gate decided but can cost the journal line whose state write already landed. That is the undercount direction, and it is the one chosen: the state is authoritative and the journal is allowed to lag it. A decision carrying no cwd is not recorded at all, and the recorder refuses rather than creating `.kit/`, so a project that has never armed a goal accumulates nothing. The log is bounded, rewritten to its newest 1 MB once it passes 2 MB. The episode also reaches the operator directly: the gate's stderr note at a boundary deny carries "held N offers over M minutes" from the same aggregate, both integers clamped by one shared rule so neither can print a figure the state could not hold, and its diagnosis clause names the case of a checkpoint whose pending-offer flag no episode vouches for.

The episode belongs to the leash rather than to a session, which is the non-obvious part. Only the bound session can produce a `deny-boundary`, so a boundary deny extends the episode it owns and otherwise takes the slot, a foreign incumbent on that path being a dead binding rather than a rival; an interactive deny records its decision and leaves any standing episode alone; and an allow clears the episode only when the allower owns it, since a bystander's compaction lands in its own context while the bound session's offers stay pending. The release markers are swept on a different rule, and it is the one allow-time action scoped by session rather than by ownership: every allow, whatever clause reached it, retires any marker naming the landing session, while a marker naming another session is not that landing's to spend and a deny retires nothing because nothing landed. The sweep needs the payload's cwd as well as a string session id, so an allow carrying no cwd reads the markers on the legs above and retires none, the same undercount direction the decision recorder beside it takes. That sweep closes a window the markers would otherwise open. A marker that missed its moment, left live through a valve, checkpoint or illegible landing, would stay honorable for the rest of its age bound, and if the same session crossed the trigger again mid-chapter inside that window the leftover would convert the deny into an allow at exactly the placement the gate exists to prevent. A manual `/compact` leaves that same leftover and the sweep cannot reach it, the gate never running for one, so an age bound is the only retirement there. Every failure direction under that model is an undercount, which degrades to the pre-recording status quo rather than to a checkpoint that outlives its hold. The read-modify-write is unlocked, so two gate processes in one project can both read a count and both write the successor: the state is authoritative and the log may disagree in either direction. It is a diagnostic surface, and nothing branches on it except the two consumers named above.

A denied auto attempt also leaves the operator a note on stderr, and that note is the operator's only diagnostic, since PreCompact stderr reaches the operator's terminal and never the model on the harness the kit runs against, an observed property of that harness rather than a documented guarantee, and the one premise the note's runnable release chain rests on: a harness that put that stderr in front of the model would hand every held session its own release recipe, so a change there is a review trigger for this note. It names both boundary kinds (a chapter close or an interim board entry), states the hold as running to that boundary or to the safety valve near the token limit, says that repeating for many turns inside one section is expected, and names the one state that is not expected: still firing after a Chapter has closed, which means either that the checkpoint was never opened or that the one opened is no longer honored (expired, carrying a pending-offer flag no deferral episode vouches for, or opened by a session other than the leash holder, which is also how every record written before the opener was recorded reads). The remedy it prints is a chain the operator can run from the project directory: prompt the session to close its boundary, or check with a runnable `node "<path>" status`, read the bound session's id from the goal CLI's `status`, which prints the binding, and release that session with `node "<path>" consent --session <id>`; each path is composed from the hook's own installed directory rather than written repo-relative, because the gate runs in every project on the machine and a repo-relative spelling resolves only inside the kit's own checkout. The note offers no `open`, since `open` is scoped to the calling session: from the operator's own shell it has no session id to write, and from another session's shell it would declare that session's boundary. A denied interactive attempt leaves a different note, and its remedy is the `boundary` verb rather than `open`, carrying the one precondition the verb itself cannot check: that the session banked its state at a natural boundary first. For a goalless seat that never loads the role skills, that note is the whole of what tells the operator the verb exists for that session, and the operator is the one who relays it, the note never reaching the seat itself.

Operating the gate is one CLI and two settings. `kit-compact-checkpoint.js` carries five subcommands, three for the leashed worker's own checkpoint and two for the release markers a goalless seat and the operator use: `open` writes a checkpoint for the armed plan and the session currently bound to it, recording the caller as its opener, and refuses when no goal is armed, since a checkpoint naming no plan could never match, when the caller's session id cannot be derived, and when the caller is not the session the checkpoint would bless (the bound session where the goal is bound, whatever is on disk; otherwise the session that armed the goal, where the caller is that session; otherwise the opener of a record already on disk for that plan), since a bystander's boundary would land the leash holder's compaction; `clear` removes one, which is what executing-work runs at the start of each section, under the same caller rule where the record is somebody's boundary, so a bystander cannot retract a boundary the leash holder declared, and it stays a no-op where nothing is open and asks no caller id over a record that is nobody's boundary (another plan's, one left with no goal armed, an illegible or oversized file, one naming no opener, one whose recorded owner is not its own opener, or, under a bound goal, one whose opener or owner is not the bound session, which the gate would refuse whoever left it), since there is no scope there to protect; both verbs refuse over a goal state that is present but cannot be read, `clear` only over a path that holds something and an absent path staying its no-op, since whether any session holds the leash is then unknown and a guess either way could retract or overwrite a live boundary, and both refuse over a checkpoint path that holds something other than a regular file, saying what is there and leaving it in place, since a scope guard can only protect a scope it can see; a path the filesystem would not let them read, or would not say what is at, is the bound session's where the goal is bound, since such a reading lifts and the leash holder is the one caller who may act there, and is refused to every caller where the goal is unbound; and `status` reports whether a checkpoint is open and, where the gate would read it as absent, which clause failed, answering from the same match rule the gate itself decides by so the report cannot drift from the verdict, and it reports each release marker on the same terms, naming the session the marker is scoped to, the timestamp it was written at, and, where the marker is live or expired rather than consumed or malformed, the bound it ages out against. It reports the gate's own recorded state too: the last decision's verdict, the clause that reached it and its age, and either the open deferral episode's offer count and age or that no episode is open. That second half is what the Stop hook's boundary directive sends a session to read, so it is the operator-and-model-facing answer to "is the gate holding, and for how long". It is deliberately not scoped to a session, which is a reporting choice rather than a decision one: every code path that acts on an episode passes the owning session id, while `status` shows what is there, so a dead binding's episode can still stand in the report for up to the four-hour idle bound after a crash. `open` reports which freshness leg it opened, reading the gate's state to decide whether to record the `pendingOffer` flag, and refuses when no goal is armed. `boundary` opens a role-boundary marker for the calling session, and it is the declaration act rather than a report: it serves a session the registry does not carry, and equally a registered seat whose project tree carries work the seat does not own and cannot clear, which is the case that has no other way to bank a boundary at all. It also stamps a machine-written `Banked:` line into the calling session's own coordinator registry entry where one exists, atomically and tolerant of an absent entry, since the stamp is a record rather than a precondition and the marker opens either way. It accepts exactly one argument form, `--cancel`, which retracts this session's own marker and reports whether one was there; nothing depends on it being run, a declaration being scoped to the moment it was made rather than to a window. `boundary --session <id>` is the natural misreading of the consent form, and it is refused rather than parsed loosely, since a parser that ignored the tail would answer by denying the named session its release and handing the ambient session one it never asked for; `consent [--session <id>] [--project <path>]` records the operator's release for the caller's session or an explicitly named one, at the caller's own directory or at a named project. Those two derive the caller's id from `CLAUDE_CODE_SESSION_ID`, as `open` and `clear` do, and refuse to write an unscoped marker where none is derivable, saying so rather than writing one. `boundary`, and `consent` without `--project`, write into the current directory's `.kit/` while the gate reads them at the compacting session's own project directory, so on those paths the working directory is load-bearing in a way no flag states: releasing a session that works another repo means running the command from that repo, and running it elsewhere writes a marker nobody reads and reports success. `consent --project` is what closes that silent miss for the operator's own case, resolving the marker against the named directory instead of the cwd, and it is corroborated rather than merely redirected: the command refuses loudly when the named session has no transcript under that project, so the failure that used to report success now reports the mismatch. That corroboration is also what bounds the widening, since the flag is the one place a caller's value reaches a marker's path. The first setting is `autoCompactWindow` in the user's `settings.json`, and it is what gives the gate something to schedule, since the gate can only defer an offer and never raise one. The second is `compactNudgeFloor` in the machine's own `claude-kit.local.json`, read tolerantly with a default of 285000, which is the consumed-token figure a hands-on hold must reach before the deferral nudge says anything to the held session at all. It bounds a voice rather than a verdict: the gate goes on silently deferring every unmarked offer at any count, and below the floor the only difference is that nobody is told. The doctor reports the configured value, recommends one sized so the trigger leaves a band wide enough for a chapter to close before the valve fires, warns when a configured value leaves that band too thin, reports a configured value that differs from the recommendation so a machine already carrying one still learns of a new figure, and writes the value only behind an explicit `-Fix` consent prompt. Two write cases, and they take different consent. Supplying an absent value is what `-Fix -Yes` is for, since it converges: run it twice and the result is the same, and nothing the operator chose is lost. Replacing a value the operator did choose is withheld from `-Yes` and waits for an interactive answer, because an unattended run cannot tell a deliberate setting from a stale one, so it would revert the deliberate one, and would do so again after every retune of the recommendation it compares against. It reads the ceiling out of the hook source rather than restating it, and says so when it cannot, because a silent skip reads exactly like a healthy result.
- **Stop** runs `stop-docs-hygiene.js`, `kit-goal-stop.js`, and `seat-stop.js`, in that order. `seat-stop.js` serves the goalless seats: it resolves the stopping session's registry entry under the machine's coordinator directory and exits silently where there is none, so the whole cost for every unregistered session on the machine is one stat, and where there is one it stamps the entry's heartbeat under a ten-minute throttle and, when that entry's own status stamp shows the seat pushed status this turn and the working tree is clean, opens the role-boundary marker for it. That is what makes a seat's banked moment structural rather than a step its runbook asks it to remember, and the CLI's `boundary` verb is the manual path for the two seats the hook cannot serve: a session no registry entry covers, and a registered seat whose project tree carries work it does not own, where the clean-tree conjunct can never be satisfied and the dirt is not that seat's to clear. `kit-goal-stop.js` is the deterministic leash that holds a `/kit-goal` run to completion. Its state is a file in the project (`.kit/goal-state.json`) that no session boundary deletes, resolved to the main checkout for a session working a linked worktree (see Worktree resolution below), and the hook enforces on session identity: native compaction preserves the session id, so an armed run keeps its leash across its own auto-compactions, while a session the hook cannot tie to the bound one is a bystander whose stop is allowed, and re-arming is the recovery. An arming may name several plans, in which case the state carries the ordered queue and a plan's terminal state advances the leash to the next plan rather than releasing the session; only the last plan releases. A `BLOCKED:` advance is keyed to the transcript entry that produced it, recorded in the state as `blockedAdvanceKey`, because the hook's read of the last assistant turn races the harness's append of it and a lead read twice would otherwise consume two queue positions off one blocker. The key rides with `blockedAdvancePlan`, the plan the advance moved to, and is retired by position rather than by deletion: it is honored while that plan is the current or the immediately previous queue position and ignored past that. Retiring rather than deleting is what stops an intervening advance, a plan behind the leash turning up Complete, from resurrecting a blocker the queue already consumed, while retiring at all keeps a stale key from widening the one collision surface the text-digest fallback has. A key with no recorded plan, which is what an older state file carries, is honored wherever it matches, since the failure direction there is holding rather than advancing. A lead whose key is already spent falls through to the ordinary hold: it never advances, never emits, and never releases. An advance also rewrites an open compaction checkpoint to the new plan, since the checkpoint is matched against the goal's current plan and a plan's own close-out opens one immediately before the stop that advances. The queue fields are strictly additive, with `plan` continuing to name the current plan and `boundSession` the leash holder, which is what lets the compaction gate read a queue-armed state with no knowledge of queues at all. One binding rides the whole sequence, and the SessionStart armed-goal notice reads that binding back rather than announcing the arming undifferentiated: the leash holder is told the leash is its own and where the queue stands, a bystander is told the leash belongs to another session and that the plan is not its business, with the re-arm path for a run that has died and a liveness hint taken from the bound session's recorded transcript mtime (a number and a unit reach the notice, never the path), and an arming no session has claimed keeps the claimable framing, naming both points a claim can land at, its first stop and its first auto-compaction offer, whichever lands first. A bound goal beside a payload carrying no session id is distinguishable from neither, so it degrades to the undifferentiated notice rather than risk telling the leash holder that its own plan belongs to somebody else. The doctor reads the same file for its armed-goal report, and reads it defensively rather than through the library's normalizer, because a hand edit is the case it exists to catch: it names the queue position and the remainder, discards a queue disagreeing with `plan` in favour of the single-plan reading, and splits the terminal-current-plan case into two warnings, since it means opposite things at the two queue positions. With plans remaining it is a stalled advance, normal mid-turn because the hook advances at the bound session's next stop, and otherwise a dead run to re-arm the remainder over; on the last plan it is the old stale goal, to clear. A separate exposure check runs alongside it, and deliberately outside the clone gate the report sits behind, because every armed session's start notice reads the state back and the gate's own journal records a session id and a work timeline beside it: it asks git whether the whole `.kit` directory under the directory the doctor was launched from is tracked, ignored, or neither, and warns on the first two of those with the command that fixes them. Both readings are taken over the directory rather than one standing in for the other, because a repository can ignore `.kit/` and still track a file inside it with `git add -f`, and the tracked reading runs first, since git stops reporting a path as ignored once it is tracked. A tracked result names every path it found, uncapped, and its remedy line names those paths rather than a hardcoded filename. Scoping it to the launch directory rather than to the kit's own checkout is what makes it reach a consuming project at all, since the kit's checkout already ignores `.kit/`. It detects the exposure without preventing it. Its three emit points also append to the goal event stream described below. Under `KIT_EXTERNAL_ENGINE=1`, `stop-docs-hygiene.js`'s blocking outcome becomes advisory text carrying no decision, so the stop is allowed: holding a headless worker at its turn end for a library-hygiene pass its directive does not cover trades a tidy `docs/` tree for a stuck run. `kit-goal-stop.js` does not read the marker, and does not need to: it binds to one session, bound at arm time when the arming CLI can corroborate its own session id against a transcript on disk, and otherwise claimed by one of two things: the user's own arming text (a plan path typed as a slash-command argument, or a message leading with the `/kit-goal` token whose argument block names the plan), or a session whose own id equals the arming session id the arm recorded, which is what reaches a run that armed a plan for itself and so typed nothing. A worker whose directive merely names the plan meets neither and is a bystander it never leashes. It has five block reasons, and only two of them carry the boundary ritual as well as the hold. The ordinary hold and the capacity-shaped refusal share one directive, spelled once in the file and interpolated twice, which names two conditions rather than one: a Chapter closed since the last boundary, or the compaction gate holding auto-compaction offers since then. The second condition exists because a run whose review rounds keep adjudicating without any section closing produces no Chapter for hours, so a Chapter-only test is silent for exactly the run the gate has been holding longest; the interim board entry is that run's boundary, and the directive names it. The second condition is additionally gated on the turn being at a clean point, since a deferral met mid-step is not a boundary and acting on one would land the compaction at the very place the gate exists to avoid. Both then tell the session to load executing-work if it is not loaded and complete that skill's boundary steps in its own order, running the memory sweep, appending the Chapter or the interim entry, honoring the section's commit model, and only then opening the checkpoint, naming the gate's two bounds (a matching checkpoint, or the safety valve near the context limit) rather than an unbounded hold. The other three reasons each decline the directive for their own reason, and the reasons are not interchangeable. The queue advance asks something narrower and specific to itself, whether the plan that just finished opened a checkpoint at its own close; note that it cannot assume a Chapter closed, because an advance on a leading `BLOCKED:` appends none, and such a run reaches its next boundary through the ordinary hold on the plan it moves to. The unusable-plan hold declines it because the plan doc cannot be read at all there, so instructing an append to it would name a step the session cannot perform. And the reason for a stop already spent carries none of it, because it fires only where the last assistant turn is an already-consumed transcript entry, so no Chapter can have closed since. This is the model-facing half of what the compaction gate's stderr note cannot say, that note reaching the operator alone.

`memq-grant.js` runs the other way and is the kit's only hook that allows rather than denies. Under the external engine's write-gated spawn vector the Bash tool refuses `node <script>` outright, which would cost a fleet worker the memq CLI, so `memq-grant.js` emits an allow decision for exactly one command shape: one `node` invocation whose first argument resolves by normalized path equality to this plugin's own `scripts/memq.js`, with the fleet-store signals present, a positively identified interpreter, no module-preload environment variable set, no shell metacharacter anywhere in the command line, a subcommand the hook's own list of granted verbs names, and none of the seven withheld flag shapes among its words. On anything else it emits no decision and the call falls through to the host's normal permission flow, so its safe failure is silence rather than the guards' fail-open allow. `docs/security-model.md` carries the invariant in full, the accepted risks, and what the grant does and does not contain; `docs/fleet-integration.md` carries the engine-side preconditions it depends on.

### Path rendering

Every channel a model reads renders filesystem paths through one renderer in `hooks/kit-compact-lib.js`, because a path under the operator's home directory carries the operating-system account name and a hook's `additionalContext` or a CLI's stdout lands in a session's context. The library exports five names for that job: `sanitizeForOutput` over a value of any kind, `displayPath` over a value known to be a path, `scrub` over a whole composed line, `scrubAfterStrip` for the relaxed second pass over text a strip altered, and `homeElisionsKnown` for whether a home directory is knowable at all. `sanitizeForOutput` takes four steps in a fixed order: elide, strip to printable ASCII, elide again with both name boundaries dropped where the strip removed something, and cap last, at 120 characters unless the caller names another, with a mark appended saying what was removed or cut. The elision carries two spellings of the home directory, the literal one and the flattened one a transcript directory's name is composed with, so an account name sitting in the middle of a path is reached as well as one at its head. `displayPath` decides containment with `path.relative` rather than a text prefix, which is what keeps a sibling directory whose name merely starts with the home directory's its own name and still elides a win32 path differing only in letter case.

Each channel binds that renderer at its own write boundary rather than at the sites that compose lines: the checkpoint CLI's two emitters, the goal CLI and the registry stamp under a guarded load, the size CLI per printed line, `memq` in CLI mode passing every chunk written to either descriptor through `scrub` once at the descriptor, the canary through one child described below, the memory session hook, the recognition nudge and the frontmatter guard over the store text they emit, and the repo-only probe runner. The shim that locates `memq` has no library to load, so it withholds the two paths it would otherwise name. `test/kit-output-channel.test.js` holds the renderer to that one file, sweeping every `.js` under the plugin's hooks and scripts directories for a second declaration of any of its parts. `docs/security-model.md` carries the property as a security claim, what a CLI prints when the library itself will not load, and the residuals that stand.

### The canary

`hook-canary.js` is the one hook whose subject is the other hooks. Every kit hook fails open, so a stale or damaged plugin cache, a hook file that no longer parses, or a guard gone inert takes the enforcement away with no signal at all. The canary probes the cache a session actually executes (`CLAUDE_PLUGIN_ROOT`) and speaks only when something about it is positively broken.

Four probe classes run over that cache. **Load checks** cover every hook named in `hooks.json`: each named file is present and `node --check` parses it. **Known-answer behavior probes** run in both directions, so a guard that answers everything the same way cannot read as healthy: a governed subagent writing a `docs/` path must deny while a main session writing the same path must allow, a read-only subagent's `git commit` must deny while its `git diff` must allow, and a throwaway fixture holding an armed goal must draw a block from `kit-goal-stop.js` while a directory with no goal armed draws nothing. `memory-frontmatter-guard.js` takes both directions too, and the allow half is not optional there: the guard matches every `Write`, `Edit`, and `MultiEdit`, so one stuck at deny would block every file write in every session and only an allow probe catches that. Its two payloads name a project-tier path under a per-run random store root the probe environment points `KIT_MEMORY_ROOT` at, one carrying a dangling `supersedes:` that must deny and one carrying a sound block that must allow. `memq-grant.js` takes six probes on Windows and five elsewhere, one allowing and the rest withholding. The allowing one is the single invocation the grant covers, which must produce an allow decision. The withholding ones each aim at a screen the allow probe cannot see the loss of: a metacharacter-carrying near-miss, a `--body-file` value, a `--rollup`, `find` in the verb position, and, on Windows only, the Git-Bash `/d/` spelling of the script path, that rewrite being what the refusal there is about. Both directions run for the same reason as the guards and one more: a deny guard gone inert eventually shows up as something unexpectedly permitted, while a grant gone inert never announces itself, because a fleet worker simply loses memq. The withheld shapes divide by what stands behind them: `--body-file`, a body-carrying `--update`, `--supersedes`, `--trigger`, `--type=<type>`, and both delete verbs are refused by the CLI as well, so a hook that lost one of those screens is one lock short, and `--drop-malformed`'s second lock is the CLI's own coupling of that flag to the `--rollup` this hook also withholds, while `find`, `--rollup`, and the `anchor` and `triggers` verbs are withheld at the grant alone and a hook that lost any of the four is open with nothing else to say so. The probes cover that division incompletely: `find` and `--rollup` each carry one, the second-locked shapes ride `--body-file`'s, and `anchor` and `triggers` carry none, so the two unlocked shapes with no probe of their own are the ones a hook regression would take away silently, `triggers` among them for every shape but its destructive replace, which the CLI now refuses under the store signals. `test/memq-grant.test.js` pins the withholding in the deny direction instead, which is a repo-suite check rather than a session-start one. Its probe environment is constructed rather than inherited, with PATH pinned to the canary's own interpreter directory and every other variable dropped unless a short keep list names it, so ambient machine state cannot fail it. Building it from that list rather than subtracting known-bad names from the inherited environment is what lets the canary need no knowledge of what any hook refuses on. `merged-pr-push-guard.js` and `pr-docs-guard.js` get a load check plus a benign-payload plumbing probe only, because their deny paths need external state (a MERGED pull request, a dirty checkout off the default branch); the repo suite owns their behavior. The goal probe runs against a temp directory with the event sink and the re-read delays pinned away from real machine state. Those two classes are a few dozen serial spawns on the current wiring, one load check per hook `hooks.json` names plus one per behavior probe. The bound is per child at 5 seconds rather than per phase, so a healthy cache costs under a second in total while a cache where every grant probe hangs costs about 35 seconds of it; `docs/backlog.md` carries the whole-phase budget that would cap the failure case. **The integrity check** spawns nothing: it only reads and hashes files, so it is free against that budget.

Integrity is the class that sees a hook whose bytes changed after packaging, which parsing and behavior probes cannot: the plugin cache is writable by the principal a session runs as, and a guard edited in place enforces whatever it now says. The check re-hashes every file the build's `hooks` map names, from the executing cache, and reports a mismatch as bytes that are not the ones the build packaged, pointing at a reinstall or update. A manifest entry with no file on disk reports as missing from the build; any other read error (a lock, a scanner holding the file open) stays silent, because it says nothing about the file's contents. The check runs last and skips a file another probe already flagged, so a wholesale-different cache cannot fill the report's line cap ahead of a guard that is present, parses, and is positively answering wrong. An absent stamp, an unparseable one, or one with no `hooks` key is silent: an older build gives the check no basis, and a cache it cannot describe is never called tampered.

Its coverage is wider than the load check's in one direction and bounded in another. The build hashes the whole packaged `hooks/` directory while the load check enumerates `hooks.json`, so every file in that directory the wiring never names is covered here and nowhere else: `kit-goal-lib.js` and the other shared libraries the wired hooks require, and the three CLIs a session or the operator runs by hand, `kit-goal.js`, `kit-compact-checkpoint.js` and `kit-registry-stamp.js`; `hooks.json` itself is in the map, because rewiring a guard out of the wiring disarms it exactly as editing the guard does; and `scripts/`, `doctor/`, and `output-styles/` ship in the same cache outside the manifest. The manifest also lives inside the cache it attests, so deleting the stamp silences the check and rewriting stamp and payload together defeats it. `docs/security-model.md` carries what that detection buys against the threat it is sized for.

A failure writes one warning into the session context naming each failed probe with its expected and actual answer, capped at 10 lines plus a count of the remainder, and points at `/kit-doctor` and a reinstall. The report's path-derived values reach the shared renderer through one child spawned from the probed cache, on the failure path alone, because the canary itself loads nothing out of the cache it is probing. The parent keeps the verdict, the failure count, each line's fixed head and the instructions, and what it checks on the way back is shape and bound rather than integrity: it refuses the whole rendering when the child fails, exits nonzero, returns a different number of lines, returns a non-printable character, or returns a line that does not begin with the head the parent composed for it, and on that refusal it prints the same lines with every path-derived value replaced by `[path withheld]`, so the diagnosis survives. Which repair to run is legible from the line: a load-check or wiring failure means a partial or damaged install, where reinstalling and restarting the session is the fix, while an integrity line means the installed file is not the one that was packaged, where updating or reinstalling the kit is what restores the packaged bytes and every guard verdict that session already took is suspect until it does. The canary always exits 0 and never blocks anything. The loud/silent boundary is deliberate: anything positively observed about the cache being broken is loud, including a missing hook file, a missing or unparseable `hooks.json`, a probed hook the wiring no longer names, and a plugin root that is not there, while an unexpected error inside the canary's own code stays silent through its fail-open catch, since a canary bug that warned at every session start would cost more than the blind spot it covers. What the canary measures is a cache's internal consistency, not its freshness against the repo: a stale but coherent cache reads healthy, and `kit-version-nudge.js` is what watches for drift. The doctor's "Hook canary" check confirms the file is present and wired into the `SessionStart` array.

One consequence lands on whoever edits a hook: `test/hook-canary.test.js` runs the canary against the repo's own `plugins/claude-kit/` directory, so a hook changed without a rebuild leaves the gitignored stamp beside it stale and the health assertions go red. That red is self-diagnosing, naming the stale stamp and telling you to run `.\build.ps1`, and the coupling is deliberate: it is also what catches a hook edited after the last build before a package ships.

### Backlog surfacing

`docs/backlog.md` is a pull surface in a push workflow, so the kit pushes it. `summarizeBacklog` in `session-start.js` reads the file under the payload cwd, scopes to its `## Active` section, and emits one block carrying three figures: the active item count, the oldest dated item's ISO date with its age in whole days, and a tally of items carrying no date. Where the read did not reach the whole `## Active` section the block states that bound instead of presenting the figures as totals. Two properties separate it from the kaizen counter beside it. It carries no kit-repo marker gate, so it fires in any project holding a `docs/backlog.md`, and `KIT_EXTERNAL_ENGINE` does not suppress it, because the block carries no engine gate of its own. Engine sensitivity is per block rather than a property of this hook: the plan block drops its drive-to-completion instruction under the marker, the unleashed notice is suppressed whole, the plugin-view line changes its remedy, and the post-compaction re-load block names the engine's own directive as the governing skill rather than executing-work, so that a worker is not handed the drive-to-completion loop by the side door after the plan block withheld it. This one is untouched.

Numbers and one regex-extracted ISO date are the only interpolations, and item text never reaches the block, so a hostile backlog line cannot inject instructions into session context. The parse is deliberately coarse. The read goes through `hooks/kit-read-lib.js`, the shared bounded reader, at a 1 MB ceiling, so a file past it comes back as whole lines with the summary marked bounded, and a UTF-8 BOM is tolerated; items are top-level `- ` bullets, with a bullet whose content is entirely parenthesized (the shape the `curating-docs` backlog template ships) and a bare empty bullet counted as structure rather than items; and the aging anchor is the first `\b\d{4}-\d{2}-\d{2}\b` token anywhere on the line, because the kit's convention puts the parked date in the title's parentheses beside other context. A cross-component pin in `test/session-start-backlog.test.js` seeds its fixture from the template's own backlog block, so the placeholder shape and the parser cannot drift apart silently.

Every failure is silent and additive. An absent file, one that is not a regular file, an unreadable one, and a file read whole that carries no `## Active` heading or no items emit no block at all, and the check runs inside its own try so it can never affect plan recovery. Silence is reserved for what the hook established: a bounded read that reached no heading or no item emits a sentence saying the file went partly unread, because nothing being there and the part that was read holding nothing are different answers and only the first is silence. One known degradation rides with the coarseness: an ISO-shaped impossible date such as `2026-02-30` either rolls to a neighboring real date or joins the undated tally, depending on the runtime's `Date.parse`, which is acceptable in a coarse age nudge. A bounded read is not one of them, because the block says so rather than reading as a total. Any read that did not reach the end of the file carries a clause stating that every figure in the summary is of what was read. The flag is set by the read alone and is not narrowed by a heading closing the `## Active` section, because the heading scan is a column-anchored `##` match that a fenced code block inside an item satisfies, which would certify a truncated read as a total. The cost of the conservative direction is that a backlog over the ceiling whose Active section genuinely ended early reads as bounded when it was complete, which understates confidence rather than overstating it.

The behavioral half lives in three skills and one template, and the hook is the primary enforcement because it fires whether or not any skill loads. The `curating-docs` backlog template states the dated item shape (`- **<item> (YYYY-MM-DD).** <body>`); that skill's prune pass doubles as the aging check, naming every item older than 90 days for a promote, retire, or keep call, where a keep writes the fresh adjudication date ahead of the original (`(2026-11-07, parked 2026-05-01)`) and an undated item is past the threshold by definition and gets a backfilled date in the same pass. That check also has a standalone trigger, offered in one line when the session-start block reports an oldest item past the threshold and no close-out is near. `finishing-work` step 5 carries each named aging item, by name and date, into the close-out status with its question, which is how an aging item reaches an operator reading close-outs on a phone. `brainstorming` step 1 reads the backlog straight after `memq recall`, so a new effort finds an already-parked solution before designing a fresh one. The two knobs are the 90-day threshold, stated in the hook's block text and in `curating-docs`, and `NUDGE_FILE_READ_CEILING_BYTES` in `session-start.js`, the 1 MB per-file ceiling `summarizeBacklog` and the kaizen note walk share.

## Memory store

`plugins/claude-kit/scripts/memq.js` is a zero-dependency CommonJS CLI over the file-backed memory store under `~/.claude`. It resolves a project's store through four legs in order: an honored pin, the main checkout's derivation where the working directory is a worktree of one, the project directory the harness filed this session's transcript under, and otherwise the working directory put through the harness's own directory-name rule, so it lands on the same directory Claude Code writes. The session leg is gated twice and answers only where both hold. The working directory has to be this process's own, since a caller naming another project's path is asking about that path rather than about where this session sits, and it has to sit inside the project the transcript names, some ancestor of it counting itself deriving that same directory name, with the climb stopped at the nearest enclosing repository root so an independent checkout nested inside the project keeps its own store rather than capturing the enclosing one's, because a transcript is evidence about this session's project only where the working directory is actually in it; without that second gate a session stepping into an unrelated checkout would capture that checkout's store. The scan reads the harness's own `~/.claude/projects` rather than the store root, since transcripts are written by the harness and a store redirect does not move them, and it answers only where exactly one project directory holds a transcript of that id, an ambiguous answer falling through to the working directory rather than picking a winner by directory order. The leg stays behind the worktree leg because the harness files a worktree session's transcript under the worktree's own project directory while this store deliberately maps a worktree's memories to the main checkout's, so consulting the session first would answer with exactly the directory the worktree leg exists to move off. The session leg folds a filing that resolves to a worktree root through that same handshake, so a worktree's subdirectories resolve the main checkout's store exactly as the worktree root does, in a session the harness filed under that worktree; a session filed under the main checkout whose working directory sits inside a nested linked worktree matches nothing, stops at that worktree's own boundary, and takes the plain working-directory derivation. The pin is the leg that wins outright: under the engine's gated store `KIT_MEMORY_PROJECT` replaces the derived segment with a fixed one, so one instance keeps one tier across workers whose working directories differ. Everything hanging off that directory follows, index and journal and sidecar and pending tier alike, which is the point; `docs/security-model.md` carries what the pin changes about who reads whose memories and why pinned content is fenced. It reads the file-per-fact memories of the project tier, a project-type tier shared by every project declaring that type, an operator tier at `~/.claude/memory-operator/` that every project on the machine reads and writes, each tier's `archive/` of retired memories, an outcomes journal (`outcomes.jsonl`) that exists per project only, and, inside a run the external engine spawned, that run's own `pending/<run-id>/` directory. The pending tier is present only under the three run signals and is scoped to the one run that owns it; `docs/security-model.md` carries what it is for and what its scoping does and does not guarantee. A used-tracking sidecar (`usage.jsonl`) sits beside each tier's memories carrying read and applied stamps; it is evidence about the records rather than a surface of its own. Retirement moves a memory into its tier's `archive/` rather than deleting it.

A fifth answer sits beside those resolutions, and it is a refusal rather than a store. An unpinned working directory whose spelling opens with two separators (`\\host\share` or `//server/share`) stands memq down at each of the twelve verbs that resolve the project memory directory from it: `log`, `find`, `get`, `recall`, `recent`, `unstamped`, `touch`, `anchor`, `triggers`, `decay-scan`, `decay-prune` and `decay-done`. The walk those verbs would otherwise take reaches `fs.statSync(<cwd>/.git)`, which under an unreachable host blocks for the SMB timeout rather than failing fast, so the refusal is what buys the verb the chance to say anything at all. The gate stands at each verb's own door rather than inside `projectSegment`, because the remaining four (`add-type`, `add-operator`, `delete-type`, `delete-operator`) reach the shared tiers alone and legitimately run from any working directory, and a gate in the shared resolver would refuse them for a reason that is not about them. Three properties of the gate are what a caller has to know. Every site reads `pinnedProjectSegment() === null && namesNetworkShare(cwd)`, so an honored pin answers ahead of the refusal and a pinned session never meets it. Three of the twelve carry a conditional site rather than the bare form, and each conditional now carries two clauses: `get`, `touch` and `triggers` each exclude the operator tier, spelled `!fromOperator` at `get` and `!toOperator` at the other two so that each names its own flag, and each also excludes a named type, spelled `namedType === null`. Both exclusions rest on the same ground, that the branch they name resolves without a working directory at all: the operator tier resolves through the store root, and so does a type tier named outright with `--type=<type>`, where the bare `--type` spelling resolves the working project's own declaration and does meet the walk. A whole-tree pin asserts that the twelve doors are exactly these and that only those two clause shapes appear, so a thirteenth gate or a third clause fails the suite rather than passing unnoticed. And `find` refuses whole rather than in part: its semantic channel resolves the project segment from the working directory itself, so standing the lexical block down alone would relocate the hang instead of avoiding it, and the refusal names both withheld channels so an unsearched one cannot read as an empty one. Every refusal is a sentence on stderr, and the status behind it splits: `log`, `touch`, `anchor`, `triggers`, `decay-prune` and `decay-done` exit 1, while the six reading verbs exit 0 with empty stdout, so a caller gating on status alone cannot tell a stood-down `recall` from a clean read of an empty store. What the predicate reads is the spelling and nothing else, so a drive letter mapped to an unreachable share is not a share to it and rides the same walk, and pays the session leg's boundary screen on top wherever that leg is armed, which resolves one link per ancestor step, each a network round trip that can block on such a drive; that residual belongs to the predicate rather than to any of the twelve doors, and a store pin is what avoids the walk where a mapped drive is the shape at hand.

Two frontmatter shapes sit in that store at once, and one field reader is what keeps them one store. On Claude Code a Write into a project's memory directory is rewritten in the same second into the harness's own shape: every key the author wrote at the top level is relocated into a column-0 `metadata:` map, keys of the harness's own join them there, and what stays at the top level is either an empty `name:` or the record's name with a `description:` beside it. Which of those variants a record gets, and which added keys ride along, varies by harness version and by which of the harness's memory features wrote it, so `frontmatterValue` promotes on the map's shape alone and tests no marker key, which is what makes the rule hold across the variants rather than across the one a probe happened to produce. It reads each of `tags:`, `created:`, `pinned:`, `machine:`, `supersedes:`, `anchors:` and `triggers:` at the top level first and inside that map second, the top-level value winning where both placements carry the field, since a top-level line on an already-rewritten file can only have been written after the rewrite and is the newer intent. A promoted value gives up one matching surrounding pair of quotes, the harness's serializer quoting the scalars that bare YAML would read as ambiguous, while a top-level value is taken verbatim because nothing rewrote it. Under any other key nothing relocates a field, so one found there is reported as misplaced rather than read, which is the answer `pinState` cannot afford to lose. Everything memq writes itself goes through Node's fs and is never rewritten, so both shared tiers and a decay pass's archive rename keep the top-level shape, and a fleet store pinned outside the harness's own directory keeps it entirely. The 40-line bound on the block is spent by both writers: the opening fence takes the first line, the harness spends four to seven of the remaining 39 with seven the common case, so a hand-written block budgets for 32 lines, and an overrun is total rather than partial, a closing fence past the bound leaving no field inside the block readable at all.

What the readers say about that overrun is a distinct answer rather than silence, and that is the store's rule for every could-not-read: no reader answers a defeated check with the value it gives a clean one. `frontmatterSite` and `frontmatterValue` carry an unclosed sentinel beside the unreadable and misplaced ones, so `pinState` answers `unclosed` and the prune exempts such a record exactly as it exempts an unreadable one, and the anchors reader answers not-checked. Two readers keep answering absent, and the ruling is stated rather than inherited: `readFrontmatterTags` and the `supersedes:` read cost a search match rather than a memory when they miss, which is the trade their own comments already make. The write door refuses the shape outright, per the frontmatter guard below. The record reaches those readers through two kinds of door, and the difference is worth knowing. `readFrontmatterAnchors` and `listMemories` take a capped head of 65536 bytes; `frontmatterField` reads the whole file, and `readFrontmatterTags`, `readFrontmatterCreated`, `pinState`, the `machine:` read, the `--supersedes` write-time screen, and the repair reader all go through it. A block that closes before the head's last line is the block every one of them sees, capped and uncapped alike, so an ordinary record is one record to the whole store. The two shapes the doors can disagree about are a block that does not close inside the head and a block whose closing fence is the head's own last line, which only a cut record can produce, and the write door declines to judge either rather than siding with one reader against the other. That is why the guard measures its own bound in bytes at the same 65536: a character bound would admit a record the store reads differently.

Inside a run the pending tier changes writes as well as reads. Every new memory file the run produces lands in `pending/<run-id>/` rather than the project tier, carrying provenance frontmatter memq stamps on anything it writes: `run:` from `KIT_RUN_ID`, `vector:` and `section:` from `KIT_SPAWN_VECTOR` and `KIT_RUN_SECTION` when those are present, and a `written:` date. Because a session's memory files are written by its Write tool rather than by memq, `memory-session.js` emits the same instruction into the session at start: the pending directory named verbatim on its own line, the frontmatter fields the file must carry, and the standing rule that `MEMORY.md` is not the run's to touch, since a pending memory carries no index line and the index entry is written at promotion by the engine. A session carrying the store signals with a run id the kit cannot honor is stood down from writing memory at all rather than left to write into the shared record. `memq log` keeps appending to the project-tier journal and gains a `run` field rather than rerouting, and `get` resolves the pending tier ahead of the project tier, following the file's own closest-tier-shadows rule. With `KIT_RUN_ID` unset there is no pending tier and every command behaves as it does outside a run.

`memory-session.js` is the store's session-start voice, and it runs eight blocks: the overdue-decay nudge, the type-tier index for a project declaring a `Project-Type`, the sync trigger, the embedder-absence nudge, the run-scoped pending destination, the pinned destination, the project-tier block that names what the project's memory index already holds and where a new memory file goes, and the anchor-drift line described under Anchors below. It is wired on `startup|resume|compact`, so a session resumed from a compaction runs the drift check rather than reading as a clean store.

One condition replaces every cwd-derived block with a single stand-down: no store pin is in effect and the working directory names a network share (the `\\host\share` and `//server/share` forms). Each of those blocks resolves the project memory directory from that working directory, whose first filesystem touch is a synchronous `statSync` on `<cwd>/.git`, and a synchronous call under an unreachable share hangs for the SMB timeout rather than failing fast. This hook carries no timeout entry in `hooks.json` and a hook that runs long loses its whole stdout, so the cost of the hang is every block, not one line. The sync trigger and the embedder nudge still run there, because neither touches the working directory. The predicate itself lives in `hooks/kit-network-lib.js`, a module holding `namesNetworkShare` and nothing else, and it reaches six consumers by two routes: `chapter-boundary-nudge.js` and `compact-deferral-nudge.js` require the module directly, while `memory-session.js`, `memory-frontmatter-guard.js` and `memory-recognition-nudge.js` reach it through memq's re-export because they already hold memq, and memq itself both requires the module and calls the predicate at twelve verb entry points. Counted at the module that is three importers, counted at the predicate it is six consumers, and the two counts are worth keeping apart: a reader taking the two hooks' direct requires for the whole would conclude the guard is ungated. The sync trigger both acts and speaks: on Windows, for the kit's own owned default store, it spawns the detached background runner that commits and syncs, and it emits a line only in the three states worth nagging about, a recorded standing-down gate, a week-old failure streak, or a broken sync chain (a spawn that recorded no outcome past a stale window), staying silent while a healthy sync does its work. The two blocks that speak to the machine's own state, sync and embedder, carry no store-derived text at all: integers the hook parsed and words that are literals in its source (a state-file reason code is a lookup key with a fixed fallback, never emitted text), which is stricter than sanitizing and is why neither needs a fence. Both stay silent under a stand-down and in a run-scoped session, whose own block already claims what the hook says about where the store stands. The decay nudge and the type index are independent of the rest; the three destination blocks are mutually exclusive, since a session must be handed one destination and never two, so a run suppresses the pin block and silences the project block, and a pin reduces the project block to its index lines alone, to a short notice when the index exists and cannot be read, or to nothing at all when the index is absent or empty. What the project block does not depend on is any harness setting: the kit states its own index and its own write destination rather than assuming Claude Code's auto-memory has supplied either, so the store behaves the same whatever that setting is. The cost is that a session with auto-memory on sees the same index twice, once verbatim from the harness and once reduced and capped by the hook; the alternative was mirroring a private harness resolver that changes without notice, which the kit deliberately does not do. A stand-down state replaces every one of them when the environment names a store the kit cannot resolve.

An ordinary session, with no run and no pin, gets the whole project block, and its two halves fail differently. The index half states one of three facts: the index lines themselves, reduced to bounded printable ASCII and capped at 60 lines against the type tier's 30 with the remainder counted; that the project has no index yet; or that the index could not be read and the tier is therefore to be treated as populated rather than empty, since "nothing is recorded" would invite a session to write a second copy of a fact already there. The destination half names the memory directory verbatim or not at all. A path that cannot be carried faithfully, longer than 260 characters or holding anything outside printable ASCII with the double quote barred, withholds the directory and the write convention with it, keeps the index lines, and points the session at `memq`, whose commands resolve the directory themselves. That is the one destination block that does not stand a session down over an unemittable path, because an ordinary session has asked for nothing the kit cannot do. Both index emissions run through one shared helper, so the read cap, the per-line reduction, the counted remainder, and the indent cannot drift between the two tiers.

Two properties shape the code more than anything else. The store is a **data-to-model boundary**: a SessionStart hook emits store content into a session's context before the user types, so a value entering a store file is bounded at the write rather than at display, in length always and in charset for the prose fields (summaries, descriptions), while a memory body is length-capped only; and the store root is settable only behind two signals rather than one, because that variable selects which data reaches the model. And its writers are **lock-free appenders around locked rewrite paths**: of memq's own writers, `log`, `touch`, `get`, and the read-stamp hook append without a lock, while `anchor`, which rewrites one project-tier record's `anchors:` line under that directory's decay and store locks in that order, `triggers`, which rewrites the same records' `triggers:` line under the same two locks in the same order, `decay-prune`, the shared-tier authoring commands (`add-type` and `add-operator`, their `--update` repair included, which rewrites the index description on every call and the record body as well when a body flag and `--confirm-shared` ride with it, the description positional being required on every form of the verb), and the shared-tier delete verbs (`delete-type` and `delete-operator`) rewrite under a per-tier lock, each leaving a backup beside every file it rewrites. A first-creation write and a memory-file move leave no backup, having no prior bytes to keep, and a delete is the one locked path that ends with less than it started: it removes the record's own copies first, that record's backup included, then both index lines, then the usage stamps, leaving a backup of each file it rewrites, and unlinks the record files last; then, once every removal step has landed, which includes the confirmed run that found no record and so removed nothing, it removes the backup beside each of those three files, whoever wrote it, so no copy of the deleted body the verb can name survives in the tier. That closing sweep is what makes the claim exact rather than approximate: an index line for a record authored without a body flag carries the whole stored body, so an index backup left beside the tier would keep the deleted memory readable in a file no reader lists and no hand may edit, the tier barring hand edits by design, and which nothing clears until some later rewrite of that same document happens to replace it. The exposure is local: `*.bak` sits in the sync's never-sync patterns, so the copy stays on the machine that made it. It runs only after the removals, because until then those backups are the single local recovery for a rewrite that stopped, and the bound is the path rather than the writer: those three are the documents this verb exists to edit, and a delete that stopped after its index rewrite leaves a backup there and no index line behind it, so a re-run bounded by what it had written itself would sweep nothing and leave the removed record's text in a file no reader lists and no hand may edit, cleared only if some later rewrite of that document happens to replace it. A backup it cannot remove is named on stderr and does not fail the delete, the deletion itself being complete by then and an error code only sending an operator to re-run a command with nothing left to do. What the sweep does not reach is a `<file>.tmp.<pid>` a hard-killed rewrite stranded at one of those three paths, `MEMORY.md.tmp.<pid>` at either index, holding that index as it then stood with the record's line in it, and `usage.jsonl.tmp.<pid>` at the sidecar, holding the stamps recorded against the record's name: the sweep names the `.bak` at each path and not the temp beside it. The copies it removes are found by listing each directory the tier writes under, its archive included, rather than by name alone, because an interrupted rewrite can leave a `.tmp` beside the `.bak` this module can name and both hold the record's text; the listing leads and nothing is unlinked before it returns, so an unreadable directory stops the verb before spending the record's only local copy on the way to the same stop. The verb runs two sweeps, the tier's own directory and its archive, and both directories are checked before either sweep unlinks anything, so a path that is not a directory at all stops the verb with every copy still whole. That check reaches the directories and not the backup paths inside them, so the other permanent case, a directory standing at `<name>.md.bak`, is not caught before the live sweep runs. What stays per sweep is the transient one: a directory that lists for the first sweep and fails for the second leaves the first sweep's unlinks done, which is a state the same command completes rather than one it cannot describe, and the report names the sweep it stopped in. The order is what makes the verb re-runnable: every state a stop can leave is one the same command completes. Whether a rewrite carries a tail copy of bytes that appeared past its read is decided at the call site rather than by a default, and on the index path saying so is mandatory: each helper there throws when its caller states nothing, so no index rewrite added later can inherit the wrong behavior by omission. The rewrite helper takes that answer directly. Every function above it on that path takes the tier instead and derives the answer from it, which is the same requirement asked in the words those callers actually know, since a caller holding an index path or a tier directory knows which tier it is holding and need not restate a consequence of it. The requirement is stated as a rule rather than as a tally of the functions carrying it, because the tally is what drifts. The journal and the usage sidecars are the other case, and the difference is worth stating rather than generalizing over: their helpers state the answer as a constant, because there it is a property of the file rather than of the caller, those files having lawful lock-free appenders in every tier and keeping the copy wherever they are rewritten. The refusal therefore guards the path where the answer varies, and a new sidecar-shaped writer modelled on one of those helpers inherits a constant that was chosen for the file it was written for, with nothing checking that it is right for a new one. The two index files are decided per tier rather than per name, because the same two filenames mean different things on either side: in the shared tiers nothing lawful appends to them, so a rewrite there takes itself as written, while the project tier's own `MEMORY.md` does have lock-free writers (the Write tool, and a reinstatement that restores an index line by hand) and so keeps the copy. The decay pass is the one writer reaching both tiers through a single code path, which is why the choice travels as an argument rather than living in the function. The replacement check is independent of that choice and runs on every rewrite rather than only the tail-carrying ones, because the whole store syncs and a pull replaces a file rather than appending to it, holding no lock this module takes: every rewrite reads the file back and proceeds only where the bytes the pass read are still its head, failing with nothing written when they are not, since the alternative is to republish a stale copy of every line the pass did not touch and drop whatever the pull added. What the call-site choice decides is the narrower question of whether bytes found past that head are spliced onto the new content or dropped. A caller that is removing a record also states what the carried tail may not bring back, so a usage stamp for the deleted name cannot ride back in past the rewrite that dropped it. That split is why the readers tolerate a torn line rather than failing on one.

A tolerated torn line is still a loss, and one contract carries that through every reader of a sidecar. `readUsage` returns a skip count beside its three-value status (`memq.js:1406-1425`), because a sidecar that reads whole while dropping one malformed line reports `ok` and is a partial loss the status alone cannot express. Every consumer whose claim rests on having read the evidence whole keys on both halves rather than on the status: `recall`'s per-tier unread flags, `recent`'s floor, `unstamped`'s two loss flags, and `decay-scan`'s evidence column and candidate suppression, so a torn applied append cannot nominate a memory for archive on a tally the scan itself half knows is false.

That leaves a persisted torn line, which every read path and every ordinary rewrite preserves, flooring its tier's coverage on every later run. `decay-prune --rollup --drop-malformed` is its one sanctioned exit, and preserving stays the default: the flag is explicit, it reaches the project tier and either shared tier the same invocation reaches, and it refuses outright any tier where no parsed stamp would survive the drop (`memq.js:7358`), keeping every line and leaving that sidecar byte-unchanged. The refusal stands down per tier, so a refusal on one does not stop a legitimate partial drop on another. `docs/security-model.md` carries it as the third irreversible operation riding that verb.

A shared-tier body reaches the store by one of two channels, and the second exists because a command line is not a reliable carrier for one. `--body` takes the text as an argument; `--body-file` takes a path and reads the body as UTF-8 from that file. Any body composed with newlines should take the file channel, because `cmd.exe` cuts a command line at its first newline and `memq.cmd` forwards its arguments through that parser, so a multi-line `--body` reaching memq through that one wrapper is cut there. The sh and `memq.ps1` wrappers pass a multi-line argument byte-exact, so the trap belongs to `memq.cmd` alone, and `docs/security-model.md` carries what the file channel removes of it and what it does not. Both channels answer the same gates, a refusal of a blank body and a 65536-character cap measured over the whole record rather than the body alone, since `get` reads and caps the whole file. The two flags on one call are a refusal rather than a merge, and `--body-file` is refused outright under the engine store signals, where a granted worker invokes the script directly, meets no wrapper, and so loses nothing to the refusal.

Truncation is only half detectable, which is what shapes the CLI's account of it. With the body flag last, the cut leaves a correct positional count and a silently shortened body at exit 0, which nothing can catch, so every successful `add-type` and `add-operator` reports the stored body's length on its success line instead. Where the cut takes a positional with it the count fails, and a hint fires on the residue truncation leaves: a free-text `--body` or `--detail` value last on the line with the positional count short. It is worded as a hypothesis rather than a verdict, because a forgotten argument leaves exactly that argv and no reading of argv separates the two, and it names the remedy the caller can actually reach, which is `--body-file` ordinarily, `--body` under the store signals, and one line for `log --detail`, the one free-text flag with no file channel behind it.

Retention runs on evidence rather than a fixed clock. A memory's idle clock is the freshest of its mtime, an author-asserted `created:` date, and its newest `applied` stamp, and each distinct calendar day of recorded application extends both decay thresholds by 30 idle days up to a 365-day cap, so a heavily used memory survives a long idle stretch in proportion to its record of use while nothing becomes permanent by accumulation. A `pinned:` frontmatter field is the judgment override for the rare must-never-age case; it is set by hand, counted in full on any scan that finds one so the exempt population cannot grow unobserved, and honored by the prune as well as the scan. Crossing a threshold nominates rather than retires, and the archive stays scoreable and fetchable, so the worst outcome is demotion rather than amnesia. A `supersedes: <name>` field on a newer record is the fourth retention state and the only one driven by evidence the store did not compute: it points back at the live same-tier record it replaces, and from the moment it lands that record is labeled by every surface that serves a record by name, demoted in `find`'s semantic ranking, and nominated at the next scan whatever its idle clock, while staying live and fetchable. The label does not reach the `MEMORY.md` index the SessionStart hook emits, index-line changes being out of the remedy's scope. The pointer is authored data rather than a measurement, which is why it nominates and never retires, why a pin outranks it, and why a mutual pair and a record naming itself are dropped rather than read as claims. A cycle labels nothing whatever its length, a self-pointer, a mutual pair and a longer loop alike, while a pointer reaching into a cycle from outside still labels the member it names. The map is an inverse scan of the tier's live records built once per invocation, so on the surfaces that already list a tier the cost sits in the same class as the pin walk beside it; `get` is the exception and it is deliberate, since answering for one name means opening the tier that held it, so it costs a tier walk rather than the single file read the lookup itself would need. Only a live successor labels anything.

Authoring the pointer splits by tier, and the two halves get different amounts of checking. The project tier writes it by hand, as it writes `tags:` and `pinned:`, so the frontmatter reader is the only thing standing between what a file says and what a line claims. The two shared tiers add a creation-only `--supersedes <name>` flag to `add-type` and `add-operator`, written as a top-level frontmatter line beside `tags:`, reported on the success line, carried across a later `--update` body repair verbatim, and refused alongside `--update` exactly as `--tag` and `--machine` are, so a record needing a different pointer is a delete and a fresh write. Six shapes refuse the command with nothing written: a name outside the record-name grammar, a name whose path is not a plain file or cannot be examined, a name whose own frontmatter cannot be read, a name no record of the tier holds, a name only the tier's archive holds, and a name whose own record already points back at the one being written, which is the pair every reader would drop whole. That gate is a typo guard and claims nothing more: its reads are lock-free, so a concurrent delete can still leave the dangling pointer the read surfaces treat as inert, and it closes the pair rather than the ring, a longer loop staying mintable through a delete and a recreate at no cost, since the readers drop every member of a cycle anyway. The flag is refused outright under the engine store signals and withheld by the grant hook, the two locks `--body-file` already carries, so an unattended worker writes the record without the pointer and the pointer waits for an attended session; `docs/security-model.md` carries why a demotion this light is withheld at all.

The write path consults the store's own search before it adds to it, so an overlap is a line the author reads rather than a discovery a later reader makes. On the creation path only, `add-type` and `add-operator` run the semantic channel `find` already owns, after every validation and before the tier lock, and print a neighbours block on stderr; an `--update` prints none, since a repair's neighbours were shown when the record was written and its own prior version would rank first against itself. The query is composed by `memory-index.js`'s exported `embedText`, the composition every indexed record is embedded through, so the name's rewrite into words is the same on both sides; the second component differs by design, the index embedding a record's body where this caller holds the description that becomes its index line. The block is a partial-sweep line and a persist-failure line where each holds, then `memq: nearest neighbours of <name>`, the shared provenance fence wherever a hit line follows, up to three hit lines ordered by raw similarity rather than by the blended rank, and a closing line wherever a hit carried the overlap label. Each hit line is the cross-store channel's own composer: name, similarity at two decimals, the provenance label with `retired` and `superseded` inside its parentheses, a `machine:` scope for a record scoped to a foreign box, and `likely overlap` at or above `NEIGHBOUR_FLOOR`, which is seeded at 0.30 against a paraphrase control that scores near 0.26. Retired records matching at or above that same floor are counted on one line and never listed, the line naming the `find --archived` rerun that shows them. Live records of every tier and every store on the machine are in scope and archived ones are withheld, since a retired record is not a fact the store still answers with and so is no reason to reconsider a write.

The block warns and never gates, and every line it can print says so. Each not-checked line and the closing line end `this check does not block the write` rather than promising the write proceeds, because the `--supersedes` target's re-assertion and the tier lock still sit between the block and the record. Where the reading cannot be had, one line names the cause instead, and the causes are the channel's own where the channel has one: an embedding stack that is absent or unusable, reported with the remedy the channel would print in a find; a search that failed or was abandoned; a search that has not answered within `NEIGHBOUR_TIMEOUT_MS`, 20 seconds, which also aborts the work behind it; a stand-down on the bare presence of `KIT_MEMORY_ROOT` or `KIT_EMBEDDER_ROOT`, each naming the variable that fired and read before the embedder loads; and a throw anywhere in the block, caught so that a broken convenience never costs the write. That stand-down is deliberately wider than the honored pair a store redirect needs, because it runs in the child while the `memq-grant` hook decides the grant, so keying it on presence is what keeps it no narrower than the grant condition. The model-judged channel is never opened here, so nothing an author types leaves the machine, and the whole block is stderr, so the success line a caller parses on stdout is unchanged.

The decay pass reads the same similarity over pairs rather than over one incoming record. After its anchor-drift block and before its candidate list, `decay-scan` prints a neighbour-pairs block on stderr for each tier it reaches, the project tier, a declared type tier and the operator tier, and never the run-scoped pending tier, which the semantic index excludes and whose records await an adjudication verdict rather than a supersession. A tier's heading leads with the pair count and, where the check could not read every record, that count against the tier's own total (`memq: neighbour pairs (project): 1 pair, 1 of 3 records not checked`); a tier read whole with nothing above the floor says `memq: no neighbour pairs (project)`, because silence and a clean answer are the one reading this block exists to keep apart. Each line is `memq: pair  <name>  <name>  <score>`, with a `pinned:` mark naming any pinned member and a `machine:` scope where one side carries it, capped at `PAIRS_SHOWN`, ten, with a counted remainder. Two shapes are withheld: a pair already joined by a `supersedes:` pointer in either direction, whose answer the store already holds, and a pair whose members carry differing `machine:` scopes, one record per box being duplication by design and every remedy the block routes to destroying one box's record. A pair never crosses a tier, a pointer resolving inside one tier's directory, so a cross-tier overlap is reported nowhere. The block nominates and never moves: no `decay-prune` flag acts on a pair, and the remedies are the author's, a fresh record carrying `--supersedes`, a body repair, or a delete. Its degrades are the authoring block's, said one heading per tier: the stand-down, an absent or unusable stack, and the expiry each replace every tier's reading, while a tier directory that cannot be listed and a throw inside one tier's own printing name that tier alone, and a throw in the work the tiers share prints `memq: neighbour pairs not checked (the check failed: ...)` with no tier on it. The derived semantic index it brings up to date the way a `find` does is the one file the scan writes, and the block reaches neither the scan's stdout nor its exit code, which are what a pass parses.

Both blocks bound their wait through one shared race, and `memory-index.js` honours the cancellation it sends. `query`, `sweep` and `embedAll` take an `options.signal` and read it at the resumption after the embedder load, at each embed batch boundary, between the items of the per-item retry a refused batch falls into, and once more where the embedding ends, answering the typed `cancelled` status the callers read as an unavailable channel. What a cancelled pass leaves on disk depends on where the abort landed: an abort read before anything was embedded writes nothing, while one read at or after an embed boundary persists what that pass did embed and names every record it never reached in `failed` with the cancellation as the reason, so the next sweep sees those as new and finishes the job rather than a slow store never building an index at all. One await is outside all of it, and the limit is stated rather than implied: the embedder load itself cannot be interrupted, so a stack that never resolves it holds the process open for as long as it takes, whatever the bound above did. The bound is on the wait and on the work that resumes after the load.

### Anchors

An anchor is a project memory's own record of which files it is about, at the bytes those files held when it was written. The field is `anchors: <path>@<sha>, <path>@<sha>` on one line at the top level of the frontmatter block, the same line discipline `tags:` takes, and the reader takes it under the harness's `metadata:` map as well. The `<sha>` is the git blob name, sha1 over `blob <length>` plus a NUL byte plus the file's own bytes, which `git hash-object --no-filters <path>` reproduces. The flag is load-bearing rather than decorative: this checkout runs `core.autocrlf=true` with no `.gitattributes`, so a bare `git hash-object` applies the clean filter and returns the LF-normalized hash, which for any CRLF file is not the hash an anchor records. Computing it from a file's own bytes is what makes an anchor verifiable by hand, valid on uncommitted content, and free of any git process at check time.

The tier is the project tier and only it, in this version. An anchor needs a project root to resolve against and a tree to hash, and the type and operator tiers have neither, so a shared-tier record declaring one is never checked and every read surface says so rather than answering clean.

The grammar is narrow on purpose, because a path lands on a report line a reader has to be able to check. A path is forward-slashed, relative to the project's main root, at most 256 characters, and refused for a leading slash, a `..` or dots-only or trailing-dot segment, a backslash, colon, `@`, comma, double quote, or any of `* ? < > |`, a win32 reserved device stem on every platform rather than only on Windows, a leading YAML indicator character, and every whitespace and invisible character. Visible non-ASCII is admitted, so a repository with non-English filenames keeps the feature. One line reads at most 32 entries and says so when it cut the rest. Three limits ride with that and are stated rather than softened: the hash is SHA-1, so an anchor gives change detection and not tamper evidence; nothing normalizes Unicode, so a name written where the filesystem stores NFD reads `missing` on a filesystem that stores NFC; and the whitespace bar costs real files, `docs/my notes.md` among them, because a stray space at either end of a quoted path is invisible on the refusal line that would report it.

`memq anchor <name> <path>...` is the writer, and it touches one line. A 40-hex value is the one field of a record a hand cannot check its own typing on, so the verb computes the hashes and writes nothing else: it merges per path into whatever line the record already carries (a fresh hash replaces the old one, the existing order is kept, a new path is appended), creates a block at the top when the record has none, and otherwise rewrites that one line, leaving the body byte for byte as it was. The write is temp-and-rename under both of the project directory's locks, decay first and then store, which is the order the file already establishes, so a concurrent decay pass cannot archive the record out from under the rewrite. Every path is judged and hashed before the lock is taken, so one refusal writes nothing at all. It refuses the two shared-tier flags with the v1 reason, refuses when no project root resolves, and refuses outright rather than answering not-checked when the working directory names a network share, because it authors a record rather than reporting on one. The success line names which entries this run hashed and which it carried across, since a line printed whole reads as though every entry on it was verified just now. Removing an entry is a hand edit in this version. The rewrite moves the record's mtime, which the idle clock counts as a sign of life, and that is correct: anchoring is a verification act.

Four read surfaces report drift, and drift nominates rather than retires. A changed file does not make a memory wrong, it makes it unverified, so the remedies are re-reading and re-anchoring, a successor carrying `supersedes:`, or a hand correction, and no drift line ever deletes anything. `memq decay-scan` prints a `DRIFT` block after its existing blocks, headed with the tier it covers because the block reads that tier alone, listing each record with its `changed:` and `missing:` paths, pinned records included, since a pin exempts a record from retirement and not from being unverified. `memq get <name>` prints one line per anchor after the body, each `fresh`, `changed (recorded <sha7>, now <sha7>)`, `missing`, or `unreadable`. `memq recall` appends a `[drift]` token to a drifted record's digest line, in the slot the `superseded by` label occupies, and `[drift?]` to one the pass could not verify. `memory-session.js` emits the count at session start, built from up to three sentences carrying integers and this hook's own words and nothing from the store.

Every one of those surfaces separates three answers rather than two, and that separation is the feature's load-bearing property: a surface whose whole job is to say "unverified" must never report "verified" because a check could not run. So a record the scan reached and could not settle is listed beside the drifted ones with its own cause, a whole tier that is there and cannot be examined answers `not checked (this tier could not be examined)`, a store pin answers with the pin as the cause, a record on a shared tier answers with the tier as the cause, and a record the session hook's own read budget stopped short of gets a sentence naming that budget rather than pointing at a scan that carries none. The hook's pass is bounded at 200 records, 500 anchors, and 8 MB hashed, because it runs at every session start and a hook that runs long loses its whole stdout. `blobSha` refuses a file over 4 MB rather than hashing it, and an anchor whose path runs through a symbolic link or junction inside the project reads `unreadable` rather than `fresh`, which is what closes the win32 hazard where a planted link to a UNC target turns a resolution into an outbound authenticating connection.

The fleet grant withholds the verb. Anchoring rewrites a record in the shared priors at a name the command line gives it, which is an authoring act on state a worker's writes are otherwise quarantined from, and a worker could re-anchor a memory onto whatever the tree holds now so that every drift surface then reports it verified when nobody read it. The CLI has no second refusal for the verb, so the grant's allowlist is the whole of what withholds it.

### Recognition triggers

A recognition trigger is a memory's own declaration of what should bring it back, written as a pattern a session's own work can be matched against rather than as a file the record is about. The field is `triggers: <type>:<pattern>, <type>:<pattern>` on one line at the top level of the frontmatter block, the same line discipline `anchors:` takes, and the reader takes it under the harness's `metadata:` map as well. Six types decide how a pattern is read: `cmd:` against a Bash command, `err:` against a failed call's output, `glob:` against a path, and `skill:`, `agent:` and `tool:` against the identifier a call names at the tool boundaries, and on a whole token against a prompt's free text at `UserPromptSubmit`. It is a sibling of `anchors:` rather than an extension of it, because an anchor carries a sha whose whole purpose is to go stale while a pattern has no bytes to hash.

The grammar is narrow for the reason the anchor grammar is: a pattern lands on a report line and inside a YAML plain scalar, and both readers have to be able to take it whole. A pattern runs to at most 256 characters, one line reads at most 32 entries, and whitespace is admitted only as an interior plain space, so that `cmd:node --test` is spellable at all. A comma, either quote, an opening bracket, a backslash, and the three sequences a plain scalar cannot carry (`: `, ` #`, and a trailing colon) are refused. Two specificity bars sit on top of that grammar and reach different types, because a bar written over a typed vocabulary holds only of the members it is true of. The four-character floor is asked of all six. The bare-token bar, a 22-word set of common command names compared without regard to case, is asked of `cmd:`, `err:` and `glob:` alone, those being the types whose pattern is a fragment of something longer; `tool:Bash` is a whole identifier with no longer spelling, so the same bar there would make the trigger unauthorable rather than ask for a better one. A `glob:` pattern takes the anchor path grammar with `*` and `?` admitted, and refuses the single quote anywhere rather than in the lead alone.

`memq triggers <name> [<type>:<pattern>...]` is one of the field's two writers, in `memq anchor`'s idiom, reaching the project tier and a run's own pending tier with neither flag and the named shared tier under `--type` or `--operator`. `--type` has two spellings answering different questions: bare, it resolves the working project's own declared `Project-Type`, and `--type=<type>` names the tier outright, the way `add-type`'s positional does, which is what reaches a type-tier record from a project that declares no type, most of them being such projects. The value rides on the flag word rather than the next argument because the verb's positionals are `<name> <entry>...`, where a lookahead would read `triggers rec --type cmd:whatever` as a type named rec. The bare spelling resolves through the working directory and so takes the network-share stand-down; the named spelling resolves through the store root alone and is exempt from it, on the same ground `--operator` is, and `get` and `touch` take that same spelling and that same exemption so a record this verb can write is one they can read back and stamp. A `glob:` entry is refused under either flag, a path glob naming a root the shared tiers have none of. It merges per entry by default, so an entry the line already carries keeps its position and one it does not carry is appended, and entries are compared as text exactly, case included, because a command line carries its own casing where a filesystem folds it. `--replace` is the other direction and the only one there is: it states the line whole, writing exactly the entries the invocation names, and naming none removes the line rather than writing an empty one, so a declaration made wrongly can be narrowed, respelled or withdrawn without deleting the record and losing its body and its applied history. Reaching a shared tier or a pinned project store that way takes `--confirm-shared`, on the footing the whole-body repair and the delete verbs take it, because a replace destroys declarations on a store every project and every synced machine reads, and a pinned project store is shared by every working directory its instance runs in. Under the engine store signals it is refused outright at both, consent flag or not, because the single backup it leaves does not sync and so is no recovery from a fleet store at all; the merge still declares a trigger there. The named-type spelling takes that same refusal at `get` and `touch`, so its exemption from the network stand-down buys reach on an attended session and none on an unattended one. Every bar holds under it, and one of the two refusals that exist because a rewrite would drop unreadable text survives it: a line cut at the reader's bound still refuses, its tail being a thing no message could name first, while an entry the parser cannot read is dropped and named, that entry being exactly the wrong declaration a replace exists to correct. A run that adds nothing writes nothing: it prints the line, says every entry was already there, and leaves the record's bytes, its one backup generation and its mtime as it found them, re-declaring a trigger verifying nothing where re-hashing an anchor does. A run that does add an entry rewrites that one line under the project directory's decay and store locks in that order, leaves `<name>.md.bak` beside the record, and moves the mtime the idle clock reads as a sign of life. The other writer is the creation-time `--trigger` flag on `add-type` and `add-operator`, which writes the same line as the record is born. Four surfaces read the field afterwards: the frontmatter guard holds a hand-written line to the same grammar at the write door, `memq get` prints one line per entry after the body, `memq recall` reads it on every shared-tier record to count the ones declaring no trigger, and `decay-scan` reports nothing at all, a pattern having no bytes that could have changed. `find` carries no trigger label on either channel, while the semantic index still embeds each record file whole with its frontmatter, so a pattern is a few words of search surface as well as a recognition rule. The fleet grant withholds the verb for the reason it withholds `anchor`: the line it writes decides when a memory is put in front of a session. One property of the reading surface decides what a declaration is worth and so belongs beside the writer rather than beside the matcher. `collectHits` appends a hit for every matching trigger of every record into one flat list and `claimHits` spends a single allowance over that whole list, keyed on tier and name, in the index's own order: tier first, project then type then operator, and name second, with no rotation. The cap is therefore pooled across every handle a call matches rather than spent per handle, so a pattern many records carry surfaces the same ones on every call, a crowded handle is a starvation rather than a dilution, and the digest counts a record that can never appear as covered. The per-session dedup is the only relief, letting a third carrier take a slot once the winners have fired, which puts the remedy at the authoring end: a handle names the moment the mistake is committed rather than the record's topic, and crowding is a standing property of a name-ordered pick over a tier every project writes to rather than a state a backfill reaches and leaves.

The nudge log is what makes the recognition layer measurable rather than merely felt. Every nudge `memory-recognition-nudge.js` claims for a session appends one JSON line to `.kit/memory-recognition-nudges.jsonl` under the project's resolved main checkout root, carrying the record, the tier it was read from, the trigger that fired and the moment, written inside the same lock that claims the emission so a rotation cannot land between one call's size check and another's append. The log is machine-local and never synced, it rotates to `<path>.old` past 1 MB, and its absence reads as no nudge has fired yet rather than as a fault. It is also the one writer that creates a project's `.kit/` from a hook running on every tool call, so it writes a `.gitignore` holding `*` into the directory at creation, which keeps the log out of a host repository that never excluded `.kit/` itself. The hook exports the reading as `nudgeStampRate(cwd, sinceMs)`, which splits the project tier's nudgeable records, those carrying at least one trigger or anchor, into a nudged arm and an unnudged one and reports each arm's applied-stamp rate over the stated window. Every bound that would shorten one arm without saying so refuses instead, the tier listing's cap, the index's byte bounds and the log's own read bound among them, because a number that flatters the feature it gates is worse than no number. That reading is the evidence the semantic tier's gate consumes, and it cannot separate the nudge causing an application from the record having been relevant to the work in the first place, which `memory-system/SKILL.md` states beside it.

### The frontmatter guard

`hooks/memory-frontmatter-guard.js` is the write door the store previously had none of. The project tier is authored with `Write`, `Edit`, and `MultiEdit`, so its frontmatter passed through none of the refusals memq's own verbs apply, and a hand-written `supersedes:` naming a record that does not exist, a `tags:` list in the YAML form memq reads as no tags, an indented `pinned:` that pins nothing, a malformed date, and an `anchors:` entry outside the grammar all landed with nothing said. The guard is wired PreToolUse on those three tools and is the only surface that sees a record before it exists.

Scope is memq's own store resolution rather than a second one. The target's directory must be a tier directory memq places, and the filename must satisfy `isMemoryFilename`, so `MEMORY.md`, `decay-stamp`, the sidecars, and anything under `archive/` are out of scope and allow. On the two shared tiers every `Write`, `Edit`, and `MultiEdit` is denied whoever is writing, the main session included, because the rule the memory-system skill already states is "never the Write tool" rather than "not by subagents"; the refusal names four commands, one per thing a blocked write could have been doing, since a create, an index-description change, a body repair and a change to the record's recognition triggers take different flag sets and naming one sends the other three authors to a command that refuses or, worse, to one that exits 0 having never opened the record. The trigger route forks on the environment, naming the state rather than a command under the engine store signals, because the command it would otherwise name is one that vector answers with a refusal. On the project tier the guard computes the resulting content, allows without validation when it has no frontmatter block or when the block matches the one on disk, and otherwise validates through memq's exported readers.

Every judgment about a record is memq's, loaded from the plugin's own `scripts/memq.js`, so the guard and the store cannot come to disagree about what a record declares. Three rules are the guard's own because memq decides none of them: the `YYYY-MM-DD` calendar form a `pinned:` or `created:` value takes, the `- ` item that follows a `tags:` key with no inline value, and the position of the opening fence. Fourteen paths deny: two on the block (one that opens on line 1 and never closes inside the reader's line bound, and a fence that is the record's first non-blank line without being line 1), one on placement (any of the seven fields memq reads indented under a key other than `metadata:`), one on list-form `tags:`, two on dates (a `created:` memq cannot parse, and either date field outside the house form), two on `anchors:` (an entry the grammar rejects, and a path escaping the project root), one on `triggers:` (an entry outside the recognition grammar), and five on `supersedes:` (a name outside the record-name grammar, the record's own name, a target held only under a variant casing or extension case, a target held only under `archive/`, and a name the tier holds no record of). Everything else allows.

The guard answers three ways, and each answer travels on a channel its reader is actually on. A deny exits 2 with one line on stderr, which is what the harness delivers to the model as its reason for blocking. A record that was checked and is clean exits 0 in silence. A target the guard placed inside the store and then could not check exits 0 like the clean one and says so on stdout as PreToolUse `hookSpecificOutput.additionalContext`, which is the one exit-0 channel the model receives, naming the tier and the cause and stating that the write is going ahead unchecked. Nineteen distinct causes reach that third answer, from a payload shape the guard does not read as a write through to a throw out of any reader it called. It is written only for a target already inside the store, because a hook that spoke on every `.md` write on the machine would be noise rather than signal.

Anchor validation is the one part of the guard that touches the filesystem beyond the record, and it is gated twice. The project root is derived only for a record that actually names an anchor, so a record declaring none pays none of the walk, and a working directory naming a network share answers not-checked before the walk runs. That second gate matters more here than at any other consumer of the shared predicate: the others cost a lost stdout block or an interruptible foreground wait, while this one sits in front of every write and would stall the operator's own tool call until the harness's hook timeout ended it.

Two bounds decide what the guard is judging rather than whether its judgment is right, and both are set from the consumer rather than from the guard. It reads the operation from `tool_name` and the subject from `tool_input`, both the harness's own fields, so a payload whose shape and name disagree is checked as the operation it actually is. And it bounds the record at 65536 bytes, measured as bytes because every memq reader bounds the same record in bytes; where the cut may have manufactured a closing fence, or the block does not close inside the head, the guard declines to judge rather than siding with one of memq's two readers against the other. Both streams are fenced for the life of the process, so the deny line is the only text on stderr and the not-checked object the only text on stdout.

Its residuals are stated in the guard's own header and are worth naming here. Store-root containment is lexical, with the real path tried as a second candidate only for a target already lexically under the store root, so a spelling the filesystem accepts and a lexical compare does not (a mapped drive letter, a UNC spelling by a fully qualified or aliased host name) places nothing and is allowed in silence; resolving either would mean an outbound connection made before the user's permission prompt. The run-scoped pending tier is not a tier directory to memq's `tierDirFor`, so a record written there is out of scope. A shell redirection never meets the guard at all, its matcher naming the three file-writing tools. And its own read cap duplicates memq's `FRONTMATTER_READ_CAP`, which memq does not export, so the two are held equal by hand.

`memq recall` is the read half. It takes no search term and emits the whole store as one bounded digest, a summary line per record across every surface, ordered by last sign of life, inside a fixed line budget whose every truncation is announced with a counted remainder. Ranking is deliberately left to the model reading the digest with its current task in context, because that is the only semantic scorer available and it is free; lexical scoring was rejected because a substring miss is silent, which is the expensive failure shape. The digest leans on nothing outside itself to have put a record in front of the reader: descriptions ride the journal, the archive surface across all three tiers, and the project tier. The type, operator, and pending tiers are the live surfaces that stay lean, the type tier because the session hook emits its index as a block of its own, the operator tier because it is reached by search rather than by emission, the pending tier because it holds the run's own writing that the run just produced. The trigger is procedural rather than ambient: `executing-work` and `brainstorming` each run it where an effort's context is assembled, a seat takeover runs it at the takeover ritual's fourth step, and a boundary taking the hand walk runs it again, so no hook pays context and latency on every prompt. The store resolves from the cwd, and a git worktree resolves its main checkout's store (memq follows the worktree's `.git` pointer through a two-way handshake), so recall works from a worktree as well as the main checkout; a subdirectory of the session's own project resolves that project's store, and so does a subdirectory of a worktree the harness filed this session under, which folds to the main checkout the way the worktree root does, since the session leg answers wherever an ancestor of the working directory sanitizes to the segment the harness filed this session under, while a working directory outside that project, a bare-repo worktree, or a worktree whose `.git` handshake fails (memq notes that one on stderr, pointing at `git worktree repair`) still resolves a different, empty store, and the tell is a digest whose coverage lines all read zero on a project known to have memories.

`memq recent` is the second reader, and it answers what happened to the store rather than what the store holds. It digests one time window (`--since <n>d` or `<n>h`, default one day, any other spelling refused) and groups by write surface rather than by tier: journal entries logged, applied stamps written, and memory files added or updated. The grouping is what makes the digest answer whether the extension layer is being used at all, because provenance rides the surface: journal entries and stamps exist only through `memq`, while a project-tier memory file arrives through a session's own Write tool. Every group opens with a coverage line carrying its count even at zero, and evidence that exists but could not be read is said in that line, so a count is never quietly a floor. Read the file group's `added` label narrowly: it says the file's creation time falls inside the window, and the editing tools rewrite a memory file rather than patching it, which resets that time on every write. So the label separates how a file was written from how it was not, never a new record from an edited one, and `backlog.md` carries the choice of what to do about it.

Its span is every tier the store has, the project tier, a declared type tier, the operator tier, and a run's pending tier, each with its `archive/` directory, so a decay pass's demotion reads as the file change it is. Archive records key on the newer of mtime and ctime rather than the mtime alone, because archiving is a rename: the rename preserves the mtime a memory carried while it was live, which for an archive candidate is idle months by construction, and moves the ctime instead. The digest carries its own 200-line budget, matching `recall`'s and tunable apart from it, and the same rule that every truncation is announced with a counted remainder, and it cuts in the reverse of its print order, so the journal, which nothing else summarizes and no session-start block carries, is the last surface to lose lines. It is read-only and stamp-free: it reads sidecars, the journal, and file stats and never serves a body, so it appends no `read` stamp of its own, since a digest that stamped the reads it reports on would corrupt the decay evidence it exists to show.

The trigger is procedural, the same shape as `recall`'s: `finishing-work` step 7 runs it over the session's span at close-out, after the memory writes, the unstamped sweep, the after-query (the `memq find` pass over the vocabulary the effort learned), and any decay pass, so the close-out status reports counts instead of asserting that the effort banked something. The cwd caveat is the narrow one `recall` carries: a Commit-and-Push session sitting in a worktree resolves the main checkout's store (the worktree handshake), so `recent` reports the real activity there; a subdirectory of the session's own project resolves that project's store through the session leg, a subdirectory of a worktree the harness filed this session under folding to the main checkout the way the worktree root does, while a working directory outside it, a bare-repo worktree, or a worktree whose `.git` handshake fails resolves a different, empty store and reports zero for a session that banked plenty.

`memq unstamped` is the third reader, and it answers which memories were opened and never reported applying. It diffs the used-tracking sidecars' `read` stamps against their `applied` evidence inside one window (`--since <n>d` or `<n>h`, a positive whole number of days or hours, default one day, on the same grammar and the same refusals `recent` carries: one `--since` per run, the value a separate argument, any other spelling a usage line) and reports the gap: one line per record carrying the tier token, the name, the age of the last read, and the tier index's description. An `applied-rollup` counts as applied evidence and is dated by the last application it folded rather than by the fold, the reading `recent` gives the same record. The window is a set-membership question rather than an ordering one, so a record applied anywhere inside it stays cleared however much later it was read again; comparing the two timestamps would re-ask an adjudicated record on every subsequent read, and the list works only while every line on it is a real question.

Its span is the live records of the project tier, a declared type tier, and the operator tier, each stating its count even at zero. Four surfaces are deliberately outside the domain, each for a reason that would otherwise teach an invocation that errors or a question with no answer: journal keys, which have no applied concept at all; `MEMORY.md`, which the stamp hook never records; the run-scoped pending tier, whose records `touch` cannot stamp; and any archived record, which `touch` refuses. The command writes nothing, not a read stamp, not a usage entry, and not a lock, since acquiring one creates the directory it sits in. It carries no line budget, unlike the two digests: its output is bounded by the swept tiers' live records carrying a read stamp inside a short window and no applied stamp, whoever wrote those stamps, and truncating an adjudication list would hide exactly the record the judgment is owed on. Where a tier's sidecar could not be read whole, or its record listing was anything but read whole, absent as readily as unreadable, that tier's coverage line says the count is a floor rather than reporting a clean zero, because the two errors cost differently: a false candidate costs one recognition question, a missed applied ages a load-bearing memory toward the archive. Output closes on one of two lines, selected by whether any tier raised a hit, or on nothing at all in the one state that reaches no tier: an absent project memory directory with no operator tier behind it, where a stderr note is the whole answer. Where a tier did, it is the same tier-aware stamp reminder `find` uses, naming the exact `touch` invocations this run's own hits need, which is why every hit is a live record of a tier this working directory resolves rather than merely a record that was read. Where none did, it is a verdict at column zero stating the read evidence behind the zeros: how many records carry a read stamp inside the window, or that none do, with a loss on either reading named where it can still be hiding a record awaiting a stamp. The two are exclusive by construction, and each is what the other's case cannot say: a reminder over an empty list would teach a `touch` with no argument to give it, and zeros with no verdict under them are byte-identical whether the window held no tracked read at all or held reads a boundary had already adjudicated.

The trigger is procedural on both ends. `executing-work` step 6 runs it at every Chapter boundary before the Chapter is appended, and the Chapter records the outcome in its `Stamps: <adjudicated N, stamped M>` field, a window that owed a hand walk saying so there, why it was owed and what the walk found, in place of a bare count; `finishing-work` step 7 runs a final sweep at close-out, ordered sweep, then after-query, then decay pass, then recap. The boundary trigger is what makes the mechanism work: read stamps survive a compaction and a session handoff, while the judgment of which read mattered does not, so a close-out-only sweep asks a long run to recall across boundaries it has already crossed. The close-out sweep precedes the decay pass because applied stamps are the evidence the decay thresholds extend on, so a sweep running after it could stamp a memory the same close-out had just archived for idleness.

The decay seeds (30 idle days per applied day, a 365-day cap), both digest budgets (200 lines each, plus `recent`'s one-day default window) and the neighbour floor (0.30, the similarity at which the authoring verbs' block and the decay scan's pairs block read two records as one fact) are invented constants with no live observations behind them, to be tuned on real tallies rather than widened speculatively.

The routing ladder is journal, project, type, operator, doctrine. The operator tier is the destination for a fact true of the operator or of a machine rather than of one project or one platform, and without it such a fact strands in whichever project store happened to learn it. It is shared by every project's concurrent sessions, so authoring goes through `memq add-operator` under the tier's lock rather than the Write tool, which cannot take one; a `machine: <name>` field on a memory scopes it to one box, which search labels rather than hides. Retrieval is most-specific-wins, project over type over operator and live over archived. The tier is deliberately absent from session start: it is reached through `recall`, `find`, and `get`, which keeps every use visible to the read and applied stamps that the decay clock runs on, where an injected index emission is use no stamp can see.

The store also syncs, and on Windows it syncs itself: the session-start hook spawns a detached background runner (`doctor/sync-store.ps1`) that commits pending memories and, where an upstream exists, fetches, screens the incoming content, rebases, and pushes, so a memory learned on one machine reaches the others with no hand-run step and no nag while it is healthy. Every git call on that path, the background runner's and the doctor's installer's alike, goes through one funnel, `Invoke-MemorySyncGit` in `doctor/install-memory-sync.ps1`, which builds the same hardened environment the hooks get from `hooks/kit-git-lib.js`: every ambient `GIT_*` variable stripped, the credential prompt refused, the current directory kept out of executable resolution, and `core.fsmonitor` and `core.hooksPath` pinned inert through git's environment-config channel, so a hand run of the sync script inherits what the unattended run has. Neither language can call the other's, so the two are restated rather than shared and `test/git-guard-parity.test.js` runs both for real on Windows, reddening on any name one side sets, changes, or strips that the other does not. `~/.claude` is a git repository whose gitignore excludes everything and re-includes only the memory tiers and the machine coordinator directory, pushed to whatever remote is configured for it; nothing in the kit reads that remote's visibility, so a private one is a precondition of an installation rather than a property of the design, which `docs/security-model.md` states in full. That allowlist is the whole boundary between replicating memories and publishing credentials, and it is not self-enforcing: a `.gitignore` inside a traversed directory outranks the root file and can re-include what the root excluded. So the guarantee is the rules plus the leak probes both committers re-derive on every run (the doctor's `-Fix` and the background runner, which dot-sources the same code), over the ignore rules, the worktree, the index, and the local committed history, refusing any commit carrying a path the allowlist does not admit. The allowlist guards both directions: outbound, those probes refuse a commit; inbound, the runner screens every entry of the incoming tree by its mode and its path before the rebase touches the working tree, so a rename, a duplicate-content push, or a symlink at an allowlisted path cannot drop a disallowed file into `~/.claude`, where nothing un-writes it. The journals merge as line unions, which fits their append-only shape. Project stores are keyed by the flattened project path, so a synced project tier resolves on another machine only where the project sits at the identical path; the type and operator tiers are path-independent and resolve everywhere; the coordinator directory holds one directory per machine by the seats' own convention rather than by anything the sync enforces, its allowlist predicate scoping to no machine, matching `coordinator/` followed by anything whose leaf is a `.md` and none of whose path components is transient-shaped, and every machine reads all of them.

The runner's own record of what it did is `kit-sync-state.json` at the store root, and it is the only channel a detached background process has. `Write-SyncState` composes five fields (`lastAttempt`, `lastResult`, `reason`, `lastOk`, `firstFailSince`), writes them to a per-PID temp file as UTF-8 without a BOM, and puts that file in place two ways: `File.Move` where no state file exists yet, and `[System.IO.File]::Replace` where one does, because a replace is atomic on NTFS while `Move-Item -Force` is a delete-then-move a concurrent reader can catch mid-gap. That `Replace` call passes `[NullString]::Value` as its backup path rather than `$null`, and the distinction is load-bearing: PowerShell marshals `$null` into a `string`-typed parameter as the empty string, `File.Replace` rejects an empty backup path, and the surrounding catch would swallow the exception, so the `$null` spelling lets only the first write in the file's lifetime land. The write is silent in both directions by construction, since the catch deletes the temp file and returns without an error, an exit code, or a record; `docs/backlog.md` carries that residual and the two triggers still reachable for it. `memory-session.js` reads three of the five fields, `lastResult` and `firstFailSince` for the seven-day failure-streak nudge and `lastAttempt` for the broken-chain check against the spawn marker's mtime. `lastOk` is the runner's own success stamp and is read nowhere outside `sync-store.ps1` and the tests.

Whether a push has anywhere to land is the doctor's question, and `Get-MemorySyncDestinationLines` in `doctor.ps1` answers it as a pure formatter over the status hashtable `Get-MemorySyncStatus` fills. Every read behind it is of a local ref or a `--local` config value, so the answer costs no network round trip and is as of the last fetch, a limit the report states rather than hides. Four states block: a detached HEAD, a branch tracking nothing, a branch tracking a remote other than origin, and a `push.default` that will not carry this branch's pair of names. The last is the one every other check reads clean over, because the runner's push leg is a bare `git push --quiet` and what a bare push does with a local branch whose upstream carries a different name is `push.default`'s to decide. The name comparison is ordinal over the raw `branch.<name>.merge` value against `refs/heads/<local branch>`, which is git's own comparison byte for byte, so a case-only difference and a short form (`merge = main`) are both refusals rather than matches; the setting itself is matched case-sensitively, because git parses it that way and rejects a value it does not recognize.

The division of labor between the two committers is stated in the report rather than left to inference, because the doctor's `-Fix` commits the store and never pushes it. What carries a commit to the remote is the background runner at the next session start, or a manual push in the store, and off Windows, where no runner spawns, both acts are hand-run. A commit reported beside an `origin:` line and a `Destination:` line naming the branch this store tracks reads as published, so the FIXED branch of the memory-sync section prints the coupled fact outright, that the commit is local until one of those two carriers moves it, and prints the manual push recipe beneath it. That recipe sits in the FIXED branch alone, and the reason is the report it sits in: every other reachable branch is a WARN or a FAIL, the FAIL raised because a non-memory blob is reachable in committed history among them, and handing the operator a push command there would hand them the exact act the leak probes exist to stop. Only the FIXED branch has proven both that the store publishes nothing it should not and that it has a destination.

What a differing pair costs is a function of that value, so the finding is too. `simple` refuses the push fatally. `matching` updates only branches carrying the same name on both ends, so it publishes nothing and exits 0, which the runner records as a success: the quietest of the set. An unrecognized value makes git refuse every push as a malformed config value, and `nothing` errors out for want of a refspec whatever the names are. Those four are blocking, which reports the memory-sync check FAIL and exits the doctor 1. `current` publishes to a branch on origin named after the local branch, so the push succeeds and lands where no other machine pulls from, which is advisory: the check reports WARN and does not fail the run. `upstream` and `tracking` push to the upstream ref whatever the two names are, so a differing pair is not a finding at all. Each finding carries its own remedy, and two of those are gated. The rename is printed as a runnable `git branch -m` only where the merge ref sits under `refs/heads/`, both names match `^[A-Za-z0-9][A-Za-z0-9._/-]*$`, and both survive `Get-SanitizedLine` unaltered, and is reported in prose with no pasteable command otherwise. The report's trailing "put HEAD on the sync branch and give it an upstream" line is emitted only for the three findings it repairs, since running `push -u origin <branch>` against a branch whose upstream on origin is already correct creates a second branch there and repoints the upstream at it, which is the silent cross-machine divergence the advisory check in the same function exists to report.

`memq find` answers by meaning as well as by substring. `plugins/claude-kit/scripts/memory-index.js` owns an embedding stack that installs per machine outside the plugin payload, so the kit core stays dependency-free, and a derived JSONL index beside the store covering all three tiers, live and archived, across every project store on the machine, and deliberately not the run-scoped pending tier, whose unadjudicated writes are one run's to read. The index is sync-excluded by design: a vector is valid only against the embedder that produced it, so each machine builds its own, and the sweep runs at query time, whether a find's or an authoring verb's neighbours check, and at a `decay-scan`, keyed on content hash so a synced checkout that moves every timestamp re-embeds nothing. Where the stack is absent, find says so in one line naming the remedy and serves lexical results; nothing degrades silently. A third channel sits above both where this machine has a model endpoint configured: `find` sends the query and the ranked candidates to it for a judged ordering with a clause of reasoning per hit, and degrades to the two local channels whenever that call does not come back a ranking. A machine with no config file is the silent case, because a line every find printed would be noise about a channel nobody configured. Every other condition costs one line naming it: a config that exists and cannot be used, a probe nothing answers, a call that outran its budget, an answer cut off at this command's own generation ceiling, an answer that is not a ranking, and a refusal the endpoint answered with, whose detail names the HTTP status, the path the request reached and the dialect it posted in, so a dialect mismatch reads as a misconfiguration rather than as an endpoint that is down. `docs/security-model.md` owns what that call sends off the machine. The channels fail differently, which is why all three stay: lexical catches the exact identifiers embeddings fuzz, semantic catches the paraphrase substrings miss, and the judged pass catches the candidate that is topically close but useless here, which neither local channel can see.

Archived records are ranked but withheld from the semantic block by default, and one line in memq's own voice at column zero is what keeps the suppression from being a silent miss. It headlines every archived record that cleared the admission floor, which is suppression's true extent, and it quotes a best raw similarity only over the archived records inside the pre-suppression display slice, which is exactly the set a `--archived` rerun puts on screen under the same 10-hit display cap. Two counts rather than one, because a similarity quoted from a record the rerun's own cap would cut sends a reader after a line that does not exist: the line names the subset's size whenever it is smaller than the headline, and where nothing archived reaches the cut it says so instead of recommending a rerun that hands back the same screen. Suppression runs after admission and ranking and before the display cap, so a live hit fills the slot an archived one would have taken. A search whose every admitted hit was archived still prints the block's framing line and the withheld line rather than falling into find's empty-result path, which exits to stderr with `no matches`: a suppressed hit is never allowed to read as an absent one. `--archived` turns the filter off, printing those records labeled `retired` and demoted by the archive-demotion constant, which under that flag is what keeps an equally similar live record ahead of its retired twin, and it prints no withheld line; it is refused with a usage line alongside `--outcomes`, which never opens the semantic channel, and on every other subcommand. The lexical channel lists live records only, so the flag changes the semantic block alone.

A superseded record is the same shape one notch lighter, and it is not suppressed: the lexical line carries `superseded by <name>` and the semantic hit carries a bare `superseded` token beside the `retired` one and a demotion by its own constant, seeded to match the archive demotion, so an equally similar record nothing replaces ranks ahead of it. The names ride the lexical label alone, and a fan-in enumerates them there name-ordered, capped with a counted remainder, while the demotion fires once whatever the count, the label being a flag rather than a sum. Suppression would be wrong here for the reason retirement would be: the record is still live and the pointer is authored data.

A semantic hit line states usage as two tokens, `applied x4, last 25h`. The count is the distinct calendar days the record was applied on and the age is the most recent of them, printed apart because one number that means a tally reads as an age. The count shown is the uncapped truth while the ranking's tiebreak keeps using the value capped at the boost's own ceiling, which is deliberate: the line is annotation, the blend stays dumb, and the reader judges freshness rather than inferring it from a rank. The semantic block spans stores the calling project never opened, so it takes the full provenance fence rather than find's narrower by-construction guard, and `docs/security-model.md` carries that distinction.

One composer emits that line for every producer of the channel, because a sanitizing guard is a property of the output channel rather than of the producer that first needed it. `hitLine` takes a hit and the flags each surface needs, the similarity, the `machine:` scope and the overlap label, and returns the whole line with every charset reduction and cap inside it; the three producers are find's semantic block, which appends its applied tokens after the shared line, find's model-judged block, which appends its clause of reasoning, and the authoring verbs' neighbours block, which passes the overlap flag. `retired` and `superseded` are properties of the hit rather than flags, printed inside the provenance parentheses wherever the hit carries them, because a label a producer could forget to ask for is a retired record reading as a live one. The same channel's partial-sweep and persist-failure lines are single-sourced beside it, so the counts a find reports over its sweep and the counts a decay scan reports over the same sweep are one account rather than two.

The `memory-system` skill owns the operating rules; this section owns the shape.

## Dispatch authority

A plan doc can carry its own arming grant. A `## Dispatch Authorization` section at the head of a plan records who authorized the work, when, and which sessions the grant covers, with "any session holding this plan" as the default scope. A session handed such a plan arms it without a confirmation round-trip once it has traced the grant to the operator, because the committed document is the grant and the message that delivered it is only a pointer to one. The trace is a step somebody performs before arming and no tool runs it: the section is prose a writer supplies, so a receiver that arms on its presence alone lets whoever wrote the plan widen its own leash. The peer-sessions skill owns that step and the states a receiver takes when the trace does not hold.

The mark is provenance, not credential. On a single-principal machine the section narrows an honest writer without authenticating one, and git history is its trail. Nothing here stops a malicious local writer, exactly as no kit guard does.

The section is inert to the machine contract. The plan-doc header and the shapes an external engine parses are a frozen v1 contract, and `## Dispatch Authorization` sits outside all of them, as `## Assumptions` does. The two take different positions, and `curating-docs` owns the rule: `## Dispatch Authorization` belongs above `## Sections of Work`, which is stricter than outside it, because no template reserves a place for the heading and both of the blocks bounded by the next `##` heading truncate silently when one lands in them, the sections block dropping every later `### N.` section and the Chapters block freezing every `Completed:` line below the intrusion. `## Assumptions` takes the weaker rule, outside the sections block and above `## Chapters`, because the spec template already places it after `## Out of Scope`.

`/kit-goal` records what it read. At arm time the CLI scans the head of each armed plan for the heading and stores that section's first sentence, screened to printable ASCII and capped at 320 characters, in an `authorizations` map in the goal state keyed by plan path; a plan carrying no such section records none. The scan reads a 16 KB head of the plan doc and refuses a heading it cannot read as a claim: one inside a fenced code block, one below `## Sections of Work`, and one whose section body ran to the window's edge with no following heading and no sentence terminator, where the end of the body is unseen rather than short. A sentence past the cap is stored with a visible truncation marker written inside the cap, so a cut claim cannot read as a whole one and re-screening a stored value cannot cut the marker off. The value is quoted file content taken at its word, re-screened on every read as well as at the write because the readers print it, and surfaced by the `/kit-goal` status report. It is an audit trail rather than a check: nothing consults it to decide whether an arm may proceed. The same arm records who ran the invocation, in an `armedBy` map keyed the same way: `self` where a run armed the plan for itself, `operator` where the operator typed the arm, with an absent or unrecognized entry reading as `operator` for compatibility with states written before the map existed. It is recorded per plan rather than per queue because an append can add a plan armed one way to a queue armed the other, and it decides text and two renders: the condition sentence the state carries, the arming clause that the ordinary hold, the queue advance and the spent-lead hold carry among the Stop hook's block reasons, the per-entry line the status report prints, and the arming line the doctor's leash report prints beside the plan it reports. The doctor's is the one render that parts an absent entry from a recorded operator arming, naming the plan and saying nothing is recorded rather than asserting a claim the state does not carry; it reads both the field name and the entry name ordinally, because PowerShell's member indexer is case-insensitive and its `-ceq` is culture-sensitive, where the JavaScript readers use `hasOwnProperty` and `===`. That one fact is deliberately all it carries, so nothing an arming asserts can stand in for the sentence beside it: what a plan grants stays in `authorizations`, where it comes from the document, and a self-armed arm over a plan recording none proceeds with a stderr warning rather than a refusal.

Queues grow rather than mutate. `--append` adds plans to an armed queue under the existing binding, deriving each appended plan's authorization from its own document exactly as an arm does, and refuses atomically when any named plan already sits in the queue, so a partial append cannot happen. The bare replace form replaces the queue outright and warns on stderr when it drops a non-empty queue, naming what it dropped, since a silently dropped armed plan is the expensive failure. The size bound is measured against the real serialized state rather than an estimate, so a queue too long to write is refused rather than truncated. An append is typed into whatever shell is at hand while the leashed session runs, so it re-reads the state immediately before writing and refuses unless the arming timestamp, the current plan, the queue position, the queue length and the history length all still match what it validated against. What it writes is that re-read with the append applied, never the snapshot, so a stop's bind or advance landing mid-validation survives instead of being reverted; `bindSession` follows the same rebase, setting only the two binding fields it owns. Neither closes the window between the re-read and the rename, which stays last-writer-wins.

Arming happens where the run happens, and where the run happens is a working tree rather than a repository: git makes a working tree the unit of an execution stream, HEAD, the index and the branch all being per-worktree, so a leash belongs to the tree that reads it and two trees of one repository carry two leashes at once without either reaching the other. What stays tied to the calling tree is the plan doc, so a plan handed to a session in a worktree cut before that plan's commit is unreachable to the receiving CLI however real the plan is at origin, and the arm refuses and the handoff defers to the next safe tree advance. The sender holds the handoff open until any of the receiver's three replies arrives, and counts it converted only on the armed acknowledgment. Two sessions sharing one working tree is a different hazard, since a shared tree shares a checkout rather than only a leash, and session start says so where it can see one: `summarizeSiblingSessions` lists this project's transcript directory for another session's `.jsonl` whose modification time falls inside a ten-minute window, excluding this session's own id, and emits one advisory carrying the count and the age of the most recent. It opens no transcript, and no name or path leaves the function. The listing is incremental through `opendirSync` under a 4,096-entry ceiling, because the store keeps a per-session subdirectory beside each transcript and a ceiling applied after a whole-directory read would bound nothing. Recency is the whole signal, so the line is a hint rather than a verdict: a file mtime cannot tell a live session from one that ended minutes ago, and a different checkout whose path flattens to the same directory looks identical from here. Every failure path is silent, an unreadable directory and an unrecognized layout included.

### Worktree resolution

The goal family resolves the leash and the live plan doc in the same direction, against the caller's own working tree, because both belong to the execution stream rather than to the repository: goal state sits at the calling tree's own `.kit/goal-state.json`, and the live plan doc is the copy on the branch that tree has checked out. `memq` deliberately answers the other way, resolving a worktree to its main checkout, because a memory is about the repository where a leash is about an execution tree; the two resolutions are pinned against each other over shared fixtures so that the difference stays deliberate rather than becoming drift.

`goalPath` in `hooks/kit-goal-lib.js` is the single resolution point, and every read and write helper in that file joins its path through it, so the whole family inherits the behavior with no per-caller edit: the Stop hook, the compaction gate, the checkpoint CLI, the two nudges, the SessionStart notice, the `/kit-goal` CLI, and the status-line widget. It joins `.kit/goal-state.json` to the caller's own working directory and consults no on-disk pointer to find it, so the location is not a trust input: no `.git` file is read on this path, nothing is resolved out of a `gitdir:` line, and there is no candidate directory for a screen to refuse.

The reach is worth stating plainly, and the claim is about the goal state and the plan docs rather than about every path the family touches: every read and write of the goal state itself lands inside the caller's own git root, so a bind, a queue advance, and the clear's unlink touch nothing outside it, and plan docs resolve against that same cwd. Three touches sit outside that root by design, and each is bounded where `docs/security-model.md` states it. The SessionStart notice reads a `.kit/goal-state.json` in each directory git names as a linked worktree of this repository, so a session learns which siblings hold a leash of their own. The goal events an advance and a release emit are appended to a machine-wide sink under the user's home directory. And a bound session's transcript path is stat'ed for an age, never opened, where the harness stores it.

### Queue position

The reported queue position is derived from the plan docs rather than read from `queueIndex`, because nothing in the system is level-triggered on the stored index. `advanceGoal` has exactly one call site in the whole plugin, inside the Stop hook, so the index moves only at a clean stop of the bound session, and `normalizeState` reconciles the stored queue against the stored plan and never against the world. A run that dies at its close-out therefore leaves an index naming a plan it finished and archived, with no later session repairing it.

`queuePosition` in `kit-goal-lib.js` answers instead from the evidence. It walks forward from the clamped stored index, never backward, since an entry behind the leash may be unfinished for a reason the leash already adjudicated; it is capped at sixteen entries; and it reports the first entry the plan docs do not show as finished. An entry counts finished on the reading tree's own evidence, the goal state and the plan docs both belonging to that one tree, so there is no second copy to arbitrate and no disagreement to resolve. Evidence is the doc's own `Status:` header read through the shared kind-and-size rule, and, where nothing stands at the plans path, the header of a same-named copy under `docs/archive/` held to that same bar: presence alone is not evidence, since nothing ties an archived file to a queue entry beyond its name. An entry no tree can resolve keeps its position and is labeled with the cause rather than skipped, because skipping renumbers every entry behind it. The walk writes nothing.

Three surfaces report from it and one deliberately does not. The SessionStart advisory names both plans where the two positions differ, the stored one and the plan actually current, and says that the leash still acts on the stored index and takes one stop per plan to catch up. `kit-goal.js status` reports the same position. The status-line widget's `Plans` segment does too, adding the corrected plan's base name and the stored index beside it (`Plans: 2/2 b_spec_v1 (stored 1)`), an `unresolvable: <cause>` clause where the entry cannot be read, and an `all complete` clause where the entry at the reported position itself reads finished, which is the state where the leash releases rather than advances. The doctor keeps printing the raw stored index, on purpose: it is the surface that exists to show a state file the hooks refuse, and one that silently corrected the number would stop being the reporting control. `docs/backlog.md` carries that as a parked decision rather than a gap.

## Session roles

Roles are the coordination vocabulary the concurrent sessions on one machine share, and they sit beside the authority rail above rather than on it. A role is a stewardship claim on a function-times-resource pair: it says which session tends a seam, never what a session may do. Any session can name itself anything, so a claim confers nothing beyond legibility, and the peer-sessions skill states that as a rule rather than a caution, because the failure it exists against is a self-chosen label read as a privilege.

The starter seats are the coordinator, the expert, the worker and the admin, and the set is open. The coordinator stewards the seam between repos and toward the operator, one per machine. The expert stewards a repo's knowledge and its plan authorship, one per repo. The worker stewards mutation of one checkout, exclusive per tree and usually leashed. The admin stewards machine state, one per machine. A claim is declared in layers and no layer authenticates: the session name advertises it under the `PROJECT: Role` convention the peer-sessions skill owns, with the harness's own `ListAgents` roster as the directory a peer looks it up in; the first-contact handshake confirms it; the session's own registry entry under `coordinator/<machine>/registry/` records it durably, written by the very session whose claim it states, which is why it advertises rather than attests; and the coordinator's board carries those claims as that seat last read them, a different file with a different writer in the same directory. A roster row carries what the harness knows about a session, and the peer-sessions skill owns that field list; nothing in a row corroborates a seat. A claim colliding with a standing claim on an exclusive seam is routed rather than assumed resolved by silence: it goes to the coordinator, or to the operator where that seat is empty or is itself party to the collision, and only an answer retires one of the two.

Every seat also declares its own compaction boundaries, which is how a goalless session earns the clean landings a leashed worker gets from its chapter checkpoint. The invariant is the gate's own, compact wherever context holds nothing the disk does not, and the peer-sessions skill owns the cross-seat routine: a seat ends a banked moment by rewriting its own registry file's status lines and running `kit-registry-stamp.js`, which is what advances the entry's `Status-updated:` stamp, and the `seat-stop.js` Stop hook opens the role-boundary marker for it where that stamp is fresh and the working tree is clean, so the next deferred offer lands at the boundary instead of riding to the safety ceiling. The status push is the declaration and the hook is what makes it structural, but only over a clean tree, and that conjunct is what leaves a whole class of seat unserved: a seat sharing a checkout with another session's uncommitted work can never satisfy it, and the dirt is not that seat's to clear. So `kit-compact-checkpoint.js boundary`, run from the project directory, is the manual path for two cases rather than one, a session no registry entry covers and a registered seat whose tree carries work it does not own. On that path the declaration is the seat's own judgment rather than a tree reading: that everything it holds is on disk, that its own edits are none or handed to a named owner, and that the messages it owes are sent. The working directory is load-bearing on that manual path because the marker lands in that directory's `.kit/` while the gate reads it at the compacting session's own. The named moments are the expert's deliverable handoff (spec committed, blind read adjudicated, dispatch acked) or a consult answered and banked, the admin's completed-and-reported action, the coordinator's end of a reconciliation pass after the board write and the next wake's arming, and an unleashed worker's own banked moment on the tree it holds, that seat having no chapter checkpoint at all since the leashed verb refuses to open with no goal armed; a seat the list does not name derives its own the same way the seats themselves are derived. The bounds on that routine belong to the gate rather than to the skills. The marker releases the interactive deny alone, so a seat a native `/goal` or `/loop` drives is classified as automation and allows at the native trigger with no marker read at all, which bites a coordinator only where a `/loop` drives the watch, the self-armed timer this seat uses reading as hands-on instead; a marker the `boundary` verb declared is honored only while no new turn has begun in the declaring session since it was written, so it covers the moment it was made rather than a window, and for a seat that is woken or messaged the arrival is what ends it; and the age bound outside that is the deferral episode's own four-hour idle bound, derived from that constant rather than restated beside it, so the three quantities bounding a seat's quiet gap retune together. The consent marker is not a seat's to write. `kit-compact-checkpoint.js consent` is run only on the operator's explicit instruction to release that session's deferred compaction, over one of the warranted channels the coordinator skill's closed list of three names, and never on the session's own judgment; `docs/security-model.md` carries what that prose bound does and does not buy.

The coordinator seat carries its own runbook, `plugins/claude-kit/skills/coordinator/SKILL.md`, on the standing-watch chassis, and its functions are closed at four: the operator interface, cross-repo dependency and portfolio sequencing, machine-resource arbitration, and kaizen capture, dispositioning and dispatch, that last one carrying the operator's standing authority for it while staying inside the seat's never-tasks-directly bound, so a disposition lands as an artifact in the repo that owns the work rather than as an instruction on the seat's say-so. Oversight within a repo is deliberately not among them, the expert seat owning that. The other seats carry the reciprocal duty rather than a share of the function: each routes captured kit friction to the coordinator and carries on, never actioning it inline and never shelving it, because a responsibility naming no owner is discharged by whichever party is least busy, which in a fleet is reliably the party least likely to have seen the friction. The seat's state is a board at `coordinator/<machine>/board.md` inside the memory store, one directory per machine because the store reaches every machine on whatever remote is configured for it, and the chassis override that makes it durable rather than gitignored is the design rather than an exception to it: a watch's state dies with the watch by intent, while a seat's state is how the seat survives the session holding it. The seat writes the file and the store's own sync commits it, that sync being the automatic committer and automatic only on Windows, so the board reaches another machine on that machine's next sync rather than on a push the seat performs, and on a platform where that script does not run it acquires history only when someone hand-runs the store's repair path. What the board holds is coordination state and never authority, and what may go on a board line is set by content bars that hold whatever the readership, since nothing in the kit reads a store's remote and so no seat can learn who will see the file: the private-remote premise is a precondition of an installation rather than a property of the design, and a seat writes the board as a public surface until the operator states otherwise. `docs/security-model.md` states the bars and that premise in full under The coordinator board. A declared blocker climbs a ladder these seats define between them: the worker asks its repo's live expert before declaring, an ask carrying the question rather than the work and never gating; on declaring it notifies the machine's live coordinator, whose brief to the operator races that worker's own relay ping rather than gating it; and the answer returns on a channel the brief names in advance, the worker's own, never through the seat, because an inbound peer message carries no authority and a document the seat itself wrote cannot satisfy the authority trace.

Operating the seat is a chassis loop whose runbook states only what it adds. A pass arms its wake before it reads anything, since a session-only timer dies with the crash that interrupted the read, and then reads the board, because everything the seat has promised or brokered lives there and nowhere else. The cadence is event-driven, the blocker funnel's messages and the operator's pings, with one paced wake: a reconciliation timer every 4 hours, which is exactly the age bound a hook-opened boundary marker takes, so a marker the Stop hook banked at the end of one pass is still live when the next paced wake fires; a marker the `boundary` verb declared is bounded by its moment instead, and the wake is an arrival that ends one. The margin is that pass's own tail and no more, since the wake is armed one step before the boundary is declared: consecutive declaring passes cover the interval between them end to end, and a pass that skips its declaration leaves the whole of the next interval uncovered. An event-driven wake arrives sooner than the paced one and is covered a fortiori. It re-derives the watched facts from durable state rather than from messages, and the runbook owns which sources those are and what reading each one takes. This document deliberately does not restate that list: a list restated on a second surface is an invariant nothing checks. It takes the board as the record only for the seat's own commitments, which no watched system can produce. The board carries two kinds, a situational line re-derived next pass and a one-record line the board is the only record of, both under the chassis's admission test unchanged, and the seat's fork for them is its own: doubt about whether a candidate belongs on the board at all keeps it off, and doubt between the two kinds falls to the one-record kind, priced on the misfiling, since a re-derivable line filed one-record costs a stale duplicate and an operator confirmation round while a commitment filed re-derivable is taken out of use with nothing left to recognise it by. A finding this seat routed to another seat for handling is one of those commitments, and it is the category that closes a specific repeat cost: a disposition that travels back only as a message dies with the receiving session's context, so the finder's next pass re-derives the finding from the world, finds nothing on its own surfaces saying it closed, and re-raises it, which is a full verify-and-dedup round on both seats. Its line therefore stays open, and is not swept past by a successor whatever its age, until it carries either a disposition pointer naming the artifact that landed the fix or an explicit open marker naming what it waits on. What a pointer establishes is that the fixer named a disposition, never that the fix landed, so a finding a later pass still finds live in the watched systems is raised anew against the pointer rather than read as closed by it. One gap is deliberate and stated rather than filled: the rule says when a line may be retired and not what becomes of a line that never earns either form, so a finding routed to a seat that answers nothing rides the board open indefinitely, visible rather than lost and costing a successor's attention at every sweep. The seat dispatches nothing: it writes the spec or the backlog entry in the repo that owns the work, asks the operator to arm over one of the three warranted channels, hands artifact-authorized plans on the dispatch-authority rail, and appends an operator ask of the Admin seat to that seat's request inbox in the machine coordinator directory, the one seat no send reaches. Handoff and contest run off the same registry. A successor reads the board and then takes the seat's name on the roster in the machine-scoped `HOSTNAME: Coordinator` form, while two live names claiming the seat freeze the board and route to the operator, the seat citing the anchor it observed rather than a commit, since handing over either version is itself a board act the freeze forbids and the seat does not rule on its own collision, a registry a contested claimant maintains settling nothing. The uses of the messaging surface that have won their way past its closed four patterns are recorded in the peer-sessions skill rather than counted there or here, and every one of them so far bears on this seat: the status round, one bounded line per live session at no more than the heartbeat cadence and answerable at the receiver's next boundary; the worker's blocker route, whose notice leg hands the seat an escalation to route while its pre-BLOCKED ask leg goes to the repo's expert and never reaches the seat at all; the claim probe, the one use whose subject is a machine resource rather than a session's own state, which this seat sends to the claimant of a claim past its bounded declared duration; and the kaizen routing message every other seat sends this one, whose subject is that the artifact it belongs in sits behind an authority only this seat holds.

Every board candidate is routed at the moment of writing rather than pruned at a cleanup later, and that is what keeps the board's admission test satisfiable: a pass that defers the question leaves the next successor a line it cannot delete without destroying the only copy. The runbook states the kinds and this document does not restate them. The two the board takes are permissions, the situational line and the one-record line above. The two that go off the board are refusals, so a candidate answering to a board kind and to one of them takes no tiebreak and the refusal wins: a durable lesson is a memory-store record written in the same pass that produced it and never also a board line, and kit friction is a kaizen note under the standing capture authorization, never a board line. Which tier takes a lesson, and how a record is authored, are the memory-system skill's to state and are pointed at rather than copied. A candidate no kind claims is written nowhere. Two exceptions re-categorize a candidate rather than bending the refusal: friction that becomes a decision the operator owes an answer on, or a finding routed to another seat, boards under the category the ledger already gives it, and a line the board is the one record of stays on the board whatever lesson was also learned from it, because the store gaining a record does not give the board's reader one. What a line carries travels with the content: the path bar and the operator's-words bar hold at the destination, with that destination's own bars on top of them, the kaizen inbox's public-board cap among those.

A board that grew before that routing existed is repaired by homing, which is a distinct operation and not a prune. The board's health rule is the readability test, that a cold successor takes the seat from one read of it, and a pass that finds the board failing it runs a homing round rather than a harder prune, since the bulk a grown board carries is exactly what a prune must either destroy or correctly refuse. The runbook states no size figure for the board, so nothing was removed to make room for that test and none is stated here either: a byte figure is a proxy a seat records and ignores. A round runs each standing or narrative line through the routing as though the line were being written now, and the content then comes off the board outright, with no pointer to the record now holding it and no tombstone, because a board that swapped each homed line for a pointer would keep a change log where the content had been and accrete at the rate it homed. One invariant bounds every cut: a round cuts only a line whose content it has confirmed landed somewhere else, and the confirming read has to establish that the record it returns is the one this round wrote, on the tier it was written to, carrying the content the round composed, with unconfirmed reading as unknown rather than absent so that it holds the line. A line no destination will take stays on the board and is a finding for the operator rather than something a round can solve. The account of the move is the memq outcome journal at each end of the round, the opening entry carrying `fail` and the closing one `pass`, and the opening entry lands before anything publishes or destroys, so a round that cannot establish that its own first entry landed, and whether it landed cut, performs neither a destination write nor the cut and leaves the board as it found it. Pruning is untouched by any of it. `docs/backlog.md` carries what that account cannot reach, which is that the journal is project-scoped while the seat is machine-wide, so a round's entries and a later reader's call can resolve different stores.

The runbook is partly exercised procedure. The seat's machine-resource arbitration, its status round, and the board write itself have all run. Several branches have been read for defects and never performed, named here rather than as a closed set: the cold start against an absent board, the seat handoff, the stub forms, the freeze on a contested seat, the homing round whose guidance ships with the routing above and whose first run is each seat's own over its own board, and the routed finding's own path, from boarding a finding this seat sent elsewhere through asking the fixing seat for a disposition pointer its reply omitted to reading that pointer when it lands.

Each seat runs at the cheapest tier its judgment surface allows, and the peer-sessions Roles table is the single owner of those figures: the coordinator at Opus on the cadence its own skill states, the expert at Fable, the worker at whatever model the session itself runs (a plan's section tiers govern what that seat dispatches, never what it runs), and the admin at Sonnet with a 4-hour poll of its inbox. Every row states an observable step-down gate rather than a feel, and the admin's is the one built against a silent failure: a month of adjudicated routing decisions with a planted line among them, because inbox volume alone cannot tell a quiet month from one where a laundering-shaped line went past.

### The coordinator directory

The machine's coordination artifacts live in the memory store at `~/.claude/coordinator/<machine>/`, `<machine>` being what `os.hostname()` reports, and four file forms live there: `board.md`, the coordinator's ledger; `registry/<session-id>.md`, one per registered session; `claims/heavy-process.md`, the machine's one-heavy-process slot; and `admin-requests.md`, the Admin seat's artifact inbox. The list is the contract, and `plugins/claude-kit/skills/role/SKILL.md` owns it. Owning is precedence rather than sole spelling: the coordinator's runbook restates the parts of the contract a pass cannot be run without, and the dispatch-brief template in `executing-work` carries a second copy of the claim protocol because a dispatched subagent inherits no skills and that copy is the only one it ever receives. A curation pass finding either restatement is reading a designed copy.

The writer rule is stated per file rather than once over the four, and that split is what the rest rests on. The board and each registry entry are single-writer, the coordinator writing the board and a registering session writing its own entry, plus the two lines a writer other than the session stamps, which is where the role skill's contract closes that set: `Heartbeat:`, which `seat-stop.js` stamps where that hook is installed, and `Banked:`, which `kit-compact-checkpoint.js` stamps on that session's own `boundary` run. Two more lines are machine-stamped without adding a writer, `Started:` and `Status-updated:`, coming from a CLI the session runs on its own entry. The claim file and the inbox are multi-writer by design, each under its own protocol. Exactly two acts reach across that rule and both are the coordinator's: it prunes a registry entry whose own heartbeat reads exited, and it releases a heavy-process claim past its declared duration. Each is written to the board before the artifact is touched, and every reading that cannot be made cleanly keeps the artifact rather than removing it, so an absent, unparseable, or future-dated stamp reads as unknown. `docs/security-model.md` carries what those two acts are bounded by, which is visibility and recovery rather than prevention. All four forms are `.md`, which is the whole of what the store's sync allowlist admits under this root, so the two rules agree in form while the allowlist stays the wider of them: any `.md` at any depth here syncs, where the contract names four paths. The directory sits outside `memory-frontmatter-guard.js`'s tier set deliberately, that guard's rule being CLI-authored-only while every writer class here writes directly.

A registry entry is a session's own account of itself, carrying `Name:`, `Role:`, `Repo:`, `Workdir:`, `Session:`, `Started:`, `Status-updated:`, `Remaining:`, `Heartbeat:`, and `Banked:`, then a few `Status:` lines holding what a public board could carry. Which of those lines the session's own push rewrites, which `kit-registry-stamp.js` stamps beside them, and at what moments any of that happens, are the role skill's push-moments paragraph to state, and the moments themselves are sourced there rather than enumerated here. `Heartbeat:` and `Banked:` fall outside the session's own push, being the two lines the writer rule above counts as writers other than the session. `Workdir:` is the gated field. The registry is the one place a working directory may live at all, readable across the elevation boundary the board is not, and an absolute path is written there only where the operator has answered who reads the store's remote. That answer's default state is unanswered, and until it arrives the field takes a repo name, a worktree-relative name, or nothing.

`plugins/claude-kit/hooks/kit-registry-stamp.js` is the instrument over those time fields, a CLI in the hooks directory that no `hooks.json` event wires, so the canary's load check never names it while the build's integrity manifest, which hashes the whole packaged directory, does. It carries three verbs. `push` rewrites the calling session's own `Status-updated:` from a clock read taken at the write, through the same shared stamping channel and the same `Session:` corroboration the checkpoint CLI's `Banked:` stamp takes, and refuses with nothing written where the shell carries no id-shaped `CLAUDE_CODE_SESSION_ID` or where the entry's own `Session:` line names another session; `push --takeover` stamps `Started:` beside it, which is the one moment that field is meant to carry, since a later rewrite would name the moment of the push rather than of the takeover; nothing in the CLI refuses a second `--takeover` over an already-stamped `Started:`, so the single write is the calling convention rather than an enforced one. `now` prints one moment for a line no stamp can reach, a board line carrying its evidence time inside its own prose rather than in a field, so what the tool supplies there is the value rather than the write. `audit` is the reading side, and each of its four readings rests on a value the artifact's own writer did not supply: a session-written stamp falling on a whole second, a session-written stamp leading that entry's hook-stamped `Heartbeat:` by more than the seat-stop hook's own throttle window, a claim file's `Started:` sitting more than five minutes from the file's modification time in either direction, and any stamp in an entry, in the claim, or in a board line sitting ahead of the clock past the compaction checkpoint's own future-skew allowance. The board takes that last reading alone, carrying no machine-written comparator and writing its moments at whatever precision the writer had, and its stamps are found by their ISO shape inside the prose since it has no field grammar to read them out of. Scope is one machine's directory under the coordinator root, judged on the real path rather than the spelling: the root itself, a directory one level deeper, a network-shaped path, and an absent one are each refused and named rather than scanned, an unreadable artifact inside a scanned scope is itself a finding, a listing too large to read whole reports as partial, and every run prints what it read, so a scan that reached nothing can never read as a directory with nothing wrong in it. The exit code carries the reading, and two of the four readings are reports rather than verdicts for reasons the module states: a whole-second stamp is a population reading, an honest clock read landing there about once in a thousand, and the heartbeat comparison reads a push made inside a turn that has not ended yet exactly as it reads a fabricated stamp, the hook stamping at a turn end and nowhere else.

`claims/heavy-process.md` models the one-heavy-process-per-machine budget as one file. Before a suite, a build, or an embedding pass, the spawner reads the live claim and then writes `Name:`, `Repo:`, `Session:`, `Started:`, and `Expected-seconds:`, deleting the file at completion and only where its `Session:` line is the writer's own. The enforcement point is whoever spawns the process rather than the seat that dispatched it, since most of a box's heavy processes are subagents', which is why the brief carries the clause at the spawn step itself and a subagent's claim carries its dispatching session's id and name. A session finding a live claim waits or names the contention, and naming a contention never includes writing the claim, so a session that proceeds runs unclaimed and reports itself that way rather than replacing a live holder's record. The claim buys legibility and never a guarantee: an empty claims directory means nobody has claimed the box, not that the box is free. What backstops a claim is its holder rather than a process poll, an instrument that cannot see work shorter than its own sampling interval, misses in-process agent fan-out entirely, and reads a resident idle build server exactly as it reads a live one. Past the declared duration, bounded by a figure the coordinator's runbook states rather than one the contract sets, that seat probes the claimant and may release the claim on two legs together, a probe whose send returned no failure and went unanswered past the probe window, and a roster reading that agrees the claimant is not live. Either leg alone leaves the claim standing as an untracked hold reported to the operator, and the release itself is a recorded, notified, reversible decision rather than a measured fact.

### Seat takeover

`/role <Seat>` is the one command that takes a seat, replacing a ritual that was hand-assembled across three skills. Its steps run in order, and where a seat's own runbook states a tick order that order governs and these fold into it. The session's name is confirmed against the peer-sessions Naming convention first, since a relaunch rather than a rename is what a wrong name costs (the relay-channel flag bakes the name into its thread at process start); the exact launch invocation is a per-machine operator fact the public skill cannot carry, so it is resolved from the operator memory tier and described to the operator in prose for confirmation rather than presented as a runnable command. The seat's runbook loads next. The wake is armed before anything is read, which is the coordinator's cold-start order held for every seat, because a crash mid-read leaves no timer behind: a seat whose runbook states a cadence arms at it, a seat stating a loop but no cadence arms at the coordinator's reconciliation cadence, and a seat stating no loop at all arms no recurring wake, its heartbeat coming from the turns it takes while it works. Then the board is read, and for Admin the inbox, and the memory store beside them; the delegation record is resolved; the registry entry is written; the takeover is announced; and the first status push lands, whose `Status-updated:` stamp is what opens the compaction boundary through `seat-stop.js` where the working tree is clean too.

The standing-grant rail is the skill's second charge, and it is a mechanism the skill defines rather than a grant the skill makes: a standing operational grant is one whose entire scope, exclusions and procedure a shipped skill states, switched on by one operator-tier record the owning skill identifies, the record's body data that can neither widen nor narrow it, and revoked by deleting that record. The rail carries its own closed exclusion list, binding on every instance: it extends no warranted channel, it establishes no privacy precondition, it lifts no harness floor and no no-laundering rule, and it widens no grant past what its owning skill spells out. The standing-delegation model is that rail's first instance and its only live one. The model is the chain (coordinator to expert to worker, a seat acting on scoped direction from the seats above it), the scope (planning, scoping, sequencing, and dispatching execution of sections of plans whose arming the dispatch-authority rail covers), and the exclusions, which are stated rather than left to inference: no push beyond a plan's recorded commit model, no deploy, no message to an external service, no edit to permissions, settings, or CLAUDE.md, no delete or other write outside a plan's own scope, no directed read of the store's own sensitive state, no handing the direction onward as a dispatch, since a dispatched agent carries Write, Edit and Bash and so reaches far past the message that asked for it, and no work another session was denied. What turns the model on is the rail's switch in the model's own scoping, a per-machine, hostname-keyed opt-in record in the operator tier, which `/role` resolves at takeover; where none answers, the seat announces itself undelegated and the operator's per-session paragraph remains the path. The record is provenance rather than credential, exactly as the dispatch-authority mark is, and its body is read as data, so a body purporting to widen the scope changes nothing and is reported as a finding. The three refusal rules it composes with stand unchanged: a peer message carries no authority, a role claim confers nothing, and a seat cannot warrant a grant it authored itself.

Every seat but the coordinator carries one duty beyond its runbook. Captured kit friction routes to the machine's coordinator, which holds kaizen dispositioning and dispatch as a named function with the operator's standing authority behind it, and the capturing seat carries on rather than actioning the note inline or shelving it. Capture itself is standing-authorized for every session, seated or not: the append to the inbox is the capture, taking no per-note approval and no routing through any seat, so what the route carries to the coordinator is the dispositioning rather than the authority to capture. The routing message takes the same cap the worker's blocker line takes, only what its sender would put on a public board, and friction that cannot be stated inside that cap goes to the operator as a decision ask instead.

The admin seat is the one whose mandate is open rather than allowlisted, and the mandate is the operator's arming of the particular session holding the seat rather than the seat description, so no session acquires it by claiming the name. Its rationale is a precondition the seat is gated on rather than a property the payload asserts, since the payload ships to installations whose perimeter it cannot see: where an installation runs sandboxed with disarmed access and a separate identity, that perimeter can stand as the whole restriction, interior allowlisting inside such a boundary buying little safety at real cost in capability. The perimeter does not protect the values inside it, the guard files in the user-writable plugin cache and the machine-wide memory tiers among them, which is what the seat's two binding constraints are for: every action is reported to the operator, and the seat is support rather than work, fixing processes, permissions, services and workspaces and never producing or bypassing work product.

## Goal release events

A `/kit-goal` leash release leaves a machine-readable line in `~/.claude/kit-events.jsonl`, so an outside notification layer watches one well-known path instead of parsing transcripts. Transport is not the kit's job; the kit's deliverable is the file and its contract.

`emitGoalEvent` in `kit-goal-lib.js` writes it, and `kit-goal-stop.js` calls it at exactly three points: the plan reaching `Status: Complete` (`goal-complete`, detail `plan-complete`), the plan file gone to the archive (`goal-complete`, detail `plan-archived`), and a last assistant message leading with `BLOCKED:` (`goal-blocked`). Two other releases deliberately emit nothing: a manual `/kit-goal clear`, where the user is already present, and the harness's own consecutive-block-cap override, which the hook never sees.

Under a queue the cadence is per plan rather than per run, and that is the only shape change a consumer sees: an arming of four plans emits at each plan's terminal state, so up to four events carrying four different `plan` values under one `session`, and only the last of them coincides with a release. The event names, fields, and `detail` values are unchanged, and each event names the plan that finished rather than the one now current, so a consumer written against a single-plan arming reads a queue correctly and simply sees more events. What it must not infer is that an event means the run ended; that was never stated in the contract and is now false for every event but the last.

That decoupling is sharpest for `goal-blocked`, which mid-queue is emitted on a stop the hook then blocks. The event says a plan hit a blocker, which is the thing worth notifying an operator about, and says nothing about whether the session stopped; the leash records the blocker, advances, and holds the session on the next plan. Emitting it there rather than suppressing it is deliberate, because a blocked plan is exactly what an operator wants to hear about and the alternative loses that signal for every plan but the last. A consumer that treats a `goal-blocked` as "the run stopped" and acts on it, by resuming or re-arming, is acting on an inference the contract does not support.

One thing the stream deliberately does not carry is the blocker's text. `history` accumulates a note per finished plan inside the state file, and the final plan's release deletes that file, so once a queue finishes the content of each mid-queue blocker survives only in the session's own closing summary. That is a soft record: a session that dies before writing its summary leaves plan paths and no blockers. That holds once the queue finishes and the goal clears; while the goal is still armed, a mid-queue blocker's recorded first line stands in the goal state, which is the field the coordinator's funnel reads and the reason its dead-worker backstop works at all. Closing the gap needs a new field or a new sidecar, both of which are event-shape changes the queue deliberately avoided, so it is a known limitation rather than an oversight.

The contract a consumer reads against:

- One JSON object per line, `{ts, event, project, plan, session}`, plus `detail` present only on a `goal-complete` and `run` present only inside a run. `ts` is ISO 8601, `project` the absolute project path, `plan` the repo-relative plan path, `session` the session id or null.
- `run` carries `KIT_RUN_ID`, and only a value memq's own `isRunId` accepts, so the event stream and the memory store cannot disagree about what a run id is and a consumer may rely on the value being a well-formed id. The field is absent rather than empty when the variable is unset or refused. Its presence says the process was told a run id, not that run-scoped memory was active: the pending tier additionally requires the store signals, so the two conditions are separate and a consumer must not read one as proof of the other.
- Every field is sanitized display data, not a command: printable ASCII, capped at 40 characters for `event` and `detail`, 120 for `plan` and `session`, and 260 for `project`.
- `project` is an absolute local path that typically embeds the OS username, so forwarding an event anywhere external is a PII call the consumer makes.
- A `goal-complete` is exactly-once per plan, but the two positions in a queue reach that guarantee differently. On the last plan the emit is gated on the clear that actually removed the goal state, so a persistently failing clear never re-reports and a racer that finds the state already gone stays silent. Mid-queue there is nothing to clear, so the guarantee rests on the advance itself: only the bound session's stops reach it and its stops are serial, and the advance is one atomic state rewrite carrying a compare-and-swap on the plan the stop decided from and the timestamp it was armed at, so a state some other writer moved in the meantime is refused rather than advanced over and the emit rides only on the write that lands. Both halves are load-bearing: a re-arm that puts the same plan back at the head, which is the ordinary crash-recovery spelling, matches on plan alone and is caught only by the timestamp. The binding alone would not carry that claim, because the CLI is a writer it does not exclude: a `/kit-goal` re-arm or clear can land inside the hook's own retry sleep. A failed or refused advance emits no `goal-complete` at all, since the write and the emit stand or fall together: the clause re-runs at the next stop against the state as it then is, and the event arrives once, late. What statelessness costs falls on the other event instead. `goal-blocked` is emitted before the advance is attempted, so a failed write means a second `goal-blocked` at the retry, and a plan can draw more than one anyway: the hook holds no record of a blocked stop except in the one mid-queue case where the spent advance key suppresses a re-read of the same turn. Dedup is therefore the consumer's policy and is load-bearing against notification spam.
- `KIT_EVENTS_PATH` redirects the sink per process, honored only alongside `KIT_EVENTS_PATH_ALLOW=1`. The intended users of both signals are the repo test suite and the canary's own goal probe, which point the stream at a throwaway file; a consumer must not honor either ambiently. An override set without the second signal is ignored in favor of the real sink, with a note on stderr. An engine that sets the path alone therefore does not fail loudly to its own watcher, it silently keeps writing to the default sink, so setting both is a deployment precondition rather than a convenience.
- Emitting is observability, never a decision input. The helper never throws, returns nothing to branch on, and leaves a stop's verdict, output, and exit code identical when the write fails. A sink that exists and is not a regular file is left untouched and nothing is written, the same FIFO-hang guard the Stop hook applies to transcript paths. The check is an `lstat`, so a symlink or junction at the sink path reads as the link rather than its target: nothing is appended through it, and the rotation cannot move a linked-to file aside. Rotation is best-effort and sized for a single writer: past 1 MB the file is renamed to `kit-events.jsonl.old`, replacing any previous one, and a rename that keeps failing degrades to unbounded growth rather than lost events.

## Status line

The kit draws one status-line segment naming the armed plan and how far through it the run is, and it ships as two files because the two halves have different lifetimes. `scripts/kit-goal-statusline.js` is the widget, and it lives inside the installed plugin payload, whose cache path carries the release version and so rots at the next kit update if it is baked into a durable setting. `scripts/kit-statusline.js` is the launcher, and the doctor's shim installer byte-copies it to `~/.claude/bin/kit-statusline.js` beside `memq-shim.js` (`doctor/install-memq-shim.ps1:44,49`), which is the stable path a status-line tool is configured with. The launcher bakes in nothing: it resolves the installed payload through `memq-shim.js`'s resolver on every invocation and loads the widget from there, so a kit update needs no doctor re-run. The dependency runs the other way for the launcher itself, and that is the one operating consequence: the operative copy is the one in `~/.claude/bin`, which a plugin update does not refresh, so a change to the launcher takes `doctor -Fix` first and the plugin update second.

The launcher requires the widget rather than spawning it (`kit-statusline.js:361`), so a refresh costs one node start rather than two. The saved cost is a whole interpreter start on every refresh of every open session, which is the load under which the segment stops drawing.

The line's two derived segments read one tree, the widget's own cwd. `Sections` counts that checkout's copy of the armed plan doc, and its cache key is taken from the same file, so the count and the key cannot come from different copies. `Plans` takes its position from the library's `queuePosition` over that same cwd, so the widget agrees with the SessionStart advisory and `kit-goal.js status`, which resolve the same way. The call is skipped outright for a queue of one, where the answer would be discarded, and a payload whose library does not export `queuePosition`, or whose answer does not carry the shape the widget verifies (integer `index` and `stored` both inside this queue, boolean `positional`), renders the stored index exactly as it did before the segment read a derived position at all.

The render is cached in the project, at `.kit/statusline-cache.json`, because this process is born and dies per refresh and nothing in memory survives it. The entry holds the last line drawn, the armed plan doc's stored path, and the modification times of the two files that line was rendered from, the goal state and that plan doc. A refresh stats both and prints the cached line on an unchanged pair, which costs two stats plus one read bounded at 8 KB and skips the plan doc's read and its parse. Not every render reaches it. The Plans segment takes its position from a walk over the queue's plan docs, and that walk reads as many files as the queue gives it: a plan's archived copy, and every entry past the stored one, both sit outside the pair the key stats. So the walk reports the paths it actually read, and a line is stored only where that report is exactly the one keyed plan doc. Every other render is refused entry to the cache and so is never served, which trades a re-render per refresh for a number that cannot freeze. What makes the refusal hold is that it is decided on what the walk read rather than on a list of the states that send it further, so an input class added to the walk later cannot quietly widen what the key fails to cover. The plan doc is in the key because the goal state is written from four call sites, arm, append, advance and bind (`armGoal`, `appendGoal`, `advanceGoal` and `bindSession`, all in `hooks/kit-goal-lib.js`), so a goal-state-only key would hold a stale section count on screen for the whole span between those events while Chapters land in the doc. The plan doc's time is taken before the render reads that doc (`planKeyMtime` in `kit-goal-statusline.js`), so a write landing between the two stores a time older than the text and costs one re-render, where the reverse order would pin the stale line until the next write.

Blank is the widget having no reading to give rather than a reading that nothing is armed: a project with nothing armed draws an affirmative `🎯 unarmed` line, so a blank widget beside a plan run reads as a fault or a payload older than the widget rather than as an unleashed run. The launcher prints nothing on the failures a status line could not act on either: no installed payload, a payload older than the widget, a widget that will not load. A failure inside a widget that did load is a different answer, and there the last line drawn is printed instead, since a segment that vanishes under load is the failure this caching exists to prevent and a slightly stale line is not. `RENDER_BUDGET_MS = 750` (`kit-statusline.js`) takes that same branch before the render starts. Everything ahead of that point, the stdin read, the payload resolution, the widget require, the cache read and its two stats, costs tens of milliseconds on an unloaded box, an order of magnitude under the bound, so a refresh that has already spent three quarters of a second is one whose host may kill the command before the plan doc is parsed, and whatever arrived before the kill is what the operator sees. That constant is the one knob, and it comes down if a status-line host is found to kill the command earlier than about a second.

Two print paths carry the line, and the split between them is where the file-derived content is bounded. A line the widget just composed is printed as composed, every segment of it already sanitized at construction. A line read back off disk goes through the widget's own `safeLine` first (`kit-goal-statusline.js`), which strips C0 and C1 controls, bidi overrides, zero-width characters, the line and paragraph separators, and lone surrogates, under a 400-character cap, because that line came from a file inside a repository and a clone or a hand can have put a terminal escape or a second line into it since. A payload whose widget did not load has no sanitizer to call, so that one refresh stays blank and the next one that reaches the widget draws normally.

The cache write is one of the two `.kit/` writes that screen their own directory. It lstats `.kit` and requires a real directory, lstats the target and requires either a regular file or nothing at all, and lands through an exclusive-create temp plus a rename, so a symlink, junction, or FIFO planted at either path is refused rather than followed. It never creates `.kit/`, a project without one having no armed goal to draw. A temp file an interrupted write abandoned is removed by any later write once it is 5 minutes old, and the entry is dropped outright when the goal state is gone, so a disarm cannot leave a retired plan's line to be drawn at the next failure. `docs/security-model.md` carries the accepted risk in full, including why the stored plan path is a stat target that must round-trip the goal library's own normalizer and is never opened here.

`test/kit-statusline.test.js` is the gate over the launcher, pinning the in-process path and both directions of the stale-but-drawn fallback, and `test/kit-goal-statusline.test.js` covers the widget, whose CLI entry point stays alongside the exports the launcher calls.
