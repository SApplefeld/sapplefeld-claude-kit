## Goal

The kit's behavior-shaping prose cannot be reviewed by the sessions that run it, because a session that has loaded the corpus grades with the judgment the corpus shaped: it ratifies what it was trained by. Meanwhile the corpus accretes four defect classes nothing currently sweeps: instructions that conflict with each other across documents, incident-born density that machinery has since superseded, operator-approval gates installed before the loop could maintain itself, and assumptions about the harness that Anthropic's own releases quietly falsify. When this plan is done: every rule document has been reduced by cold readers to a list of claims, each an imperative sentence with its bound, its class and its source, beside an inventory line saying what the document is for and when a session loads it; cold readers who never held the corpus have swept those lists for conflicts, duplicates, bloat, and operator-gates; a warm judge holding the corpus's full history has adjudicated every finding against its provenance, so no load-bearing scar is deleted for reading like verbosity, and has written the why of every surviving claim into a rationale ledger beside the document it governs; the kit's beliefs about the harness live in one inventory a release-notes diff can be run against; the first upstream verdict (Anthropic's Subagent Memory feature against the kit's own memory system) is banked so it is never re-litigated; and the operator has ruled on the surviving findings from a batched brief, with the rewrite of the corpus authored as the follow-on plan, one section per rule document in load order, each carrying a declared word target. The audit itself changes no rule text but the one declared line Section 7 adds to the kaizen skill: its deliverables are judgment and the ledger, durably recorded.

## Evidence

- The self-review blindness is already encoded in the kit's own machinery: the blind-reviewer and blind-reader charters exist because loaded context ratifies itself, and this plan is that principle aimed at the corpus instead of at a diff.
- The corpus's density is incident-born by design: the doctrine's staged-index paragraph traces to a real cross-session sweep, re-confirmed 2026-08-29 when the staged-list read caught a peer's four staged files ahead of an expert commit. A cold reader flags such prose as bloat at a high rate, which is why generation and adjudication must be different agents with opposite context.
- The representative-reader argument, the operator's ruling: the corpus's production audience is Opus-and-below (worker seats, implementer tiers, dispatched reviewers), so a confusion that only trips an Opus reader is a real defect, and a Fable-only read would under-report the ambiguity that bites the fleet daily.
- The banked-verdict precedent is the Warden evaluation: evaluated once, verdict recorded in project memory with reasons (`warden-ai-evaluated-and-declined`), never re-opened from the README. The upstream lane adopts that shape per feature.
- The census lane's motivating instance: the kaizen capture nod, retired 2026-08-29 by the operator's standing grant, turned out to be the keystone of a routing architecture spanning four skills (seats forbidden to append, a message leg recorded as a sanctioned pattern on the gate's existence), and the operator's read at the retirement is that the literal phrase is the minority: the population is the semantic family of escalations, confirmations, and waits on the operator, each needing a keep-or-retire call against the loop model rather than a blanket sweep.
- The motivating upstream instance: Anthropic shipped persistent Subagent Memory (the sub-agents page of the Claude Code docs, under Enable persistent memory), reported by the operator 2026-08-29 and unevaluated as of authoring; the kit's assumption that memory needs hand-rolled machinery is exactly the kind of belief no corpus reader can check, because the falsifying evidence lives on Anthropic's servers, not in the tree.
- The 2026-09-09 measurement that promoted the audit: review rounds per section rose from about one in mid-August to 4.3 in the first week of September in this repo and to 3.2 in AI-OS, over the same weeks the executing-work skill grew from 11,900 words to 21,823 and finishing-work from 4,570 to 18,127; `docs/plans/claude-kit_lean-kit_program_v1.md` carries both tables and the reading. A cold reader handed 20,000 words of prose reports a feeling of length; handed a list of claims, it reports two lines that say different things about one moment, which is a finding a judge can rule on.
- The goal library's rule at the head of `plugins/claude-kit/hooks/kit-goal-lib.js`: a linked worktree holds a leash of its own and the main checkout's is untouched by it, so a second leashed session on this repository is the designed case, which is what lets the audit run beside the implementation seat.

## Decisions

Decided 2026-08-29 by the operator in the design dialog.

1. **Hybrid tiering, not end-to-end Fable.** Generators run at the corpus's production tiers: Opus cold readers per cluster, scenario probes at Opus and Sonnet, plus exactly one Fable adversarial pass over the doctrine alone as the deepest surface. Orchestration, adjudication, the upstream verdict, and the operator brief are Fable, because the failure mode there is deference to a plausible finding, and because an orchestrator below its adjudicators inverts the review hierarchy. Rationale: end-to-end Fable loses the representative-reader property and re-buys depth the adjudication pass already provides; the generators are expected to over-report, and the Fable pass is sized for that.
2. **Scope is the behavior-shaping prose: doctrine, skills, agent charters.** Hook code is excluded; the test suite and the code reviewers already police it, and prose is the unpoliced surface. Hook-emitted message text rides only where a finding from the prose sweep leads into it.
3. **A dedicated seat, never the implementation queue's worker.** Review and adjudication stay isolated from the seat doing implementation, on the operator's word.
4. **The audit is read-only and its findings are hypotheses.** Nothing ships from the audit itself: found work is handed off through the Section 8 follow-on plan, per the act-on-found-work rule's own handoff clause, every cold finding is a hypothesis until the provenance trace runs, and the only outward products are the ruled brief, the banked verdicts and memories, the inventory, the follow-on plan, and since decision 6 the ledger.

Decided 2026-09-09 by the operator, at the keyboard and on the relay thread, in the sanity-check dialog `claude-kit_lean-kit_program_v1.md` records.

5. **The audit runs over a claims list, not the prose.** Four passes: the inventory (what each document is for and when it loads), the extraction (every instruction as an imperative sentence with its bound, its class and its source), the overlap and conflict sweep over the extracted lists, and the rewrite from the ruled list. Rationale: the sweeps' readers cannot hold a 20,000-word skill whole, and what they report from prose is length rather than defect; two claims side by side make a duplicate or a contradiction a pointing matter. The scenario probes and the Fable doctrine pass stay on the prose, because they stand in for the sessions that load it.
6. **The rationale ledger is a committed deliverable.** One ledger per owning skill in its references directory, with one heading per document it covers and the claims of each keyed by claim under that heading, loaded by nobody by default and read by a session about to change a rule. Rule text says what happens; the ledger says why; git says when. Rationale: the why inside the rule is what grew the rules, and a why that lives nowhere is re-litigated at the next review.
7. **The follow-on is the rewrite, and its growth is declared.** One section per rule document in load order, each carrying a declared word target and the reason, per the program's first binding decision (a plan that changes a rule file's size states the net words per file and a one-paragraph reason, the plan reviewer judges the reason before arming, and the file's cap moves by the declared amount when the section commits); `claude-kit_test-audit_spec_v1.md` rides beside it because the rewrite reds the wording pins by construction. Scope widens from decision 2 to every document a session loads as instruction: the doctrine and its copies, the output style, every skill body and its references, every agent charter, and the reviewer dispatch template inside executing-work; Section 1 names the paths. Three things sit outside it: hook code and the message text a hook prints, which is a program's output rather than a document a session loads; the probe corpus under `test/probes/`, which a tool reads; and plan documents under `docs/`, which instruct one run rather than the kit.
8. **Concurrent with the tourniquet, in a linked worktree.** The tourniquet is the review-loop provenance plan, `claude-kit_review-loop-provenance_spec_v1.md`, stage 0 of the program. The audit arms right behind it rather than after the queue drains, in a dedicated Fable session holding its own leash in a linked worktree of this checkout. Rationale: the stored queue no longer runs ahead of the audit, so the corpus the audit reads is the corpus the rewrite starts from; what the tourniquet changes in rule text is re-based at Section 5 against the extraction commit rather than waited for.

## Sections of Work

### 1. The inventory and the claims extraction

Model: opus readers, dispatched; sonnet completeness critics, dispatched; orchestration is the session per decision 1.

The documents in scope under decision 7, by path: the doctrine at `plugins/claude-kit/skills/operating-instructions/SKILL.md`, its mirror `home/claude-kit-doctrine.md` (byte-identical under `test/doctrine-parity.test.js`, so one extraction serves both and the ledger records the mirror; the copy at the plugin root is generated and gitignored, and is not a document here), the eight-bullet core pinned inside `plugins/claude-kit/output-styles/kit.md` under `test/output-style-parity.test.js` (extracted once with the doctrine and recorded as a copy), `home/CLAUDE.md`, the rest of the output style, every other `plugins/claude-kit/skills/*/SKILL.md`, every markdown file under a skill's `references/`, every `plugins/claude-kit/agents/*.md`, and the Reviewer Dispatch template, which sits inside the executing-work skill body and is extracted with it. Each is reduced to two artifacts by a cold reader dispatched with the file alone and no intent story. The inventory line: one paragraph stating what the document is for, which moments it owns, and when a session loads it, in one of four load classes: at every session start (the doctrine and its copies, the output style), at every plan run (the run skills and the charters they dispatch), on a named trigger (a skill loaded before a specific act, the memory-system skill before a memq write among them), or on demand. The claims list: every sentence that tells a session to do or not do something, restated as one imperative sentence carrying its bound (when it applies, what excepts it), its class, and its source as file and line at the extraction commit. The four classes close the list: a rule (what must happen), a mechanic (how it happens: a command, a path, a field, a threshold), a pointer (read that other surface for this moment), and rationale and example (why the rule holds, or an instance of it). A sentence that instructs nothing is no claim and is left out: a heading, a narrative aside, a fact about the harness with no act hanging on it. A sentence that constrains an act without commanding one (the definition of a term the act uses, a condition stated on its own) is no claim of its own either; it rides as the bound of the claim it constrains. A pointer counts as a claim only where it tells the session to go and read; a bare citation of where something lives does not. The classes are the vocabulary Sections 3 and 5 rule in, so a reader that cannot place a sentence returns it under the class it leans toward with a note, never omits it. A document over 8,000 words at the extraction commit is split at its `##` headings, and at `###` where a `##` chunk still exceeds the bound, into chunks each with its own reader, the chunk bounds recorded, because a reader handed the whole of executing-work drops claims from its middle. A second reader at sonnet, one per chunk where the document was chunked and one per document otherwise, reads the prose against the finished list and names every instruction the list missed; the misses are appended before the list is accepted. The critic's silence earns itself with a withheld control: one claim the reader found is held back from the list the critic receives, and a critic that does not name it is re-run rather than believed. Every list and the inventory land in the audit worktree's `.kit/` scratch, one file per document. The Section 1 Chapter records the extraction commit, the chunk bounds, and per document the claim count by class, which is the coverage figure the later sections read against. Sections 2, 3 and 4 read the claims lists rather than the prose; Section 5 builds the ledger on them; Section 8 orders the rewrite by the inventory's load class, then by word count within it.

Tests: none mechanical; the gate is the dispatch discipline (files only, no intent story, stated in every brief) and the completeness pass, no list accepted before its critic has run.

Files in scope: none tracked.

### 2. The blind conflict sweep

Model: opus readers, opus and sonnet probes, dispatched; one fable doctrine pass; orchestration is the session per decision 1.

Cluster the corpus into review sets that pair documents governing the same moments (the doctrine with each skill it delegates to; executing-work with finishing-work; peer-sessions with coordinator and role; the reviewer charters with the skills that dispatch them; the session names the full set and records it in the Section 2 Chapter, which Sections 3 and 4 read their clusters from). Per cluster, one cold reader dispatched with the cluster's claims lists from Section 1 alone, no prose and no intent story, charter: find two claims that speak to one moment and instruct differently (a contention), and two claims that say one thing from two documents (an overlap, which the program's one-owner decision leaves as one owner and one pointer), each finding naming both claims by their source. Beside the readers, on the prose rather than the lists since they stand in for the sessions that load it, scenario probes at opus and sonnet: each probe is handed a concrete situation the kit governs (mid-section peer message, failed gate at a boundary, a stale anchor, a park request mid-fan-out; the session authors the scenario set from the corpus's own decision points; these probes are authored fresh for the audit and are distinct from the ruled set under `test/probes/`, which `tools/probe-corpus/run.mjs` runs) and asked what the corpus instructs, with any fork or contradiction it hits reported as a finding. One fable-tier cold pass runs over the doctrine alone, its prose and its claims list both. All reports land in `.kit/` scratch, never `docs/`.

Tests: none mechanical; the gate is the dispatch discipline itself, every reader brief carrying files-only with the no-intent-story bar stated, checked before dispatch, and the Chapter quotes that line from each brief as dispatched, so the check leaves a record rather than an assertion.

Files in scope: none written outside `.kit/` scratch.

### 3. The blind bloat sweep

Model: opus readers, dispatched; orchestration is the session.

Same clusters, over the claims lists with the prose beside them, second charter: candidates for retirement or compression, and the lists' own classes seed them. Every claim of the rationale-and-example class is a candidate by construction, the ledger being where a why goes to live. Every rule whose source passage runs past the two sentences a rule and its bound take under the program's definition of lean (rule text is what needs to happen; a sentence is one idea of about twenty words; a rule and its bound are two sentences; one example survives only where the rule cannot be stated without it, and the brief quotes that definition whole) is a candidate for compression. Every mechanic a hook, a guard or a CLI now enforces is a candidate for retirement as superseded. Every overlap Section 2 found is a candidate for a pointer at the owner. Each finding names the claim, the exact passage, and what the reader believes it could become. The brief states plainly that findings are candidates for a provenance judge and over-reporting is expected and priced in, so readers flag freely rather than self-censoring. Each reader is briefed with the prose bar in `writing-skills/SKILL.md` as amended by the subtraction-bars plan, and a finding names the sentence and the clause of the bar it fails.

Tests: none mechanical; same dispatch-discipline gate as Section 2.

Files in scope: none written outside `.kit/` scratch.

### 4. The operator-gate census

Model: opus readers, dispatched; adjudication rides Section 5.

The claims lists are swept for every claim whose bound names the operator's approval, confirmation, presence, or word: the literal nod family and its semantic kin (escalate to the operator, wait for the operator's call, goes up as a decision ask, on the operator's word). A gate holds the act until the operator speaks; a bound that only informs the operator, that names a rollback without waiting, or that cites a positional grant the operator wrote earlier (a plan header, a standing-grant record) is not one. Grep over the prose seeds the list but does not bound it, because the family is semantic rather than lexical; the retired kaizen routing's own consequence paragraphs never contained the phrase. Cold readers per cluster enumerate the gates their lists carry, reading the prose where a bound reads incomplete, each entry naming the surface, the exact gate, and what it holds up, with a proposed class: a blast-radius gate (irreversible, outward-facing, destructive, or materially consequential acts; the dispatch-authority rail), which the loop model keeps; a loop-maintenance gate (approval to capture, record, adjudicate, or improve the kit's own machinery), which is a retirement candidate under the standing-grant precedent the kaizen capture retirement set; or a genuine operator decision (product, design, risk trade-offs), which stays. The classification is a hypothesis like any other finding: Section 5 adjudicates it, and the surviving retirement candidates ride the Section 8 brief for the operator's batch ruling, because the asymmetry is the ruling's to weigh and not a reader's: a gate wrongly retired removes a safety property, while a gate wrongly kept costs one round-trip. The dispatch-authority rail named above is the role skill's (`plugins/claude-kit/skills/role/SKILL.md`).

Tests: none mechanical; same dispatch-discipline gate as Sections 2 and 3.

Files in scope: none written outside `.kit/` scratch.

### 5. Provenance adjudication and the rationale ledger

Model: fable.

Every finding from Sections 2 through 4 is traced before it survives: for a bloat candidate, whether the passage is incident-born (git history, the memory store, the kaizen archive), whether the incident class is still possible, and whether machinery now supersedes the prose, with retire-as-superseded the only honest simplification and taste never a verdict; for a conflict, whether it is real at execution time or two intentionally different semantics, and if real, which side the history says is right; for an operator-gate entry, whether the proposed class survives the gate's own history, meaning what incident installed it and what blast radius it actually guards. The twelve sections of `claude-kit_kaizen-prose-batch_spec_v1.md` enter this pass as findings and are ruled the same way, each section traced against the corpus at rest and the plans that closed since it was authored; Section 8's follow-on plan carries the upheld ones. Verdicts are keep, rewrite, or retire, each with its reason and its evidence pointer, recorded in a scratch adjudication log the brief is built from. Any surviving rewrite of behavior-shaping wording is flagged for baseline-testing per the writing-skills discipline, to be performed in the follow-on plan, never here.

Then the ledger, per decision 6. One file named `rationale-ledger.md` per owning skill, in that skill's references directory, carrying every document the skill owns under its own heading: a skill's own body and references; the operating-instructions skill's ledger carries the doctrine, its mirror, and the output style; and every charter sits under its own heading in the executing-work skill's ledger, one place rather than a per-charter routing, because a markdown file placed under `plugins/claude-kit/agents/` reads as a charter and the ownership map is keyed by moment rather than by charter. A skill with no references directory yet gets one; the ratchet measures every `SKILL.md` and every markdown file one level under a skill's `references/`, which is what makes the sync below necessary. Each document's heading opens with its inventory line from Section 1 and then carries one entry per claim, retired ones included so the next audit does not re-find them, keyed by the claim's imperative sentence: its class, its source at the extraction commit, its provenance (the commit, incident, memory or kaizen note that installed it, or `no provenance found`), and the verdict (keep, rewrite, retire) with its reason; what a rewrite becomes rides in the Section 8 rewrite spec, never in the ledger, which states current fact only. Before any ledger is written, the worktree merges `origin/main` at the first merge point the Execution surface names, and each document is diffed between the extraction commit and the merged HEAD, the claims in changed hunks re-extracted, which is how the tourniquet's changes to the run skills and the reviewer charters enter without a wait. Nobody loads a ledger by default; the audit reads it, and so does a session about to change a rule, which the rewrite spec states for itself. Each ledger is a tracked file under a measured root, so its cap is created through `node plugins/claude-kit/scripts/kit-size.js sync <path>` on the named paths before the commit, else the ratchet reds on a tracked file no cap names.

Tests: none mechanical for the adjudication; the gate is that no finding reaches the brief without a recorded trace, checked by re-reading the adjudication log against the finding lists, and that every claim has a ledger entry, checked by matching entry keys against the claims list as the re-extraction adjusted it, never by count alone. `test/size-ratchet.test.js` is green after the sync.

Files in scope: `plugins/claude-kit/skills/<skill>/references/rationale-ledger.md`, one per owning skill, the documents each carries placed per the paragraph above and recorded in the Chapter; `test/size-budget.json` through `kit-size.js sync` on those paths alone; `.kit/` scratch for the adjudication log.

### 6. The harness-assumptions inventory

Model: opus.

The opus reader drafts the document under `.kit/` scratch and the session itself lands it at its `docs/` path, since the docs-write guard admits the session and the curator alone. One curated document collecting what the kit believes about the harness it runs on: leash and compaction mechanics, tool contracts, dispatch and messaging behavior, cache resolution, drawn from the doctrine's environment section, the skills' contract-facts sections, and the project memories that record harness behavior. It admits beliefs a release note could falsify and nothing else: not the kit's response to a belief, not a kit rule conditioned on one, and not a belief about the kit's own code, whose falsifying evidence sits in the tree. Each assumption carries its source pointer and what observation would falsify it, so the upstream watch's release-notes diff has a fixed surface to run against, and the document carries one line recording the Claude Code version it was last diffed against, which Section 7 sets at the proving run and each later diff advances. Section 7 consumes it. Curated state only, no journey narration, per the doctrine's document rules.

Tests: none mechanical; acceptance is a blind-reader dispatch over the finished document whose findings are fixed or recorded before the section closes.

Files in scope: `docs/harness-assumptions.md` (or the name `curating-docs` prefers at implementation), its index line where docs/ carries one.

### 7. The upstream watch, proved on Subagent Memory

Model: fable.

The lane's proving run: fetch the current Claude Code sub-agents documentation live (never from training memory, per the doctrine's external-specifics rule), evaluate the persistent Subagent Memory feature against the kit's own memory system on the properties the kit actually leans on (cross-session recall, the applied-stamp evidence loop, the shared tiers, decay, recognition), and bank the verdict as a project memory in the Warden idiom: adopted, declined-with-reasons, or watch-with-named-trigger, so it is never re-evaluated from a headline. The standing watch ships beside it, and its trigger is a version change rather than a calendar: the kaizen skill has no weekly pass (its pass is gated on pending items), so the skill gains one line under the pass stating that the pass runs the upstream diff (current release notes against the Section 6 inventory) whenever the installed Claude Code version (`claude --version`) differs from the version the inventory records as last diffed against, advancing the recorded version and entering its findings in the inbox as ordinary kaizen notes. Declared growth, per the program's first decision: about 60 net words in the kaizen skill. Reason: the watch has no home but the pass and no trigger but the version; the line is the whole of what makes the harness inventory a live instrument rather than a document. The pass predicate that decides whether a pass runs at all is hook code and stays out of scope, so the watch fires inside a pass that runs for another reason, and the section closes by writing a kaizen note asking for the hook-side trigger.
