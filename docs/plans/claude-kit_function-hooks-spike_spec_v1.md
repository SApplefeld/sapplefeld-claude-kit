## Goal

Claude Code 2.1.260 and later carry an early-access prototype of function hooks behind the environment flag `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1`: a plugin module exports `register(on)`, registers Koa-style handlers on engine events, and receives a `$` capability object (store, fs, model, http, process, clock, ui, session). The proposal's author states that whether it ships depends on community response, and the generated type file's header says the surface may change between releases without notice. Four kit surfaces would change shape if it ships: the memory recognition nudge (today four command-hook spawns per tool cycle), the session-start recovery block (today lost at every compaction and re-read by hand), the PreToolUse guards (today one process each), and the judgment sidecar's capture (today a spool, a daemon and a watchdog). Nothing can be planned on those until six runtime facts are measured rather than read: what a module may import, how long a hook may run before it is skipped, whether an in-process nudge says what the command hook says, whether a prompt.context block returns after a compaction, whether a rewritten tool result is what the transcript and a command PostToolUse hook see, and whether a fork at turn end shares the session's prompt cache. When this plan is done: a scratch plugin per probe sits under `spikes/function-hooks/`, loadable only by `--plugin-dir` and never installed; an opt-in live test lane drives each probe through a headless run and reads its evidence from disk; every measurement is in this plan's Chapters with the command that produced it, save the one compaction reading only the operator can take, which the Chapters either record or name as outstanding; the operator-tier record carries the measured facts; and the final Chapter states, for each of the four kit surfaces, port, wait or never, with the measurement that decides it or the outstanding reading that withholds the decision, plus a draft comment for the upstream issue listing what the kit needs and cannot get today.

## Approach

One scratch plugin per probe, each under `spikes/function-hooks/<probe>/` with its own `.claude-plugin/plugin.json` and `hooks/hooks.json`, so a probe loads alone and the one-plain-hook-per-event rule never makes two probes collide. Each probe writes its evidence with `$.fs.writeFile` into the working directory the headless run was started in, which is a temporary fixture directory the test creates, so the jail is the isolation and the test reads the evidence back as a file. The live lane is one test file, `test/function-hooks-spike.test.js`, that skips with a stated reason unless `KIT_FH_SPIKE=1` is set, and under that flag spawns `claude -p` with `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1` in the child's environment, `--plugin-dir` naming exactly one probe by absolute path, `--model haiku`, `--output-format json` and `--debug-file` into the fixture, from `node` directly rather than through Git Bash so no path rewriting applies; the child inherits the box's own login, as the probe run did. A helper takes the fixture's memory directory from `projectMemoryDir(cwd)` and the transcript directory from `sessionTranscriptDir(sessionId)`, both exported by `plugins/claude-kit/scripts/memq.js` (they are separate resolutions, per Evidence), and returns the JSON output, the session id, the transcript path and the evidence file. Where a probe needs a settings-shaped hook beside it, the fixture's own `.claude/settings.json` registers it, so the run depends on nothing installed. Each run costs about five cents at the probe's size; the whole plan runs under two dollars. The offline lane is ordinary: module functions called with a fake `$` and a fake `next`, in the same test file. The generated type file is committed once under `spikes/function-hooks/types/claude-code.d.ts`, because it is the contract every measurement here was taken against, it carries its own version header, and upstream publishes it nowhere else; a later `/plugin-types` run diffed against it is how these findings get re-checked when the API moves. Nothing in this plan touches `plugins/claude-kit/`, its `hooks.json`, or any installed plugin, and the flag is set only inside the live lane's spawned processes.

No contract sweep was needed: the plan adds files under two new paths and edits none of the kit's shared code surfaces; the shared files it touches are `test/size-budget.json`, to add the new test file's cap, and `docs/architecture.md`, whose Repo layout list names every top-level directory and gains one bullet for `spikes/`.

## Decisions

Decided 2026-09-05 by the Expert seat; reversible at arming.

1. **One plugin directory per probe, loaded one at a time.** A plugin may hold one plain hook per event, and the recognition port and the redactor both want `tool.call`; separate plugins keep each measurement clean and let a probe be re-run alone. Costs a few duplicated manifest files.
2. **The spike lives at `spikes/function-hooks/`, a new top-level directory, and ships nothing.** Under `plugins/claude-kit/` it would enter the build and the installed plugin; under `test/` it would enter the size ratchet and read as suite fixture; under `.kit/` it would be gitignored and lost. The `sidecar/` directory is the precedent for a top-level non-plugin component. Reversal: a move.
3. **Haiku drives every live run.** The probes measure the harness, not the model; the one probe that reads model output (section 4's answer check) needs only that a placeholder be echoed.
4. **The type file is committed under the spike, once.** Argued under Approach. Reversal: delete it and rely on the version string in the Chapter.
5. **The ordering question in section 4 is answered by a fixture-registered PostToolUse hook, never by the sidecar's spool.** The spool is consumed by a daemon whose timing the test does not control; a command hook the fixture registers receives the result through the same payload field the sidecar's capture reads, so it answers for the class without the race.

From a terminal at the repository root with the recovery probe built: from Git Bash run `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1 claude --plugin-dir "D:\claude-kit\spikes\function-hooks\recovery"`, or from PowerShell set `$env:CLAUDE_CODE_ENABLE_FUNCTION_HOOKS = '1'` first and then run `claude --plugin-dir "D:\claude-kit\spikes\function-hooks\recovery"` (the absolute path either way, so the plugin resolves wherever the session's working directory is). Before asking anything, read the probe's store file under `~/.claude/plugins/store/` and note its contents, since the file persists across every run that loaded this probe and the test's own runs leave their counts in it under their session ids. Then ask for the fixture token, type `/compact`, ask for the token again, then `/clear` and ask once more; then read the store file again and report both readings. Three tokens answered and a count of three under the key that appeared for this session means the block returns after both; anything else is the reading, reported as it is. The section's Chapter records the report or that it is outstanding, and section 6 reads that line before it opens.
