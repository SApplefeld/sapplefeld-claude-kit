# Fleet Integration

The kit runs inside sessions an external engine spawns, and this document is the contract between the two. The engine in question is the AI OS Spine, which delivers the kit per spawn with `--plugin-dir <payload>` rather than a per-account plugin install, sets a marker on every worker, and reads three of the kit's surfaces back. Everything here is the kit's half: what the engine must set, what the kit does with it, and where a mismatch shows up. `architecture.md` describes each mechanism in its own section, and `security-model.md` states what the gates buy; this document is the assembly.

Delivery through `--plugin-dir` is the reason the seams exist at all. A plugin loaded that way still fires its SessionStart, PreToolUse, PostToolUse, PreCompact, and Stop hooks, and `CLAUDE_PLUGIN_ROOT` still resolves to the payload directory, so every ambient hook the kit ships runs inside a worker exactly as it runs in an attended session. The marker is the only signal that separates the two.

## Environment contract

Nine variables carry the whole contract, two of them gate signals that must never arrive without the variable they gate. The kit's rule is that every environment override redirecting a path takes a second signal, so an override arriving alone is ignored with a note on stderr rather than honored.

- **`KIT_EXTERNAL_ENGINE=1`** declares the session a spawned worker. It redirects nothing and takes no second signal, because the engine setting it already controls the spawn outright.
- **`KIT_MEMORY_ROOT`** with **`KIT_MEMORY_ROOT_ALLOW_DATA=1`** points the memory store at the engine's per-instance store. The pair is load-bearing twice over: it selects which memory content reaches the model, and it is the condition the memq grant hook checks before allowing anything.
- **`KIT_MEMORY_PROJECT`** pins the store's `projects/<segment>` directory, which is otherwise derived from the worker's working directory. Set it on every spawn. The engine's three spawn shapes carry three working directories (the reviewer and the phone-driven worker run in the instance directory; a plan worker runs inside the repository it is working on, or a per-branch copy of it), so without the pin one instance's store fragments into a tier per working directory and a memory promoted out of a plan run lands where no later run and no reviewer ever reads. Omitting it does not fail: it fragments, and for the two spawn shapes that carry no run id (the reviewer and the phone-driven worker) the project-memory block then names the cwd-derived directory as the destination in the kit's own voice, so the fragmentation arrives stated rather than merely guessed at while nothing reports it as a misconfiguration. That is the failure worth designing against. Honored only alongside the store pair above, carrying no separate signal of its own for the same reason `KIT_RUN_ID` carries none, and answering the same directory-name grammar. Set it explicitly rather than relying on inheritance, which beats a value inherited from the parent environment; it does not beat configuration that runs inside the spawned session's own shells afterwards. Three behaviors to model. Under a pin the project tier's content is fenced on the way into a session's context, because the worker that wrote it is not the session reading it back. Anchor drift is not checked at all under a pin, and every surface says so rather than reporting clean: a pin names the project directory the store reads and says nothing about the working directory, so no root is derived, `memq get`, `recall` and `decay-scan` answer not-checked with the pin as the cause, and the session hook's drift line stays silent. And a session with no run id is told the pinned directory as its memory destination, with `MEMORY.md` beside it as the ordinary index, unlike a run's pending tier, alongside that pinned tier's own index lines under the same reduction and caps the type index gets.
- **`KIT_RUN_ID`** scopes the run's memory writes and reads. It is honored only alongside the store pair above, carries no separate signal of its own because it selects a subdirectory inside an already-gated store, and its value becomes a directory name, so it must satisfy a conservative token grammar of at most 40 characters that also refuses the Windows spellings aliasing onto a different directory than they name (dots-only, trailing dots, reserved device stems). A value failing the grammar is refused loudly rather than fallen back on.
- **`KIT_SPAWN_VECTOR`** and **`KIT_RUN_SECTION`** are optional provenance. They redirect nothing and are recorded in a pending memory's frontmatter.
- **`KIT_EVENTS_PATH`** with **`KIT_EVENTS_PATH_ALLOW=1`** redirects the goal event sink. Both or neither: an engine setting the path alone does not fail loudly to its own watcher, it keeps writing to the default `~/.claude/kit-events.jsonl` that nobody is watching, so shipping both together is a deployment precondition rather than a convenience. One consequence reaches past the engine's own watcher: a machine-coordinator seat reads the default path for `goal-blocked` events as the backstop that catches a worker which died before it could message anyone, so a session spawned with the redirect is invisible to that backstop and reaches the seat by its own message or not at all.

## Hook stand-down

Under the marker, nine hooks change behavior and the rest run unchanged. `session-start.js` drops its drive-to-completion push and emits the In Progress plan inventory as plain information followed by one line stating that the engine's directive owns scope and continuation. Its compact-source re-load block still fires but names no skill of its own, saying "the skill the engine's directive names" where an attended session is told to re-invoke executing-work, so a compacted worker is not handed the loop the plan block withholds. Its other five blocks are unaffected, the backlog block included: a worker in a repository holding a `docs/backlog.md` still receives the item count and oldest-item age. The shared-checkout advisory is one of the five and fires in a worker exactly as it does in an attended session, since a spawned worker sharing a working tree with a live session is the same collision the line exists to name. `branch-reaper-nudge.js` and `kit-version-nudge.js` emit nothing, and `hook-canary.js` returns before its first child spawn. All four ask for something an attended operator would do and a headless worker cannot. `stop-docs-hygiene.js` keeps running but downgrades its blocking outcome to advisory text carrying no decision, so a worker is never held at its turn end for a library-hygiene pass its directive does not cover. `kit-compact-gate.js`, the PreCompact gate, allows every auto-compaction rather than deferring one, and the marker is checked ahead of both of its deny paths, so neither the boundary schedule nor the interactive deferral applies in a worker. A worker is fresh per section, so there is no mid-chapter context for a schedule to protect, and it is unattended, so there is no discussion for the interactive deferral to keep intact; a worker therefore compacts at whatever trigger the machine's `autoCompactWindow` sets. `chapter-boundary-nudge.js`, the PostToolUse hook that reminds a leashed session of its chapter-close checkpoint, emits nothing for the same reason read from the other end: with no compaction schedule to protect there is no checkpoint to owe, and a worker that is fresh per section has no boundary ritual to be reminded of. `compact-deferral-nudge.js`, the PostToolUse hook that tells a held session the gate is holding auto-compaction offers, whether that session holds the leash or is being held on the gate's hands-on leg with no leash at all, stands down on the same reasoning and one step earlier than its siblings: the marker check runs before the hook takes its interval stamp, so a worker gets neither the reminder nor the write. With the gate allowing every offer in a worker, there is no hold for it to report. `memory-recognition-nudge.js` stands down on the same scope reasoning, and its check runs before it resolves a store at all: a worker is fresh per section and works to a directive rather than to a project's accumulated memory, so a recognition nudge has no store-reading session to serve. Those four are the stand-downs taken for a scope reason rather than an attendance one.

Everything else stays live deliberately: the doctrine refresh, the memory wiring, all five PreToolUse deny guards (`memory-frontmatter-guard.js` among them, so a worker's hand-written memory record meets the same write door an attended session does), the grant hook, the three PostToolUse hooks the marker does not touch (`format-on-edit.js`, `memory-usage-stamp.js`, and `kit-sidecar-capture.js`, the judgment sidecar's capture-and-delivery hook, which stays live because subagent and worker coverage is part of that design and the hook is dormant anyway on any machine whose judge daemon has never created the spool root), and the goal leash. Guards and memory are wanted inside a worker, and the leash needs no marker of its own, because nothing an engine directive does can bind one. A session holds the leash in one of two ways: it ran the `/kit-goal` arm CLI, which binds the session its own shell names once it corroborates that id against a transcript on disk, or its transcript carries the user's own arming text, a plan path inside a `/kit-goal` command-argument span or a message leading with the `/kit-goal` token whose argument block names the plan. A directive is prose that runs no arm, so a worker whose directive merely names a plan is a bystander.

Three controls go with the canary and are worth naming rather than discovering. Its SHA-256 integrity check over the shipped hook files does not run in a worker, so payload tampering is undetected there and payload integrity is the deploy's concern. Nor do its both-direction probes of the memq grant, which means a grant gone inert in a fleet worker produces no signal at all beyond the worker quietly losing memq. Nor do its both-direction probes of `memory-frontmatter-guard.js`, whose allow half is what catches a guard stuck at deny; in a worker that guard sits in front of every `Write`, `Edit`, and `MultiEdit` with nothing probing either direction of it.

## Run-scoped memory

A run's memory writes are quarantined by scope rather than withheld. Every new memory file lands in `<store>/projects/<segment>/memory/pending/<run-id>/`, where `<segment>` is the pin when one is set and the sanitized working directory otherwise. Under the pin this contract mandates it is always the pin, and that is the path an adjudicator promotes from. The file is stamped with `run:`, `written:`, and the optional `vector:` and `section:` provenance. The run reads its own pending memories back through `find`, `get`, `recall`, and `recent` exactly as it reads the project tier, with `get` resolving pending ahead of project and `recent` counting the tier's stamps and files alongside the others'. What the tier withholds is entry into the shared record, and that is the engine's half of the contract: promotion of a pending memory into the project tier and the `MEMORY.md` index line that goes with it are an adjudication verdict the engine applies. The kit writes neither.

Two limits belong in the engine's model of this. The scoping is a resolution rule, not an enforced boundary: a process resolves the one directory its own `KIT_RUN_ID` names and enumerates no others, so cooperating runs do not see each other, but nothing stops a session holding Bash from naming a different id. And the tier bounds the project record only. `memq log` appends to the project-tier journal with a `run` field rather than rerouting, and `memq add-type` writes the shared type tier and its index directly, provenance-stamped rather than quarantined. Under a per-instance store the reach of both is that instance, which is why the store root the engine chooses is what actually does the containing.

## The memq grant

The engine's write-gated spawn vector refuses `node <script>` through the Bash tool, which would cost a worker memory recall and outcome logging, so `memq-grant.js` allows exactly that one command and nothing else. It grants only when the store pair is present, the command is one `node` invocation whose first argument resolves by normalized path equality to the payload's own `scripts/memq.js` in an absolute spelling, drive-rooted where the host is Windows, the interpreter on PATH is positively identified as the hook's own, the subcommand is one the hook's own list of granted verbs names, and the command line is clean. Clean means more than metacharacters, and the extra classes are worth knowing because an ordinary command can hit them: no C0 control byte or DEL anywhere, tab excepted; no word separator other than space and tab; no backslash outside quotes and none before a quote; no unquoted brace, glob character or bracket; no unquoted tilde opening a word; no unquoted word beginning with `#`; and no unterminated quote anywhere in the line. Each of those is a spelling on which the words this hook reads and the words bash builds diverge, and a screen reading a different word list than the child receives is no screen at all. On anything else it stays silent, and on this vector that silence is the Bash refusal above rather than an approval: a command the hook declines to grant is a command the worker cannot run.

One coupling runs the other way and the engine owns it. The hook refuses the grant outright whenever `NODE_OPTIONS`, `NODE_PATH`, or `NODE_REPL_EXTERNAL_MODULE` is set at all, since node honors all three in the granted child. An engine that sets any of them ambiently on its spawns turns this grant dark, and one ordinary configuration does it: a benign `--max-old-space-size`. Workers keep running and quietly fall back to the vector's deny, losing memq with no error anywhere. Over-refusing is the correct direction for a grant surface, so the behavior is deliberate, but the engine's spawn environment therefore decides whether fleet workers keep the memory CLI. The plugin cache's own path is a second such switch: the hook refuses a command line carrying shell metacharacters, the quoted script path included, so a cache under a path with parentheses, `$`, or `&` in it (a `Users\Name (Work)` profile, say) is never grantable, and workers there lose memq the same silent way.

What a worker can do prompt-free is set by a list of granted verbs rather than by a list of refused ones, and the direction matters to an integrator. The granted verbs are `log`, `get`, `recall`, `recent`, `unstamped`, `touch`, `add-type`, `add-operator`, `decay-scan`, `decay-prune` and `decay-done`. Every other word in that position withholds the grant, which today means five verbs. `delete-type` and `delete-operator` are withheld because their destruction leaves no local recovery. `find` is withheld because its semantic channel loads an embedder package in process from a directory resolving under the home directory, which no environment screen can constrain because `HOME` is always set. The two authoring verbs reach that same load at the neighbours block they print before a creation, and `decay-scan` at the neighbour-pairs block it prints after its drift block, and all three stay granted because each block stands down before the load whenever `KIT_MEMORY_ROOT` or `KIT_EMBEDDER_ROOT` is present at all, a condition the granted child's own environment answers and one wider than the store pair the hook conditions on, so a granted `add-type`, `add-operator` or `decay-scan` prints a not-checked line in the block's place, one per tier for the scan, and loads nothing. `anchor` is withheld on what it authors rather than on what it destroys: it rewrites a project-tier record's `anchors:` line in place at a name the command line gives it, so a worker could re-anchor a memory onto whatever the tree holds now, and every drift surface would then report that memory verified when nobody read it. `triggers` is withheld on that same account at the record's other half: it rewrites a record's `triggers:` line in place on any tier, the two shared tiers included, and that line is what decides when the memory is put in front of a session, so a worker could aim a record's recognition wherever it liked, or crowd the line to the entry cap so the triggers the operator wrote go unread, with nothing on any surface saying the declaration changed. Its reach is wider than aiming and crowding, and the wider half is the quieter one: `--replace` states that line whole, so it removes every entry the invocation does not name, and naming none removes the line outright. An aimed trigger fires somewhere a reader eventually notices; an erased one leaves a record that simply never surfaces again, on every machine the store syncs to. A shared-tier replace requires `--confirm-shared`, which is a typo guard rather than a second lock on this vector, being a token on the same command line the grant would already cover. `anchor` and `triggers` are two of the three withheld verbs the CLI does not also refuse for itself, `find` being the third, so this list is the whole of what withholds `find` and `anchor`, and for `triggers` it is the whole of what withholds every shape but one: a `--replace` reaching a shared tier or a pinned project store is refused inside memq under these same signals, that being the shape which erases a declaration rather than authoring one. The deletes are the contrast, refused a second time inside memq for every shape they have. The canary probes `find` in both directions and `anchor` and `triggers` in neither, and `docs/backlog.md` carries that gap as an item. It also means any verb memq gains later, until this list learns it: a new verb is not prompt-free on arrival, and the symptom is the same silent fall-through to the vector's deny. That is the correct direction for a grant surface, and it is the same trade the preload variables make.

Seven flag shapes withhold the grant wherever they appear in the line, each matched as a whole word or carrying an attached value, so a write verb keeps the grant only without them: `--body-file`, which names a file the CLI reads into a record; `--update` together with `--body`, which is the shared-tier body repair; `--supersedes`, which points a new record at a live one and thereby demotes and labels it; `--trigger`, which declares at creation the moments that later put the new record in front of a session, the same line the withheld `triggers` verb writes; and `--rollup`, which runs both halves of the age-based compaction: it folds every expired journal entry's prose into a tally, and it prunes each tier's usage sidecar, folding raw applied stamps into a rollup and keeping read stamps newest-only. Both leave what they replaced only in a local `.bak` no sync carries. The sixth is `--drop-malformed`, which rides `--rollup` and removes outright the unparseable usage lines every other read path and every other rewrite preserves, leaving them in that same backup and refusing any tier where no parsed stamp would survive the drop. The seventh is `--type=<type>`, and it is the one shape of the seven matched only with an attached value rather than as a whole word too, because the bare `--type` keeps its grant: bare, the flag resolves the calling project's own declared type and nothing else, while the attached spelling names any type tier the store holds, so what is withheld is the naming of a foreign tier rather than the flag. The CLI refuses that spelling under these signals as well, at the two granted read verbs, so this one is not the hook alone. memq refuses the first four itself under the store signals, so the hook's screen on those is a second lock rather than the only one, and `--drop-malformed` has one of a different kind: without `--rollup`, which the hook also withholds, the CLI answers it with a usage error. `--supersedes` is one of two of the seven withheld on which records it can reach rather than on how much it does to one, `--type=<type>` being the other, and it is worth an integrator's attention because that reasoning does not follow the rest. Its effect is light in the sense that matters here: nothing is destroyed, the target stays live and fetchable, and the pointer only demotes it in the semantic ranking and labels it. Reversible it is not, on this vector: a pointer is unwritten only by deleting the record carrying it, and both delete verbs are refused here. What is not light is its reach. Every other granted path that *retires* a record stops at a pin, `decay-prune`'s archive flags being refused against a pinned name outright, and this one is bounded by no pin at all, while `decay-scan` is granted and prints the pinned count with the first ten names. So a worker with nobody in the loop could enumerate the operator's own exemptions and demote them in one further command, which is the capability the screen exists to withhold. Read that as a claim about retirement and rank rather than about pins generally, because the pin is narrower than it looks on this vector: `pinState` is consulted by the scan, the prune, and the archive gate and by nothing else, so the granted description-only `--update` already rewrites a pinned record's index line, which is the text the session hook emits and the only text the lexical channel matches on. That is an accepted risk of the grant rather than something this screen changes. The worker keeps the write itself: an ordinary `add-type` or `add-operator` still lands, carrying every other field. What it does not keep is a way to add the pointer afterwards, since the flag is creation-only and `--update` refuses it, so recovering the pointer means an attended re-run of the whole add, and for a record that already landed, a delete and a fresh write. `--rollup` has no second lock: the hook is the only thing withholding it, because the CLI cannot refuse it on the store signals without taking `decay-prune`'s archival half with it, and archival is the half a worker's decay pass is for. One flag runs the other way and that same pass needs it: `--confirm-shared` is not screened here at all, while the CLI requires it alongside `--archive-operator` always, and alongside `--archive-type` once more than one project declares the type or the declaring-projects scan cannot be run, refusing the whole pass rather than part of it when it is missing. That refusal is loud, which is what separates it from the preload variables above rather than making it their twin: memq names the missing flag on stderr and exits 1 with nothing archived, and the grant permits the flag, so a worker that reads its own stderr re-runs and succeeds. What loses the pass outright is a fixed command line whose stderr nobody reads. Recall is the verb an engine's own loop depends on and nothing touches it, but a worker written to search the store by meaning, to roll up its journal, to repair a body, or to delete a shared record needs its engine to reach those some other way.

Two further facts bound what the grant means. It conditions on the store pair alone, so under the pair without a valid run id a granted memq writes the project tier directly rather than pending. And it is agent-blind: a read-only judgment agent running inside a worker gets prompt-free memq writes, which `security-model.md` records with its compensating controls and their limits.

## What the engine reads

Three surfaces flow back out. The goal event stream at `~/.claude/kit-events.jsonl`, or wherever both events variables point it, carries one JSON object per line; inside a run each line gains a `run` field carrying `KIT_RUN_ID`, and only a value the kit's own run-id grammar accepts, so the event stream and the memory store cannot disagree about what a run id is. The field's presence says the process was told a run id, not that run-scoped memory was active, because the pending tier additionally requires the store pair. The full consumer contract, field caps, PII call, and dedup rules are in `architecture.md` under Goal release events. One cadence property matters to an engine reading the stream as run telemetry: an arming may name a sequence of plans, and the stream then carries one event per plan rather than one per run, each naming the plan that finished under a single unchanging `session`. Only the last of them coincides with the leash releasing, so a `goal-complete` says a plan is done and never that the worker is.

The pending tier is the second, read by the adjudicator that promotes from it. The plan doc is the third, and its header and structure are a frozen v1 machine contract: eleven parsed shapes, each case-sensitive and anchored to the start of a line, five of them carrying a value rule the engine enforces silently rather than loudly. A plan may also carry an `## Assumptions` section between `## Out of Scope` and `## Chapters`, holding the assumptions the plan was approved on; it adds no row and is inert to the parser, and the kit freezes it at approval and routes every execution-time assumption to the Chapters instead, so the region the approval-scoped fingerprint covers is not rewritten by ordinary progress. A plan may carry a second inert section, `## Dispatch Authorization`, recording who authorized arming it and which sessions the grant covers; it adds no row either, and the kit places it above `## Sections of Work` rather than merely outside that block, since no template reserves a position for it and a `##` heading landing inside either bounded block truncates the block silently. Both sections sit above `## Chapters` and so inside the fingerprinted region, which is why the kit treats adding either to an approved plan as approval drift to record rather than a drive-by edit. The `## Chapters` block carries a second entry kind alongside the Chapters themselves: a run that goes long with work in flight and no section closing appends an `### Interim board N - YYYY-MM-DD` entry recording each in-flight section's stage, the live dispatches and what each was asked, the current gate baseline, the rulings adopted since the last boundary, and the next action per section. That heading cannot match the parsed `### Chapter N` row, which reads only the literal word and the number, and the entry carries no `Completed:` line, so a Chapter's own completion and next lines are still the first ones the engine finds. The `curating-docs` skill owns the table and is the normative reference, with pointers from `brainstorming`, `executing-work`, and `writing-skills` so the rule sits in the skill a session has loaded at the moment it writes a header or a Chapter. The `Model:` value rule is one of the silent ones: the engine accepts only the bare tokens `haiku`, `sonnet`, `opus`, and `fable`, downgrading anything else to a sonnet default with no error, and the kit's skills emit only those bare tokens, with a section's execution locus carried on its separate `Locus:` line that no consumer parses. Changing the shape or value rule of any row is a coordinated versioned change across both repositories, never a drive-by edit to plan-doc prose.
