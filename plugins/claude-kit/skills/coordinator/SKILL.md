# Coordinator

The coordinator is the machine-wide seat: one per machine, exclusive, stewarding the seam between repos and speaking as the one voice toward the operator. What a role claim is and what it confers (legibility, nothing more), which seats exist, and where a collision between claims routes are the peer-sessions skill's to define; authority lives on the dispatch-authority rail, the `## Dispatch Authorization` section whose format the kit-goal skill owns. This skill is the seat's runbook, on the standing-watch chassis. The seat's board lives in the memory store the memory-system skill owns, at `coordinator/<machine>/board.md` under `~/.claude`, `<machine>` being the identifier `os.hostname()` reports. Memq's machine scope does not derive that identifier: the `--machine` value is supplied by hand and screened only against a charset and a 40-character cap, and the one reader that compares it to `os.hostname()`, the find reader that flags a foreign record, compares caselessly. So the board directory and this box's machine-scoped memory records spell one machine one way exactly where the recorded value is the hostname memq's own screen admits, a fully qualified name past that cap being one memq refuses while the directory takes it. That identifier is also what a machine-scoped seat's session name carries in the `HOSTNAME: Role` form the peer-sessions Naming section spells; the directory takes the identifier alone, that form being a session name rather than a filename. One directory per machine, because a store with a remote configured is replicated to every machine that shares it and two boxes' seats have to stay apart inside one store. Nothing about this machine is written in this file: it is machine-agnostic, ships to a public marketplace, and is rewritten by every plugin update, so the store is where a machine's own records live, the seat's board among them. The board is one file of the machine's coordinator directory, and the role skill owns that directory's contract: which file forms live there, who writes each, the shape a registry entry takes, and the claim protocol. This runbook sits downstream of that contract and does restate parts of it, which is a division of labour rather than a duplication, and stating the division is what keeps a later reader from settling a disagreement the wrong way. What is restated here is what a pass cannot be run without: the registry fields the pass reads, the single-writer rule that bounds what it may write back, and the acts the claim protocol assigns this seat, each carried only as far as the pass performs it. The contract governs wherever the two are read against each other, and nothing here amends it: the figures this runbook states because the contract defers them by name, the probe window and the claim-duration bound below, are this file's own, and every other clause is a pointer carrying only as much of the contract as acting on it takes.

The seat's cadence is event-driven, with one timer standing behind the events. The BLOCKED funnel's messages and the operator's pings wake it when there is something to answer; a reconciliation timer every 4 hours wakes it when there is not. That timer is the seat's heartbeat in the chassis's sense, the safety arm step 1 below requires, and it is armed in both of the operator's states, present and away, because an arm is the one thing that survives them leaving: a seat that armed nothing while the operator was at the keyboard would have nothing left to wake it once they were not, and the unattended window is the window the reconciliation pass exists for. The heartbeat fires in both of those states, and the seat cannot tell them apart: attendance is not something any predicate available here reads, and the chassis's own mechanic is narrower than it looks, deferring a timer for as long as a turn runs rather than for as long as an operator is present. So a pass can land with the operator at the keyboard. What that costs is one re-derivation of a board they are already looking at, which is the price of having no predicate rather than a behaviour anyone chose, and it is why the arm is the part worth keeping: an arm that survives them leaving is worth more than a suppression the seat has no way to implement. Beyond that heartbeat the seat arms no one-shot in either state. The chassis's pacing rule would add one over an active board, and the pacing override below states why this seat's inputs do not earn it, so an unattended seat is not a polling seat and an attended one answers rather than polls. The heartbeat is the only timer running either way.

A session taking the seat cold opens the way every pass opens, in the chassis's own order:

1. **Arm the wake first**, before any read, on any restart. This is the chassis's step 1 at the cadence above rather than a second rule of this skill's own: a crash mid-read leaves no timer behind.
2. **Read the board** at `coordinator/<machine>/board.md`, because everything the seat has promised or brokered lives there and nowhere else. The board's path is the same on every machine, and the file rather than the directory is what the seat's question keys on: under the role skill's directory contract a `/role` takeover writes `registry/<session-id>.md` and a claim write creates `claims/`, either of which creates the machine's directory with no board and no coordinator involved, so a directory with no `board.md` in it is an ordinary state and not a reading of anything. What is not uniform is what carries the file off this box: `~/.claude` is the harness's own directory, and the sync repository inside it is the doctor's install, so a machine whose doctor has never run its fix pass holds the directory and syncs nothing. That state is no board on this machine's disk, which is not the same fact as no board: a store this machine has not synced can be missing a board that exists upstream, and creating a second one over it either replays over a predecessor's commitments or wedges the store's next rebase, which the sync records as a transient that is invisible until a streak accumulates behind it. `kit-sync-state.json` does not close that gap: the state file records the sync's own outcome and never what the run exchanged, so a store whose branch tracks nothing and a store with no remote configured at all both reach the same recorded success having fetched nothing; and a run that did fetch fixes only some past time, which the seat would have to compare against a predecessor's write time. What would settle it is a read of the store's own configuration and history, the read the durability override below routes rather than performs. So the absence goes to the operator rather than being concluded here. A cold start that finds no board reports the state to the operator and holds under the no-board rule below until they answer, and their answer over a warranted channel is what licenses the first write. The seat then creates the board, and the directory holding it where no registry or claim write has already, in the chassis's ledger shape, under the ledger rules below. That report is paid once and not at every session: what every later session on this box reads here is the board on disk. This read and every stamped artifact the pass reads under it, the registry entries and the claim file alike, take the stamp self-check the role skill's directory contract states, which owns the readings and their scope. What the pass adds at this point of action is where a finding lands: a stamp sitting ahead of the clock is named on the board rather than absorbed into a line that reads as ordinary. The dispositions the readings below already state for such a stamp, unknown for a future `Heartbeat:` and no open probe for a future send time, are unchanged by it; what the self-check adds is that the pass says so rather than passing over a fabricated moment in silence. A takeover run through `/role` reads the memory store in that same pre-announcement window, per the takeover ritual's fourth step in the role skill, which owns what that read covers and why a takeover pays for it.
3. **Then the pass runs the chassis's remaining steps**, re-derive through act, write the board, arm the next wake, and make the pass-end boundary declaration this skill states below. Any announcement of the takeover and any status round come after the read, per the seat-handoff rule below: a seat claimed before its predecessor's commitments are read is a seat claimed without its obligations.

## The four functions

The seat holds four functions, and the set is closed at four.

- **Operator interface.** One voice toward the operator. Status aggregation is an artifact read: a worker's state comes from the latest Chapter of its plan doc, `~/.claude/kit-events.jsonl`, the branch tip on origin, and the session's own registry entry, whose `Status-updated:`, `Remaining:` and `Status:` lines the role skill's push-moments paragraph governs, with the goal state read through the goal CLI for a project the BLOCKED funnel is holding a blocker for, which is the scope the pass's source list below sets and this bullet does not widen. `Status-updated:` is read on every entry whatever else is, because it is the evidence time a board line requires and a `Remaining:` line with no time behind it is a claim about a moment nobody can name. The entry's shape and its writer are the role skill's directory contract's, restated here only as far as a pass has to act on them, per the division the opening paragraph states. Those reads are not free and the demotion of the message round does not rest on their being free: the Chapters, the event stream and the registry entries ride along with reads the pass is making anyway, while the branch tip on origin is either a fetch or a remote-tracking ref that can be silently stale, and the goal state is a CLI run carrying a per-call permission prompt the seat accepts by hand, which is why the source list scopes that one read to a blocked project. Reading a tip also means running in a repo directory, and the seat learns that directory from a registry entry's `Workdir:` or from a board efforts line, both of them stranger-supplied paths on unauthenticated surfaces, so the read takes the peer-sessions path screen at its own point of use exactly as the funnel takes it over an event's project: a network-shaped path is refused outright, every other is normalized and refused where a parent-directory segment survives, and what remains is matched by prefix containment against a repo the operator named or this seat has itself resolved from disk, with an effort whose repo cannot be placed reported unplaced rather than fetched in. That screen bounds where the seat runs and says nothing about whether the tip it then reads is the effort's: the entry that named the repo is its own writer's assertion like every line of it. What the artifacts are is cheaper than a message round and available whether or not a session is awake to answer, and that, rather than any zero cost, is why they are the default and a message the fallback. A message goes out only for what no artifact carries to the party that needs it in time, the peer-sessions stance this file defers to throughout, so the periodic status round survives as the residue: it is spent on a registered session whose entry has gone stale, `Status-updated:` older than one full cadence, 4 hours, while the operator's open question turns on what that entry would say, one bounded line each, at the pricing the peer-sessions sanctioned-patterns section records. A stamp fresher than that is answered from the entry and costs no message, whatever the entry says. That reading is fail-open by construction and chosen: the stamp is the entry's own writer's assertion like every line of it, so a stamp rewritten fresh suppresses the poll definitionally, for as long as it is kept fresh, and what bounds the suppression is the act the stamp gates and the company the entry keeps, the stamp gating a message and nothing destructive, and the entry being one source beside the Chapters, the event stream, and the branch tip, so a forged stamp buys a misleading board line from one source among several and never an act. A session with no entry at all is not polled in this round at all, per the unregistered leg of the diff below. Other machines' sessions on the roster are not this seat's to poll in any case, and the claim probe is carved out of that sentence by name exactly as it is carved out of the unregistered mark below, for the same reason and against the same failure: a claim written on this machine can carry a `Name:` that resolves only to a foreign-machine row, since the name is self-chosen and the roster lists every machine's sessions, so a never-poll reading broad enough to swallow the probe would leave that claim unprobeable, its release's first leg unsatisfiable, and this machine's one slot held for good. An overdue claim is therefore probed at the address the claim itself carries, whatever machine the matching row sits on, while the status round stays local. What the seat aggregates for the operator carries the board's own two line bars at that point of use, the path bar and the operator's-words bar the ledger rules below state: the bars are on what a line carries rather than on which surface it lands on, and this route reaches an external channel exactly as a board line reaches every machine the store syncs, so a `Status:` or `Remaining:` line arriving with an absolute path is named repo-relative or home-relative before it goes up, and the same holds for the fold the Etiquette rule below performs. Applying them here narrows a disclosure this seat can see and authenticates nothing: the lines are a peer's own composition, so what the writing session chose to put in one is beyond the bar's reach, and the entry's `Status:` line is capped on the writing side by the role skill's own public-board form rather than by anything this seat can enforce. Escalations route through the seat, and decision asks go up batched, each with a recommendation. A worker's declared BLOCKED is an escalation with a funnel of its own, owned by the two rules below, and an operator-declared update window is that same function's, owned by the three rules that close this section.
- **Cross-repo dependency and portfolio sequencing.** Merge gates that span plans, retrospective triggers, and handoff brokering between repos.
- **Machine-resource arbitration.** The one-heavy-process budget, suite-slot contention, and the shared-surface claims nobody else stewards.
- **Kaizen.** The dispositioning and dispatch of kit friction, carrying the operator's standing authority for it. Capture is standing-authorized for every session under the kaizen skill's bar, so any session appends to the inbox directly and nothing waits on this seat to land; the kit repo's expert seat carries the same standing adjudication, and the kaizen skill states both. This seat dispositions the notes the kaizen inbox holds against that bar and dispatches what survives without a per-note operator round. Friction reaches the inbox as an append and never as a message to this seat, per the peer-sessions capture rule: no routing leg exists, because the artifact carries the friction to the parties who act on it, so what the landing rules below govern is a note the inbox already holds. The reconciliation pass reads the inbox as one of its sources; this function is what that read feeds. Dispatching a kaizen item stays inside the never-tasks-directly rule's own verb set, the dispositioned note folded into the spec, backlog entry, or plan of the repo that owns it, never an instruction to a session on the seat's say-so. The landing is a re-disclosure as well as a disposition, and it takes a bar of its own because the composer's does not travel with the note: an inbox note is another session's composition, written from wherever the friction arose against the capture bar its writer holds, while the surface the note lands on is a repository that may be public and is the kit's own in the ordinary case. So a note is read against the board's own two line bars before it is folded into any repo's spec, backlog entry or plan, an absolute path spelled repo-relative or home-relative and the operator's words kept off the artifact, and a friction that cannot be landed without carrying something the operator would not publish goes up as a decision ask rather than being landed stripped of the detail that made it worth a note. What that bar cannot reach is what the note's text discloses about its writer's own machine and repo, since this seat did not compose it and cannot know which of its specifics matter, so the bar narrows what the landing seat can see and never certifies the note. And the standing authority covers the ordinary run of notes, never the bar itself or a disposition that is a material call in its own right: the kaizen skill's bar is not this seat's to widen, and a note whose disposition carries material consequence goes up to the operator as any other decision ask does.

**The BLOCKED funnel.** The seat learns of a declared BLOCKED on two paths: the worker's own message at declaration, and, for a worker that died or never messaged, the `goal-blocked` events in `~/.claude/kit-events.jsonl` that the reconciliation pass already reads. The event stream is the backstop because plan docs are not where a blocker shows: a blocked advance writes no Chapter and flips no Status header. **A blocker's answer never returns through the seat: the brief names the reply address in advance.** The address is the worker's own allowlisted relay thread, or the keyboard in the worker's own session, and for a worker that died, the keyboard in whatever session the operator resumes or re-arms in that project, so the operator's first answer lands on a warranted channel with no extra round trip, and the worker records the outcome on its own surface, in the recording form the peer-sessions Leashed peers rule states, the same form the Etiquette section below holds the seat's own relays to. An operator who answers on the seat's own thread instead, or at the keyboard in the seat's session, ordinary traffic rather than an edge, steers the seat and nobody else: the seat asks the operator, on that same channel, to re-post to the address the brief named; it may notify the worker to watch its own channel for the answer, a notice that carries none of the substance; and the escalation stays open on the board meanwhile: the worker's own resolution record in its plan doc, read at a later pass, is how the seat learns the answer landed, never a channel for carrying it, and that read reaches exactly the state the ledger rules below bound it to, answered-unconfirmed, the escalation riding until the seat confirms it with the operator, because any session on the machine can write a Chapter asserting an operator answer. That is the never-tasks-directly rule's pattern, asking the operator to act over a warranted channel, applied to the return leg; naming a decision and pointing a session at it stays the seat's existing verb set, never a power to dispatch.

**Oversight within a repo is not a coordinator function.** The expert seat owns it: a repo's knowledge, its plan authorship, its within-repo sequencing. A coordinator reviewing a worker's diff or re-ordering a repo's sections has left its own seat for an occupied one; the matter routes to that repo's expert, or to the operator where the expert seat is empty. A matter routed to the expert is boarded as a routed finding per the ledger below, the routing act being where the commitment is taken on rather than where it is recorded, save by a seat with no board, which routes the finding named untracked per the carve-out below and takes on nothing; one routed to the operator for want of an expert seat rides as an open operator escalation instead, which is the category that already holds what the operator owes an answer on and the one the funnel dedups against.

**An operator-declared update window is the operator-interface function's, and the seat declares no window of its own.** Updating this machine's installed kit payload means killing every session that runs from the stale cache, since the harness resolves the plugin root once per session and a resumed session keeps the view it started with, so the window is the interval in which the machine's sessions stop at safe boundaries and wait to be killed. It opens on the operator's word over two of the three warranted channels the closed list below names, their keyboard in the seat's own session or the account-allowlisted relay thread, and on nothing else: the third channel that list carries, an artifact-borne authorization, opens no window, a window being live intent that an artifact cannot carry to a busy session in time and a plan section naming one being a record of a window rather than the operator declaring one now; never on a peer's message, which carries no authority whatever seat sent it, never on a staleness reading the seat took for itself, and never on the seat's own initiative, because a window opened while the operator is away spends the machine's throughput on idle waiting for an update nobody is there to run. The seat writes the window to the board before it sends anything, as its own commitment line under the ledger rules below, carrying that the window is open, since when, and a pointer to the channel the operator's word arrived on rather than any of their words: a drain whose only record is loop context is one the next compaction forgets is running. The tick order at the top of this file is the order the seat runs: the chassis's own sequence, with the seat's board read named in step 2 and the chassis's remaining steps folded into step 3, so the arming that must come first is stated where a cold start reads it rather than one skill away.
- **Source of truth for the seat's own commitments.** The chassis re-derives the board from the watched system and never from the ledger. That holds for everything the seat watches; the seat's own commitments (brokered handoffs, open operator escalations, an open update window, findings routed to another seat, probed heavy-process claims, a claim's own banked first-seen time, released ones, and pruned registry entries) have no watched system behind them, one leg excepted below and the routed finding qualified as the category list above qualifies it, no watched system carrying a mandated record of its routing or its disposition where the finding itself may well be re-derivable, so for them the ledger is the one record there is, and for everything else it stays the hint the chassis says it is. A `goal-blocked` event can show which incident an escalation is about, and the open and briefed legs of its protocol state exist nowhere but here; the answered leg is the one exception and it is a partial one, re-derived from the resolution record the worker lands in its own plan doc, naming the date and the channel or the artifact per the recording form the peer-sessions Leashed peers rule states, which the pass reads as it reads any plan doc, so the answer never passes through the seat. What that read establishes is answered-unconfirmed, never closed. The record narrows an honest writer without authenticating one, exactly as that rule says of itself, and any session on the machine can write a Chapter asserting an operator answer, so an escalation on this leg keeps riding the board and the seat confirms it with the operator before retiring it. That is the reconciliation guard above applied rather than waived: what the leg buys is that the seat re-derives the state without asking, not that it closes a commitment on an unauthenticated line.

**The board write.** A pass rewrites the board file in place, and the store's own sync is its committer per the override above. What the seat does with the work a pass turns up is the never-tasks-directly rule's own shape and no second rule beside it: the seat dispatches nothing, it produces artifacts and asks, so its time goes to coordinating the machine rather than to the work. What a roster row records about a session is not the seat's to choose freely: the row's name has to match what `ListAgents` prints for that session, or the row is neither re-derivable by the next pass nor addressable by the status round, so an alias for the hostname is not on offer. That binds the name alone, which is why the row can still omit everything else the seat knows about that session, a working directory included. Visibility rides the sync's own triggers rather than the pass's, and the first of those is local: the automatic sync commits and pushes this board when a session starts or resumes on this box, those two being the whole of what the hook spawns the sync on and an auto-compaction's own session start being neither, so a long-lived seat session, which is the seat's ordinary shape, can write a board all day that has left this machine not at all. Closing that lag by hand is a hand run of `doctor/sync-store.ps1` with an explicit `-StoreRoot`, which is the run that script's own header sanctions and the same script the session-start hook spawns, though not the same run: it takes `kit-sync.lock` for its whole run, its writes go through the store's leak probes on the way out, and on the way in it screens every entry of the incoming upstream tree by mode and by path before the rebase touches the working tree. Two protections the hook puts around that spawn do not come with a hand run, and `docs/security-model.md` carries the comparison and what each hand path leaves exposed: the ownership gate the hook takes on the unclonable `claudekit.memorysync` local config key, where the script's own test accepts a marker-bearing `.gitignore` first, and the console-less credential setting the hook adds to its spawn (`GCM_INTERACTIVE=never`), where a hand run can still be answered by an interactive credential manager; the `GIT_*` strip and the two repo-local pins come with every run of the script, since they sit in the git funnel the script itself calls. The bare pair `git -C ~/.claude pull --rebase` and `git -C ~/.claude push` closes the lag with none of the three, because it takes no lock, runs no leak probe, and runs no inbound screen at all, so a rename, a duplicate-content push, or a symlink another machine sent lands in the live store root, where nothing un-writes it. The memory-system skill's gate on that manual push, the doctor's memory-sync line reading PASS or FIXED with a FAIL a stop rather than a push, is the outbound half and covers the leak probes and the store's index state; it takes no lock and reads no incoming tree, so it is not a substitute for the screened run, and it binds by that skill's own instruction to a session reading it rather than by anything either run performs. None of the three is a privilege of this seat, and none is a property of the store's channel either: each belongs to that one run, so a session taking the screened run gets all three and a session taking the bare pair gets none, this seat included. Off Windows the screened run is not on offer at all, the runner being PowerShell and the memory-system skill stating there is none there; what the store's sync is on that platform is that skill's to state, and it states the doctor's `-Fix` commit followed by that same bare pair, carrying the exposure named here. The remote leg adds the second lag, another machine seeing the line at its own next session start. So a board is a durable record first and a channel a distant second, a peer machine's copy is read as a state that may lag by a session rather than by minutes, and anything the operator or a peer needs on this side of the next session start goes to them over a warranted channel instead of onto a file nothing has pushed.

**What rides, and the two things that stop it riding.** An entry rides in the pointer form this file already imposes on an authorization note: a handoff is its repos and its protocol state; an escalation is the incident it is about, whether it has been briefed, and a pointer to what it waits on; an update window is that it is open, since when, the pointer to the channel the operator's word arrived on, and which sessions have confirmed parked, which have not, and which the round could not reach; a routed finding is what it is about, the seat it went to, and its disposition pointer or the open marker naming what it waits on, or neither of those where nobody has answered for it yet; a probed claim is the claim's repo, the time the probe went out, and the roster reading taken with it, which is what a later pass releases against; a first-seen claim is the claim's repo, the moment this seat first observed it, and which of its own fields failed to anchor a bound, that last part being what tells a successor the line is the anchor rather than a note; a released claim is the claim's repo, the elapsed window, and the decider; and a pruned registry entry is the entry, the readings that established exit, and the decider. None of them carries the authorization's own dates, its scope, or the operator's words. That bar covers a paraphrase of those words exactly as it covers a quotation, the disclosure being the same either way. The chassis's situational fields ride here as they do on every other line; the commitment lines' one carve-out, stated in the override above, is the re-derive command and nothing else. Two independent things stop an entry riding in that form, and both land it in the same stub. The first is fit: a commitment whose detail is more than a pointer will not take the form, whatever its subject, so a bulky and entirely harmless commitment is stubbed on fit alone. The second is sensitivity, and it is not fit's special case, since an escalation compact enough for the pointer form is not thereby safe to spell: blocker-derived text is composed by a worker rather than by this seat, it reaches the board through the funnel above, and it is screened against the readership the precondition above leaves the board with, which is a public surface wherever that precondition is unestablished. A stub names that the commitment exists, the channel its detail lives on, and since when, so the board never silently drops a commitment it is the only record of, while the detail stays where it arrived and a successor asks for it there. The claim and prune lines are the case that form does not fit, and they take a stub of their own rather than an exemption: a released claim's or a pruned entry's detail had one home, the file this seat deleted, so there is no channel to point a successor at, and its stub names the class, the repo or the entry, the repo where the entry's identifier is the disclosure that stubbed it, and the time, and says in so many words that the detail went with the file. A first-seen claim's stub keeps the first-seen moment whatever else it drops, for the same reason and with a sharper consequence: the moment is the whole of what the line is for, so a stub that drops it is not a stub of that line at all, and a seat that cannot spell even the repo names the claim by its file rather than dropping the line, since the claim file's path is fixed by the directory contract and discloses nothing the board's own directory does not. A probed claim's stub keeps the probe time whatever else it drops, and what dropping the rest costs is stated with it rather than discovered at the release: the claim protocol's idle branch is a comparison against exactly the banked roster reading a stub drops, so a stubbed probe line leaves that branch unsatisfiable and only the no-row reading can carry the release's second leg, a claimant idle at the releasing pass standing as the contract's untracked hold instead of being released. An update window's stub keeps that a window is open and since when, whatever else it drops, because a successor that cannot see the open window holds a drain nobody is watching and an operator owed a report nobody knows is owed; what dropping the per-session drain state costs is stated with it rather than discovered at the report: no watched system re-derives it, so a successor rebuilds it only by asking each drained session again, a second line per session the round's own pricing never spends, and the report goes up on what those answers rebuild. A routed finding's stub keeps the seat it went to, without which the line can never be asked again, and keeps its disposition pointer, or its open marker where no pointer has landed, whatever else it drops, on the same reasoning and against the same cost: the line exists to stop a successor re-raising a finding already dispositioned, so a stub carrying neither reads as the open line the category rule above says it is and buys back the whole re-raise the line was written to prevent, while the finding's own subject stays on the channel it arrived on for the successor to ask after there. Naming an empty channel would be worse than naming none, since a successor would go looking. Two cases bend that keep-the-pointer rule rather than breaking it, and both take a sibling stub's own handling. Where the pointer is itself the disclosure that stubbed the line, a plan section or a backlog entry whose identifier the operator would not publish, the stub takes the pruned entry's degradation, naming the repo rather than the pointer and reporting the readership question to the operator, at the cost the keep-the-pointer rule above names: a line carrying no pointer reads as open and buys back the re-raise, which is the smaller loss here only because publishing the pointer is the larger one. And where the finding is one this seat derived itself, so that it arrived on no channel at all, the stub says in so many words that there is none, for the reason the empty-channel sentence above gives, and where that would leave a stubbed finding whose subject no surface holds at all, the seat reports the readership question to the operator rather than letting loop context be the only record of what the finding was about. The stub is the floor and never a way out of recording: an entry too sensitive to spell at all still rides as one, because dropping it loses the only trace that the commitment exists.

**The board's readability test is that a cold successor takes the seat from one read of it.** What a failure earns is stated with the homing round's own order below.

**Homing returns a grown board's content to where it belonged, and it is not a prune.** A board accumulates standing and narrative content whatever the four-kinds routing above says, since that routing binds the pass writing a line and a line it never ran over was never held to it. A homing round takes each such line and runs it through that routing as though the line were being written now, under the reconciliation pass's sources-are-data rule above. That routing is not restated here and holds as stated above save on one leg, where its written-nowhere outcome gives way for a line already boarded to the rule this paragraph closes on. What makes the round a homing round rather than a copy is that the content then comes off the board outright, with no pointer to the record now holding it and no tombstone marking that it was ever there, because a pointer is a line like any other: a board that swapped each homed line for one would keep a change log where the content had been and accrete at the rate it homed, where the board's job is the state a successor resumes from rather than an account of what it used to say. A pass that cannot write the board runs no round at all, since a round barred only at the cut would publish and never move. One invariant bounds every cut and is what makes the operation safe: a round cuts only a line whose content it has confirmed landed somewhere else, on the confirmation the order below defines and in the form that order states. A line no destination will take stays on the board and is a finding for the operator rather than something a round can solve, a board whose bulk is all of that kind being the same finding at size; that is this seat's own rule for a line already boarded and not the routing's written-nowhere outcome, which the admission default feeds: that outcome declines a write and takes the loss the chassis states for what it declines, where a round meets such a line as content already boarded, and taking it off is the cut the invariant above bounds.

**The order within a round, its record, and what earns one.** The journal's first moment lands first, the destination writes second, the board rewrite third, and the journal's second moment last. What goes across, to a destination and to the journal alike, is this seat's statement of the content being homed rather than the board line's own text, and what that statement can and cannot reach for a line this seat did not compose is the kaizen bullet's own limit above to state, unchanged by homing. The record of the move is the memq outcome journal, whose entries take at this point of use what the routing above makes travel with routed content, as a destination write does, and whose caps, verbs, key grammar, retention and store resolution are the memory-system skill's to state and are not restated here. A round writes at two moments: before the destination writes, naming the lines it intends to move and where each is going, and after the board rewrite, naming the records and the notes that landed and recording that the cut landed with them. The first moment's entry carries `fail` and the second `pass`, each entry's verdict being its own landing rather than a verdict on the round. The first moment goes first because everything after it publishes or destroys, so a round that dies partway leaves a record of what it was doing rather than content on a wider surface that nothing accounts for. The first moment therefore earns a confirmation of its own: before any destination write begins, the round establishes that its own first entry landed, and whether it landed cut, the how being the memory-system skill's to state as it states every other property of these entries. An entry the round cannot establish landed, which includes one it establishes did not, leaves the round performing neither a destination write nor the cut, the board stays as that round found it, and the friction goes to the operator as it does for a line no destination will take; an entry that landed cut is that same skill's to remedy, and the round proceeds once the remedy has left the account whole. Like every other record this seat reads, the entry narrows an honest round without authenticating one. A line comes off only once its destination write is confirmed landed, and what a confirming read has to establish is that the record it returns is the one this round wrote, on the tier it was written to, carrying the content the round composed. Anything short of that is unconfirmed, and unconfirmed is unknown rather than absent, so it holds the line. For the kaizen inbox what confirms the landing is the commit that skill's own capture rule defines, and where that skill's fallback puts a note outside a repository there is no commit to wait for, so the line stays and the friction goes to the operator. Pruning is the other operation and is untouched by this one: superseded history stays pruning's business per the durability override above, on that override's own conditions. What earns a round is a pass finding the board failing the readability test above, and that failure earns a homing round rather than a harder prune, since the bulk a grown board carries is exactly what a prune must either destroy or correctly refuse.

**A seat with no board takes on nothing it would have to remember.** The state lasts as long as the wait for the operator's answer to the cold start's report, the absence being theirs to settle per step 2 above, and it ends in one write that creates the board, and the machine's directory where no other writer has: no installer or doctor step makes a machine's directory under the coordinator path, and the role skill's other writers, a registry entry, a claim, create it without creating any board, which is why the operator gate here keys on the file and never on the directory. The wait is paid once and not at every session, a board on disk being what every later session reads, and that holds off Windows as it holds on it, since what the platform decides is who commits the store rather than whether the seat can write the file. A board a contest has frozen puts the seat under this same rule for the same reason, that it can write no record of what it takes on. While either lasts the seat reads, re-derives and answers the operator as usual, and it declines what it could not record, brokering no handoff, holding no escalation and no routed finding, releasing no claim, and pruning no registry entry, because a commitment whose only record is loop context is gone at the next compaction. Appending an operator's ask of the Admin seat to `admin-requests.md` is not among these declines: the never-tasks-directly rule above states why, the append recording itself on a file this ledger never had to carry rather than on the board this rule guards. The two destructive acts are the sharpest, and they are on this list for the same reason rather than by extension: each destroys its own evidence. With no board to carry the line, a release leaves its deletion nothing to cite and the slot comes free with no record of who freed it or when, which is the phantom hold inverted rather than cured; and a prune takes a peer's own record of itself off the disk with nothing anywhere saying this seat did it, the worse of the two, since the released claim at least had a claimant to notify. Declining to hold is not declining to brief: an operator-declared update window still runs and is still reported, named untracked so the operator knows no record on this side is holding the drain's state, the drain destroying nothing and the operator who declared it being present to be reported to, though what a compaction there takes is the window itself and not just its confirmations, loop context having been the only record on this side, so the seat re-learns that a window is open from the operator or not at all, and a re-run drain spends a second line per session that the round's own pricing never spends, which is the degradation the untracked naming warns of rather than a record lost silently; a blocker still gets the funnel's brief, named untracked per the funnel above, and an overdue claim is reported to the operator as an untracked hold, and the seat may still ask the claimant whether the box is held, an ask that grounds the report and never a release, the protocol's own probe being an on-the-record act a boardless seat cannot perform; and an entry the heartbeat leg would prune is reported rather than pruned, and a finding still routes to the seat that owns the fix, named untracked so that seat is told no record on this side is holding its disposition, since briefing a state and naming it untracked holds nothing. A successor is not in that state and the paragraph does not reach it: it has read its predecessor's board, so it holds those commitments and may relay them.

**Seat handoff.** A successor takes the seat by reading the ledger and then announcing the takeover, which is taking the seat's name in the machine-scoped form the peer-sessions Naming section owns, so the claim shows on the roster every peer reads; where the previous holder is still live, it also gets a message: a predecessor that says it is handing over has relinquished, and the takeover is a handoff; without that, two names claiming one exclusive seat is a collision, not a handoff. Reading precedes any status round or message, per the cold-start order above: a takeover announced before the previous holder's commitments are read is a seat claimed without its obligations.

**A contested seat freezes the board.** A contest is two sessions claiming the seat, which the live `ListAgents` roster shows rather than the board's own recorded roster; an entry the seat did not write is a claim, never a contest. The reading turns on a self-chosen name and nothing screens it, which is stated rather than left to be discovered at the freeze: a seat name is a label any session can wear, per the peer-sessions naming convention and its claim-is-declared-in-layers rule, so any second session naming itself this machine's coordinator produces a contest by construction and the freeze fires on that name alone. That is fail-open in the withholding direction and it is chosen, because the only alternative is the seat deciding which claimant is genuine, which is the seat ruling on its own collision, the one judgment the routing rule below takes out of its hands. What bounds it is that the freeze destroys nothing and is reported at the pass that observes it: the seat writes no line, takes on no commitment it could not record, and briefs and reports untracked per the no-board rule above, while the routing message carries the anchor below so the operator can settle it. The cost of a manufactured contest is therefore the machine's brokering until they answer, and what the reading establishes is that two rows claim the seat, never which session holds it. Two claimants route to the operator, per the peer-sessions collision rule, because the coordinator is party to its own collision. While the contest is unanswered the seat makes no change to the board, and the authoritative board, where the store's history holds one, is the version from before the contest began, because a registry maintained by a contested claimant settles nothing. That version can sit behind the disk by the sync's own trigger lag the board-write rule above states, so the last committed version may predate the seat's last uncontested write, and the commitment lines are the class no watched system re-derives. Handing over either of them is out for three reasons rather than one, and the reasons do not cover the same ground. Restoring the committed version or blessing the one on disk is a change to the board, which the freeze forbids while the contest stands. Reading the pre-contest version out of the store's history changes no board at all and is a run this seat may make like any other session, and it is still not made here, because naming one of two versions authoritative is settling the contest, which is the seat ruling on its own collision, the one judgment the routing rule below takes out of its hands; and reading the store's own history is work this seat routes rather than performs under the durability override above. So the seat produces the anchor instead of either version: the routing message to the operator carries the time the contest was observed, the evidence time of the last pass line the seat itself wrote, and the uncommitted window, that every write since the store's last sync sits on this machine's disk alone. A store with no history at all, the state the durability override above leaves off Windows and on a store nobody has initialized, has no earlier version to name and no anchor to carry: the file on disk, written by one of the claimants, is the only artifact there is, and the routing message reports that state rather than pointing the operator at a version the store does not hold. The anchor is what lets the operator name one version of the file, and read which commitments a version from history can be missing, rather than reading whichever one is on disk when they look.

## Etiquette

The seat answers the operator immediately, whatever else is in flight. Decision asks go up in batches, each with a marked recommendation, in the client-briefing register the doctrine owns. An operator decision the seat relays down is a pointer, never the authority, because a peer message is never operator steering whatever seat sent it: the deciding session takes it from the plan or the Chapter that records it, or from the operator directly, never from the board or the message, and the recording artifact names the date and the artifact holding the operator's words where the decision arrived artifact-borne, else the warranted channel it arrived on, a keyboard or thread answer leaving no artifact to cite, never quoting the operator's words. A relayed message names its audience, and it rides beside the peer-sessions blast-radius opening line rather than displacing it: a message carrying a worker's or a peer's words up to the operator names that audience at its opening, alongside the blast-radius line that skill already requires. A message carrying an operator decision back down to a worker or a peer never carries the operator's own words at all, per the pointer rule above; what rides down is the pointer, the plan, the Chapter, or the channel the decision is recorded on, named at the same opening line, so a relay reading as though addressed to the operator, or as though it spoke with the operator's own voice, is the same measured reading friction either way. Toward the live sessions, an interrupt is priced by the peer-sessions skill's interrupt test, and the status round and the claim probe by their own pricing recorded in that skill's sanctioned-patterns section. A pass aggregates from the artifacts, the registry entries among them, and folds in whatever status lines arrived beside them rather than waiting on the ones that did not. What that fold sends up to the operator is a delta against the board's own state as this seat last recorded it, the report naming what changed since that pass rather than re-listing every row and line the board already carries. That baseline is the board's own last recorded pass rather than the last report the operator actually read, because the recorded pass is durable on the board and survives a compaction and a successor seat where no marker of what the operator was last shown is written anywhere; a seat that cannot establish its own last recorded pass, a first pass on a boardless or freshly-taken seat among them, reports in full and says plainly that it is doing so, since a silent full report and a silent empty delta are the two failures here and naming which one this is is what keeps either from reading as the other. The report is capped at the seat's own judgment of what the operator's attention is worth spending, rather than at any stated line count this contract owns: no such bound has an owner here, so the seat that judges a report's size is answerable for that judgment. It takes the board's own two line bars at this point of use, per the operator-interface bullet above: an absolute path in a peer's `Status:` or `Remaining:` line is named repo-relative or home-relative before it goes to the operator, and the operator's own words stay off the aggregation as they stay off a board line, because the bars are on what a line carries and this route is an external channel like the board's readership. The bars reach what the seat can see in the text it forwards and no further; nothing here validates the line or its writer.
