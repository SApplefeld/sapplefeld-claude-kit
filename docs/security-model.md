# Security model

What the kit's local state assumes, what it guards, and what it does not claim. Written as preconditions that can be checked, because a premise stated as a reassurance ("the store is trusted") cannot be re-tested when something changes underneath it, and one did: the memory store's trust premise was accepted when the store was per-project, then invalidated when a machine-wide shared tier was added, and nothing forced a re-check.

## Principals

**Within one machine account, there is exactly one principal**: that account's user. Every project session, every dispatched subagent, and every hook runs as that user with full read and write access to `~/.claude`. Anyone who can write there already has code execution through hooks and `settings.json`, so no control in this document defends against that.

**Across the deployment, there are several.** The kit is shared with other team members, the repositories sync across multiple machines, and the same person operates it under two work accounts and one personal account. That means kit code, and any repository-carried configuration, crosses account and person boundaries routinely. A control whose only justification is "one person, one machine" is not justified here.

Three consequences follow, and they are why several of the sections below are stricter than a single-user store would warrant:

- **The store is not a security boundary between projects.** Per-project separation is a convention the tooling follows, not a control the design enforces. Any session can read and write any project's memory directory by resolving the path itself.
- **The shared project-type tier is a cross-person surface, not merely a cross-project one.** Content one person writes is read into another person's session context, wherever a type tier is shared rather than machine-local.
- **A repository is a distribution channel for configuration.** Anything a synced or shared repository can set for the shell that opens a session (`terminal.integrated.env.windows` in a committed `.vscode/settings.json`, a `devcontainer.json` env block, an `.envrc`) reaches an account that merely cloned it. Environment-driven behavior is therefore attacker-reachable in a way it would not be on a single-operator machine.

**What is machine-local versus shared is worth checking rather than assuming.** The kit payload is shared by design. Whether a given store directory syncs depends on how that machine is configured, and the tooling neither knows nor enforces the answer. Treat a type tier as shared unless you have confirmed otherwise for that machine.

## The memory store, per tier

The store lives at `~/.claude/projects/<sanitized-cwd>/memory/` (project tier), `~/.claude/memory-types/<type>/` (type tier), and `~/.claude/memory-operator/` (operator tier). The `<sanitized-cwd>` of the project tier is derived by an ordered contract carrying four legs and two refusals, and the refusals sit at different positions in that order rather than together. The working directory's spelling is validated first, ahead of every leg: a directory that is not a non-empty string, that is absolute under neither the win32 nor the posix grammar, or that opens with a single backslash naming no drive is refused before anything else runs, a pinned session included, which is why a pinned session can be refused on working-directory grounds at all. A spelling opening with two separators is not in that refused class, in any mix of backslash and forward slash: those name a network share, and the share refusal below is what judges them, which is why the refused class is spelled as a single leading backslash rather than as a missing drive. An honored store pin answers next. The network-share refusal sits behind that pin and ahead of the remaining legs, standing the store down on a spelling whose two leading separators name a share, rather than walking a path that can hang for the SMB timeout on an unreachable host. Then the worktree's main checkout, because memq follows the worktree's `.git` pointer to the main checkout only when a two-way handshake holds (the pointed-at gitdir has the `.git/worktrees/<name>` shape, its `commondir` and back-pointer resolve, and `<main>/.git` is a real directory). Then the session-transcript leg, which answers only under three conditions together: the handed directory is this process's own, some ancestor of it (itself counted) derives the same segment the session's transcript is filed under, and no repository boundary lies in between. And last the plain working directory. Every leg ends in the same flattening, the chosen path's non-alphanumerics replaced, and that flattening maps distinct directories onto one segment. The equivalence class it creates is wider than the working directory's own projection, because the session-transcript leg matches on the derived segment while climbing, so an ancestor's projection can collide into it too. That handshake is a trust boundary in itself: a `.git` pointer file is repo-adjacent data in a directory the session cd'd into, so a planted one must never redirect memory reads and writes, and only a link git itself maintains carries the back-pointer the handshake checks.


**The resolver is a cross-project data-separation boundary.** It decides which project's memory tier a session reads and writes, so a wrong answer crosses two projects' records: one project's memories reach another project's session at SessionStart, and a write lands in a tier its author never named. Nothing else in this document states that boundary, and the ordered contract above is what holds it. Four residuals sit inside it, and each is a real reachable state rather than a theoretical one.

A stray `.git` written anywhere between the working directory and the filed project root silently disables the session-transcript leg, since the ancestor climb stops at the nearest enclosing repository boundary. The direction is fail-safe, the leg declining and the resolver falling back to the session's own working-directory-derived store rather than to another project's, and the origin is third-party-triggerable, since anything that can write into an intermediate directory can create one.

The flattening admits a posix-rooted spelling on Windows, and that is the widest of the four. `sanitizeProjectPath('/foo')` answers `-foo` on win32, which carries the same per-drive ambiguity the driveless refusal exists to close, and carries it in the worse direction: two different projects, one on `C:` and one on `D:`, both entered as `/proj/app`, collapse into the single segment `-proj-app`, so one project's records enter the other's SessionStart emission. The code deliberately does not refuse it, and the reason is a property of the rule rather than an oversight: a committed test pins that spelling because the absoluteness test accepts either platform's grammar, which is what lets a win32 path literal sanitize identically on a POSIX host, and refusing the spelling would break that. What bounds the blast is the flattening itself, which leaves no separator and no `..`, so a wrong value selects a wrong real segment and cannot traverse out of the store. The caller whose working directory is genuinely attacker-influenced is the sidecar's memory index, fed from spool lines any local process can write; it screens for a network share and not for this.

The equivalence class the flattening creates is stated above and belongs here too as a residual, since it is what makes the collision above possible at all rather than merely awkward.

And on an unpinned working directory sitting on a mapped network drive, the session-transcript leg's ancestor climb pays one link resolution per step plus the initial resolution and a transcript-directory sweep, each a network round trip that can block for the SMB timeout, inside the session-blocking SessionStart hook. The share stand-down predicate keys on two leading separators and cannot see a mapped drive, so no branch protects that path. The store pin is what avoids the walk where a mapped drive is the shape in front of you.

**Project tier.** Authored by that project's sessions and emitted into context by the kit's own SessionStart hook (the index emission below). Inside the trust boundary in the ordinary sense: the thing that wrote it is the thing that reads it. That condition, and not any harness behavior, is what leaves the tier unfenced where it is unfenced; Claude Code's auto-memory may also inject the same index when it is enabled, but nothing in the kit depends on whether it does.

Under a store pin that description does not hold, and the difference is the point of the pin rather than a side effect. One pinned tier serves every repository the instance works in, so the Principals section's "the store is not a security boundary between projects" stops being a caveat about what the tooling fails to enforce and becomes the operating condition: cross-repository sharing inside one instance is the intended behavior, because the instance is the entity meant to accumulate, not the repository. Two consequences follow. The tier's content is fenced on the way into context, per the fence discussion below. And the containment that remains is the store root: every memq-mediated write stays inside the root the engine chose for that instance, which is why that root, not the segment, is the boundary. For the memory files a session writes with its own file tools, the destination block is an instruction rather than a boundary, the same status this document gives the data-not-instructions framing.

**Type tier.** Authored by *any* project on the machine that declares `Project-Type: <type>`, and read into the context of *every* project declaring that type. This is a machine-wide shared read-and-write surface. A claim that no store-controlled content reaches a session's trusted context is false by design for this tier.

**Operator tier.** `~/.claude/memory-operator/`, authored by *any* project on the machine and read by *every* one of them. It is the type tier's sharing without the type tier's opt-in: no declaration gates it, so it is machine-wide by construction rather than by a project's choice, and the same sentence holds, that no-store-controlled-content-in-trusted-context is false by design here. Its content is fenced wherever it enters context, on the same reasoning the type tier's is. Two properties narrow the surface rather than widen it: authoring is CLI-only and mechanically so, `memory-frontmatter-guard` refusing every `Write`, `Edit` and `MultiEdit` here whoever is writing, so a memory arrives through `add-operator` under the tier's lock rather than through any session's file tools, and the tier is not emitted at session start. It does not follow that it enters context only through a command a session chose to run, and since the recognition nudge widened past the project tier it no longer does: the nudge reads this tier unprompted at three of its four boundaries, the two tool ones and a subagent dispatching, never at a prompt, whose door admits the project tier alone, and can put a record's name and the trigger text that fired in front of a session that issued no memory command at all, a dispatched subagent included, which is the one reader that never issued a prompt either, under the bounded gate and the fence the table below states. A `machine:` field scopes a fact to one box; it is a label rather than a boundary, and both of its readers re-validate it against the writer's own identifier gate before printing, find's semantic channel and the recognition nudge, so a hand-edited or synced value cannot put free prose on a search line or on a nudge. The second reader is the one that matters most here, being the one that reaches context with no command invoked at all.

**Two seat rituals read the operator tier for something privileged, and neither is covered by the Principals section's already-has-code-execution reasoning.** That reasoning bounds what a writer on *this* machine gains; both of these records are writable by any local session and reachable from every machine the store syncs, so the writer need not be here at all. The first is the launch invocation `/role` resolves at its name check: the exact command that starts a seat's session is a per-machine operator fact the public skill cannot carry, so it lives in one record per machine. Per machine is a convention there rather than a mechanism: unlike the delegation record below, nothing keys that record to a hostname, the ritual runs no machine comparison when it resolves one, and `memq get` applies no machine filter, so a record written on another box answers here. What the ritual does with it is the whole control. The resolved text is never presented as runnable: the launcher, the seat name and each flag are described in prose, and the operator confirms that description against what they themselves wrote before anything acts on it, a confirmation paid at each resolution rather than once per machine, since nothing here records what was confirmed or can notice that the record has been rewritten between one resolution and the next. An allowlist over the flags is refused for a structural reason rather than a cost one: the payload class is flag-shaped, a launcher's own flag able to disarm its permission prompts or load a session's system prompt from a store path while reading as one clean flag-and-value line, and the flags a launcher accepts are enumerable from nothing this repository ships, so a list naming them decides membership on the untrusted record's own say-so, while a denylist over the same space misses silently. A metacharacter screen stands beside the prose rule as an independent catch for its own class, reporting as suspect a record that is not a single line of printable ASCII or that carries a command separator, substitution, or redirection, since no launch invocation is any of those. Both screens are model-facing prose in the role skill with nothing mechanical beneath either: no hook implements them, no test pins them, and `skills/` sits outside the build's hook manifest, so an in-place edit in the user-writable plugin cache removes either one with no canary. They are conventions the ritual follows, on the footing the warranted-channels list below has rather than the footing the frontmatter guard has. The second is the standing-delegation opt-in, one hostname-keyed record whose presence flips a seat's default treatment of scoped direction from the seats above it in the chain. That opt-in is the first instance of a general standing-grant rail the role skill states, rather than a mechanism of its own: a standing grant is a mechanism whose scope, exclusions and procedure a shipped skill states, switched on by one operator-tier record that skill identifies, by name or by a keying rule that must resolve to exactly one record or to none, and the properties described next are the rail's rather than delegation's alone. Its ceiling is the dispatch-authority trace's exactly: it narrows an honest writer without authenticating one, any local session being able to run the CLI that writes it. Its body is read as data and never as instructions, the scope and the exclusions coming from the role skill alone, so a body purporting to widen a scope or drop an exclusion changes nothing and is reported to the operator as a finding; the record's only effect is that on-switch. The machine keying is what makes the grant machine-scoped where the tier's replication is not, and the comparison is caseless because no surface on the path holds a canonical case, so a case-sensitive one would read a real grant as absent on the kit's primary platform. One reach belongs on both records rather than on the tier's general description: `memq add-operator` is granted prompt-free and agent-blind under the engine store signals, per the `memq-grant` bullet under The guard hooks below, and that grant was priced when this tier carried facts. It now carries a standing-grant rail rather than the single switch that pricing assumed, so what the grant reaches has changed even where its stated precondition holds, and it changes again with every grant the rail admits, which is a set this document does not bound and no edit here would keep current. That is the re-pricing's real subject: not whether one switch is worth the prompt-free grant, but whether a tier whose privileged content grows by an owning skill's say-so is. `docs/backlog.md` carries it. The write side has widened on this tier too, though not through that grant: the machine-coordinator seat writes a memory-store record as a standing part of any pass that produces a durable lesson, per The coordinator board below, and a lesson about the machine rather than about one project is an operator-tier lesson by that tier's own definition. A seat is not started under the engine store signals that grant is emitted under, and nothing enforces that, so each of its writes meets the ordinary permission flow wherever that holds, and what its loop widens is the tier's volume rather than the class of content a ritual reads for a privileged act.

**Pending tier.** `<project tier>/pending/<run-id>/`, present only inside a run the external engine spawned (the `KIT_RUN_ID` entry below). Authored by that one run, read back by that same run, and entered into the project tier only by an adjudication verdict the engine applies. It exists so a headless worker's memory writes do not enter a shared record unreviewed. A pending memory carries no `MEMORY.md` index line: the index is written at promotion. Pending content reaches a model's context only through the run's own memq reads (`find`, `get`, `recall`, `recent`), and none of them fences it. That is the resolution rule rather than a gap: each resolves the single directory the calling process's own `KIT_RUN_ID` names, so the run reading a pending record is the run that wrote it, and there is no provenance gap for a fence to frame. What `memory-session.js` emits for a run is the destination path, not the tier's content, and that path is fenced as the configuration it is (the destination block below).

The scoping is a resolution rule, not an enforced boundary. A process resolves the single pending directory its own `KIT_RUN_ID` names and enumerates no others, so runs do not see each other in ordinary operation. Nothing stops a session that holds Bash from setting a different id and resolving another run's directory, which is the same limit the Principals section already states for every tier.

The run-scoped destination block carries content into context and differs from the paths above in its source: the block `memory-session.js` emits names the pending directory, and that path embeds `KIT_MEMORY_ROOT`, so its content is environment configuration rather than store content, and the environment is attacker-reachable per the Principals section. It is emitted faithfully or not at all (a value that would be truncated or reduced stands the session down instead), and it rides on its own indented line inside the block's data fence, so printable-ASCII prose set as a store root reads as a filesystem destination and not as an instruction.

The pin destination block is the same shape: under a store pin (the `KIT_MEMORY_PROJECT` entry below), a session with no run id is told where its memory files go, and that destination embeds the pin as well as the store root. Same treatment: emitted faithfully or not at all, on its own indented line inside the block's data fence.

The project destination block is the third of that family and the one with the widest trigger, since an ordinary session with no run and no pin still gets it. Its path embeds `KIT_MEMORY_ROOT` the same way, and it takes the same faithfully-or-not-at-all rule, but it answers an unemittable path with a third outcome the other two do not have: it withholds the directory, emits the index lines anyway, and points the session at `memq`, which resolves the directory itself. The write convention goes with the directory rather than staying behind, since a session that cannot be told where the directory is cannot follow an instruction to write a file in it, so what it is told instead is to report the condition rather than guess a path for one. It does not stand the session down. The reason is that a stand-down is a response to an environment that asked for something the kit cannot deliver, and an ordinary session has asked for nothing: standing it down would cost a developer their memory writes over a path this block happens not to be able to spell.

Its steering condition is the least gated of the three that decide where the model's own file tools write memory: the store pair alone reaches it, two variables and no `KIT_MEMORY_PROJECT`, where the pin destination block needs all three. Fewer preconditions means broader reach, which is why this block is the one to audit first. The consequence to keep in view is that a store root pointed inside a cloned repository puts a session's memory writes into that repository's working tree.

**The project index emission carries project-tier content into context with no command invoked at all, at every session start, and it fences unconditionally.** The `recall` and `recent` digests in the table above are automatic in the weaker sense of running at a fixed point in a workflow. Two paths need nothing invoked at all, and they differ in when: this one at every session start, and the recognition nudge on the tool stream, on a prompt arriving and on a subagent dispatching. Under a pin, the justifying condition below (the project that wrote it is the project reading it) is false by design, so the writer is another of the instance's workers. The emitter does not key on that: it reduces, caps, indents, and frames the project index in every state, which is stricter than the rule below requires. That is deliberate and should not be "corrected" toward the looser rule, because the block's own trigger is the widest in the hook and a per-state fence would be one more branch to get wrong.

Every hop above carries the fence, the table's rows other than the decay scan's pairs block together with the run-scoped, pin, and project destination blocks, and the fence rather than the charset is the control on a body. Further surfaces carry store content at column zero and deliberately do not fence it, under the same reasoning: two over the project tier alone, named below, and the decay scan's pairs block over the shared tiers as well, on the precedent of that same scan's pinned block, which prints shared-tier record names at column zero unfenced because both are the tool's own lines about tiers it walked rather than content lifted out of a record, and whose row above states the bound on that reach (find's withheld line, every coverage line, and `unstamped`'s closing verdict also sit at column zero, but they carry counts and figures this tool computed, at most alongside a charset-closed identifier such as the declared type name or the regex-bounded `--since` label, rather than store prose, so no fence question arises for them): `memq find`'s lexical channel, one bounded, charset-closed, quote-stripped line per hit, labelled by tier and never a body, over the caller's own tiers; and `memq unstamped`'s project-tier lines, the same shape over the records this project's own sessions opened. All are guarded by construction rather than by framing, because a single sanitized line cannot forge a block, and that narrower guard is the claim to check rather than assuming the fence covers it. The first two take the fence the moment the reach widens: each command indents its type-tier and operator-tier lines under the full framing line, and `unstamped` also fences its project lines under a store pin, since a pin makes that tier another worker's writing. The narrower guard is tied to the narrower reach, which is why `find`'s semantic channel, spanning every store on the machine, sits in the table above under the full fence rather than sharing this exception. The exposure it leaves is real and worth naming: under a pin, a description another of the instance's workers wrote arrives in the tool's own voice, as it already does for the type tier. The exposure that distinguishes them is frequency rather than guard: the index emission and both digests are automatic, `recall` at every effort start and `recent` at every close-out, and the close-out's after-query runs `find` there too, while a `get` is a deliberate fetch of a named record. Frequency moves how often the exposure is met rather than how wide it is: the narrower guard above is tied to reach, so it holds identically whether the channel runs once or at every close-out.

**The anchor surfaces take a grammar in place of the charset reduction, and that substitution is deliberate rather than an omission.** An anchor path reaching a display line, on `memq get`'s per-anchor lines, on `decay-scan`'s `DRIFT` block, and on the CLI's own anchor refusal lines, does not go through `sanitize` the way a record name or a description does. It goes through `isAnchorPath` at the write door instead, which is a stricter gate on everything except the one axis the sanitizer covers: no whitespace, no C0 or C1 control, no bidi or zero-width character from a named enumeration, no double quote, no backslash or colon, at most 256 characters, and a refusal line strips both unshowable classes and names each reduction it made, over text the home elision has already run on twice, before the strip and again after it, and ahead of the cap, since a refused entry is free text a record can put an absolute home-anchored path into and both channels that carry it, this CLI's stderr and the frontmatter guard's deny reason, are read by a model. The two recognition-trigger surfaces take the same substitution through `isTriggerEntry`, on `memq get`'s per-trigger lines and on the `triggers` verb's own stdout and refusal lines. That grammar is deliberately looser than the anchor one in one respect and no other: a trigger pattern admits the plain space, because a command trigger has to be able to name `node --test`. Every bar that keeps a record's own text from forging a column-zero line, or from ending the frontmatter block it sits in, is kept, and the grammar's two members keep them by different routes, because a bar stated over a typed vocabulary holds only of the types it is true of. The five free-text types, whose patterns admit the plain space, bar the control character, the bidi and zero-width character, both quote kinds, the bracket, the backslash, and the three spellings a YAML plain scalar cannot carry (`: `, a trailing colon, and ` #`). The `glob:` type admits the bracket a character class needs and bars instead every whitespace character and the colon outright, which closes the same two properties at their root rather than character by character: the annotation a forged line would have to spell opens with a space, and each of the three YAML spellings needs a colon or a space to exist at all. It bars the single quote as well, for neither of those reasons but because a quoted scalar's round trip hands the value back with its quotes still attached, which the reader then refuses. What it admits and the sanitizer would not is visible non-ASCII, and that is the point: `sanitize` strips every non-ASCII character, so quoting a refused `src/Übersicht.cs` back through it would name a different file, and a repository with non-English filenames would lose the feature outright. The residual is homoglyph confusion rather than injection, and it is narrower than the enumeration is complete: the invisible class is a hand-written list, so a visible-width-zero character such as U+3164 HANGUL FILLER is admitted. The drift block's record names still take `sanitize`, and a shared-tier record's anchors are answered with fixed text carrying nothing from the record at all, which is what keeps a path from a tier every project on the machine can write out of column zero.

The sync trigger (`memory-session.js`) is a further path into context and needs no fence, because it carries no store-derived text at all. The hook's own checks are read-only git subcommands and never a fetch, so a session start costs no in-hook network round trip and the "behind" figure it may report is what this machine last knew rather than what the remote holds now; the fetch, rebase, and push happen in a detached background runner (`doctor/sync-store.ps1`) the hook spawns off the session's critical path. Every value in an emitted line is an integer parsed out of a fixed count, a boolean read from whether `git status --porcelain` printed anything, or a fixed literal from the hook's own source (a state-file reason code is a lookup key mapped to a fixed literal with a fallback, never emitted text); no path, branch name, remote URL, or state-file string reaches the line, which is stricter than sanitizing and is what makes the fence unnecessary rather than merely absent. Only three states speak at all: a recorded standing-down gate, a failure streak past a week, and a broken sync chain (a spawn that recorded no outcome past a stale window); a healthy sync is silent.

Several conditions gate it, and they gate the spawn more tightly than the line. The store root must hold its own `.git`, checked by a stat before any git call runs, because git discovers repositories upward: without that check a store root merely sitting inside an unrelated checkout would be described as the memory store. Every `GIT_*` variable is stripped from the child environment (not only `GIT_DIR`/`GIT_WORK_TREE`), because a repo-carried `GIT_COMMON_DIR` would otherwise redirect even a `--local` config read at an attacker-supplied config. The background spawn, which commits, fetches, screens, rebases, and pushes, runs only when the store is the kit's OWN repository, established by the local git config key `claudekit.memorysync` rather than the marker-bearing `.gitignore` that also proves ownership elsewhere: a committed file rides into a clone and could be planted, but a `--local` config value is never cloned, so this gate is not forgeable by shipping a repo at the store root. The spawn also runs only at the default `<home>/.claude` root (an environment-overridden root is synced by the operator's own hand, since `os.homedir()` follows the attacker-reachable `USERPROFILE`, so ownership rather than the path is the security gate) and only on Windows, where the PowerShell runner exists. The runner screens the inbound direction as tightly as the doctor's probes screen the outbound: every entry of the incoming upstream tree is checked by its mode and its path against the allowlist before the rebase touches the working tree, so a rename, a duplicate-content push, or a symlink at an allowlisted path cannot materialize a disallowed file (`settings.json`, a credential) in the store root, where nothing un-writes it. The trigger is silent under a store pin the kit cannot honor and under a run-scoped session (a fleet of run-scoped workers each spawning a sync would be contention with no owner), whose own block already claims the whole of what this hook says about where the store stands; it rides beside every other state, a localized pin stand-down included, exactly as the decay nudge does.

The embedder-absence nudge is the same shape and needs no fence for the same reason: it reports whether the local embedding stack is installed, and every word of it is a literal in the hook's own source or the install remedy the doctor and `memq find` share, so nothing store-written or machine-derived rides it. It is gated identically, silent under a stand-down and inside a run.

The anchor-drift line the same hook emits is a third member of that class. Every word of it is a literal in the hook's own source and every value on it is an integer the hook computed, at most three of them: how many project memories anchor a changed or missing file, how many the pass reached and could not settle, and how many its own read budget stopped short of. No record name and no anchor path rides it, which is why the line points at `memq decay-scan` for the detail rather than carrying it. Silence there is reserved for three inputs and each is a true nothing-to-say: an honored store pin, every count at zero, and a memq whose export table has moved, which the hook tests for before it calls anything. A throw is not on that list and answers in its own fixed sentence, because an error boundary that returned the clean answer would be the same defect the three-count split exists to prevent.

**The sync repository's allowlist is the boundary the whole replication design rests on, and it is not self-enforcing.** The store root holds `.credentials.json`, `settings.json`, `history.jsonl`, and every session transcript, so a git repository there is one careless add away from publishing them. The gitignore excludes everything and re-includes only the memory tiers and the machine coordinator directory, admitting under each root the forms that root's own contract defines rather than one set shared across all four. There are three distinct sets across the four roots, because the roots do not hold the same things. The project tier admits `*.md`, the extension-less `decay-stamp`, and both journal sidecars under the names memq's own constants give them, `outcomes.jsonl` and `usage.jsonl`, since the journal and the decay stamp are per-project and both of their writers resolve through the project memory directory. The type and operator tiers admit `*.md` and `usage.jsonl` alone, the usage sidecar being the only memq output written into a shared tier. The coordinator directory admits `*.md` alone, the form every file its contract names takes, so a journal or a stamp some other tool writes under that root stays on the machine that wrote it. The set stays form-shaped rather than path-shaped, and so stays wider than that contract: a `.md` at any depth under any directory there syncs, while the contract names four fixed paths. What the narrowing buys is that the admitted form is one the contract's own writers produce, where the retired one was a form no writer of that root produces at all. Deriving each root's forms from its own contract is what closes the hole an extension form leaves open, since a re-include written as `*.jsonl` admits whatever any tool writes with that extension anywhere under the root, and that tool need have no relationship to the store at all. Three residuals stay and none is closed by naming. A re-include by name still admits any file carrying that name anywhere under its root, so a foreign writer that happens to choose `usage.jsonl` is admitted exactly as memq is. A root that gains a form later is a widening someone performs deliberately, which is why one definition per root feeds both the generated text and the path predicate rather than each carrying its own list to drift. And the widest of the three is the one this narrowing does not touch at all: every root still re-includes `*.md` by extension, which under the same reasoning admits any `.md` a foreign tool writes anywhere beneath it. That one is exempt rather than overlooked, and the exemption is structural: a memory record's filename is chosen by whoever writes the record, so there is no closed set of names to enumerate in place of the form. Naming closed the journal sidecars because memq owns those two names; it cannot close a form whose whole purpose is to carry names nobody has picked yet. But ignore rules alone do not close it: a `.gitignore` planted inside a directory git traverses outranks the root file and can re-include what the root excluded. So the guarantee is the rules plus four direct probes the doctor re-derives on every run, reading the four surfaces a path can reach by, the ignore rules, the worktree, the index, and the object history. Each answers a question the others cannot: a tracked file ignores the ignore rules entirely, and a blob in history survives being untracked. Any drift in the allowlist is a FAIL rather than a warning, and a probe that cannot answer is also a FAIL, because an unproven negative is not a clean one. The commit path refuses rather than repairs: it will not add or commit unless both managed files verify canonical, and it restores the index it found rather than leaving a disallowed path staged.

**The doctor's sync report is a trusted output channel carrying store-derived strings, and two lines in it are commands an operator pastes.** Branch names, the upstream ref, the configured `push.default`, and the origin URL are all read out of the store's own git state and printed to the terminal an operator reads before deciding what to do about a broken sync, so each goes through `Get-SanitizedLine` first: bytes outside printable ASCII stripped, length capped at 200, and any truncation marked in the line rather than silent. That bounds what reaches the eye and says nothing about what is safe to run. The first of the two runnable lines, the `git branch -m <local> <upstream>` rename remedy on a name-pair finding, therefore takes a gate of its own rather than resting on the sanitizer: the merge ref must sit under `refs/heads/`, both names must match `^[A-Za-z0-9][A-Za-z0-9._/-]*$`, and both must survive sanitization unaltered. Git permits `;`, `&&`, `|`, `$()` and quotes in a branch name, every one of them printable ASCII, so a store branch named `main;calc` would otherwise render a remedy that runs `calc` when pasted. A leading `-` is barred for a different reason: it carries no shell meaning, but git reads it as an option, so a branch named `-f` would compose a forced rename that clobbers an existing ref. Where any clause fails, the finding is still reported in prose with no runnable command. On the read side the doctor's git invocations pass an argv array with no shell, so a hostile branch name reaches no second command and no config key. The second runnable line is the manual push recipe, `git -C <store> pull --rebase` then `git -C <store> push`, printed in the memory-sync section's FIXED branch beside the statement that the fix pass committed and did not push. It takes no gate of the first line's kind and needs none, because it interpolates no store-derived string: its one substitution is the doctor's own `$claudeDir`, composed from `USERPROFILE` at the top of the script rather than read out of the store's git state. It is deliberately embedded raw where a branch name would be sanitized, since `Get-SanitizedLine` strips non-ASCII and would silently cut a non-ASCII profile name out of a path the operator is meant to copy, turning a correct command into one that names a different directory. What bounds it instead is where it prints: the FIXED branch is the only one reachable after the leak probes have all read clean and a destination has been resolved, so the branch that hands over a push command is the branch that has proven there is nothing there to leak, and the FAIL raised because a non-memory blob is reachable in committed history carries no such line. The residual is `USERPROFILE` itself, which is attacker-reachable in the same way it is everywhere else in this document, and which redirects the path the operator would run the push in rather than the command they would run. One disclosure is outside all of that: the report prints the origin URL as configured, so a remote in the `https://<user>:<token>@host/path` form puts the token on screen and into whatever the operator pastes into a chat or an issue. `docs/backlog.md` carries the redaction item.

**Project-tier output is unfenced only while the project that wrote it is the project reading it.** That is the whole justification, so it holds exactly as far as the condition does. Under a store pin the condition is false by design: one tier serves every repository the instance works in, so a memory written while working one repo is read back by a session working another, and the writer is a spawned worker rather than the attended session reading it. That is the same sentence this document uses to justify fencing the pending tier, so pinned project-tier bodies and pinned digest records carry the fence too. The decision is keyed on whether a pin is in effect, never on the tier's name, because the name is precisely what stops being a reliable signal.

One record type is outside that rule today: `recall`'s journal lines print at column zero under a pin, each carrying the latest summary another of the instance's workers wrote for that key. `recent`'s journal lines are fenced, and the two differ because the surfaces differ in size, one line per key against one line per entry inside a window. The residual is real and narrower rather than absent, and it runs more often, since `recall` fires at every effort start. `docs/backlog.md` carries the item.

A second, narrower residual sits on `recent`'s framing line. The line is decided from the type-derived records the digest built, not from the ones that survive the budget cut, so a pinned digest whose every type line was cut still names the type tier in its provenance line. The direction is over-claiming provenance rather than under-fencing content: no line loses its indent, and every fenced line still rides under a fence.

## Storage properties

Plaintext. The three memory tiers and the machine coordinator directory are versioned: `~/.claude` is a git repository once the sync repo exists, and that repository replicates to whatever remote is configured for it, nothing in the kit reading that remote's visibility or refusing a public one, which The coordinator board section below states at length and which this sentence deliberately does not narrow back to a private one. The coordinator directory is versioned without the merge attribute the tiers carry, and by construction rather than by omission: `Get-MemorySyncAttributesText` derives one `merge=union` rule per `.jsonl` form per root from the same per-root form sets the allowlist is written from, so the coordinator root contributes no rule because its set holds no `.jsonl` to merge, while two of its four file forms are multi-writer across machines by their own contract, so an ordinary concurrent append there takes a content conflict rather than a union merge, at the blast radius the conflict paragraph above describes. The single-generation `.bak` written before a rewrite is the only local recovery for an overwritten memory, and the next rewrite of that file overwrites it; that is unrelated to, and much weaker than, what git itself now retains. Four paths back up a memory record itself, being the four that overwrite one, and they are worth counting together because each leaves the same single-generation `.bak` and no other local recovery. The shared-tier body repair (`add-type`/`add-operator` with `--update`, a body flag, and `--confirm-shared`) is the first. The second is `memq anchor`, which rewrites one project-tier record's `anchors:` line and leaves a `<name>.md.bak` beside it holding the record as it stood before the rewrite. The third and fourth are the two directions of `memq triggers`, which rewrites a record's `triggers:` line on any tier: a merge, which only ever adds an entry, and a `--replace`, which states the line whole and so removes every entry the invocation does not name, removing the line itself when it names none. The replace is the one of the four that destroys text on a shared tier at a caller's word rather than as a side effect of authoring, which is why it takes `--confirm-shared` as the body repair does, and why the `.bak` it leaves is doing more work here than at the other three. That backup is worth knowing about for what it is not: no listing surfaces it, and a successful anchor names it nowhere, the clause that reports a backup riding the verb's failure line only. It holds the pre-rewrite text of a record whose body the verb never touched, so what it exposes is the same body already live one file over rather than anything new, and `*.bak` sits in the sync's never-sync patterns, so it stays on the machine that made it. The other locked rewrites leave a backup of what they rewrite rather than of a record: `decay-prune`, the create path, the `--update` repair of a description or a body, and both delete verbs each take one beside every index, journal, or sidecar file they rewrite, and `decay-prune` moves a record rather than overwriting it, so it has no record backup to leave. Those `.bak` files never leave the machine: `*.bak` sits in the sync's never-sync transient patterns, so the recovery is local only. A record removed by `delete-type` or `delete-operator` leaves no local recovery the verb can name, deliberately, and that holds for the index and sidecar backups as well as for the record: any confirmed run reaching its end, including one that finds no record left to remove, removes the backup beside each of those three paths, whoever wrote it, which also spends whatever single generation any other record in that tier had there, a spend the command's own output does not report, on the reasoning that a copy of a body the operator just destroyed is the archive the verb exists not to leave, and an index line for a record authored without a body flag carries that whole body. Three things leave a backup- or temp-shaped copy of the removed record and nothing else does, the git history above and the vector index and transcripts the Not-claimed section covers lying outside the verb's reach entirely: a delete that stopped before its closing sweep, where the backups are the recovery for a rewrite that did not land; a completed delete whose sweep could not remove one, which is named on stderr and deliberately does not fail the command, so a zero exit is not on its own evidence that the residue is gone; and a `<file>.tmp.<pid>` a hard-killed rewrite stranded at one of those paths, which the sweep does not name and which the Not-claimed section below describes.

Removal replicates asymmetrically, because the sync's merge policy differs by
file. A record file and the `MEMORY.md` index lines are ordinary tracked
content, so a delete propagates as a deletion and a rewrite exactly as an add
propagates as a creation. The usage sidecars do not:
`memory-types/**/usage.jsonl` and `memory-operator/**/usage.jsonl`, the
shared tiers' two among the four rules the attributes text derives, one
per `.jsonl` form per root, carry `merge=union` in the store's
`.gitattributes`, which is what keeps two
machines' concurrent appends from colliding, and union merge has no way to
express a removal. A delete's removal of a record's usage stamps therefore
holds on the machine that ran it and is undone for any stamp another machine
still carries, which returns at the next merge touching both sides. What
returns is a name and a timestamp in an applied-stamp line, never a body, and
the record those lines counted is gone from every tier; what it means is that
the stamp removal is local hygiene rather than a replicated guarantee. That
matters because the stamps are not inert. A record created later under a
removed record's name inherits any applied history that came back, and an
applied history extends decay thresholds by 30 idle days per distinct applied
day up to the 365-day cap, so a fresh record can outlive the retention policy
written to retire it. The recycled name is reachable rather than theoretical:
the create path's duplicate check reads the live file only.

A delete meeting a record another machine has since modified is a git
modify/delete conflict, and the store's sync handles it by standing down
rather than by choosing a side. The background runner's rebase fails, the
run aborts it so the worktree is left exactly as it was found, and it records
`transient` with reason `pull-conflict`
(`plugins/claude-kit/doctor/sync-store.ps1`). Nothing is lost and nothing is
silently resolved, which is the sane behavior; what is worth knowing is the
blast radius. The stall is the whole store's, not the conflicting record's, so
until someone resolves it by hand that machine stops syncing every tier, every
project, and the journal along with them, behind a soft nag rather than an
error.

A credential, connection string, or token written into a memory file, a journal entry, or any file of the machine coordinator directory outside its `claims/` subdirectory, which the allowlist excludes outright as machine-local mutual-exclusion state, is committed, and on a store with a remote pushed, with no further deliberate act on Windows, where the background sync runner does both at the next session start and the doctor's `-Fix` commits on demand, leaving the push to that runner or to a manual push in the store. Any session on this machine is a third actor, by either of two hand paths that are not equivalent. It can run that same sync runner by hand at a moment of its own choosing, which performs both acts, or push an already-committed store with the bare-git pair two shipped skills document, which performs the push alone. Neither is screened the way the hook's own spawn is, and they are not screened alike either, which is worth stating because the hook is the path a reader pictures. A hand run of the sync script takes that script's own ownership test, which accepts a marker-bearing `.gitignore` first, where the hook reads the unclonable `claudekit.memorysync` local config key; the bare-git pair takes no ownership test at all, and no allowlist probe, no inbound tree screen and no lock. And the hook spawns that script under an environment with every `GIT_*` variable stripped, where neither PowerShell script scrubs anything and bare git scrubs nothing, so either hand path carries the invoking session's `GIT_CONFIG_*`, `GIT_SSH_COMMAND` and `GIT_PROXY_COMMAND` into the fetch and the push, and its `GIT_DIR`, `GIT_COMMON_DIR` and `GIT_WORK_TREE` besides. Those last three are the severe half, because they re-aim the run at another repository rather than steering a run already pointed at the store, and `GIT_COMMON_DIR` redirects even a `-C <root> config --local` read, so it answers the ownership gate itself. Those are properties of every hand path into this store, the manual push named above and a hand invocation of the sync runner alike, and no skill's prose confers or withholds them. Off Windows no runner spawns, so both acts are hand-run there, which narrows the window rather than closing it: the credential is still committed by the first fix pass anyone runs and still reaches the remote at the first push. From there it persists like any other tracked content: a later edit or local delete leaves the earlier blob reachable in history, and once pushed it reaches the remote object history too, recoverable by anyone who can read that repository until the history is rewritten everywhere that cloned it and the credential rotated. The sync boundary is path-shaped rather than content-shaped: the allowlist probes prove a path sits inside a memory tier or the coordinator directory and takes one of the admitted forms, and nothing on the commit, push, or check path reads a byte of content looking for a secret. The only control preventing the write in the first place is the instruction in the `memory-system` skill telling the model not to record one, and that instruction reaches the memory tiers alone, because it is an instruction to that skill's writers and the coordinator directory's writers are the classes the role skill's directory contract names, seats, the hooks and CLIs that stamp their own machine-written lines, claim-writing subagents, and inbox appenders, none of which load it to write a board line, a registry entry, a claim, or an inbox request. Nothing states the equivalent for that directory. Its own content rules are per file form rather than one rule over the directory, and none of them is about secrets. The board bars The coordinator board section below states, no absolute path and none of the operator's words, reach the board alone and bound two named disclosures rather than content in general. A registry entry takes its own bar from the role skill's contract, and that one is conditional: an absolute `Workdir:` is permitted where the operator has answered who reads the store's remote, the default state being unanswered. The claim file and the Admin inbox carry no content bars at all. So a credential in a board line, a registry `Status:` line, a claim, or an inbox request is refused by nothing, and every one of them but the claim syncs like any other admitted content. Sync does not weaken the memory-system instruction where it reaches, but it changes what a lapse costs: what stayed on one machine now reaches every machine that pulls. There is no redaction, no scanning, and no mechanical guard, on write or on sync.

## The capture spool

`kit-sidecar-capture.js` is a PostToolUse hook that appends one JSON line per completed Bash
tool call to `~/.claude/kit-sidecar/spool/<UTC-date>.jsonl`. The line carries the call's stated
intent, its command text, and its output, so the spool holds verbatim whatever any command
printed, credentials and tokens among it. Each judged field travels at up to 6,000 characters
(a 16,384-byte line bound over the record), and a field past the cap keeps its head and its
tail around an in-band cut marker, so the end of a long output, where a build or a stack
trace often prints its most sensitive lines, is part of what the spool and the egress below
carry. The three identity fields, `sessionId`, `cwd` and `tool`, are cut to 512 characters on
a plain head slice instead, because the whole-line pass cannot shorten them and a skeleton
over the line cap drops the record. It is the same single principal as every other surface
here: no privilege boundary separates the sessions being observed from the file observing them.

The hook is dormant unless the spool root already exists, and it never creates it. The judge
daemon does, which makes the root the activation lever in both directions: running the daemon
once turns capture on for every session on the machine from its next tool call, and deleting the
root turns it off at the next one, with no restart and no setting.

The spool does not reach the store remote, and by construction rather than by a rule anyone has
to remember. `Get-MemorySyncAttributesText`'s allowlist in
`plugins/claude-kit/doctor/install-memory-sync.ps1` opens with `/*`, excluding the whole store
root, and re-includes only the memory tiers and the coordinator directory; `kit-sidecar` is not
among them and appears nowhere in the doctor. So the spool is machine-local in the strong sense
the memory tiers are not.

At rest it is protected by the profile directory's ACL and by nothing else on Windows, which is
this fleet's primary platform. Day files are created with mode `0600`, and Node maps a mode to
the read-only attribute alone on Windows: `0o600` carries write permission, so no attribute is
set and the file inherits whatever the containing tree grants. The mode is a real control on a
POSIX host and an inert argument here, so the ACL is the whole story on the machines actually
holding the data. That posture is roughly the one the session transcripts in the same tree
already have, which is why the spool is not a new class of exposure so much as a second
concentration of one.

Retention is bounded in two places and neither is a guarantee about the past. The hook stops
appending to a day file past a size cap, and the daemon sweeps day files older than the window
`sidecar/CONTRACT.md` states. A machine whose daemon is stopped or uninstalled keeps its existing
spool with nothing sweeping it.

**The spool is not tamper-evident, and nothing here claims otherwise.** Removing the spool root
stops capture instantly, and the tool call that removed it is itself uncaptured, so a spool that
was switched off reads exactly like a fleet that was idle. Any session can append hand-written
lines as easily as real ones, and the intent side of every line is authored by the same party the
line is evidence about. Full closure is out of reach under the single-principal model this
document opens with, so the limit is stated rather than engineered around: a verdict count is
evidence about calls that were captured, and it is not evidence that all calls were.

Egress belongs to the daemon rather than to the hook, and it crosses a machine boundary. The
daemon sends the intent, action and result triple to a local-model endpoint named by
`~/.claude/kit-endpoint.json`, a machine-local file the operator authors per machine. On this
fleet that endpoint runs on a different machine reached over a private network switch, over
whatever transport the configured URL names, which for the usual local-inference default is
plain HTTP with no authentication, and it serves other tenants besides the sidecar. Nothing on
that path redacts, and no section of the sidecar plan screens what goes. A command that echoed a
secret therefore puts that secret in a prompt on another machine.

The 6,000-character figure above bounds what the hook writes rather than what this path can
carry. The daemon reads a judged field back under its own defensive cap of 12,000 characters
(`sidecar/spool.js`), twice the write side, so a line the hook wrote is never touched by it and
a line something else appended to the spool can put twice as much of a field on the wire.

The daemon writes its own records beside the spool, and they are a second copy of the
same material rather than a summary of it. `~/.claude/kit-sidecar/logs/` holds one
`verdicts-<sessionId>.jsonl` per observed session and a shared `findings.jsonl`, and each
record carries the call's stated intent in full, a bounded preview of its command, and the
model's one-clause reason. The reason is model output derived from whatever a command
printed, so it is neutralized at the daemon where it is parsed: control characters, the
bidirectional controls and overrides, the zero-width and invisible formatting characters
(the soft hyphen, the variation selectors and the byte-order mark among them), and the
Unicode tag block, the invisible channel an instruction can be encoded into whole and
recovered from intact, are all stripped before the reason reaches a log line or a findings
file. The class lives in a Unicode-flagged pattern, because the tag block sits in a
supplementary plane a non-Unicode character class cannot express at all. The delivery hook
applies the same guard again on the way out.
Three surfaces name that screen and two implementations carry it. The shared endpoint client
owns the implementation, and the daemon's text module re-exports it rather than keeping a
second copy. The delivery hook keeps its own, pinned equal to the daemon's by a test rather
than shared by a require, because it is a hot PostToolUse path that must not pay a larger
module's load to answer one question. Re-applying the guard at the boundary that reaches the
model is deliberate and not redundancy: the inbox is a plain file, so a reader that trusted
the producer would be inheriting a guard the writer of a given line may never have run.

Those logs are swept on the same schedule as the spool and bounded the same way, which
matters because the preview's justification depends on it. A preview is safe to keep only
while the full command still sits in the spool, and past the retention window the log copy
would otherwise be the only copy and would outlive the material it was taken from.

The endpoint the daemon sends to is named only by the machine-local config file, and no
component writes the address to a log line, a record, or a report. What the records and the
startup line carry instead is a truncated hash of the host, which is enough to tell two runs
apart or to notice that an endpoint changed between them, and not enough to name it. The
address is the host and its port, and the path is not screened beside it: a refusal the
endpoint answered with a non-2xx status carries the pathname the request reached, so a
configured URL bearing its own path contributes those segments to that detail, and the daemon
carries that detail onto the surfaces named here, on both of its legs: the judgment leg's
durable gap record for every pass whose run of refusals opens on a live one, up to the third
consecutive refusal, past which a latch writes a fixed sentence in the transport's place, the
recognition leg's own gap record for every gapped call with no coalescing at all, the
operator-pasteable rollup over both, and stderr wherever either leg stands down on a streak of
refusals. Those surfaces do not reduce the text the way the relevance channel's printed line
does, and they do not all treat it alike: the two gap records and stderr carry it as the
transport worded it, while the rollup strips the control, bidirectional and zero-width
characters and cuts it at 2000 characters, which is neither the printable-ASCII reduction nor
the 120 characters that channel prints. The relevance channel section below states the same
residual for its own surface. The daemon and `memq find` alike report loudly when the
configured host is neither loopback nor a private address, the daemon at startup and the
search on the call it is about to make. The reading is one implementation in the shared
endpoint client rather than a check each producer remembers to make, because a warning the
second producer forgets is one that covers whichever path happened to be written first. That
is a detection control and not a prevention one: anything running as this user can rewrite the
config, which is the same single principal the rest of this document assumes, so what the
warning buys is that a redirected endpoint is visible on a surface someone reads rather than
invisible on every surface at once.

The judgment prompt (`sidecar/prompts/`, the judgment line) fences the judged call's
three sides with a per-call nonce drawn from a cryptographic source after the content it
fences already exists, so fenced content cannot pose as instruction: a forged fence
marker can only match by guessing the draw, and one whose tag differs is data by the
prompt's own rule. The party being judged writes all three fenced sides, which is the
whole reason the fence exists, and the sidecar holds no authority either way.

The prompt also marks partial input, and the marking is condition-bounded rather than
authenticated, which is a deliberate posture with a named residual. A triple built from
an entry whose `truncated` flag is set opens with a capture-cut notice
above the fences, and a command cut at prompt-build time carries the cut in its ACTION
label; the prompt pairs each marking with the reading it licenses, that absent text is
unknown rather than evidence, scoped to the marking's own field where it names one. The
flag is raised by the capture hook running inside the judged session, and again by the
daemon's own read-side cap when that cap cuts a judged field, so a defensive cut is
never judged as if it were whole text. The judged party therefore controls whether the
notice appears on its own lines. What that control buys is bounded by the
grant: the leniency is absence-leniency only, a visible contradiction still convicts in
a cut input exactly as in a whole one, so a false flag cannot launder evidence that is
present, and a suppressed flag buys only the unmarked reading, under which the prompt
promises nothing about completeness (its claim is pipeline-scoped: this pipeline cut
nothing, never that the text is whole). A third marking is in-band: a field cut at
capture keeps its head and tail around a cut-marker line naming the count of characters
removed, and the prompt reads that shape as a marking only inside a triple that opened
with the capture-cut notice, since capture happens before the per-call nonce is drawn
and the marker therefore cannot be authenticated, only condition-bounded. The residual
that bounds it is priced: a forged marker under a genuine notice buys placement of the
perceived hole and the adjoining-evidence reading around it (the text on either side of
the mark is read as that field's own head and tail, so a forger chooses where a seam
appears to sit), and nothing more, because the immunity it triggers is the same
absence-leniency, and in a triple with no notice a marker-shaped line is ordinary
fenced data. SYSTEM names its own markings, the notice, the fence labels and the cut
marker, in the fenced-data shape list, so a judged party printing any of those shapes
inside its output has produced data by the prompt's own rule rather than a marking.

### What recognition adds to the egress

Judgment sends one call at a time: its stated intent, a bounded preview of its command,
and a bounded result. Recognition sends something else alongside it. To ask which stored
records bear on a call, the daemon sends that project's whole memory INDEX: one line per
record, each carrying the record's human-authored title and its one-line description, for
every record in that project tier. Record bodies never travel, and this call sends no tier but
the project's own. That second bound is recognition's rather than the machine's: the memq
relevance channel below is a separate path on which the shared type and operator tiers do leave
this machine.

That index is a different kind of material from a command and its output. It is a curated
list of what a project has learned, so its titles and descriptions name internal systems,
recurring failures and operational habits in compressed form, and it goes off this machine,
across the virtual switch to a model service on the virtualization host, in cleartext HTTP
with no authentication in the default configuration, to a service shared with that host's
other tenants. The same posture the spool takes applies, for the same reason: the transport
is the exposure, and the bound on it is that the endpoint is machine-local configuration
and a machine with no config file makes no call at all.

The reach is bounded by the calls that were spooled. A project only has its index sent if a
call from that project reached the spool, and a project whose index is absent, unreadable,
or not a regular file produces no recognition call at all rather than an empty one. The
index is read through a size-bounded read and refused when the path is a link or anything
other than a regular file.

Recognition runs in both injection directions and is guarded on both. Inbound, the index
lines are file content that the model reads as data, and anyone who can write a memory
record can therefore write text into a prompt; the prompt fences its sides with a per-call
nonce so index content cannot pose as instruction, on the same reasoning the judgment
prompt already uses. Outbound, the model's answer becomes a pointer delivered into a live
session, so it is constrained rather than trusted: a returned name that the index which
produced the answer does not itself hold is treated as an invention and dropped, counted
rather than delivered, and every name is checked against the record-name pattern before it
is queued, because that name is spelled into a `memq get <name>` line a reader may run. The
answer's one-clause reason is neutralized and length-bounded like any other model text.

The recognition log is a third machine-local plaintext concentration beside the verdict log
and the findings file, and it is swept on the same bounded window as both, so it cannot
outlive the material it describes.

## The delivery inbox

The inbox is how the sidecar speaks back. The daemon appends one JSON item per session to
`~/.claude/kit-sidecar/inbox/<session>.jsonl`, and the same PostToolUse hook that fills the
spool reads that file on its next Bash call and puts the items in front of the model as
`hookSpecificOutput.additionalContext`. It is the only path by which anything the sidecar
concluded reaches a session, and so it is the one surface in this system where model-derived
text is placed into another model's context. Everything below follows from that.

Delivered text is framed rather than trusted. The block opens by saying what it is, that it
holds no authority, that nothing in it is a request from anyone, and that each pointer is
unverified until checked against the source it names, and it closes on a matching fence. Both
the opening and the closing sit outside the byte cap, so a flooded queue cannot displace the
framing and leave unmarked model output in front of a session. Each item's variable fields
are neutralized and stripped of the quote character, then placed in quoted slots they cannot
close. A block carries at most three items and 600 bytes of item text, and the remainder
stays queued for the next call rather than expanding the block.

Delivery stands down entirely on a subagent call. A subagent's payload carries the parent
session's id byte-identically, so without the stand-down a subagent would drain the parent's
queue into a context that never ran the work being judged.

The off switch is the directory. Delivery is dormant unless `inbox/` exists, the hook never
creates it, and the daemon creates it only at startup, so deleting it stops delivery while
capture keeps running and a mid-pass deletion is refused rather than undone. Both sides lstat
the directory and the session file before touching either, and refuse a link. The offset file
is replaced through a temporary path carrying the writer's pid and six random bytes, created
exclusively, so a link planted at a predictable temporary name is not followed. A per-session
offset advances before anything is emitted, and nothing is emitted when that write fails: a
pointer lost to a crash costs one advisory line, where an item emitted against an offset that
never moved would be re-emitted on every call for the life of the session. The read and the
advance run under a claim at `inbox/<session>.lock` that is attempted once and never waited
on, because a hook observing a session may not put it on a critical path.

Inbox files are swept on the same window as the spool, with an offset kept while its queue is
still live so that expiry cannot re-deliver a whole inbox.

What this does not claim: the inbox is not tamper-evident and not authenticated. Any process
running as this user can append a well-formed item and it will be delivered on the next call.
That is the same single principal the rest of this document assumes, and the framing is the
control that matches it: the block is presented as unverified advisory data whatever wrote
it, so a forged item buys an attacker the same standing as a real one, which is none.

## The memq relevance channel

`memq find` is the one verb in the CLI that sends anything off this machine, and it does so
only where the operator has written `~/.claude/kit-endpoint.json` on this machine. With no
config file the verb opens no socket, creates no file and no directory, and prints exactly
what it printed before the channel existed. That is the bound on this egress: it is
machine-local configuration, and its absence is the default state.

Where the file is present, find probes the endpoint on a short clock and, if something
answers, sends one ranking call on a longer one. The endpoint does not run on this machine.
On this fleet it runs on the virtualization host, reached across the virtual switch, over
whatever transport the configured URL names, which for the usual local-inference default is
plain HTTP with no authentication, and it serves that host's other tenants including the
operator's own agent harness. Nothing on that path redacts. Where the configured host is
neither loopback nor a private address, find says so on the call it is about to make, through
the same shared client the daemon warns from.

That warning's reach is narrower than it first reads, and the gap matters because this fleet
lives inside it. The legitimate endpoint is itself a private address, so the warning fires
only on a redirect that leaves the private network, and a config rewritten from the real host
to another private address, a peer machine or another tenant of the same host, does not trip
it. What covers that case is identity rather than locality: a call names its endpoint by a
truncated fingerprint of the host, so two endpoints read differently on the surface in front
of whoever is running the search, without the address itself ever being printed. The warning
answers whether the endpoint left the network and the fingerprint answers whether it is the
same one as last time. Neither is a prevention control, since anything running as this user
can rewrite the config.

What crosses that boundary is the query text and at most twenty candidate records, each
carried as a name, a bare tier token and the record's one-line index description. The tier
token is the word alone, `project` or `operator` or a type's name. The provenance label the
rendered line shows spells a store's own directory path, which on the project tier is the
flattened absolute path of the repository the record belongs to, and it stays on this
machine: the candidate set spans every store here, so sending that label would export the
directory names of repositories the session never opened, and the account name they sit
under, to a multi-tenant service. The model does not need it, a candidate being identified
on the wire by its position in the list.
Record bodies never travel. The candidates are the records the other two channels put on
screen, which makes the reach wider than the daemon's recognition call in the one respect
worth stating plainly: recognition sends one project's own index, while this sends whatever
the lexical and semantic channels ranked, and the semantic channel spans every memory store
on the machine, the shared type and operator tiers among them. A description written by
another project of the same type can therefore leave this machine because a session in an
unrelated repository typed a matching query. What bounds it is the candidate cap and the
admission floor, not a tier boundary.

One tier is excluded. A run's pending records are unadjudicated drafts the run itself wrote,
and the store's own policy already keeps them out of the semantic index so a run's writes
never reach another session's search. Posting them to a multi-tenant service on another
machine is further than the reach that policy refuses rather than nearer, so the tier that is
deliberately unsearchable locally is not a tier this channel exports. They still print in the
lexical block, which is the session reading back its own drafts.

The address itself is named only by the machine-local config file. No code path writes it to a
line: the transport's error classifier returns a fixed sentence for the one failure shape
whose message would otherwise spell the URL back out, which is a credential embedded in the
configured address. That screen covers the address. What a refusal puts on a line, the
configured URL's own path among it, is inventoried with the degrade lines below. The same
client serves the judge daemon, so that screen is one implementation rather than two.

The model's answer is constrained rather than trusted, because it reaches a terminal and
anything quoting it. An entry must carry both an index into the candidate list it was sent
and the name it believes sits there, and the two must agree: the index selects the candidate,
the name is held to the store's own record-name rule and then compared against that
candidate's own name, and an entry failing either check is dropped. Requiring both is what
makes a fabricated record unrepresentable rather than merely improbable, since a model
inventing a name has no index that resolves to it and a model returning a bare index has
named nothing to check. Two counts are reported and they answer different questions: entries
that resolved to no candidate, which is the invention question, and entries naming a candidate
already ranked, which is the model listing one record twice and raises no question about the
store at all. Neither count names the entry, since the only thing established about it is that
this store does not hold what it claimed. The name that reaches the line is the candidate's
own spelling taken from the store, so the model supplies the ordering and one clause and never
an identifier. That clause is the only model-authored text on the surface, length-bounded and
reduced to short printable ASCII with the double quote barred, on the same screen every other
untrusted string this CLI prints passes through. The block rides under the same provenance
fence as the semantic block, naming itself as model-judged and advisory. Neither the two authoring
verbs' write-time neighbours check nor the decay scan's neighbour-pairs block reaches this
channel: each reads the local index alone, so a record's name and description stay on the
machine at a write and at a scan.

Failure is silent about nothing and fatal to nothing. A missing config stands the channel down
without a word, because a line every find printed would be noise about a channel nobody
configured. A config that exists and cannot be used, a probe nothing answers, a call that
outruns its budget, an answer cut off at its generation ceiling, and an answer that is not a
ranking each cost one line naming that condition, and in every case the lexical and semantic
blocks print exactly as they would have. What a refusal puts on that line varies by its shape,
so the shapes are named here rather than summarized. A non-2xx answer carries the status, the
path the request reached and the dialect it posted in, which is what makes a dialect mismatch
legible, bounded in practice by the 120 characters this surface prints. An error object inside
an otherwise readable answer carries the endpoint's own message, which is text chosen off this
machine rather than by this code. Two screens stand between it and the line, and they are not
one screen: the transport neutralizes it, stripping the control, bidirectional and zero-width
characters and collapsing runs of whitespace, and cuts it at 200 characters, and this surface
then reduces what it prints to short printable ASCII with the double quote barred, at the same
120. Every other shape, an unreadable or oversized body and a missing response among them,
carries its own condition and nothing further. The probe ahead of the call stays blind to the
dialect throughout, because it answers liveness alone and any answer counts. The path that
refusal names is the URL's path component and never its host or its port, so the screen above
holds for the address as that screen means it. What rides into the printed path beyond the
dialect's own suffix is whatever path the configured URL itself carries, so a secret kept in
that path prints there, and so does an address, a proxy-style URL nesting one inside its own
path being the shape where the two claims meet. Both are residuals rather than closed holes,
and both are empty on a config naming a bare host and port with no path at all. The endpoint
is never a dependency of a store operation, and nothing on this path writes to the memory
store.

## The evaluation batteries and the harvest command

`sidecar/battery.js` and `sidecar/harvest.js` are the sidecar's evaluation pair. Both are
on-demand developer commands rather than anything the fleet runs, and both create
concentrations of the same material the capture spool holds. Neither is covered by the spool
section's properties above, so they are inventoried here on their own terms.

`sidecar/batteries/` is frozen fixture content committed to this repository, which is public.
`judgment-v1/cases.json` holds thirteen real production tool calls harvested from real
sessions: each one's stated intent, its command text, and its output. `recognition-v1/index.md`
is a verbatim copy of a project's `MEMORY.md` index. What is frozen there is therefore
published, permanently and to anyone, and git is the whole of that exposure: `build.ps1`
packages recursively under `plugins/claude-kit/` and nothing else, so `sidecar/` is absent from
the plugin zip by construction.

That makes the freezing step, rather than any runtime control, the place where disclosure is
decided. A fixture is screened before it is committed, structurally rather than by keyword: a
real account name, session identifier, agent identifier, endpoint address, or credential
appearing in harvested output is redacted and the redaction is stated in the case's own note,
with the sweep's predicate and its positive control recorded. `sidecar/batteries/README.md`
owns that procedure. The control matters more than the sweep, because a sweep whose pattern is
wrong returns the same empty result as a clean one.

One identifier class is screened by inspection and kept rather than redacted, and the decision
is recorded here because the freezing step is where disclosure is decided. A machine hostname
appears in the frozen judgment cases inside a `kaizen/notes-<machine>.md` path, where it names a
file in this repository rather than a network destination. That is the per-machine-artifact
class the public-repository section below already accepts, and the path is tracked content here
already, so the fixture copy adds no exposure. It is recorded here rather than left to the
case's own note because the sweep cannot carry the class: a bare hostname has no structural
shape, so the all-caps hyphenated pattern catches this one only because this machine's name
happens to take that form, and a host named as an ordinary word passes it untouched. For that
class the hand read of every field is the whole screen, and `sidecar/batteries/README.md`
carries the per-case record.

A battery run writes a second concentration that is machine-local rather than published. It
builds a throwaway state root, under the system temporary directory by default, holding a spool
of the fixture calls plus the verdict logs, recognition logs and inbox items the daemon
produces from them, and it leaves that root in place when it exits so the run can be read
afterwards. None of the spool's own properties apply to it: it is outside `~/.claude`, so the
profile directory's ACL is not what protects it. The daemon's fourteen-day retention sweep does
run over that root, since a battery run is the daemon running against it and the sweep covers
whatever spool, logs and inbox the state root it was handed derives; what the sweep never does
is reap the run's own material, none of which is older than the window while the run is
happening, and nothing sweeps the root at all once the run exits. So retention is not what
removes it either way: removal is the operator's, and the command prints the path and says so.
`harvest.js`'s optional output file is the same class and the same posture.

The egress is the daemon's, unchanged: a battery run is the daemon judging fixture calls, so
every fixture command, its output, and the whole frozen memory index are posted to the model
endpoint over the same cleartext cross-machine HTTP request the sections above describe. What
differs is only that the material is fixture content chosen in advance rather than whatever the
fleet happened to run.

## Environment overrides, and why they differ

Variables that redirect where the tooling looks are gated, and so is the one below that redirects nothing and steers a control's timing instead; all of them are deliberately gated differently:

- **`KIT_MEMORY_ROOT`** relocates the store root, and is honored only when `KIT_MEMORY_ROOT_ALLOW_DATA` is also set. It selects *which data reaches the model*, and, since the `memq-grant` hook below conditions on the same pair, it also selects whether one fixed Bash command shape bypasses the host's permission prompt. That second consequence is newer than the gate's original data-only rationale, and it is why the pair is now load-bearing for execution and not only for content. A third consequence is the background sync's: the auto-sync spawn is gated both to the default `<home>/.claude` root and to a store the config key marks owned, so relocating the root with this variable does not arm the automatic commit-and-push against the relocated directory. That is deliberate, and it is why the gate is ownership rather than the path: `os.homedir()` follows `USERPROFILE`, which is attacker-reachable, so a path check alone would move with the attacker while the un-clonable config key does not. Set without its signal it is ignored for the store root, the real store is used, and a note goes to stderr, with a control reading the bare variable rather than the honored pair: the authoring verbs' write-time neighbours check and `decay-scan`'s neighbour-pairs block stand themselves down whenever this variable is set at all, through one shared predicate, so an ungated value still costs both. The breadth is deliberate, since the check runs in the granted child while the `memq-grant` decision is made in the hook, and a stand-down keyed on the pair would be narrower than the grant condition it is there to cover.
- **`KIT_PLUGINS_ROOT`** relocates the plugin payload the `memq` shim executes, and is honored only when `KIT_PLUGINS_ROOT_ALLOW_CODE` is also set. It selects *which program runs*.
- **`KIT_RUN_ID`** routes a run's memory writes into the pending tier and scopes its reads to that tier plus the main one. It is honored only alongside the `KIT_MEMORY_ROOT` pair above, and carries no separate signal of its own because it selects a subdirectory *within* an already-gated store: the store's gate is the one that decides whether the redirection happens at all. Set without those signals, the memory routing is ignored, the session behaves as an ordinary attended session, and a note goes to stderr. One deliberate exception to that word: a goal-release event still carries the id in its `run` field, since the field is correlation metadata on an outbound record rather than a routing decision, and it is validated by the same grammar. The value becomes a directory name, so it is validated against a conservative token grammar that also refuses the Windows directory-name shapes that alias onto a different directory than they spell (dots-only names, trailing dots, reserved device stems) and is folded the way the platform's filesystem folds it. A value that fails the grammar is refused rather than fallen back on, because a silent fallback would place an unadjudicated write in the shared record.

- **`KIT_MEMORY_PROJECT`** replaces the `projects/<segment>` directory name, which is otherwise derived from the working directory, and is honored only alongside the `KIT_MEMORY_ROOT` pair. Like `KIT_RUN_ID` it carries no signal of its own, because it selects a directory *inside* an already-gated store. It exists because an engine instance spawns workers with three different working directories (a plan worker runs in the repository it is working on), so without it one instance's store fragments into a tier per cwd and a memory promoted out of a plan run lands where no later run and no reviewer reads. Set without the store pair it is ignored, the cwd derivation stands, and a note goes to stderr; set with the pair and unusable as a directory name it is refused loudly rather than falling back, since a silent fallback would scatter the instance's memories back across per-cwd directories invisibly. It answers the same grammar `KIT_RUN_ID` does, from one shared predicate.
- **`KIT_EMBEDDER_ROOT`** relocates where the optional embedding stack is loaded from, and is honored only when `KIT_EMBEDDER_ROOT_ALLOW_CODE` is also set. It selects *which program runs*, the same class as `KIT_PLUGINS_ROOT` and deliberately not the data class: the install location is spelled from the home directory rather than from the store root, so a store redirect gated as data can never move where code loads from. The stack is located by a direct file check rather than by module resolution, because resolution walks upward through parent `node_modules` and would make "installed" depend on where the process happened to start. Set without its signal it is ignored for the load location, the real location is used, and a note goes to stderr, with the same exception the store root above carries: the authoring verbs' neighbours check and the decay scan's neighbour-pairs block stand down on the bare variable, so an ungated value still skips both.
- **`KIT_EVENTS_PATH`** redirects the goal-event sink `emitGoalEvent` appends to, and is honored only when `KIT_EVENTS_PATH_ALLOW` is also set. Unlike the others it selects *where data is written* rather than what reaches the model, which is true of the variable and not of the stream: the coordinator seat's BLOCKED funnel reads `~/.claude/kit-events.jsonl` and briefs the operator from what it finds, so that file is content reaching a session as much as an outbound feed an external watcher reads, and the funnel treats each entry as a claim to corroborate for exactly that reason. The gate is unaffected by the correction, because the variable steers the writer's sink while the seat reads the fixed path, so a redirected writer cannot plant what the seat reads. What a redirected writer can do is silence, and the consequence is stated here because it is stated nowhere else: a repo whose environment carries the pair sends its own sessions' goal events to a file the funnel does not look at, so the dead-worker backstop is off for that repo's sessions, which the funnel's standing honesty about an absent event never proving an absent blocker already covers and which nobody reading either surface alone would derive. Set without its signal, it is ignored, the real `~/.claude/kit-events.jsonl` is used, and a note goes to stderr. The intended users of both signals are the repo test suite and the hook canary's own goal probe, which point the stream at a throwaway file. What the signalled override grants is worth naming exactly, because "sink" understates it: the named path is appended to, and past 1 MB renamed to `<path>.old`, replacing any previous file of that name. Pointed at a regular file the user can write, a goal release therefore appends to it and can move it aside. A symlink or junction at the sink is refused (the regular-file check is an `lstat`, and a hardlink is a regular file that passes, deliberately), and the rest sits inside the accepted framing above, that the gates remove accidents rather than contain a deliberate actor.
- **`KIT_MERGED_PR_GUARD_NO_DEADLINE`** turns off the deadline on the merged-PR push guard's `git` and host-CLI queries, and is honored only when `KIT_MERGED_PR_GUARD_NO_DEADLINE_ALLOW` is also set to `1`. It is the one variable in this list that redirects nothing: it steers a control's timing, and it takes the same gate because here the timing is the control. Every way that guard's queries can fail ends in an allowed push, so a deadline short enough to time them all out would be an off switch for a deny guard, silent and indistinguishable on every surface from a healthy allow. What closes that is the switch's shape rather than its gate: it is a boolean carrying one direction, and that direction is toward waiting longer. Honored, each query runs under `execSync`'s `timeout: 0`, which is how Node spells no deadline; unhonored, each runs under its own production budget, which is per-query and never shared (3 seconds for each git read, 8 for the host query, so a four-query invocation's worst case is 17 seconds). Removing a deadline can only remove `ETIMEDOUT`, and `ETIMEDOUT` is one of the paths that ends in an allowed push, so no setting of this pair can stand the guard down and the honored setting can only make it more likely to block. The gate is uniformity with the rest of this list rather than this guard's safety, and it earns its place by letting a reviewer check one property across every kit override instead of re-deriving a per-variable argument; the same uniformity decides what a value other than `1` means, which is nothing at all, so `NO_DEADLINE=0` reads as no request rather than as a refused one. What the honored setting costs is an unbounded wait, and what bounds it is the caller rather than this hook: the only intended caller is the repository's test suite, which spawns the hook under its own `spawnSync` timeout and so holds the ceiling itself. The switch exists for that suite, which spawns the hook and a faked host CLI on a box under parallel load and so pays spawn costs a developer's machine never does, where a query that overran was read as a missing block. Set without its signal it is ignored, the production budgets stand, and a note goes to stderr, written once per process and only on the allow path, so it never rides alongside the reason a denial feeds back to the model; an invocation that consults no query at all (a non-push command, or a push whose own refspec names develop, main, or master) writes no note, because nothing read the switch; the configured-default exemption and a bare `git push` each reach a git read before deciding, so those write the note like any other consulting invocation.

**What the gates buy, stated plainly, because the uniform rule invites over-reading.** An actor who can set one variable from a committed file can set two in the same file, so against the repository-as-distribution-channel threat above, a second signal is not a mitigation. What it does buy is real but narrower: one auditable rule that holds across every override, so a reviewer checks a property rather than re-deriving a per-variable argument, and the elimination of the accidental case, where a variable set for an unrelated reason or inherited from a parent process silently steers a session. Read the gates as removing accidents and making deliberate redirection legible, not as containment.

**The ungated residual under all of them.** Every default path above ends in `os.homedir()`, which reads `USERPROFILE` on Windows and `HOME` on POSIX. One of those, set from the same committed file, relocates the store, the plugins root, and the event sink together, with no second signal anywhere. The Principals section places an actor with write access to `~/.claude` outside every control here; this is the adjacent case it does not state, an actor who redirects what the kit believes `~/.claude` is. It is a broader compromise than any single override (the harness's own settings and transcripts move with it), which is why no gate here addresses it, but a claim that every path-redirecting variable is gated is only true one level down from this one.

**`KIT_EXTERNAL_ENGINE`** redirects no path and carries no gate, and it is one of three deliberately ungated behavior-steering variables the payload reads (`CLAUDE_CODE_SESSION_ID` and `KIT_GOAL_STOP_RETRY_MS` follow below, and the two the repo-only probe runner reads sit outside that set, at the end of this section), because an external engine must be able to declare itself on a spawn it already fully controls. Set to `1` it stands these hooks down: `session-start.js` drops its drive-to-completion push, `branch-reaper-nudge.js` and `kit-version-nudge.js` go silent, `hook-canary.js` returns before its first probe, `chapter-boundary-nudge.js` emits no reminder, `compact-deferral-nudge.js` neither emits nor stamps (and writes nothing either, its guard returning before the interval stamp rather than after it, which matters because that hook takes its stamp first and emits only if the stamp landed), `memory-recognition-nudge.js` returns before it resolves a store at all, so it neither nudges nor writes its log, and `kit-compact-gate.js` allows every auto-compaction (the compaction-gate section below carries why that is a scope decision rather than a lost control). `stop-docs-hygiene.js` also downgrades its block to advisory. Two consequences belong here rather than in the architecture doc, because they are the loss of controls this document credits elsewhere: the canary's integrity check (the SHA-256 manifest comparison) and its `memq-grant` both-direction probes do not run under the marker, so in a fleet worker neither the tamper detection nor the grant's health check is active, and the Stop-scan backstop for scratch reaching `docs/` becomes advisory. Setting the marker is therefore enough to turn off the detection this document describes, without any second signal. That is accepted rather than mitigated: the actor who can set it on a session is the actor who spawned that session, and the controls it disables all report to an attended operator who is not present in a spawn. What it means for the reader is narrower than it sounds and worth stating exactly: the manifest check protects an attended machine against a hook edited in place, and it has never protected a fleet worker, whose payload integrity is the deploy's concern.

**`CLAUDE_CODE_SESSION_ID`** is the second deliberately ungated behavior-steering variable, and the only one here the kit does not own: the harness sets it in every tool shell it spawns, naming the session the shell serves. Three readers steer three different things with it. The `/kit-goal` CLI's `arm` steers the leash binding: an arm run inside a session binds that session at arm time instead of arming unbound and waiting for a claim point. The compaction checkpoint CLI's session-scoped verbs steer two things with it: which session a release marker names, and, at `open` and `clear`, whether the caller is the session the chapter checkpoint blesses, the same id `open` writes into the record as its opener. Both gate the value more weakly than `arm` does, on character set and leading character alone with no corroboration against a real transcript. The memory store's own resolver steers which project's memory tier answers: its session-transcript leg reads the id to decide which project a working directory is filed under, so the value moves which project's records reach the model at SessionStart and which tier a write lands in. The weaker gate is tolerable because of what a wrong value can reach, which is bounded differently at each reader. At the checkpoint CLI it reaches a compaction's timing, where a wrong leash bind holds a real run. At the store resolver it reaches which project's memory tier answers, and the bound there is a selection rather than a naming: a wrong or hostile id cannot name a store. It can only select, among directories that already exist, one satisfying all four of a single transcript of that id under the harness projects root, the working directory being this process's own, an ancestor of it deriving that same segment, and no repository boundary in between. Two limits ride with that bound and are stated rather than left implied: the corroboration is a filename's existence rather than its content, and the variable is settable by any process running as the operator. It is not inert, though, and the two wrong-value cases differ. A marker naming a session that offers no compaction releases nothing and ages out. A marker naming a live session releases that session's next deferred compaction, which is the cross-session reach the release-marker paragraphs below state. The variable is undocumented upstream. A dispatched subagent's shell carries the dispatching session's id beside the child-session marker, so a marker written from one names the seat that dispatched it, which is the granularity every reader of the variable works at: a session and the agents it dispatched are one identity to the kit, and whether a marker so written is inert or effective turns on whether the named session is live. No second signal gates it, because the pairing rule above exists to remove accidents, and the accident case here is handled by corroboration instead: the id binds only when it is UUID-shaped and a transcript file with that basename exists under the harness's transcript store, checked before anything is written, so a stale export, an inherited value, or a repo-committed terminal env carrying a UUID that names no real session on this machine arms unbound rather than binding. It does not fall back to the claim points on the same terms as an arm with no variable at all, and the difference is worth stating because the corroboration is exactly what it survives: a shaped id is recorded as `armingSession` whether or not its transcript resolved, and that field is itself one of the two things a claim point binds on, so the session bearing that id claims the leash at its next stop or auto-compaction offer. An arm that could read no shaped id at all records nothing, and there the typed arming text in some session's transcript is the only route left. What the recorded id can reach is bounded by the same fact that makes it useful: a claim happens only where a session carrying that id actually reaches a hook, so an id naming no live session claims nothing and stays inert for as long as it sits there. What the corroboration cannot refuse is a value naming a real transcript on this machine that is nonetheless not the arming session; that binds a leash no session enforces, is visible in the arm output's binding report and in `/kit-goal status`, and re-arming recovers it, the same bounded, recoverable blast the claim predicate's accepted risk below states. Two smaller residuals ride with the mechanism: the transcript scan can store another project's transcript path in this repo's `.kit/goal-state.json` when the id's single match lies in another project's directory, the first-of-several case being closed, since an id filed in two project directories arms unbound (the path is never surfaced, per the goal-state section below), and the scan composes its candidate paths from `os.homedir()`, which the ungated-residual paragraph above already places outside these controls. The variable is undocumented upstream and can change or vanish without notice; either direction degrades to the unbound arm and the claim points, never to a wrong bind.

**`KIT_GOAL_STOP_RETRY_MS`** is the third and the narrowest. It replaces the completion leash's re-read schedule in `kit-goal-stop.js`, the short delays that stop the hook concluding from a single read while the harness is still appending the turn's final assistant entry. It carries no gate because the code reading it bounds both ends of what it can do: each delay is clamped to 5 seconds and the schedule to 5 delays, so no value pins a synchronous hook to its timeout, and the hook's top-level call is wrapped so that any error allows the stop. What a hostile or accidental value buys is therefore the opposite of a disabled control in the sense the guards above use: disabling the retries makes a leash release slightly more likely, never less, and the leash is guidance enforcement rather than a security boundary. It is listed here because a claim that every behavior-steering variable is gated is only true of the ones that can cost something.

**`PROBE_CLAUDE_BIN`** and **`PROBE_HOME_DIR`** are ungated as well, and they sit outside the three above rather than beside them, because nothing an installed session loads ever reads them: they steer `tools/probe-corpus/run.mjs`, a repo-only instrument. The first names the binary the runner spawns as its cold reader, which is the *which program runs* class `KIT_PLUGINS_ROOT` and `KIT_EMBEDDER_ROOT` take a second signal for. The second names the directory the runner copies the reader's credential from and reads a `home/<name>.md` shape entry out of, which is the *which data reaches the model* class. The `--claude` and `--home` flags beat both. The scenario-probe runner section below states what stands in for the gate and what it does not reach.

Two further variables, **`KIT_SPAWN_VECTOR`** and **`KIT_RUN_SECTION`**, redirect nothing. They are recorded as provenance in a pending memory's frontmatter, reduced to bounded printable ASCII at the write boundary so a value cannot forge an additional frontmatter field or break the document's structure.

No gate may be loosened to match another, and the reason the store root carries one at all is worth keeping: it was originally ungated on the reasoning that it redirects data rather than code. The project-type tier voided that. The SessionStart hook reads the store, so a redirected root supplies content a session sees before the user types, which makes it a behavior-shaping input and not merely a data path.

The precondition the old gate rested on was **the launching environment is trusted**. In a deployment where repositories sync across machines, accounts, and people, that precondition does not hold: a committed `.vscode/settings.json` (`terminal.integrated.env.windows`), a `devcontainer.json` env block, or an `.envrc` sets environment for whoever opens the repository. The gate exists because cloning a repository must not be enough to steer what a session reads.

## The `memq.cmd` residual

On Windows, `memq` resolves to a different wrapper per shell: PowerShell resolves `memq.ps1` (arguments splat directly onto node), Git Bash resolves the extensionless `memq` (`"$@"`), and only a caller inside `cmd.exe` reaches `memq.cmd`.

`memq.cmd` forwards arguments as `%*`, which `cmd.exe` substitutes into the command line before parsing it. An argument carrying an odd number of double quotes therefore ends the quoted region, and a following `&` starts a second command. This is confirmed by probe, not theoretical.

What covers it: the `memq.ps1` and sh wrappers keep the two common shells off that parser entirely, `memq` strips double quotes from free-text fields at the write boundary, and the skill instructs the model to compose summaries itself rather than pasting raw tool output into an argument.

The limit of that coverage: the write-boundary strip protects stored *summaries and descriptions*, not memory *bodies*, which are length-capped only.

For bodies specifically, `--body-file` takes the text off the command line altogether: the argument is a path, and the content reaches memq through a file read rather than through any shell's parser. What that removes is the composing hop, and that much is a property of `--body` alone, so a body of any composition should take the file channel. It does not remove the residual this section closes on: a body reaches the store unstripped whichever channel wrote it, so what `get` hands back can still carry the command break onto a later command line. What the file channel adds in its place is an encoding surface the argv channel does not have, since a file holds bytes no command line could carry. On the file's content it answers that surface and only that surface, the channel's path-text, file-shape and size guards being a separate matter: a UTF-16 file, a file that is not valid UTF-8, and a file holding a NUL byte are each refused by name, a UTF-8 byte order mark is stripped, line endings are normalized, and the result meets the same cap gate `--body` takes. Body *content* stays ungated on both channels, which is the standing position stated above rather than anything this channel changes: the fence `get` puts around another writer's body is the control there, not the charset.

This one is rated higher than a single-operator store would warrant. With a shared kit and a shared type tier, a body one person wrote can reach another person's command line, so the exposure is no longer bounded by one operator's own paste.

## Locks are availability, not integrity

The lockfile serializes rewrites of shared files. Two properties to know:

- A lock path can be wedged by a directory, or by a file whose contents are valid JSON but not a lock record, either of which the stale-break correctly refuses to remove. There is no in-tool recovery; the fix is deleting the file by hand.
- Whether a locked rewrite copies bytes that appeared past its read is stated by each call rather than defaulted, and the helper refuses a call that states nothing. The files with a lawful lock-free appender take the copy: the outcome journal, the usage sidecars in every tier, whose read-stamp hook appends without the lock by design, and the project tier's own index, whose lock-free writers the next two bullets name. Growth alone does not establish an append, because the whole store syncs and a pull replaces a file while holding no lock this module takes. So the head check is not the copying caller's to opt into: every rewrite reads the file back first and fails, with nothing written, unless the bytes the pass read are still that file's head, in preference to republishing a stale copy of every line the pass did not touch. What the per-call statement decides is the narrower question of whether bytes found past that head are carried forward or dropped. A window remains between that copy and the rename in which one concurrent append can be lost, which is one usage stamp and matches the tolerance the sidecar's readers already carry for torn appends. A caller that is removing a record also states what the carried tail may not bring back, so a usage stamp for the deleted name cannot ride back in past the rewrite that dropped it.
- The two index files are decided per tier, not per name. In the shared tiers nothing appends to them lawfully and a sync pull replaces them whole, so a rewrite there takes itself as written; the project tier's own index does have lock-free writers and keeps the copy. What the shared-tier choice gives up is stated rather than implied, and a pull landing inside that window is no longer last-writer-wins. One that replaces the file whole loses instead: the head check fails the rewrite with nothing written. One that only appends, which is the shape another machine adding a memory produces, leaves the bytes the pass read as the file's head, so the rewrite proceeds and drops what was appended, that being exactly what this choice declines to carry.
- The shared tiers' usage sidecars have both properties, and so does the project tier's sidecar. They keep the copy, because the read-stamp appender is the common case and the rebase collision is the rare one. The project tier's own index keeps the copy for a different appender: `merge=union` is written per name rather than per extension and reaches only the sidecars each root admits, so `MEMORY.md` gets no union merge, and what makes it append-friendly is that a session's Write tool adds an index line beside a memory it just wrote, and a reinstatement restores one by hand, both lock-free by design. The residual is stamps a prune had just removed coming back, which is the same reinstatement the union merge produces anyway. A rebase result that no longer carries the read bytes as its head is not spliced at all: the rewrite fails with nothing written, and the same command run again rebuilds from the file as it stands.

## Hooks fail open, and what that costs

Every kit hook swallows errors and exits 0 silently, by design: a hook bug must never trap a session. The monitoring consequence follows directly and is easy to miss.

**Absence of a nudge, a stamp, or a warning is not evidence of health.** A hook that cannot run, cannot resolve its dependencies, or cannot write produces exactly the same observable output as one with nothing to say. The hook canary exists because of this, and it probes cache consistency rather than correctness.

## How the hooks invoke git

Several hooks ask git a question about the project a session opened, and one of them (`session-start.js`) runs unattended on startup, resume, and every compaction, in whatever directory that session opened, including a clone of this public repository nobody has read. Two properties of a naive invocation make that dangerous, and both are closed at a shared boundary rather than at each call site.

**The executable is not resolved against the repository under inspection.** On Windows a bare command name is resolved against the invoking process's working directory before the system PATH, unless that process carries `NoDefaultCurrentDirectoryInExePath`, which a session launched from a shortcut, from PowerShell, or from Windows Terminal does not, and which is recorded in neither the per-user nor the machine environment key. An MSYS2 shell such as Git Bash does set it, which makes this expensive to probe honestly: a probe run from one comes back clean and the clean reading is the shell rather than the code, so the probe belongs in a parent with the variable explicitly removed and beside a control in a directory holding nothing. A repository carrying a file named `git.exe` would therefore run its own binary the moment a hook asked that directory a question. Two shapes close it, and which one applies is decided by whether the call needs a shell. `hooks/kit-git-lib.js`, through which every shell-free git call runs, spawns from its own directory and names the repository with `-C`, so the working directory is never one an attacker can write to; anyone able to write into the plugin's own hooks directory already controls the code being run. `merged-pr-push-guard.js` cannot take that shape, because its queries run through a shell (the `az` CLI is a `.cmd` shim) and its host queries find the repository through the working directory, so it sets `NoDefaultCurrentDirectoryInExePath` in the child environment instead: `cmd.exe` reads that variable from its own environment rather than from the spawning process, which is what makes the child-side setting effective there and ineffective for a direct spawn. The library sets it too, one level down, for anything git itself invokes through a shell such as an alias or a credential helper.

**The child environment carries no `GIT_*` variable.** `GIT_DIR`, `GIT_WORK_TREE` and `GIT_COMMON_DIR` make git answer about a repository other than the one named, and `GIT_CONFIG_GLOBAL` and its siblings make it read an attacker-supplied config, so an ambient environment a repository steered (a committed terminal profile is the documented route) would otherwise decide what a hook reports. The strip is wholesale and case-insensitive rather than a named list, and `GIT_TERMINAL_PROMPT=0` is set after it so no invocation can block a session on a credential prompt. Arguments are an array and the library runs no shell, so no repository-supplied string reaches a command position.

The boundary is shared rather than per-caller for a reason the tree already demonstrated: the correct pattern existed as a private helper in `memory-session.js`, and the next hook to need git reimplemented the call without it. A guard belongs to the channel its callers run through, not to the caller that first needed it.

One residual is not closed. The kit resolves git by name rather than by absolute path, so a `PATH` an attacker controls still places their git ahead of the real one. The environment a session runs under is repository-reachable by the routes the Principals section names, so this is a real residual rather than a theoretical one; closing it needs a trusted absolute path the kit does not currently establish.

## How the hooks read a repository's files

`session-start.js` and `stop-docs-hygiene.js` read files a repository supplies, at sizes and kinds nobody vouched for, and list directories whose length nobody bounds: `docs/backlog.md`, each note and brief file under `kaizen/`, and the plan docs under `docs/plans/` that both hooks walk. One of the two runs unattended at startup, resume and compaction and the other holds a turn end, in whatever directory the session opened, including a fresh clone of an untrusted repository nobody has read. The kaizen walk's only gate is a bare existence check on a path every clone of this public repository carries. So the file that sets each bound is the manufactured one rather than the honest one, and every cost is spent synchronously while a session is blocked. `hooks/kit-read-lib.js` is the shared boundary those reads and listings go through, with the same standing as `kit-git-lib.js` above and for the same reason: a guard behind an unexported helper stays correct and stops being applied.

**One read reaches outside the checkout, and it is judged on the path text first.** `session-start.js` also reads a `.kit/goal-state.json` in each directory `git worktree list --porcelain` names, which is how a session learns that a sibling worktree of this repository holds an armed goal of its own. Those directories are repository-supplied in the same sense as the files above: git reports each from `.git/worktrees/<id>/gitdir`, a file present in any project directory distributed as an archive rather than cloned. The read does not go through `kit-read-lib.js`. It goes through `kit-goal-lib.js`'s `readGoal`, which owns that file's shape and its byte ceiling, so a sibling's state is normalized by the rules a session's own state is normalized by rather than by a second hand-rolled parser. Three bounds hold what the walk can cost. Each listed path is judged before anything opens or resolves it, through the same `storablePathValue` every stored path field routes through, so a planted entry naming a UNC or device path is refused rather than opened by the kit at every startup, resume and compaction, which is what keeps the read itself from becoming an outbound SMB connection authenticating as the logged-in account; what the screen cannot reach is the enumeration that produced the entry, since `git worktree list` consults each recorded worktree path inside its own process to report prunability, and the two-second bound on that spawn is what limits it; the judgement is repeated after the path is folded, because a local spelling can resolve onto a share through a junction or a subst drive. The walk stops at fifty entries, since a filled `.git/worktrees/` would otherwise buy thousands of synchronous reads and megabytes of listing, and a walk that stops says so on the block. And only each tree's leaf directory name reaches the payload, never its path, which on the default layout embeds the OS username. The residual is `validTranscript`'s: a path on a mapped network drive letter is indistinguishable from a local disk without a syscall.

**The kind is settled on the descriptor, not on the name.** A FIFO reports size 0, passes any size ceiling, and then blocks inside `open()` until a writer appears, which no surrounding try can rescue because the call never returns. A FIFO named `docs/backlog.md` in a clone would otherwise hold every session start in that checkout open indefinitely. Two things close it together, the pair every reader in `kit-read-lib.js` applies and `memq.js`'s `readGitPointer` carries for the git pointer's own read: off win32 the open itself is non-blocking, which is what makes opening a FIFO return rather than wait, and the kind verdict is then taken from an `fstat` on the open descriptor. The descriptor is what makes the verdict binding. Judging a name and then opening that name leaves a window a local process can swap the file inside, and a descriptor answers only for the file that was actually opened.

**The size that bounds the read is the descriptor's, for the same reason read the other way.** A size taken off a name before the open describes whatever stood there then, so a file that grew in between comes back short while its own flag calls it whole, which is a partial reading reaching a session as a total. The ordinary read stats no path before the open, which also removes a stall the name-first shape carried: a symlink into a dead network mount fails at the open the operating system is already timing rather than hanging in a stat ahead of it. One exception is opt-in and is named where it is taken: a caller asking for a link at the final component to be refused gets that refusal from the open itself where the platform defines `O_NOFOLLOW`, and from an lstat ahead of the open where it does not, which is every Windows host, since Node exposes the constant only where the platform has it. So on Windows a caller taking that option carries back both the name-first stall and a window between the lstat and the open, narrowed rather than closed. The residue is not the same size for every caller, and it is stated per caller at `readFileBounded`'s own header rather than counted here: that header sits at the one place a call is added, so a call added later falsifies it in front of the author adding it, where a roster kept in this document goes stale silently and reads as complete while it does. What this document holds is the bound rather than the roster. A target under the operator's own `~/.claude` needs a writer already inside that directory to plant a link at all. A target inside a project's own `.kit/` IS repository-reachable, since a project that does not ignore `.kit/` can carry one in its history, so its residue is bounded by what the read can do with a swapped file rather than by who can reach the path: every such reading is parsed field by field into capped values, with nothing echoed and nothing executed.

**A partial result says it is partial, and a listing says the same about a directory.** Two things make a read partial, a file larger than the ceiling and a fill loop that ended short of what the descriptor promised, and both set one flag, because a caller summarizing what it read has to say the same thing either way. The trailing fragment goes with a partial result: a byte cut lands mid-line and possibly mid-codepoint, so everything after the last newline is discarded and a caller only ever sees whole lines. Left in, a line counter counts a fragment as an item. A listing carries the same flag when a cap binds or a directory will not answer, and an absent directory is an empty listing rather than a bounded one, since nothing there is nothing to miss. What the flag buys is stated narrowly on purpose: every reading it qualifies reaches the session accompanied by a statement of the bound, as a clause on the count where the reading is a count and as its own sentence where a whole payload is qualified at once, so no bounded reading is rendered as a total. It is not a promise that the reading is complete, and a session handed a bounded count reads a floor.

**Two byte bounds and two listing bounds hold what one session start can be made to spend.** Each file is read to a 1 MB ceiling, and the kaizen note walk carries a 4 MB budget across every file it opens, because a per-file ceiling bounds one file and nothing bounds their product. Each directory walk is read incrementally under an entry ceiling as well as a keep cap, so a directory filled with non-matching names cannot turn a capped walk into an unbounded read, and every walk in both hooks takes the shared listing rather than a local one. The worst case a hostile checkout can force at one session start is roughly 5 MB read across at most about a hundred file opens, with the entry ceiling holding each of the three walks.

**A repository-supplied path must resolve inside the checkout.** The boundary follows a symlink by default rather than refusing one, because the question it answers is what the read would block on: a link to a regular file reads exactly like that file, while a link to a FIFO reports as a FIFO on the descriptor and is refused with it. That leaves a second question, what the read may reach, and it is answered at the callers rather than in the reader, through one exported helper that defers to the same containment rule `normalizePlanArg` applies to every stored plan path. Both nudge readers resolve their subject and require that it stay inside the project before opening it, so a clone whose `docs/` or `kaizen/` is a link out of the checkout yields no reading rather than a count taken off a file elsewhere on the disk. The exposure that closes is small and real: what would have escaped is a count of bullets and one date-shaped token, never file content, since no repository-supplied byte reaches a context block by any path here.

**Failure is a refusal the caller reads, never an exception a hook has to catch.** An absent file, a non-regular one, an unreadable one, a path resolving out of the checkout, and a failed listing all degrade to a value the caller inspects. That is a property of `readFileBounded` and of the listing; `readFully`, the primitive a caller uses when it has already settled the kind and owns the window, answers to its caller's try instead, handing back a bad descriptor's `EBADF` and an over-large length's `RangeError`, because only the caller that owns the descriptor can say what a failure of either means.

**One script outside the hooks reaches both of those boundaries, and the Chapter template hands it a repository-supplied root.** `scripts/kit-size.js` is a repo-only size reader rather than a hook, and the Chapter template's `Delta:` field has every leashed run invoke it with `--repo <the project's root>`, so it measures whatever project a session opened, a clone of this public repository among them. It asks git nothing directly and opens no worktree file directly: git runs through `hooks/kit-git-lib.js` and worktree content through `hooks/kit-read-lib.js`, so the executable-resolution and `GIT_*` properties above and the descriptor-settled kind and size in this section hold for it unchanged, and each git call carries its own timeout. Two properties are its own, and both are about what it prints rather than what it reads, because its output is quoted verbatim into a tracked plan document. Every path it prints is spelled relative to the repository under measurement wherever it resolves inside it, on the containment rule `kit-read-lib.js` states rather than a bare two-dot prefix test, since an absolute checkout path embeds the operator's user name on the default layout. And every path it prints goes through the same value screen a stored authorization sentence takes, with backtick runs and a leading hash run dropped rather than escaped, because a backtick closes the quoting fence early and a line opening with a hash run ends the Chapters block the status line's plan parser is reading.

**Its third verb writes, which makes the size reader a member of the mutating-CLI class the read-only reviewer guard's `node <script>` hole leaves open below.** `init` creates `test/size-budget.json` from current sizes and never edits one: the write is an exclusive create, so an existing budget is refused rather than overwritten, and containment binds this path whatever `--budget` names, because a reading taken against a budget elsewhere yields a figure the operator asked for while an unbounded write creates caps outside the reviewed checkout that a later `check` then reads back as the gate's own. Beyond containment it refuses to write at all where the caps would be untrustworthy: a measured file differing from HEAD, so no cap bakes in uncommitted content; a tracked file whose bytes the bounded reader will not hand over; a tracked file under a measured root that nothing classifies; a tracked path the pathspec listing does not return; and a corpus with nothing in it. The exposure is bounded by what it can produce, a JSON map of paths to integers inside the checkout, and it runs by hand rather than from any hook.

## The scenario-probe runner

`tools/probe-corpus/run.mjs` reads the kit's own prose back through a cold model, which it pays for by spawning the metered CLI and putting a copy of the operator's live credential on disk. It is repo-only, like the size reader above: it ships in no payload, no hook invokes it, and an installed session never runs it. What runs it is a hand invocation or finishing-work's step 5 inside this repository. Each probe under `test/probes/` names a context shape, the runner copies that shape's files into a scratch run directory, and the Claude Code CLI is invoked headless once per probe and shape with those files inside the prompt.

**Its two environment overrides carry no second signal, and what stands in for one is where the runner lives.** `PROBE_CLAUDE_BIN` selects the binary spawned as the reader, which is the same *which program runs* class `KIT_PLUGINS_ROOT` is gated for, and `PROBE_HOME_DIR` selects the directory the credential is copied from and a `home/<name>.md` shape entry is read out of. Neither takes an allow variable. The mitigation is the runner's provenance rather than any check: the file exists only in this repository's tracked tree, which is the operator's own code and reviewed as such, and an actor who can edit that tree can change the spawn directly and has no need of the variable. The residual is the one the Principals section names and the gates elsewhere in this document only narrow: an environment a repository sets for the shell that opens it (`terminal.integrated.env.windows` in a committed `.vscode/settings.json` is the documented route) reaches these two variables, so a checkout whose runner the operator then invokes by hand can be pointed at another binary with nothing said. The flags `--claude` and `--home` beat the variables, and the suite points every end-to-end case at a fixture home so no test reads the operator's.

**The credential copy sits under the OS temp root, where its exposure is access-control-list-dependent rather than mode-enforced.** The runner creates a scratch directory under `os.tmpdir()`, chmods it 0700, and writes `.credentials.json` into it at 0600 through an exclusive create and a rename. Those modes are the protection only where the platform honours POSIX modes. Windows honours neither, so what bounds the copy there is the access control list the temp root gives a directory created under it, and on this machine `os.tmpdir()` resolves to `D:\Temp`, a machine-wide directory rather than the per-user temp directory under a profile. Any local account the root's list admits is therefore inside the copy's reach for as long as it exists. The copy is never written inside the run directory, which is the evidence artifact a reader of the report opens. It is refreshed before every invocation because the OAuth token rotates while a run is in flight, newer-wins on both files' `lstat` mtimes so a token the reader itself rotated is not overwritten with a stale one, and a link at either the source or the destination refuses the copy and stops the run. It is removed when the run ends, when the process exits by any route, and when the run is interrupted, and a copy an earlier run stranded is swept by the next one. A removal the runner could not take is reported on stderr naming the scratch root and retried at exit, so a surviving copy is named rather than silent. An accepted risk rides with all of it: the reader and the session that started it hold the same credential, and a refresh by either rotates the other's token, which costs a reading rather than corrupting one.

**Its refusals and warnings can print an absolute home-directory path, which carries the account name.** A reader binary that resolves to no file is refused by name and the message spells the candidate path, which under the default resolution sits under the operator's home directory; the cleanup warning spells the scratch root. Both go to stderr rather than into a tracked document, and both pass the shared renderer's whole-line elision before they are written, bound lazily from the hook library beside the runner in the tree; where that library is absent or will not load, the runner says so once on stderr and prints the lines unelided, because the loudest of them says a live credential copy is still on disk and a withheld version of that warning is not actionable. What screens a quoted line at the one place it can reach a tracked document is the `Gate:` line's rule in executing-work's Chapter template, which has its full path respelled repo-relative or left out.

**What the reader may be handed is bounded at the shape, twice.** A shape entry names a file under `plugins/claude-kit/` or one markdown file directly under the home directory as `home/<name>.md`; those two roots are `probe-file.mjs`'s and the runner applies them again at the read boundary, because a library caller composing shapes never passes the parser. A path carrying `..`, `.`, an empty segment or a backslash, and an absolute path, is refused by name before anything is read, in worktree and `--before` mode alike, since `git show <commit>:<path>` refuses neither and the scratch copy is written at a path joined from the same string. What survives that lexical judgment is checked with `containedRealPath` from `hooks/kit-read-lib.js`, the same containment rule the hooks read repository files under, which makes the runner a second caller of that boundary though not of the git one: it resolves and spawns git itself, from the directory the git binary sits in. A link is refused in both modes, by `lstat` in the worktree and by a `git ls-tree` mode read at a ref, because a link committed to a tree is a blob whose bytes are a path on somebody's machine and `git cat-file -t` calls it a blob like any other.

**The reading is isolated from this machine by argument rather than by any sandbox.** The reader runs with tools disabled, an empty setting-source list, a minimal system prompt, a child environment with every `CLAUDE` and `ANTHROPIC` variable dropped (the proxy and certificate variables are inherited by design), `CLAUDE_CONFIG_DIR` pointed at the scratch directory holding the credential copy and nothing else, and an empty working directory under the temp root. `tools/probe-corpus/isolation-control.mjs` is the four-rung control behind those choices, and its bare rung establishes that the copied credential is what the reader authenticates from: with the environment scrubbed and no credential in the config directory, the reader does not run at all. Two things that shape is not: a `CLAUDE.md` above the temp working directory is discovered by the CLI, and the runner answers it by walking the chain and naming what it found on the report's isolation line rather than by refusing the run, so a planted file there is reported and counted rather than fatal; and the production rung's reader still names the CLI's own identity preamble, which `--system-prompt` prepends rather than replaces, beside system-reminder blocks carrying the operator's email address and the date, none of which instructs anything about the corpus.

## The guard hooks

Six of the seven PreToolUse hooks mechanically enforce the agent access model: five guards that deny, and one grant that allows a single fixed command shape. The seventh, `memory-recognition-nudge.js`, enforces nothing: it is a memory-store surface and is covered among the paths that carry store content into context above. Each is the teeth under a skill's routing wording, and none is a security boundary: by the Principals section, every agent runs as the one machine principal, so the guards defend the work against well-intentioned-but-wrong agent behavior (a reviewer "fixing" the code under review, an implementer writing reports into the curated docs tree, a push stranding records off a merged branch, a memory record landing in a shape the store cannot read), not against an attacker.

- **`readonly-agent-guard`** holds the state under review immutable, by agent class. Strict agents (adversarial-reviewer, blind-reviewer, security-reviewer, council-member, design-facilitator, consultant, blind-reader, prose-reviewer) get a read-only repo tree: writes, file mutations, git and GitHub state changes, package installs, and formatters are denied. The gate-runner (qa-verifier) builds and runs suites, so it may write and delete freely inside a fixed list of build-output directory names (bin, obj, TestResults, node_modules, .vs). Outside those directories it may still bring into existence a file that does not already exist, by `touch`, by `New-Item`, or by a copy to a fresh path (test scaffolding needs that), but not by any content-writing spelling: a redirect, `Set-Content`, `Add-Content` and `Out-File` are denied at a fresh path exactly as at an existing one. It may not modify the content of, overwrite, delete, move, or rename anything existing, though `chmod` on an existing path is allowed it and the exec bit is tracked state; a stray created file leaves a tracked-tree delta the review bracket sees, or an untracked entry `git status` shows. Every other agent type and the main session are untouched, and `.kit/` (gitignored) is scratch both classes may write. Command text is judged against a quote-masked copy in which every command substitution bash would perform, at the top level, inside double quotes, and standing in an arithmetic operand alike, is blanked whole to a sentinel and its interior collected and scanned as a command of its own, with nested executor payloads descended recursively within a depth bound, and containment against the git root above the payload cwd. A substitution or an executor payload that the depth bound leaves unexpanded is unresolved rather than absent, and denies. git's own command-line alias surface denies on the same rule and is bounded at the config key rather than at the value: `git -c alias.<name>=<value>` and both `--config-env` spellings of an `alias.` key put the real verb inside a config value, which is data to the shell and a command to git, so the quote mask is right about it and cannot be what bounds it, and the subcommand is simply unresolvable from the command line. The rest of that class is residual rather than covered, and is named because the bound that works for an alias does not reach it: `core.pager` carrying a bang, `core.sshCommand`, `core.fsmonitor`, `credential.helper`, `diff.external`, `uploadpack.packObjectsHook`, and an `include.path` naming a file that sets any of them each run a command from a config value too, and every one of them allows, because keying on those names would deny the everyday review spelling `git -c core.pager=cat log` and bounding them needs a value-shape rule this instrument does not have. Coverage extends to a second dispatch route on one condition. On v2.1.205, established by probe rather than inferred, an agent dispatched through `Workflow`'s `agent()` with `agentType` naming a governed kit agent carries that identity into the PreToolUse payload, so its policy class resolves and the guard governs it exactly as under an Agent-tool dispatch; the named agent's frontmatter `tools:` list applies alongside its prompt, so the named agent holds no write tool on either route. Both halves are load-bearing, because the read-only property rests on two controls at once: `hooks.json` matches this guard on `Bash` and `PowerShell` only, so a strict agent's inability to write is held jointly by the guard denying write-shaped shell and by the `tools:` list withholding Write and Edit. A dispatch that omits `agentType` presents as `workflow-subagent`, resolves to no policy class, and loses both controls together rather than only the guard; what default toolset such an agent receives is unprobed and must not be assumed read-only. That condition is why the doctrine's Workflow grant and both skills' dispatch templates require the field.

  One command shape is exempt from that command-position scanning, and its residual is stated rather than closed. Where the entire command is a single simple command whose whole content is one `cat` or `tee` writing one quoted-delimiter heredoc into the class's own writable set, or to a destination outside the git root entirely, the body is data and is masked rather than scanned, so a reviewer writing a report about `git push` or `rm -rf` is not blocked by its own subject matter. Anything outside that one shape leaves the body's command positions scanned. Redirects are the standing exception in either case: a `>` inside any quoted-delimiter body stays blanked whether the shape qualifies or not, so a hidden write is the miss the guard's own header names and this exemption neither widens nor closes. What the exemption itself leaves open is a literal body written to any path the exemption admits, inside the class's writable set or outside the tree alike, and run by a later, separately scanned command carrying a file operand (`bash <path>`, `sh <path>`, `. <path>`, `source <path>`, an interpreter with a file operand, `$(cat <path>)`). The guard already carries that residual in another spelling, a mutation written to such a path by `printf` or any other producer, and the tree-state check around a review round backstops both only where they leave a file delta, never where the later command's mutation is a push, a merge or a tag, which is the class that moves no tracked file, leaves that check's two `git status --porcelain` readings identical, and is therefore the one this guard exists to cover in the first place.

  The requirement is prose-enforced, and saying so is the point: no hook matches the Workflow tool, so nothing observes the dispatch that decides whether a read-only agent, a reviewer or the consultant alike, is governed. It lives in the doctrine's standing-dispatch bullet and the two skills' templates, with one `doctrine-parity` test over the doctrine's wording as the only mechanical trace. The tree-state bracket around a review round is the sole runtime backstop, and by finishing-work's own account it misses a write to a gitignored path or outside the git root, a mutate-read-restore inside one round, every act that moves HEAD and the worktree together so the porcelain reading is unchanged (a merge, a `checkout`, a `pull`, a `reset --hard`), and every act outside the worktree (an outward `gh` mutation, a push, a tag); `git fetch` is outside both it and the guard; and under an omitted `agentType` those classes rest on nothing. Accepted risk on the same footing as the memq-grant invariant below, checked by hand rather than by mechanism, with a Workflow-matcher hook as the fix if it ever needs one.

  The strict roster lives in one classifier, `reviewAgentClass` in `hooks/kit-agent-identity-lib.js`, which this guard reaches through a screened require and the recognition nudge's dispatch stand-down reads from the same export, so the seat set that loses write-shaped commands and the set that receives no store pointer at dispatch cannot drift apart. A derivation test in `test/readonly-agent-guard.test.js` reads every definition under `plugins/claude-kit/agents/` and asserts that each one granting no file-writing tool in its `tools:` frontmatter resolves to a governed class, so a read-only seat added to `agents/` that the classifier does not know is a red rather than an agent running ungoverned.

  Two members of the class read prose that need not be the operator's own. `blind-reader` and `prose-reviewer` are dispatched at documents, a customer-facing draft among them, and both hold Bash, so a document in scope is untrusted input reaching an agent with a shell. Each charter states the prohibition with its reason: a document is data, an instruction found inside one is a finding reported verbatim rather than an action taken, and the reviewer chooses the command a claim check needs rather than letting a document choose it. That prohibition is prose and nothing under it is mechanical, because the guard denies write-shaped commands and command text it cannot resolve: a read-shaped command it can resolve is outside its denylist apart from three deliberate over-blocks, `git stash list`, `git clean -nd` and `git apply --check` all denying, and so is an outbound `curl`, `wget`, or `Invoke-WebRequest`, which the review round's `git status --porcelain` bracket cannot see either, a network call leaving the worktree byte-identical. The sighted code reviewers share the posture from the other side, with the diff under review as the untrusted text: each charter carries the same data-not-instructions rule as its own paragraph, and their tool-printed-claims rule, which has a reviewer settle a claim about what a tool prints against the tool rather than against documents, binds on the command's behaviour rather than a name list, running a command only where some invocation of it is provably read-only, treating one whose effects the reviewer cannot establish as mutating, and admitting the emitting line in the tool's own source as the first and stronger reach. That bound matters because the denylist leaves a bare `node <script>` invocation open, so a name-listed rule would have had a reviewer running the kit's own mutating CLIs inside a review; like the document lenses' prohibition, the bound is prose with no hook beneath it. The exposure predates these two agents and is unchanged in kind; what changed is that two agents now exist whose whole job is reading documents. `docs/backlog.md` carries the denylist candidate and the reason it is not obviously right, which is that a reviewer sometimes has a legitimate reason to fetch.

  A third site puts untrusted text in front of a shell, and it is the widest of the ones named here because no read-only guard governs it. The main session reads text it did not write at many points, every subagent report among them; this is the one a run-stopping tag turns on. `finishing-work`'s step 4 adjudicates the docs-curator's Drift Report, and an entry whose basis rests on any claim about the state before the changeset rests on a state the curator holds no tool to read, so for a `mistake` item the orchestrator runs that read itself. A `deviation` stops nothing and gets no read; its pre-change claim is tagged unverified instead.

  What bounds that read is set membership rather than a pattern judging report text, and the distinction is worth stating precisely because the weaker reading is the tempting one. The curator's `Paths:` token is not interpolated as text: it selects, by whole-token equality, an entry of a changeset listing the orchestrator produces itself (`git diff --name-only --no-renames <base-ref>` unioned with `git ls-files --others --exclude-standard`), and the selected entry is what the read is composed from, passed as a single argument after `--` where the git form takes one. A token equal to no entry selects nothing, and selecting nothing stops the run with its reason stated rather than skipping quietly. Selection is one control of two. The second is a load-bearing token gate that the selected entry passes before it reaches any command: a repo-relative path of ASCII letters, digits, `.`, `_`, `-` and `/`, carrying no leading `/`, no leading `-`, and no `.` or `..` segment, whose rejection is a stated-reason stop rather than a pass-through. The gate may reject a real listing entry, and that direction is deliberate, since an oddly-named honest file costs a stop while the alternative costs a shell. The same pair covers every other curator token a command or a file write consumes rather than the `Paths:` list alone: the `LIBRARY HYGIENE` block's `docs/plans/<file>` paths, selected against the orchestrator's own listing of that directory because a stale plan sits in no changeset of this effort, and the cross-reference block's plan names, which reach an `Edit` rather than a shell. The gate carries more of the weight on the hygiene route, since step 5's archival `git mv` ends in a shell command holding that name as an operand and `docs/plans/` sits under the `docs/` the curator writes ungoverned.

  The honest residual is that equality makes a selected entry byte-identical to the token that selected it, so what the control actually establishes is provenance and membership, not that the text is the repository's rather than the report's. The curator's writes under `docs/` are ungoverned, so a file it creates joins the untracked half of that listing and its own name becomes selectable; and `git show <base-ref>:<path>` takes no `--` to put the path behind. Two exits follow from that, and each has a control of its own. What keeps such an entry from retiring the run-stopping tag is not the selection but the two rules beside it, that a refutation must be responsive to the claim and retires only the pre-change premise. What keeps it from reaching a shell as command text is the token gate above, and quoting alone would not have: a filename may legally contain a single quote, so a name of the form `docs/x'$(echo PWNED)'.md` is whitespace-free, joins the untracked half of the listing, selects itself by equality, and closes the surrounding single quotes when it is composed. The report's prose is held as data by skill wording alone, with no hook beneath it, exactly as the document-reading agents above are. And the `file:line` citations take no screen whatever, being opened with the file-reading tool: that removes the command-injection surface and nothing else, since the read is deliberately unbounded, so a citation may name any file the session can open and whatever it holds enters that session's context as untrusted text.

  One channel at this site is genuinely an interpolation surface and is bounded rather than absent. Curator prose reaches a pull request body, so step 6 passes that body with the host CLI's file form (`gh pr create --body-file <path>`) and summarizes instead where a host has none, and the title is the orchestrator's own words because it rides the command line either way. Whether the pre-change read meets a permission prompt is a property of the operator's settings rather than of anything the kit installs.
- **`docs-write-guard`** keeps non-curator subagents out of `docs/`: only a main session and the docs-curator agent curate the library; reviewer and implementer reports belong in `.kit/`, with the plan's Chapter as the durable record.
- **`memory-frontmatter-guard`** holds a memory record to what memq will actually read of it, on the Write, Edit and MultiEdit path. The two shared tiers are refused outright whoever is writing, which is the mechanism behind the CLI-only authoring the Shared tiers section states; that section's claim rests on this hook rather than on convention. A project-tier record is judged field by field against memq's own readers, loaded from the plugin's own `scripts/memq.js`, so the guard and the store cannot come to disagree about what a record declares. Fourteen deny paths sit behind that, and the list is closed by the guard's own set rather than by this sentence: two on the block itself (a block that opens on line 1 and does not close inside memq's line bound, and a fence that is the record's first non-blank line without being line 1), one on placement (any of the seven fields memq reads indented under a key other than `metadata:`), one on `tags:` (a key with no inline value followed by `- ` items), two on dates (a `created:` memq cannot parse, and a `pinned:` or `created:` outside the `YYYY-MM-DD` calendar form), two on `anchors:` (an entry the grammar rejects, and a path that escapes the project root), one on `triggers:` (an entry outside the recognition grammar), and five on `supersedes:` (a name outside the record-name grammar, the record's own name, a target held only under a variant casing or extension case, a target held only under `archive/`, and a name the tier holds no record of). Each carries the repair memq itself names for that shape. A record whose bytes run past memq's capped readers and whose block does not close inside them is reported as unchecked rather than judged, because the capped and uncapped readers can disagree about it and no verdict there would be about the record the store will read.
- **`pr-docs-guard`** blocks creating a PR while `docs/` carries uncommitted changes attributable to the checkout the PR is created from, so documentation ships in the same PR as the code. A command that chains its own `git commit` ahead of the PR create is allowed, and a checkout parked on the default branch or a detached HEAD never denies.
- **`merged-pr-push-guard`** blocks a push to a branch whose PR the host reports MERGED, the stranded-commit trap. Its shell calls are fixed literals with the one variable (the branch) allowlisted before interpolation; that discipline is load-bearing against command injection. It finds the push at a real command position rather than anywhere in the command string, cutting on the separator set `readonly-agent-guard` uses plus the literal backtick that hook masks and this one does not, and admitting the `NAME=value` assignment prefixes every POSIX shell treats as command position, so a push behind a newline, a bare `&`, a subshell, or `GIT_SSH_COMMAND=... git push` is guarded and a following command's operands stay out of the branch it judges. Both error directions are residue rather than coverage. A separator inside a quoted string still opens a command position, which over-detects into a needless query and at worst a needless block. In the other direction, a push the shell reaches through a layer the parser does not model (a quoted string executed later, a backslash-newline continuation between `git` and `push`, an interposed runner such as `xargs`, an alias or shell function) is not seen at all, and neither is any command-position push after the first inside one compound command. `test/merged-pr-push-guard.test.js` asserts the caught shapes and each of those misses by name, so the residue is a recorded decision. The guard's git and host queries run with every `GIT_*` variable stripped from the child environment, the wholesale strip `memory-session.js` takes for the same reason: a repo-carried `GIT_DIR` or `GIT_CONFIG_GLOBAL` redirects every read the block decision rests on. `HOME` and `XDG_CONFIG_HOME` reach the same global config and are not stripped, since git needs `HOME` for legitimate config; `docs/backlog.md` carries that residual, whose worst outcome is a spurious block or the fail-open default rather than any grant.

- **`memq-grant`** is the inverse of the five guards: it never denies, and it emits an allow decision for exactly one command shape so a fleet worker on the engine's write-gated spawn vector keeps the memq CLI for recall and outcome logging. The invariant: a grant is emitted only when the fleet-store signals are present (`KIT_MEMORY_ROOT` with `KIT_MEMORY_ROOT_ALLOW_DATA=1`, checked through memq's own exported `storeSignalsPresent()` so the hook and the CLI share one definition), the command is one `node` invocation whose first argument is an absolute spelling resolving by normalized path equality to this plugin's own `scripts/memq.js` (anchored to the hook's on-disk location, never an environment variable, never a pattern; relative spellings are refused because the Bash tool's shell keeps a working directory nothing pins to the payload cwd, and on Windows a spelling without a drive-letter root is refused because this process and Git-Bash resolve it to different files), the interpreter is positively identified rather than accepted by name (the hook walks its own inherited PATH and grants only when the first `node` candidate realpath-equals its own `process.execPath`, so a PATH-planted node or wrapper refuses; that is the hook's PATH rather than provably the child's, since the shell the Bash tool runs can rewrite PATH, and that residual is a divergence between the two rather than an unchecked interpreter; PATH is not the only channel, though, because that shell persists across calls, so a shell function or alias named `node` defined by an earlier approved call preempts the PATH lookup with nothing this process can observe, and against that one the pin is not weakened but absent, leaving the grant's own store bound as what limits it; the module-preload variables `NODE_OPTIONS`, `NODE_PATH`, and `NODE_REPL_EXTERNAL_MODULE` refuse the grant outright whenever set, since node honors them in the granted child), and the command line is free of shell metacharacters, with the executors banned across the whole line including quoted spans (a `$` and a backtick compose text inside double quotes too), with every C0 control byte and DEL banned line-wide, tab alone excepted, because bash strips a NUL from a command line outright and what a shell and this tokenizer each do with the rest is unspecified rather than agreed, and with word separators restricted to space and tab and the divergent spellings (a backslash outside quotes, a backslash before a quote, an unquoted comment tail, and an unterminated quote anywhere in the line) refused because the hook must never judge different words than the shell builds. The expansion characters are banned too, and where they are banned is the whole of their rule: bash rewrites a brace, a glob, or a leading tilde into a different list of words after a hook has tokenized the line and before the child sees them, so a screen reading one word list while the child receives another is no screen at all. Bash performs none of those expansions inside quotes, so the ban is scoped to unquoted spans: `{ } * ? [ ]` unquoted refuse the grant, and quoted they are ordinary free text, which is what a summary naming a test glob or a description carrying a bracketed note is made of. The tilde takes that span rule with a position rule on top, because only a leading tilde expands: an unquoted tilde opening a word refuses the grant, while a tilde anywhere else in a word is a literal to bash and grants. That last clause is a correctness requirement rather than a concession: refusing every mid-word tilde would withhold the grant over words the shell rewrites into nothing the screens care about, an argument carrying one, a description mentioning one, and a Windows 8.3 short path, which carries its tilde mid-word. One mid-word shape is not literal, and the hook admits it knowingly rather than by oversight: bash expands a tilde after the `=` of an assignment-shaped word and after each `:` within one, so a word of that shape does carry a substitution. What makes it admissible is that the expansion keeps everything before the tilde, so such a word can become neither one of the screened tokens, which are matched whole, nor the script path, which is matched by path equality; what it can become is a longer argument of memq's own, which memq validates. A screen that ever matched a word's interior rather than the whole of it would have to revisit that. That last is not a spelling the grant covers, though, and for an unrelated reason: the script path is judged by resolved-path equality with no realpath step anywhere, so an 8.3 spelling of it is refused at the path check like any other spelling that is not the resolved one. What makes the leading tilde a control rather than a curiosity is that it substitutes caller-controlled content: with `HOME` set to a verb name, a word the hook reads as a bare tilde reaches the child as that verb, which is how a screened shape would otherwise arrive wearing an unscreened spelling. The invariant screens the command's own words as well as its shape, because a shape check alone would hand a worker every verb the CLI has. The subcommand is judged against a list of granted verbs rather than a list of refused ones, and that polarity is the point: a verb memq gains later is withheld until this list learns it, where a refusal list would grant it on arrival and reopen whatever it does. The granted set is `log`, `get`, `recall`, `recent`, `unstamped`, `touch`, `add-type`, `add-operator`, `decay-scan`, `decay-prune` and `decay-done`, which is memq's own dispatch less five. Two of the five are the delete verbs, whose destruction leaves no local recovery the verb can name, the residues being enumerated under Storage properties above. The third is `find`, whose semantic channel requires and runs an embedder package in process from a directory that resolves under the home directory, which is not a thing a hook can screen on, since `HOME` is always set and refusing on it would refuse every command; `find` is withheld from the grant for that load, and a test pins which verbs can reach it. It asserts memq's exact set of code loads past its built-ins, naming each one and the function it sits in, and then walks the caller graph transitively, so that the closure of every function able to reach any of those loads contains only entry points belonging to `find`, which is withheld from the grant, or to granted verbs that stand the same load down before reaching it: the authoring verbs `add-type` and `add-operator`, whose write-time neighbours check reaches the embedder load, and `decay-scan`, whose neighbour-pairs block reads the same index after its drift block. Each stands itself down whenever `KIT_MEMORY_ROOT` or `KIT_EMBEDDER_ROOT` is present, through one shared predicate, so no two of them can disagree about the condition or about which variable they name. That stand-down is the child's own, read from the child's environment rather than the hook's, so it carries the same divergence stated above for the interpreter pin rather than closing it: a shell that has dropped the store root since the grant was emitted leaves the hook granting on an environment the child no longer has, and the verbs then reach the load with no store bound at all, which is the reverse of what the grant's own condition describes: the root is gone, so `memoryRoot()` falls back to a directory under the caller's own home, and the checks then run with no store bound at all, the neighbours block ranking every store on the machine and the scan's pairs block pairing the tiers the calling project resolves, each printing the names it finds into the context of a worker nobody is watching, the pairs block marking any pinned member of a pair it lists, a reach the granted vector itself never has, since the block stands down there. What crosses is what the fence-table row above bounds, charset-closed names, tier labels and figures rather than bodies, so the residual is a reach the grant did not intend rather than a body crossing a path closed to it. Keying the stand-down on either variable's bare presence rather than on the honored pair is what keeps it no narrower than the grant condition it stands in for, at the cost of a skipped convenience in a shell carrying a stray variable. The transitive walk is the load-bearing half, because the relevance channel puts loads two functions deep, where a check on one function's direct callers would have gone quiet. The fourth is `anchor`, which rewrites a record in the shared priors, an authoring act on state a worker's writes are otherwise quarantined from; it is withheld at this grant alone, `cmdAnchor` carrying no store-signals refusal of its own, so the allowlist is the whole of what withholds it. The fifth is `triggers`, which authors the same records' recognition triggers and is withheld on the same ground and by the same single mechanism, `cmdTriggers` carrying a store-signals refusal over one shape alone, a `--replace` reaching a shared tier or a pinned project store, and none over the merge that is the verb's ordinary use. Seven flag shapes are withheld anywhere in the line, each matched as a whole word or carrying an attached value: `--body-file`, which names a file the CLI reads and admits into a record; `--update` together with `--body`, which is the shared-tier body repair; `--supersedes`, which points a new record at a live one and thereby demotes it in the search ranking and labels it wherever the store is read; `--trigger`, which writes at a new record's birth the same `triggers:` line the withheld `triggers` verb writes afterwards, so admitting it on a granted verb would hand back through `add-operator` the reach the verb list withholds; `--rollup`, which replaces each expired journal group with one synthetic tally line and discards the prose of every entry in it; and `--drop-malformed`, which rides `--rollup` and removes outright the unparseable usage lines every other read path and every other rewrite preserves; and `--type=<type>`, the attached-value spelling naming a shared type tier outright, withheld because on the two granted read verbs it would widen what a worker reaches from the calling project's own declared type to any type tier in the resolved store, the bare `--type` staying granted because it resolves that declared type and nothing else. `--supersedes` is one of two of the seven withheld on which records it can reach rather than on how much it does to one, `--type=<type>` being the other, and it is worth stating apart because that reasoning does not follow the rest. On the project tier it refuses a pointer naming no live same-tier record and allows a pointer naming one, so what survives is a hand-written pointer at a real target, which is the instruction-rather-than-boundary residual the delete paragraph below records, and every read surface honors it. On Claude Code that reach includes a project-tier record written with the Write tool, whose frontmatter the harness relocates under a `metadata:` map that memq reads at both placements. Every withholding here is chosen against that cost rather than against an approval that never arrives.

A further invariant this hook introduces, load-bearing for anything added later: a grant must stay disjoint from every deny guard's command shape. Today it is, and no mechanism checks it, so a new guard or a widened grant is checked against this rule by hand. On anything else it emits nothing and the call falls through to the engine's normal permission flow; its safe failure is silence, the opposite direction from the guards' fail-open-by-allowing. Accepted risks: arguments after the script path are granted along with it apart from what the screen above withholds, which is the seven flag shapes plus every word in the verb position that the allowlist does not name, because node hands everything past the script to the script, so the rest are memq's argv and memq's own argument validation is the control there; and the grant is agent-blind, so a strict read-only agent inside a fleet worker gets prompt-free memq writes (`readonly-agent-guard` does not deny memq, which writes the external store rather than the reviewed tree, and its agent classifier cannot be shared without restructuring that hook, while a second copy of the class list is exactly the drift the gated-override rule exists to prevent). The compensating controls, each with the bound it actually has: the grant surface ships in the build manifest like every hook (`hooks.json` rewiring included), so widening it is a stamped edit, and the canary probes the grant in both directions at session start, because a grant hook gone inert never announces itself in use: the allowed invocation must grant, and five withholding probes on Windows, four elsewhere, must each stay silent (a metacharacter-carrying near-miss, a `--body-file` value, a `--rollup`, `find` in the verb position, and the Git-Bash `/d/` spelling of the script path). The probes cover three of the twelve withheld shapes, so nine have no probe of their own. Seven of those nine share `--body-file`'s posture, the two delete verbs, a body-carrying `--update`, `--supersedes`, `--trigger`, `--drop-malformed` and `--type=<type>`: a second lock stands behind each, so a hook regression on any of them degrades to that lock rather than to nothing, though `--drop-malformed`'s is the CLI's coupling of the flag to a shape this hook also withholds rather than a refusal of its own. Those seven are the same accepted risk covering more shapes rather than a new one. The remaining two do not share that posture and are the ones the probe set closes first: the verbs `anchor` and `triggers`, each being the operator's own. `anchor` is refused nowhere but here. `triggers` is refused nowhere but here for every shape save one, its shared-tier and pinned-tier `--replace` now carrying a refusal under the store signals, which is the shape that destroys a declaration rather than authoring one; every other shape of the verb, the merge included, still rests on this allowlist alone, which is why it stays on this list, so a regression on either screen degrades to nothing and no probe would say so; what stands in its place is `test/memq-grant.test.js`, which pins the withholding in the deny direction and runs in the repo suite rather than at session start, and closing that is what the probe set would buy if it grew. Both of those are attended-session controls only. The canary stands down under `KIT_EXTERNAL_ENGINE`, which the engine sets on every worker it spawns, so in the deployment this grant exists for, neither the manifest check nor the grant probe runs. State it plainly rather than counting it twice: the detection covers the machine where a person would act on it, and does not cover the fleet worker.

The quarantine is not a control here, and an earlier reading of it as one was wrong. The grant conditions on the store pair alone, while the run-scoped pending tier additionally requires a valid `KIT_RUN_ID`, so under the store pair without a run id a granted memq writes the project tier directly. Even inside a genuine run the tier bounds less than the word suggests: `log` appends to the project-tier journal and adds a `run` field rather than rerouting, `add-type` writes the shared type tier, and the grant's verb allowlist admits `decay-prune`, which archives memories and rewrites an index. The honest bound is the store: everything a granted invocation does lands inside the redirected store the engine owns, which is why the reach is that store rather than the machine, and it is the store boundary rather than the pending tier that does the containing. That bound is itself a property of the child's environment and not of the hook, so it carries the same caveat the refusal below does rather than standing flatly. The hook reads its own environment and memq reads the child's, and where those diverge the redirection is what is lost: memq falls back to the operator's real `~/.claude`, so a granted invocation reaches the machine's own store rather than the engine's. The two failures are one failure, since the same divergence that unbinds the store also silences the CLI-side refusals, which is why those verbs are additionally screened at the hook, where the argv cannot be forged by the environment the child controls. That bound is a property of memq's own argument surface rather than of the hook, so it holds only while no memq argument names a path outside the store. `--body-file` is refused outright whenever the store signals are present, for exactly that reason: it reads a caller-named path, and a granted worker invokes `scripts/memq.js` through node directly rather than through a wrapper, so it never meets the `cmd.exe` truncation the flag exists to route around and loses nothing to the refusal. Any argument added later that reads or writes a caller-named path has to take the same refusal, or the sentence above stops being true.

A second class of memq argument takes the same refusal, on a different reason. The store bound answers where a granted invocation can reach; it says nothing about how much of the store it can destroy. The risk this grant accepts was written on a reading of `decay-prune` that its archival half supports and its other half does not: an archived record keeps its description in the archive's own index and still answers `get` by name, so nothing an `--archive` flag touches is gone, but `--rollup` on the same verb replaces each expired journal group with one synthetic tally line and discards the prose of every entry in it, and folds each memory's raw applied stamps into one rolled record while pruning its read stamps to the newest, in the project tier and in either shared tier the same call works. It leaves that text in a single-generation `.bak` no sync carries. The shared tiers now carry a whole-body repair and two delete verbs on top of that. That is not a bound on reach but a bound on blast radius, and it exists because the grant is agent-blind and prompt-free: a fleet worker, or a read-only agent holding Bash inside one, would otherwise irreversibly remove a record every project reading that store reads, with no operator in the loop, no archive copy, and, under an environment-overridden root, no automatic git sync to recover from. The `--confirm-shared` gate does not narrow that, because it is a token on the same command line the grant already covers: it is a typo guard, not consent. What the refusal costs a fleet worker is nothing it had before those verbs existed, and the ungated description-only `--update` still answers there. Two properties of that refusal are worth stating rather than leaving an auditor to find. It is CLI payload rather than a wired hook, so it sits inside the manifest gap recorded below: `scripts/` is unstamped, and an in-place edit disabling the refusal is not attested and not reported by the canary. And the hook evaluates `storeSignalsPresent()` in its own process while memq evaluates it in the child, so the CLI half of the refusal binds while those two environments agree, the same structural assumption the interpreter pin already rests on. That assumption is why the refusal is not CLI-only. `grantable()` screens the argv it already holds: the verb position must name one of the granted verbs, and the grant is withheld for `--body-file` anywhere, for an `--update` carrying `--body`, for `--supersedes` anywhere, for `--trigger` anywhere, for `--rollup` anywhere, for `--drop-malformed` anywhere, and for `--type=<type>` anywhere, that last matched only with an attached value since the bare `--type` keeps its grant. Twelve shapes are withheld in all: the five verbs `delete-type`, `delete-operator`, `find`, `anchor` and `triggers`, and the seven flag shapes `--body-file`, `--update` carrying `--body`, `--supersedes`, `--trigger`, `--rollup`, `--drop-malformed`, and `--type=<type>`. Eight of the twelve have a second lock in the CLI, so a hook regression on those degrades to that lock rather than to nothing: both delete verbs refuse under the store signals, and so do both body-writing shapes, the supersedes pointer, the creation-time trigger declaration, and the attached-value `--type=<type>`, which `get` and `touch` now refuse under those signals because a tier the calling project never declared is not a tier an unattended worker has any claim on. `--drop-malformed` is the eighth on a different footing: it is an argument error unless `--rollup` accompanies it, so its second lock is that coupling to a shape withheld here rather than a refusal of its own. Four have no second lock and rest on the hook alone, and they are `find`, `anchor`, `triggers` and `--rollup`. `triggers` belongs on that list with one qualification worth stating rather than rounding away: its shared-tier `--replace`, the one shape of the verb that destroys a declaration rather than authoring one, does now carry a refusal inside the CLI under the store signals, on the footing the body repair and the delete verbs carry theirs. Every other shape of the verb still rests on this allowlist alone, which is why the verb stays listed here rather than moving out of it. One is `find`, which is why the pin on memq's code loads is load-bearing rather than tidy: it is the only mechanical statement of which verbs can reach a code load at all, and its assertion is that the closure of every function reaching one holds `find`'s own entry points and, beyond them, only granted verbs that stand the load down first, the two authoring verbs and `decay-scan`. Another is `anchor`, which rewrites a project-tier record's `anchors:` line at a name the command line gives it, so a worker could re-anchor a memory onto whatever the tree holds now and every drift surface would then report that memory verified when nobody read it; `cmdAnchor` carries no store-signals refusal, the verb being the operator's own, so this screen is the only thing withholding it. The third is `triggers`, which rewrites a record of any tier at the line deciding when that memory is put in front of a session, the shared tiers included, so a regression on its screen would let a worker aim recognition across every project on the machine, and, through `--replace`, strip those lines instead of aiming them, which is the quieter half: an aimed trigger fires somewhere a reader notices, where a removed one leaves a record that simply never surfaces again, on every machine the store reaches. `cmdTriggers` carries a store-signals refusal over one shape and no other: a `--replace` reaching a shared tier or a pinned project store is refused outright there, that being the shape which destroys a declaration rather than authoring one. Every other shape of the verb, the merge included, rests on this allowlist alone, which is why the verb sits on this list rather than off it. The `--confirm-shared` a shared-tier replace requires outside those signals is a typo guard on the same command line rather than a second lock here. The last is `--rollup`, withheld here and nowhere else, because the CLI cannot refuse it on the store signals without taking the archival half of the same verb with it, and archival is the half a fleet worker's decay pass is for. That is the half that survives a divergence, and it survives it only because the expansion refusals above hold: the screen is a content test on words, so it is worth exactly as much as the guarantee that the words the hook reads are the words the child receives. A caller-controlled expansion breaks that guarantee rather than bypassing the screen, which is why an unquoted brace, glob, or leading tilde refuses the grant outright instead of being screened. Withholding is silence rather than a deny, so the call falls through to the ordinary permission flow and the hook stays a pure grant hook. Silence is not leniency here: on the vector this grant exists for, that flow is the Bash refusal the grant was written to route around, so a withheld shape is one a worker cannot run. The flag screen matches a whole word or a word carrying an attached value, so `--body-file=x` is withheld exactly as `--body-file x` is. No flag this function is asked about parsed an attached value when the screen was written, which made the attached-value half a screen over spellings this CLI would have rejected anyway. That is no longer true of the set: `--type=<type>` on `triggers`, `get` and `touch` is a working attached-value invocation, so that half now screens a live spelling rather than only dead ones. The narrow claim is the one to hold, since attached values were never universally rejected here, `--since=<n>d` on `recent` and `unstamped` having always parsed. The screen was written to hold either way, because the alternative is a screen whose completeness depends on a parser rejection two files away, which is the coupling this surface keeps paying for and the reason a parser change like that one costs nothing here. The verb screen reads the subcommand strictly as the first argument past the script path, the same position the CLI's own dispatch reads, so no leading global flag can shift a screened verb out of it. A parser that later admits a flag ahead of the subcommand needs the screen widened with it. The gap it cannot see: it judges command text and its own environment, not what runs, so it cannot see what the granted memq process does with its arguments, nor an interpreter swap that happens after the decision, and an engine vector that already allows the command gains and loses nothing from it.

**Every guard fails open on its own malfunction; one of them denies on command text it cannot resolve. The grant fails the other way: silence.** A guard that cannot decide allows the call; a grant that cannot decide emits nothing, which leaves the call to the host's normal permission flow. The two directions are both the safe one for their own hook, and reading either as the general rule inverts the other. A parse error, an unidentifiable agent, an unresolvable path, a missing CLI, or a host timeout allows. One branch runs the other way, and it is named here so the rule above is not read past it: `readonly-agent-guard` denies command text it cannot resolve, a substitution or an executor payload nested past its depth bound and a name with a substitution spliced into it among them. A second branch runs that way too: a destructive cmdlet whose every path operand fails resolution denies where an enumerating cmdlet feeds it, though the same unresolvable operand standing alone allows. Both are deliberate, on the reasoning that a parser fails closed on exactly the ambiguity a bypass exploits, an allow-list's lapse failing open and silently where an ambiguity check's failure announces itself. The accepted risks that follow, per guard:

- The gate-runner's build-directory list is a policy assumption the guard does not check: a repo that tracks real content under one of those names gets no protection there.
- Agent identity comes from the hook payload's subagent-type field; a call the guard cannot positively attribute to a governed agent is allowed.
- A literal payload written to any path the heredoc exemption admits, inside the class's writable set or outside the git root entirely, and executed by a later, separately scanned command carrying a file operand is unseen, whether a heredoc body or a `printf` wrote it, and the tree-state check sees it only when it leaves a file delta.
- Several parsing shapes reach a mutation the guard names elsewhere and allow it anyway. They are lexer limits rather than policy choices, and the list is open rather than closed: each was found by driving strings at the hook, which is a method that finds what it was pointed at. A command substitution standing as a whole token, in a verb or a subcommand slot, is stepped over rather than read, so `git $(echo push)`, `gh pr $(echo merge) 1`, `git ls-files | xargs $(true) rm` and `find /tmp -exec $(true) rm <path> ;` all allow, where the spliced spelling `git $(true)push` denies on the unresolvable token; bash drops the empty unquoted word and runs the denied spelling, and the bulk-idiom member is the highest-consequence of these, reaching a delete of the tracked worktree. The mirror case is a substitution spliced before a flag's dash rather than after it (`sed $(true)-i s/a/b/ <path>`), which evades every flag reader while `sed -$(true)i` denies. A heredoc introduction in comment position still opens a body range, so a redirect or a continued command on the lines beneath a `# <<'A'` is blanked as body text where the shell opens no body at all. An operand standing past a redirect in a simple command is dropped with the segment the operand scan reads, so `rm >/dev/null README.md` allows, while the descriptor-prefix spelling denies on the prefix itself read as an operand. And the PowerShell pipeline branch scans a destructive-cmdlet list carrying `Remove-Item`, `Move-Item`, `Rename-Item` and their `ri`/`rd`/`del`/`erase`/`mi`/`move`/`ren`/`rni` aliases, so `Get-ChildItem src -Recurse | rm` allows where `| Remove-Item` denies. All of them sit inside this section's accepted heuristic risk and are named rather than closed.
- `docs-write-guard` covers the Write/Edit tools exactly and shell writes heuristically; an exotic write (python, `sed -i`, `Copy-Item`, a variable-assembled path) is out of its reach and is caught, if at all, by the Stop-scan backstop. When the payload carries a cwd, its `docs/` match is contained against the git root above that cwd, so a path outside the session's project tree (a session scratchpad, a fixture repo) is out of scope; without a cwd, or for a target unresolvable before the shell runs (a variable, a home-relative path), the shape-only match stands and over-reaches in the false-deny direction.
- `pr-docs-guard` carries a residual false-deny: a payload cwd resolving to a different checkout that is both dirty and parked on a non-default branch still denies.
- `memory-frontmatter-guard` matches Write, Edit and MultiEdit only, so a shell redirection into the store never meets it. Its store-root containment is lexical first, with the directory's real path tried as a second candidate only for a target whose lexical path already sits under the store root and is not UNC- or device-rooted, which resolves a short name or a link inside the store while asking nothing of any other write on the machine. What that leaves out is a spelling of the root itself that the filesystem accepts and a lexical compare does not: a short name of the store root, a mapped or `subst` drive letter, a UNC spelling by a non-admin share name, and an admin-share host spelling outside the five `isLocalHost` compares against, a fully qualified name and a DNS alias among them. Each of those places nothing and allows the write in silence, on the tier where silence is never the right answer. Resolving them would mean an outbound SMB connection made before the user's permission prompt, which is why the check stops where it does. One further residual rides the store root's own location: `memoryRoot()` is `os.homedir()` plus `.claude` absent an honored override, so a profile redirected onto a mapped network drive puts the store root itself on a network-backed volume, where the resolver runs and the shared network predicate does not fire, that predicate answering only the UNC and `//server` forms. And a record's own field values reach the deny line the harness hands the model as its reason for blocking: capped, reduced to printable ASCII, with CR and LF folded so no second line can be forged, but not delimited from the guard's own prose, so store text and hook text meet in one sentence.
- The guards' case tables under `test/` are the lists their authors wrote rather than a proof of coverage, and one of them reads as exhaustive without being so: `docs-write-guard`'s redirect heuristic carries named misses no case in that file exercises, which `docs/backlog.md` enumerates. `merged-pr-push-guard`'s push detector carries named misses too, and its own case table asserts each of them, so there the misses are recorded decisions a change has to re-adjudicate rather than gaps a reader has to find. They sit inside the heuristic-with-a-Stop-scan-backstop risk this section already accepts rather than adding a new one.

**Compensating controls, and the gap each cannot see:**

- Every strict agent's frontmatter grants no Write or Edit tools, the code reviewers, the two document lenses, the council and facilitator seats, and the consultant alike (each holds `Read, Grep, Glob, Bash` and nothing more), so the guard only has to police shell commands. Gap: nothing frontmatter can do about what Bash reaches.
- The executing-work skill brackets every review round with a `git status --porcelain` capture and comparison, so a write that slips past the guard surfaces as a tree delta and is treated as an incident. Gap: the comparison is two `git status --porcelain` readings rather than a byte comparison of the worktree, so it misses every act that moves HEAD and the worktree together while leaving that reading unchanged (a merge, a `checkout`, a `pull`, a `reset --hard`, so a `reset --hard` discarding committed work is invisible here) as well as every act outside the worktree (a `gh` or `az` host-state mutation, a push, a tag); `git fetch` is outside both this comparison and the guard.
- The Stop-scan backstop (`stop-docs-hygiene`) catches scratch that reached `docs/` by any route, including the exotic writes the write-guard cannot parse.
- The build stamps a SHA-256 manifest of every shipped hook file (`hooks.json` included, since rewiring is an equal disarm path to editing a guard) into `.claude-plugin/build-info.json`, and the canary verifies the executing plugin cache against it at session start, warning loudly on drift. This exists because the guards execute from the user-writable plugin cache: a governed agent holding Bash can overwrite a guard there, outside any git root where no tree comparison looks, disarming all five with no signal, and that write is confirmed reachable. The manifest converts a permanent silent disarm into a bounded loud one. Its limits: it is detection, not prevention, and it speaks at the next session start, not in the moment; the canary that performs the comparison stands down entirely under `KIT_EXTERNAL_ENGINE`, so the detection covers attended sessions and not the engine's spawned workers, whose payload integrity is the deploy's concern rather than this check's; and the manifest lives in the same writable cache as the payload it attests, so deleting the stamp file alone silences the check (the canary treats an absent manifest as an older build), and rewriting stamp and payload together defeats it outright. The actor who does either deliberately holds write access the Principals section already places outside every control in this document; the threat the detection is sized for is a model misstep or a rationalized edit, and one naive overwrite is exactly what it catches. Coverage is the shipped hook files; the cache's other executed payload (`scripts/`, `doctor/`) is outside the manifest today, and so is its model-facing prose, `skills/` and `output-styles/kit.md`, which steers behavior when read rather than when executed. The style is the one member of that prose needing no load to take effect: the harness reads it into the system prompt of every main-thread session the plugin is enabled for, so a cache edit to it reaches the model in every session rather than when something invokes it. `test/output-style-parity.test.js` is not that control, since it attests the repo copy against the repo's doctrine and never reads the installed cache.

## The goal state file

`.kit/goal-state.json` is the leash's whole state, and eleven surfaces read it, ten of them belonging to the project that owns the leash: the Stop hook that enforces, the compaction gate, the checkpoint CLI, the chapter-boundary nudge, the compaction-deferral nudge, the SessionStart notice, the `/kit-goal` CLI's own status report, the status-line widget, the doctor, and the status-line launcher. The last of those reads it for one derived answer only: the status-line launcher, deciding whether its render cache is still fresh, needs the armed plan path and the modification time of the doc that path names, and takes the path from its own cache entry while the doc's key resolves under the caller's own cwd through this library's own reader, so the kind, cap and re-validation rules the rest of this paragraph describes cover it exactly as they cover the nine. What it does with the answer is a modification time; it never opens the plan doc itself. It is written only by `kit-goal-lib.js`, and its plan paths are normalized at write time to repo-relative paths that cannot traverse out of the project. Write-time normalization alone would leave a hand edit unchecked, so every read re-validates: the stored current plan and every queue entry must round-trip the same normalizer, and a value that does not round-trip is by definition not one this library wrote. A current plan that fails reads as no armed goal at all, which turns the leash off and leaves the doctor as the surface that flags the file; a queue entry that fails collapses the queue to the current plan rather than being dropped, because dropping one entry would silently renumber the positions `queueIndex` counts. The position walk the bullet below describes re-applies that same round-trip to each entry itself rather than resting on `readGoal` having done it, because it derives a second path per entry that `readGoal` never saw; containment there is a guard the walk holds itself to, not a convention it inherits from its caller. The property that buys is that no reader can hand an unvalidated path to an `openSync`, which matters because a path naming a FIFO would block one, and the readers include a Stop hook where a block wedges the stop. Re-validation is one of two legs, and it covers only paths that came from the state file. Two readers take paths that were never in the state file at all: the SessionStart plan inventory, whose paths come from a `readdir` of `docs/plans/`, and `stop-docs-hygiene.js`, which scans that same directory for a completed-but-unarchived plan and walks `docs/` for leaked scratch, testing each candidate for the plan-header contract. For both the property rests on the kind rule alone, which is why the kind rule below is stated over every reader of a plan doc rather than over every stored path. The Stop hook is the sharper of the two for the same reason the leash is: a blocking open there wedges the stop at every turn end in that checkout, so a FIFO planted under `docs/` at any name either walk reports would hold the session rather than costing one skipped file. Re-validation answers where the path may point; a second rule answers what may be at the end of it, and both are needed, since a path that round-trips the normalizer perfectly can still name a FIFO. So every node-side reader of a plan doc, the armed plan's own, the unarmed ones the SessionStart inventory scans, and the Stop hook's own two directory-derived reads alike, goes through one shared kind-and-size rule that lstats first and reads only a regular file, and every node-side reader of the state file itself is preceded by the same lstat, kind and cap check. The qualifier is load-bearing and names a real exception: the doctor, the ninth reader in the list above, is PowerShell and reads both files with a bare `Get-Content -Raw`, with no lstat, no kind check and no size cap. That is deliberate for what the doctor is, the surface that exists to report a state file the hooks refuse, and it is why this document credits it as the reporting control rather than as a hardened reader. It has two consequences worth stating plainly rather than leaving to be discovered. A plan doc symlinked outside the repo reads as unusable to every hook while the doctor follows the link and reports the goal active, which is the two-readers-disagree shape in a place the shared rule does not reach. And an oversized file at either path is read whole on an attended doctor run where every hook refuses it, which is a backlogged item rather than a closed one. The rule resolves exactly one link, and only where the target is inside the project and round-trips the normalizer, because a plan doc reached through a symlink is genuinely readable and refusing the whole non-regular class outright is not a safe default here: it fails closed on a leash, where a plan the reader calls absent while the goal stays armed holds every stop until the harness's block cap fires. That is one rule at one site rather than a spelling per reader, deliberately: the failure this design has actually produced is not a missing check but two checks that answer the same question differently, where one reader calls a path absent and its sibling follows the link, and the branch between them falls through to silence. The check is a round-trip rather than an acceptance test, which makes it stricter than the write path in one direction worth knowing: normalization is platform-dependent, so a state file carried from another operating system can read as malformed on arrival. It fails safe, and it is consistent with the file being machine-local in the first place. Staying machine-local is the other half of its posture, and it is a property of the consuming repository rather than one the kit can impose: the kit's own `.gitignore` covers `.kit/`, but nothing stops a project from tracking the file, and a tracked goal state puts one clone's plan paths into history where every collaborator's session start reads them back. So the doctor checks the property instead of assuming it, and it checks the whole `.kit` directory rather than any one filename, because the gate's state and its journal sit beside the goal state under the same posture and a probe keyed on a single path reports PASS on a repository tracking either of them. It reports paths under the directory tracked, the directory neither tracked nor ignored, or the directory ignored, each with the git command that fixes it, names every tracked path it found rather than truncating the list, and reports a git it cannot run rather than skipping silently, so an absent check never reads as a passing one. The two readings are taken over the same directory and the tracked one runs first, since git stops reporting a path as ignored once it is tracked, and a repository can ignore `.kit/` while still tracking a file inside it through `git add -f`. The check inspects the directory the doctor was launched from rather than the kit's own checkout, which is the whole point: the kit's checkout already ignores `.kit/`, so a check scoped to it would be a permanent pass over the one repository where the exposure cannot occur. Detection is most of what there is. One creator prevents the exposure in code for the file it writes: the recognition nudge's log writer puts a `.gitignore` holding `*` into `.kit/` at the moment it creates the directory, so a host repository that never excluded `.kit/` still does not track that log. A second writes it by instruction rather than in code: the park skill has the parked handoff's writer plant the same rule where the directory carries no ignore file of its own, creating and never replacing, which is the weaker of the two, a prose step a model performs rather than a code path that runs, and it guards the one `.kit/` payload carrying no content cap at all, since the handoff body is exempt from the caps its filename takes. Every other creator of the directory writes no such file, so for the goal state, the checkpoint and the gate's own records the doctor is the whole of the control, and it runs only when somebody runs it; the general fix, one shared creator that writes the nested ignore whatever made the directory, is backlogged. An arming adds `queue`, `queueIndex`, `history`, `authorizations`, `armedBy`, and `armingSession` to it whatever the queue's length, a single-plan arm included, where `armingSession` is the arming process's own environment id, recorded only when it is session-id shaped, re-checked against that same shape on every read so a hand edit cannot park a value a claim point would act on, and read only while the goal carries no binding, a leash that has bound or blocked adds `boundTranscript`, `blockedAdvanceKey`, and `blockedAdvancePlan`; `queue`, `queueIndex`, and `history` carry the same provenance and the same guards as the fields beside them, being plan paths and an index the same writer produced, `blockedAdvanceKey` is a capped printable-ASCII token the hook derives from a transcript entry and compares only against itself, and `blockedAdvancePlan` is a plan path of the same provenance as the queue's, used only in equality compares against `plan` and the preceding queue entry and never opened. `authorizations` and `armedBy` are the exceptions to that provenance among the fields, and the two paragraphs below state what each costs; the reported queue position, its own bullet further down, has the same provenance without being a field, and the two claims stay separate rather than either widening to cover the other.

The eleventh is the only foreign one, and it is the newest: the machine-coordinator seat reads a blocked project's state from outside that project, through the CLI rather than by opening the file, which is what keeps the bound transcript's absolute path out of a seat composing a brief for an external channel. What makes that a control rather than a hope is a property of the command's output rather than anything the skill can enforce, so it is pinned in `test/kit-goal-lib.test.js`: `status` prints the recorded blocker note and not that path, and the pin's absence check is required to go red against output carrying it before it is trusted passing against the shipped command. One field survives that filter, the recorded authorization, which carries the operator's own quoted words, so the bar keeping those words off a board line and out of a brief is what bounds this reader and is stated where the seat reads it.

**The state file belongs to the working tree that reads it.** A leash names an execution stream rather than a repository, and git makes a working tree the unit of one: HEAD, the index and the branch are per-worktree. So `.kit/goal-state.json` resolves against the caller's own working directory, for a linked worktree exactly as for an ordinary checkout, and two trees of one repository carry two leashes at once without either reaching the other. The path is fixed relative to that directory and no on-disk pointer is consulted to find it, so the location is not a trust input: no `.git` file is read on this path, nothing is resolved out of a `gitdir:` line, and the reads and writes a leash performs, a bind, a queue advance, and the clear's unlink among them, all land inside the payload cwd's own git root rather than outside it. The doctor reads a different tree from the hooks, and co-located state narrows what one doctor run can say: it derives the clone it inspects from its own plugin root rather than from the working directory a hook resolves against, and its goal-state block runs only for a repo clone, so it reports on that one tree. A repository now holds one state file per working tree, so a malformed or oversized state file in a linked worktree is outside what a doctor run resolving the main checkout reports, which bounds the reporting control this document credits the doctor as. `memq` deliberately answers differently, resolving a worktree to its main checkout through a two-way handshake, because a memory is about the repository where a leash is about an execution tree; the two resolutions are pinned against each other over shared fixtures so that the difference stays deliberate rather than becoming drift.

**`authorizations` is the only field whose value comes from a document rather than from this writer, and it is asserted, never authenticated.** It maps each queued plan path to the first sentence of that plan's `## Dispatch Authorization` section, or to none where the plan carries no such section, and the CLI derives it from the artifact at arm time rather than accepting it from a caller, so there is no flag with which to assert an authorization a plan does not itself state. `--self-armed`, which records the arming the paragraph below describes, does not weaken that: it asserts who ran the invocation and never what the plan authorizes, so the two facts never meet in one value and no flag can put a sentence into this field that the plan itself does not carry. What that buys is a trail and not a check: the sentence is the plan's own claim about who authorized arming it, the file's content is taken at its word, and nothing consults the field to decide whether an arm may proceed. On a single-principal machine it narrows an honest writer without authenticating one, exactly as the guard hooks above do, and git history is what makes the claim traceable. The value is quoted plan-doc content on its way into a file whose readers print it, so it is screened as untrusted input at both ends: stripped to printable ASCII and capped at write, and re-screened identically on every read, because the field is written back verbatim by every advance and bind and a hand edit that never went through the writer must not survive one round trip into the file the readers trust. A value with nothing printable left in it records as none, since an empty quote would assert a section that said nothing. The scan that produces it reads a bounded head of the plan doc through the same kind-and-size rule as every other read of a plan path, so a plan doc that is a FIFO or a directory yields none rather than blocking, and a section the window does not reach records as none rather than as a partial sentence. That covers two shapes: a heading below the window entirely, which the scan never sees, and a section whose body ran to the window's edge with no following heading and no sentence terminator, where the end of the body is unseen rather than short. A body the window did reach the end of is recorded whatever its punctuation, since the heading that bounds it is evidence the scan saw the section end. A sentence longer than the cap is the one partial the field does carry, and it carries a truncation marker so it cannot read as whole; the marker is written inside the cap rather than past it, which is what keeps the screen idempotent against the re-screen every read applies.

**`armedBy` is asserted by the caller rather than read from any artifact, and nothing authenticates it.** It maps each queued plan path to `self`, where the invocation was one a run made for itself, or to `operator`, where the operator typed it, with an absent or unrecognized entry reading as `operator` on every read. It records that one fact and no other. What authorizes a plan to be leashed is a separate fact with its own field, `authorizations` above, which the CLI derives from the plan doc rather than from a caller, and holding the two apart is what lets this one be asserted safely: a claim about who typed a command decides nothing, where a claim about what a document grants would. The value comes from the caller because the caller is what the arm has: an arm a session runs for itself reaches this writer with the same session id and the same arguments an operator typing the command supplies. That is not to say the tree holds no evidence anywhere. `userCommandArgsClaimPlan` in `kit-compact-lib.js` does discriminate a user-typed claim on a plan path from an assistant's echo of one, skipping assistant, harness-injected and sub-agent entries and anchoring on a typed lead token, and the leash consults it for the stronger decision of whether an unbound goal may be claimed by a session. It is deliberately not consulted here, because it answers a narrower question than this field records: it recognizes the plan path inside a typed slash-command argument block, so an arm issued as a direct CLI invocation, which is the form this kit's own skills direct a run to use for `--append` and `--self-armed`, is invisible to it. Gating on it would refuse or mis-record honest armings, which is the failure a gate over an asserted value always has. So the assertion is recorded and bounded rather than checked. It is recorded per plan rather than per queue, because an append can add a plan armed one way to a queue armed the other, and the entry a plan is worked under is its own. Its reach is text and two renders: the condition sentence the state carries, the arming clause that the ordinary hold, the queue advance and the spent-lead hold carry among the Stop hook's block reasons, the capacity refusal and the unusable-plan and wrong-tree holds carrying none, the per-entry line the `/kit-goal` status report prints, and the arming line the doctor's leash report prints beside the plan it reports, on each of its three paths that has established a readable plan. Nothing about enforcement, the binding, the queue, or any gate outcome reads it. Nothing refuses an arm on its account either, and that is a decision rather than an omission: a refusal keyed on an unauthenticated claim leaves the honest spelling unrunnable while the dishonest one stays green, so where a plan armed as the run's own records no authorization the arm proceeds and the CLI warns on stderr at exit 0, naming those plans. That warning is specific to the self direction; an operator arming over a plan recording no authorization is silent. What it costs is that a run may record `operator` over an arming it made itself, or `self` over one the operator typed, and no surface can contradict it. That is the single-principal posture the field above takes, narrowing an honest writer without authenticating one. The repair direction is chosen for compatibility rather than for safety, and the difference is worth stating because the safety reading runs the other way: a state written before this field existed genuinely was an operator arming, which is why an absent entry reads as `operator`, but `operator` is the stronger of the two claims, asserting a request a person made where `self` asserts only what an invocation declared. So a self-armed state whose entry is lost to a hand edit reads back as the operator's, and the next advance recomposes the stored `condition` to match. Of the two renders, only the doctor's parts a recorded operator arming from an absent entry, in a third sentence saying nothing is recorded and that a state predating the field and a hand edit both read that way; the status report's per-entry line does not, so the disagreement is legible on a doctor run and nowhere else until the recompose.

**The SessionStart hook reads the harness transcript store, listing only.** Its shared-checkout advisory enumerates `~/.claude/projects/<flattened-cwd>/` for sibling `.jsonl` files and takes their modification times, to say that another session may be live in the same working tree. It opens no transcript, so no other session's content crosses into this one, and the line it emits carries a count and an age and nothing else: no path, no session id, no filename. Every path fails open, including an unreadable directory and a layout that does not match, because a session start that breaks over a detector is worse than a detector that stays quiet. Recency is the whole signal, so the line is a hint rather than a verdict, and a checkout whose path flattens to the same directory as another is the residual it cannot tell apart.

- **`boundTranscript` is the one field naming a path outside the project, and it is never surfaced and never executed.** The path is stated and stat'ed, never followed and never opened. It has two provenances: an arm-time record from the `/kit-goal` CLI's existence-checked scan for `<sessionId>.jsonl` under the harness's transcript store (candidate paths composed from `os.homedir()`), and a claim-time record from the hook payload's `transcript_path`. Either way it is sanitized as a length-capped string with control characters refused and a network-shaped path (two leading separators, the UNC and `//server` forms) refused outright, and its only use is an `fs.stat` whose result reaches the model as a number and a unit ("last active about 20 minutes ago"), never as the path. So a hand-edited state file can point the stat at an arbitrary local path and learn nothing from it that reaches a session beyond an age in minutes. The FIFO-hang concern that governs transcript reads elsewhere does not arise, because the path is stated rather than opened, but the stat has a hang of its own and the network refusal is most of what answers it: the call is synchronous and runs at every session start, so a path naming an unreachable share would hold the hook for the SMB timeout. That refusal covers the UNC and `//server` forms only. A path on a mapped network drive letter is indistinguishable from a local disk without a syscall and passes it, so a state file naming one can still hold the stat for the SMB timeout. The harness itself never hands a hook such a transcript path, but the arm-time scan composes its candidates from `os.homedir()`, so a home resolved onto a mapped network drive makes the kit compose one with no hand edit; the residual is reachable from that configuration as well as from a hand edit, and it stays stated rather than closed because the only closure available is a syscall in the path the guard exists to keep cheap.
- **The reported queue position is derived from the plan docs, not read from `queueIndex`.** Three surfaces report where a run stands in an armed queue: the SessionStart advisory, the `/kit-goal` CLI's status report, and the status-line widget. All three walk the queue and ask the plan docs themselves, reading each entry's `Status:` header under the frozen machine contract and, where nothing stands at the plans path, the header of a same-named copy filed under `docs/archive/`. The stored index moves only at a clean stop of the bound session, so a run that died at its close-out leaves it naming a plan that is finished and archived, which is the state this derivation exists to report truthfully.

  What that adds to the trust surface is a new input, and it is repository content rather than state-file content: what sits in `docs/plans/` and `docs/archive/` in the reading tree now influences the number a session is told. Four bounds hold it. The walk runs forward only from the clamped stored index and never backward, so it can move the reported position past a finished plan and never behind a live one. It is capped at sixteen entries, so a hostile or corrupt queue cannot turn a session-start notice into an unbounded scan. It never writes back, so a misreading costs a wrong number on one render rather than a mutated leash. And an entry counts finished only where the tree holding the leash reports it finished. The goal state and the plan docs are that one tree's, so there is no second copy to arbitrate and no disagreement to resolve.

  The paths it opens are each entry's own doc and one derived sibling under `docs/archive/`, and the derived one is the reason containment is restated here rather than assumed. A stored entry that passes a bare `docs/plans/` prefix test can still carry traversal in its tail, so the archive path is round-tripped through the same normalizer every stored plan path answers to before anything stats or opens it, and a path that does not round-trip yields nothing rather than a target outside the project. An entry that does not round-trip at all is reported unresolvable, named as such, and keeps its position rather than being skipped, because skipping it would renumber every entry behind it. The archived copy is held to the same header bar as a doc still in `docs/plans/`: presence alone is not evidence, since nothing ties a file under `docs/archive/` to this queue entry beyond a matching name, and a plan deleted rather than filed, with a same-named doc from an earlier effort already in the archive, would otherwise read finished.

  It decides nothing, and that is the whole of why two readings of one queue can coexist safely. The leash still acts on the stored index: every hold, release and advance reads `queueIndex` and nothing reads the derived position, which is a reported number and a sentence, carrying display trust alone. The doctor is again the deliberate exception, and sharper here than elsewhere: it renders the raw stored index, so on exactly the defect state this derivation exists for, the doctor and the hooks report different numbers by design. That is the reporting control doing its job, since a doctor that silently corrected the state file it exists to show would stop being one, and it is stated here so an auditor reading two numbers knows which surface is claiming what.
- **A hand edit is the threat model here, not a remote one.** Nothing outside the machine writes this file, and anything able to write it could equally have written `plan` or `boundSession`, which are the fields with real leverage. The readers are defensive anyway rather than trusting: `readGoal` normalizes every read to a consistent shape, so a queue disagreeing with `plan` or a non-array `history` is repaired rather than propagated, and the doctor discards a queue that disagrees with `plan` in favour of reading the file as a single-plan arming.
- **Advancing is the same write as arming, and it inherits the same atomicity.** The advance is one temp-file-plus-rename rewrite, so a state file is never observed half-advanced. What it does not have is a lock, and the session binding is deliberately not credited as one in its place: the binding serializes the Stop hook's own writes, while the `/kit-goal` CLI is a writer it does not exclude, so a re-arm or a clear can land between the snapshot a stop decided from and the advance's own re-read. A compare-and-swap is what closes that. The advance carries both the plan the stop decided from and the timestamp that state was armed at, and refuses when the re-read state no longer matches either. The timestamp is not redundant: a re-arm that puts the same plan back at the head is the ordinary crash-recovery spelling, and on the plan alone it would pass the compare and let a stop advance a queue that had just been freshly armed. A refused advance holds the stop rather than releasing it, so the failure direction is a retry at the next stop rather than a queue position spent against state the caller never saw. `arm --append` is the fourth writer and guards itself on the same reasoning in its own terms: an append is typed into whatever shell is at hand while the leashed session runs, and validating one opens a plan doc per path, so it re-reads the state immediately before the write and refuses unless the arming timestamp, the current plan, the queue position, the queue length and the history length all still match what it decided from. The timestamp alone would not carry it, because an advance preserves the timestamp by design. What it writes is the re-read with the append applied, never its own snapshot, so a bind or a blocked advance landing mid-validation is kept rather than reverted, and a bystander cannot come to claim a leash whose binding an older snapshot put back to null. `bindSession` takes the same rebase for the same reason, setting only the two binding fields it owns onto a fresh read. Neither closes the window between that re-read and the rename, which stays last-writer-wins. The compaction gate is a third write trigger, reaching the same library to claim a binding at an auto-compaction offer, and the binding cannot serialize it either, because it fires precisely in the unbound state where there is no binding yet. That write carries no compare-and-swap: it is last-writer-wins, so a clear or a re-arm landing between its read and its write can be resurrected by it, recoverable by clearing again.

## The compaction gate

`kit-compact-gate.js` is a PreCompact hook, and it is not a guard: it governs no agent and protects no state from anyone. It schedules. Native auto-compaction lands wherever context happens to fill, which on a leashed plan run is mid-section; the gate defers it until the run declares a boundary, a section's close or, during a drought between closes, an interim board entry. The only lever the harness offers is a veto, and a denied auto attempt is re-offered once per assistant turn indefinitely, which is what makes vetoing a schedule rather than a cancellation.

**The invariant:** the gate denies in exactly two states and allows every other, and both denials are bounded by the same ceiling. Two preconditions gate both: the trigger is `auto` and `KIT_EXTERNAL_ENGINE` is unset. Past those, it denies **boundary-gated** when a kit goal is armed for the project, the compacting session is the one bound to that goal's leash, no boundary checkpoint is open that matches the armed plan, matches the bound session, was opened by that same session, and is still fresh, consumption read from the session transcript is legibly below a named ceiling, and no live operator-consent marker names the bound session. Those four checkpoint legs are one predicate in the shared library, which the gate's verdict and the CLI's status report both answer from, so what the report says gates nothing is what the gate treats as absent. It denies **interactive** when no goal is armed for the project, an armed one is bound to a different session, or an armed one is unbound and this session's transcript makes no claim on it, the transcript shows no native `/goal` or `/loop` driving it, consumption is legibly below that same ceiling, and neither a live role-boundary marker nor a live operator-consent marker names the compacting session. An armed goal no session has claimed yet is resolved by the same two claim routes the leash itself uses, both single-sourced with the Stop hook: where the compacting session's transcript shows the user typing the arming command, or where the session's own id equals the arming session id the state records, the gate claims the binding and takes the boundary-gated path, and where neither holds, the session is a bystander and takes the interactive path. That second claim point exists because the leash's other one is a stop, and a run holding the completion contract does not stop while work remains, so a stop-only claim leaves a well-behaved run unbound and therefore ungated for its whole length. One armed state still allows outright: an armed goal beside a payload carrying no usable session id, which is an anomaly rather than evidence of a bystander, and from which no binding could be written in any case, so it is resolved toward allowing. Any other state, any read error, any ambiguity allows. Each denial writes its own stderr string carrying no input-derived data, distinct per kind so a reader can tell which deferral fired; the boundary note's composed values are the hook's own install directory, spelled into the two CLI paths its remedy names, so the commands it offers the operator resolve outside this repo's own checkout. Manual `/compact` is never gated, checked in code as well as by the `hooks.json` matcher so a rewiring cannot silently widen it. Deny is exit code 2; the JSON deny form is inert for this event on the versions probed, so nothing is built on it.

**The scope of the interactive state, stated plainly because it is this section's widest claim.** The deny reaches every session the harness offers an auto-compaction to, not only the sessions that opted in by arming a kit goal, and the ceiling assumption below rides along with it onto that default population. What bounds the exposure is that the gate can only veto an offer the harness already made, never raise one, and that the same ceiling ends every deferral. The reach also makes the transcript reader a per-session code path rather than a per-plan-run one, which is why its input handling is treated as untrusted parsing rather than as a convenience read.

**Accepted risk: the automation detection reads attacker-influenceable transcript content.** The transcript holds file content, tool output, and agent reports, so the literal command markup the detector keys on can be planted by anything the session reads, including this repository's own documentation. Detection is therefore structural rather than substring-based: an entry must parse as JSON on a line of its own, carry the right entry type, and hold the markup in the user-typed position, and tool results, meta entries, compaction summaries, and sidechain rows are excluded. Content quoted into a transcript rides inside a JSON-escaped field and so cannot produce the standalone line the test requires, which is the property the whole defense rests on. The residual is bounded rather than absent, and it runs in both directions: the detector reads retirement evidence too (a completed goal, a `clear` argument, a loop's terminating stop), so a plant can push a session either way. What bounds it is that both destinations are treatments the gate already applies to real sessions, and both answer to the same ceiling: a plant can move a session between compacting at the native trigger and deferring to the ceiling, and can do nothing else. It cannot extend a deferral past the ceiling, and it cannot reach any file or process. The parsing itself is the sharper edge: the reader caps its read, parses line by line rather than with a whole-file pattern, and its span scanning is linear, because a backtracking pattern over untrusted transcript text is a denial-of-service reachable from every session's compaction path.

**Accepted risk: the claim predicate is an authorization decision taken from the same transcript.** The automation detection above only steers a deferral; the claim decides which session holds a leash and writes `boundSession` into the goal state, so an entry that satisfies it moves real state. It is not a second reader written for the gate. It is the predicate the Stop hook has always claimed a binding with, single-sourced in `kit-compact-lib.js` and called by both hooks, so the gate adds no evidence shape the leash did not already trust. A second claim route sits beside it at both hooks and rests on evidence of a different kind, which is why it is stated here rather than folded into the account above: an unbound goal is also claimed by the session whose own id equals the `armingSession` the state records, with no transcript read at all. It exists because a run that arms a plan for itself types no command, so the transcript route reaches it never, and its leash would otherwise enforce on nobody while every surface reported it armed. The two routes are deliberately not the same kind of evidence. The typed one reads transcript text, which a session can emit, which is what the anti-steal exclusions below defend; this one reads an id the arming process took from its own environment, which no text a session emits can reach, so the exclusions have nothing to defend on it. What it is worth stealing is the same bounded thing the typed route is worth: a claim makes the claimer held at stops and denied auto-compaction, and the only adverse direction is denying a real run its leash, which re-arming recovers. The exclusions are the anti-steal set: the entry must be user-type and neither a sidechain, an `isMeta` harness injection, nor a compaction summary; local-command stdout is stripped before the tag scan; and the path match is directory-qualified, so a same-basename file elsewhere is not the plan. Two invocation shapes then count, and only those two. In the markup shape the plan path must sit in a `<command-args>` span belonging to a `<command-name>` that is exactly `/kit-goal` or ends `:kit-goal`, so another command taking a path argument cannot claim. The typed-lead shape covers the arming the harness does not parse into markup (a multi-line `/kit-goal` with one plan path per line): the message's first non-whitespace characters must be the `/kit-goal` token (optionally plugin-namespaced), and the plan path must sit inside the argument block, the text from the token to the first line that is empty or opens with a backtick or `<`, so quoted, fenced, or injected material after the argument list can never supply the path, and a message that leads with prose, or that mentions the path only behind one of those boundaries, never claims. One residual survives the block boundary: a contiguous prose line inside the block (a lead-token arming of one plan whose very next line, with no blank line, fence, or tag between, mentions another armed plan) can still claim, since the block cannot tell a path line from a prose line; the blast is the same bounded, recoverable one this paragraph already accepts, and arm-time binding shrinks the unbound population it can act on. Array content carrying any `tool_use` or `tool_result` block discards the whole entry rather than being filtered block by block, one step stricter than the sibling readers in the same file, because a claim is a decision and an entry mixing genuine user text with tool output is where planted markup would ride beside a real turn. What a claim would buy an actor who forged one is bounded and recoverable: the claiming session becomes the boundary-gated one and the real run becomes a bystander to its own plan, which re-arming undoes. The write carries no compare-and-swap, the residual recorded under the goal state file above.

**Accepted risk: the checkpoint file is user-writable and steers compaction timing.** `.kit/compact-checkpoint.json` is an ordinary file in a writable tree, so anyone who can write the tree can open or remove one. The worst case is bounded and small: a compaction landing earlier or later in a session than intended. A freshly rendered line is printed as the widget produced it, which is already sanitized segment by segment at construction. The stored plan path is a stat target and never opened, and it must round-trip the same normalizer every other reader of a stored plan path applies, so it cannot name a target outside the project. The write is one of the two `.kit/` writes in this section that screen their own directory, the gate-record writers being the other: it lstats `.kit` and requires a real directory, lstats the target and refuses anything that is not a regular file, and lands through an exclusive-create temp plus rename, so a symlink, junction, or FIFO planted at either is refused rather than followed. A hardlink at the cache path is admitted, matching the goal state's posture. The file is disposable: deleting it costs one re-render, and the first refresh after a disarm that renders inside its budget drops it, the disarm itself removing only the goal state.

**Residual, documented rather than closed: most of these checks screen the file, not the directory holding it.** Every `.kit/` path in this section is composed by one shared resolver from the payload's cwd, and every read lstats its target and refuses a kind it does not expect. The resolver is a fixed suffix on that cwd in the ordinary case and, for a cwd inside the memory store, a fixed suffix on an unsynced per-machine root keyed by the cwd's store-relative path; either way the caller supplies no part of it. One path is the exception and is the reason this sentence no longer says "never from a caller's value": `consent --project <path>` takes the directory from the command line, and the corroboration its own paragraph above describes, refusing unless the named session has a transcript under the named project, is what stands in place of the composition guarantee there. The `.kit` component itself is screened on four write paths and on none of the read paths. The gate-record writers check it: `gateStateTarget` runs `gateScratchTarget`, which lstats `.kit` and requires a real directory, so a symlinked `.kit` is refused rather than followed for both the gate state and the journal. The deferral nudge's hold-stamp writer runs that same `gateScratchTarget` screen, so `.kit/compact-hold-nudge.json` inherits the directory leg the gate-record writers take and screens its own target file besides, removing a kind that writer cannot have produced rather than refusing it. The status-line cache's writer checks it the same way, for the reason its own paragraph gives. The recognition nudge's log writer checks it twice, before and after its own recursive create, because a recursive create walks through an existing symlinked parent rather than refusing it, and its append open composes `O_NOFOLLOW` where the platform defines that constant, which refuses a final-component symlink at the open itself, the write then going through that descriptor rather than a path-re-resolving append. Node exposes `O_NOFOLLOW` only where the platform has it, so on Windows the open is a plain append one and a link planted between the screen and that open is still followed: the screening narrows that window rather than closing it there, and the log is best-effort observability whose failure costs a line rather than a nudge. It is also the only one that creates `.kit/` from a hook running on every tool call rather than behind an explicit operator action, so it writes a self-ignoring rule into the directory at creation, which keeps a log of store-derived text out of whatever repository the session happens to be standing in. Every read, and the checkpoint and release-marker files' own writes, do not: a `.kit` that is a symlink, or that sits under a symlinked ancestor, redirects them to wherever it points, with the file at the far end still passing its own kind check because it genuinely is a regular file. The reachable consequence is bounded by what those files do, which the checkpoint, release-marker and gate-records paragraphs state: a redirected checkpoint, release-marker, gate-state, or hold-stamp read shifts a compaction's timing. One of the four is no longer only a read, and the enumeration says so rather than carrying "read" for all of them: the hold-stamp writer removes a stamp file whose kind or size says it cannot be that writer's own output, so a redirect landing at the far end of a symlinked ancestor lands an unlink there too. `gateScratchTarget` screens the `.kit` component itself, so this is the ancestor case rather than the `.kit`-is-a-link case, and the harm stays bounded to deleting one fixed filename at the redirected location rather than reaching a caller-named path. It is left as a residual rather than fixed because closing it means resolving and re-validating a directory component on every hook invocation on the pre-verdict path, and because planting that link requires the tree write access the Principals section already places outside every control here.

The compaction-deferral nudge writes as well as emits, which makes it the first hook whose emission is gated on its own write landing. `memory-recognition-nudge.js` shares both properties, read from the other side: it writes a per-session marker under its own state directory and returns silently when that write fails, the write there being the deduplication and the cap rather than a rate limit, so a hook that emitted without it would repeat on every tool call. Its second write is not coupled that way and is not meant to be: the nudge log records what the marker has already authorized, appended under the same lock so the two cannot disagree about what fired, and a failed append costs the stamp-rate reading a line rather than costing the session a nudge. It is not the first PostToolUse writer either: `memory-usage-stamp.js` appends a read stamp to the memory store's usage file and emits nothing at all, and `format-on-edit.js` spawns a formatter that rewrites the edited file. What is new here is the coupling. This hook takes its stamp *before* it emits, returning silently when the stamp does not land, and which files that stamp touches depends on which of its two paths ran. On the episode path, serving a session that holds an armed goal's leash, it writes both of the gate's files: the interval stamp on the episode in the state, and one journal line recording that the stamp was taken. On the hold path, serving a session the gate is denying interactively because it holds no leash or because nothing is armed at all, it writes no gate state at all: that path's interval lives in `.kit/compact-hold-nudge.json`, one entry per session, and the journal is the one gate file it does write, taking a line that records the event under its own name. So the write is the rate limit rather than a side effect of the reminder, which is also why the external-engine stand-down keeps it from writing: that guard returns before any of this runs, not because the write rides on the emission. No path is caller-chosen, all three being fixed suffixes on the payload cwd, and the two stamps are not equally narrow. The episode stamp is a compare-and-set against a re-read of the state that fails closed to no stamp. The hold stamp deliberately carries none, and the asymmetry is a property of what each one writes: the episode stamp sets a field inside a state the gate rebuilds from scratch on every decision, while the hold stamp owns its own file, so there is no episode for it to restore and the failure the compare-and-set exists to prevent has no counterpart on that path. What that path does carry instead is a refusal: its write rebuilds the whole file from a prior reading, so the reader answers whether the contents are known rather than only what they were, and a file that is present but unreadable, an lstat failure that is not a plain absence, and a read whose fill loop ended short of what the descriptor promised all stop the write outright rather than letting it rebuild the list from an empty reading. That third leg is the one the reader had to learn to state, and the reason is worth keeping: a file past the ceiling and a file the read could not finish are the same partial result to a caller and are opposite facts to this writer, so the reader now names which bound stopped it and the writer trusts only a bound positively named as the ceiling. The other two unknown readings take the opposite direction, because this writer's own file cannot be behind either of them: a link at the final component, where the writer renames a regular file into place, and a file past the ceiling, where its own file holds at most a handful of short entries and cannot approach the cap. Neither holds a stamp worth preserving and neither lifts on its own, so both are removed before the write rather than refusing it forever, and the checkpoint CLI's status verb reports all five, wording the two that heal apart from the three that refuse. That read is taken through the same shared bounded reader the signpost read uses and asks for the same opt-in link refusal beside its own lstat, so a planted link is refused at the open as well as named by the lstat. An absent or empty file is a reading rather than an unknown, and is written over as before. Without the refusal a single unreadable read would erase every other held session's stamp and re-nudge all of them at once, which is the shape a caller cannot see because the empty list and the unknown one look alike. What bounds the hold stamp instead is an age rule, an entry older than the nudge interval being dropped when the file is read, so in the ordinary case an eviction discards only a stamp that no longer throttles anything. The count cap is a backstop against an unbounded file and it leaves one residue the age rule cannot reach: where more sessions than the cap are held in one project inside a single interval, an eviction drops a live stamp, the evicted session fires on its next covered tool return and evicts another, and the list degrades to a round robin re-nudging each held seat every few fires rather than once an interval. One further user-writable input steers this hook and it is the only one whose path this hook composes by hand outside the project: `compactNudgeFloor` in `~/.claude/claude-kit.local.json`, the machine-local signpost. It is not the only read that can land outside the project the payload names, since `kitScratchDir` resolves a store-resident seat's scratch directory under the home directory too, so the project-relative framing above is about how the path is built rather than about where it lands. The signpost sets the consumed reading at or above which the hold path speaks. It is read through the shared bounded reader, whose kind verdict is taken on the descriptor rather than on the name and which refuses a link at the final component on this caller's own request. What that refusal is worth is stated as what it does rather than as a claim about the file's writers: the read will not follow a link out of `~/.claude/`, so a link planted at the path cannot aim this read at a file elsewhere on the disk, and it cannot hand the open a target whose device stalls a hook that runs after every covered tool return. The two installers that own the file reach the same property from the write side, and it is the write's shape rather than a check that carries it: `setup.sh` and the doctor each compose the new contents into a sibling temp file and rename that into place, so the write replaces the name's directory entry rather than truncating whatever the name currently resolves to, and no window stands between a verdict about the name and a write to it for a link to be planted in. One branch sits outside that shape and is bounded rather than covered by it: where `setup.sh` finds no node interpreter and nothing at all at the path, it creates the file with a truncating redirect, so a link planted between that emptiness test and the redirect is followed. What bounds it is that the branch runs only on a machine with no node and only where the path was empty, and that what it writes is the two-key template rather than any operator value. The link check each writer keeps in front of that write is a report rather than the defence: it refuses and says so, on the doctor's warning channel and in `setup.sh`'s non-zero exit, so an operator who has deliberately linked the signpost is told rather than having that arrangement silently replaced. A hard link is invisible to that check and needs no visibility, the rename leaving the other name holding its own content. The cost of the refusal is likewise stated rather than implied: an operator who has deliberately linked the signpost out of a dotfiles repository gets the built-in default with nothing on any surface saying why. Every unusable reading, an absent file, unparseable JSON, or a value that is not a finite number, means the built-in default rather than an error. Only a number is taken from it and nothing it holds is ever rendered into the sentence the model reads, so a planted signpost can move the threshold at which the directive appears and cannot put text into it. The compare-and-set is load-bearing rather than tidy. Without it a stamp landing across a valve or an illegible allow would restore an episode that allow had just cleared, and a restored episode hands a stale checkpoint the long freshness leg instead of the short one, which admits exactly the mid-chapter compaction the gate exists to prevent. So the hook that only reports a hold could otherwise extend one.

The gate's decision writer is the one path where that same restoration is still reachable, and it is a residual rather than a closed hole. `recordGateDecision` does its read-modify-write without the fingerprint verify the stamp uses, so a bystander session's `deny-interactive` carries the deferral episode through from a read of its own; where that read predates the bound session's valve or illegible allow, writing it back restores the episode the allow had just cleared, and a pending checkpoint the allow left standing is vouched for a second time. It needs two gate processes in one project inside the same few milliseconds, and its cost is the ceiling every other failure direction here already accepts: one compaction landing mid-chapter, which is the state before the gate existed. It is carried rather than fixed because giving a lock-free writer a retry loop is a larger change than the exposure buys.

**Compensating controls, and the gap each cannot see:**

- **The safety valve is the control the rest rests on.** Sustained denial on a run that declares no boundary, neither a section close nor an interim board entry, would otherwise climb to the model's hard context limit, where a session dies outright on an over-length prompt, which is a strictly worse outcome than the mistimed compaction the gate exists to prevent. At or above the ceiling the gate allows regardless of any checkpoint, and the interactive denial answers to the same constant. Its gap: the ceiling is an absolute token count assuming the roughly 1,000,000-token window these sessions carry, because the PreCompact payload carries no `model` field to derive the real one. On a window falling between the trigger and the ceiling the valve would sit above the hard limit and never fire. That is the single direction of this design that is not fail-open, and it is an assumption pinned in the code rather than a property the hook can verify. One shared ceiling is a deliberate choice rather than an oversight, and through the interactive state it governs every session rather than only opted-in runs; what keeps the exposure bounded is that reaching the deny at all requires the harness to have offered a compaction, which a window too small to reach the trigger never does.
- **The doctor's auto-compaction-window check** reads the ceiling out of the hook file rather than restating it, warns when the configured `autoCompactWindow` would leave too small a band between the trigger and the ceiling, the state in which the valve allows everything and the gate defers nothing, and reports a configured value that merely differs from the recommendation, which is the only way a machine already carrying a value learns of a new one. Its one write that touches an operator's own choice, replacing a differing value, is withheld from the unattended `-Yes` consent and takes an interactive answer; supplying an absent value is not, because that case converges while replacement does not. Its gaps, stated plainly because this control is easy to credit with more than it does: it is an attended check that speaks only when someone runs it; it reads the configured window, which is not the running model's real context window, so **the not-fail-open direction above is not covered by this check or by anything else**, and a model whose window is smaller than the ceiling is caught by nothing; and if it cannot read the ceiling constant out of the hook source it reports the skip rather than the comparison.
- **The checkpoint expires.** A boundary is often reached below the trigger, where no compaction is pending, so a checkpoint with no staleness bound would sit open and admit the next offer, which arrives mid-section. The gate treats a stale checkpoint as absent, and it measures staleness on two legs rather than one, because a checkpoint opened below the trigger and one opened while an offer is already being held are not the same object. The first takes a short window of ten minutes, which is what retires the leftover. The second takes an outer bound of 24 hours, and it is not available on the record's own say-so: the CLI stores a `pendingOffer` flag at the open, and the gate honors the long leg only when it can corroborate that flag against its own recorded state, requiring an episode still open, owned by this binding, and dated before the checkpoint it vouches for. An absent or uncorroborated flag falls back to the ten-minute leg, which is the fail-safe direction, and the future-skew check applies to both. The predate requirement is the security-relevant half: without it the flag would mint its own licence, since the very denial that refused a stale checkpoint opens the episode that would corroborate that same checkpoint one turn later. The 24 hours is a sanity cap against a hand-made or clock-skewed record rather than an operating figure; the operating ceiling is the episode's own life, which ends four hours after its newest denial. The executing-work ritual independently clears the checkpoint when the next section starts. That second guard covers a section close alone: no section starts during a closure drought, so a checkpoint opened at an interim board entry rests on the expiry by itself. This is a correctness control rather than a security one, listed here because its absence makes every claim in this section describe a feature that is not doing anything. Two gaps ride with it. The short leg's bound is wall-clock, so a chapter that crosses the trigger within ten minutes of the previous boundary can still spend a stale checkpoint, costing one mistimed compaction. And the long leg has a residue no discriminator closes: an allow that lands without clearing the episode leaves a hold standing with no offer behind it, which a manual `/compact` produces (the gate's matcher is auto-only, so it never sees one) and so does the `no-session` allow (which carries no id, so the ownership test cannot clear). Inside the episode's idle window a boundary opened in that shadow takes the long leg with nothing waiting for it, costing one mistimed compaction, which is the pre-gate status quo. What would close it, whether a compaction landed by some other route, is not observable to a hook the harness never invokes on that path.
- **Session binding retires an orphaned checkpoint.** The checkpoint records the goal's bound session alongside the plan, and the gate requires both to match, so a checkpoint left behind by a crashed run cannot open the gate for the session that resumes the plan. Its gap: it assumes a single writer, since the gate's read-then-delete is not atomic; a concurrent writer landing between the two would burn a boundary. A second legitimate writer of that file exists, the queue advance, which rewrites an open checkpoint to the plan it moved to so a plan's own close-out boundary is not retired by the advance that follows it. It writes from the bound session's Stop event, the same session and a different event from the gate's read. Four further writers sit at the claim points, two in each hook, one per claim route, and each rewrites only the owner field of a record that carries none, for the session it is binding in that same call. They are bounded by that condition rather than by the single-writer assumption: a second adopter finds an owner already recorded and declines, and a record naming another session is never touched. A checkpoint opened while the goal was still unbound records a null session and is given the leash holder's id at the claim, so the boundary the run banked is honored rather than costing a further chapter of deferral, and the record keeps its original opening timestamp so the adoption grants it no extra life.
- **The build's SHA-256 manifest covers these files like every other shipped hook**, so editing the gate or rewiring it out of `hooks.json` is a stamped edit the canary reports. Its gap is the manifest's own, stated in full under the guard hooks above: detection rather than prevention, at the next session start, and stood down entirely under `KIT_EXTERNAL_ENGINE`.

**Not a control:** the gate stands down under `KIT_EXTERNAL_ENGINE` because an engine's workers are fresh per section and have no mid-chapter context to protect. That is a scope decision, not a security property, and it removes nothing an attacker would otherwise face.

**The chapter-boundary nudge rides beside the gate and shares its posture.** `chapter-boundary-nudge.js` is a PostToolUse hook closing the gate's one-way signal: the gate's deny note reaches the user and never the model (an observed property of the harness version rather than a guarantee, carried as an accepted risk above), so a leashed run that skips the chapter-close checkpoint would be denied every offer with no word to the party able to write one. When a Chapter heading is added to the armed plan's own doc, matched by path so a sibling plan under `docs/plans/` never fires it, the hook emits the boundary steps into the model's context. Its model-visible output is a single fixed string carrying no payload, transcript, or repo data, the same injection posture as the gate's deny notes and the checkpoint CLI's sanitized output, and the string states the hold as bounded by the safety valve rather than as permanent, so the one surface that speaks to the model does not contradict the ceiling documented above. It fires for the session holding the armed goal's leash, which is the bound session or, where the goal is unbound, the session whose id the state records as having armed it, and it stands down for a subagent's tool call on the payload's agent keys rather than on the session id, because a subagent's payload carries the parent session's own id and the leash-holder check alone would pass one. It never exits 2, and never exits non-zero at all: the kit library requires are deferred behind the guards so a damaged installed cache degrades to silence, every guard and every internal error fails toward a silent exit 0, and a payload cwd naming a network share (the UNC and `//server` forms) is refused before any filesystem touch, so its worst failure is a missed reminder rather than a degraded edit loop. That refusal covers the two-leading-separator forms only: a project hosted on a mapped network drive letter is indistinguishable from a local disk without a syscall and can still hold the goal read for the SMB timeout, the same residual the goal library states for its own transcript stat. Its silence, like the other fail-open hooks', is not evidence of health.

## The coordinator board

`coordinator/<machine>/board.md` in the memory store is the machine-coordinator seat's state, and it is the one such artifact a single seat maintains continuously about a machine's other sessions. It is not the only durable record one session keeps about another: `~/.claude/kit-events.jsonl` is machine-wide and durable too, though each of its entries is written by the session it describes, and the peer-sessions skill has each side of a handoff record its own half in its own Chapter, the receiver its held or deferred plan and the sender its unconverted handoff. It holds the roster with its role claims, active efforts per repo with plan paths and anchors, machine-resource claims, and the seat's own commitment lines, which are the record no watched system can reproduce: a pending handoff with its protocol state; an open operator escalation, carrying the incident it is about, whether it has been briefed, and what it waits on; a finding this seat routed to another seat, carrying what it is about, the seat it went to, and either a disposition pointer or an explicit open marker naming what it waits on; an open update window, carrying that it is open, since when, a pointer to the channel the operator's word arrived on rather than any of their words, and the drain's own state, meaning which sessions have confirmed parked, which have not, and which the round could not reach; a heavy-process claim this seat has probed; a claim whose first-seen time this seat banked; a claim this seat released; and a registry entry this seat pruned. The routed finding is the one whose absence costs the most, since a disposition recorded only on the fixer's surface is re-found and re-raised by every successor of the finder. An efforts entry may note that a plan carries a `## Dispatch Authorization` section, as a pointer to the plan and nothing more: no dates, no scope, none of the operator's words.

**The four-kinds routing and the homing round each write outside the seat's own directory, and a landing that is none of those writes gates a cut.** The four-kinds routing every pass applies to a board candidate sends a durable lesson to a memory tier and kit friction to the kaizen inbox in the kit checkout, so a pass producing either writes outside this directory as a standing part of its loop rather than as an exception. The writes this section names are a memory-store record on the tier the memory-system skill assigns it; a note appended to a `kaizen/notes-*.md` file in the kit checkout; and an entry in the memq outcome journal at each end of a homing round, which is that round's own write rather than one the four-kinds routing sends, what gates a cut being the runbook's own to state. Those are the members this section names, swept here rather than standing as the class. The landing is not one of those writes: for a kaizen-destined line the landing a round confirms before it cuts the board line is the commit and the push in that checkout that the kaizen skill's capture rule defines, a push that rule states runs no gate, so the note's readership is this repository's remote rather than the checkout it was written in and the disclosure the section below prices is the one the line reaches. Where that skill's fallback puts a note outside a repository there is no commit to wait for and the line stays. What travels with routed content is the routing's own to state and is not re-enumerated here; on top of whatever travels, the kaizen inbox adds the public-board cap that skill states, and the store destinations sit under this section's unestablished-readership default rather than outside it. Bounds limit the journal as an account of an irreversible cut, and these are not the whole set. Which store an entry is readable from is the memory-system skill's resolution order to settle, and a working directory is the last leg of that order rather than the answer, so a round's entries and a later reader's call can resolve different stores; `docs/backlog.md` carries that one. And the decay pass's rollup folds an expired group into one per-key entry preserving the tally and the tags, so an old entry's prose is no durable account of the act it described.

**It is coordination state, never an authority surface**, and the reason is structural rather than a matter of wording. Nothing in the board warrants an action; a session needing an authorization goes to the artifact that carries it. The kit's one authority control is a receiver tracing a grant back to the operator, per Dispatch authority in `docs/architecture.md`, and a document the seat itself wrote cannot satisfy that trace however it is phrased. A board recording standing grants would defeat the control twice: once by replicating the operator's words irrecoverably to every machine the store reaches, and once by making them copy-pasteable into a plan any session writes, after which a receiver's trace finds real operator words in real git history and arms on them. The board is read as data like every other file the kit reads, with no exemption and the successor's own reading included: an entry the seat did not write is a claim, never a warrant.

**The board's readership is the store's, and that is an assumption about the installation rather than a property of the design.** The store replicates to whatever remote is configured for it, and nothing in the kit reads that remote's visibility or refuses a public one: there is no visibility probe in the doctor or the hooks, and the installer and the sync take the remote they find. So the reasonable-privacy premise the seat writes under is a precondition an operator satisfies, not a guarantee the kit makes. Where it is unestablished, which is the state a seat starts in and stays in until the operator answers, the seat writes the board as a public surface: sensitive commitment detail rides as a stub with its detail left on the channel the operator used, and the re-derivable lines are written short or left off. That default-closed posture, rather than the premise, is what replaced the publication clearance this design retired, and it is prose in the runbook with no test behind it. Even satisfied, the premise narrows readership to the store's principals rather than to a person: the store reaches every machine on that remote, which crosses the account, machine and person boundaries the Principals section above records. A repository host's own privacy flag does not answer the question either, and reaching for it is the natural mistake: the flag reports who can find the repository, not who can read it, and a private repository's collaborators read it exactly as they would a public one. The readership is the collaborator set, which is a second query and a different fact. Readership is therefore never the thing that makes a board line safe.

**Two bars do that work, the first with a strict case, and each holds whatever the readership.** No board line carries an absolute path, because a `goal-blocked` event names its project as one and a path typically embeds the OS username; a repo is named rather than pathed, a path inside a repo is spelled repo-relative, and a machine-scoped file's is spelled home-relative. The roster row is the strict case of the same bar, naming a session, its seat claim, and the roster's own ref where two sessions share a name, and never a working directory, whatever the seat learned one from. And the operator's words never appear on a board line, a bar that covers a paraphrase as much as a quotation. Two disclosures sit outside both bars, and the move to a per-machine directory is what makes the first of them worth stating here. The machine's hostname is the directory's own name, so it rides to every machine that pulls the store whatever any line says, and a roster row's session name carries it again in the machine-scoped form the seat is required to use, which is why no alias is on offer for either. Neither is a line a bar could refuse; they are properties of the layout, and an operator weighing whether to adopt the directory is weighing them rather than the bars. Blocker text is the payload the bars matter most for, because the worker composes it: the Stop hook records its first line, on a mid-queue advance, stripped to printable ASCII and cut at 120 characters, into the blocked project's goal state, and the funnel reads that line onto a brief and a board line. The cap the peer-sessions Worker seat states, that the line carries only what its sender would put on a public board, is what stands between a worker's own sentence and that replication, and it is deliberately independent of where the board lives: it is stated against a public board so that moving the board somewhere quieter never reads as relaxing it.

**The commitment categories fall back to a stub rather than vanishing.** The seat is the only record of what it has promised or brokered, so an entry whose detail will not take the pointer form rides as a stub while the detail stays on the channel the operator used, rather than being dropped. Two independent things stop an entry riding in full, matching the runbook's own split: fit, which stubs a commitment too bulky for the pointer form however harmless it is, and sensitivity, which is not fit's special case, so an escalation is not cleared by being compact enough to fit.

**One control here is input-side, and it is not one of the bars above.** The seat runs a command in a directory named by an absolute path it took from a machine-wide append-only file any local session can write, so before anything under that path is opened a network-shaped path (two leading separators, the UNC and `//server` forms) is refused outright whether or not the seat can place it, and every other path is normalized, refused where a parent-directory segment survives that normalization, and then matched by path-prefix containment against the normalized absolute path of a repo the operator named or the seat itself resolved from disk, with one it cannot place reported unread. The two surfaces that would most conveniently answer the placement question are refused as sources by name: a roster row's repo name is the self-chosen half of a session name, and the board is the same unauthenticated cross-machine artifact the screen exists to distrust, so a placement drawn from either is corroboration taken from the surface under test. That is distinct from the corroboration rule stated earlier: corroboration decides whether an event is believed, and this decides whether a path is opened at all. The same screen runs in the other direction over paths the board itself carries, and there are two classes of those: a plan path on an efforts line, and a routed finding's disposition pointer where that pointer resolves as a path. Both take the screen at every point of use rather than at the doc-open alone, opening the document, re-deriving from origin in the repo the path names, and passing the path into a brief or a command each counting as an act on it, because the screen is a property of the channel rather than of whichever reader first needed one. The board is the same unauthenticated cross-machine artifact the screen exists to distrust, so a path it carries places nothing on its own.

**The seat's channels are recorded, never established.** A warranted channel is a closed list of three, stated in the coordinator skill: the operator's keyboard in the session, the account-allowlisted relay thread whose broker checks each author against a one-account allowlist, and an artifact-borne authorization per Dispatch authority, excluding one the seat itself wrote, which that skill bars whoever later traces it. Two properties of the list are worth stating rather than assuming. Whoever controls the allowlisted account holds what the relay leg confers, the check establishing an account rather than a person, and the broker performing it is an external system this repository neither implements nor tests, named among External integrations in `docs/architecture.md`, so that leg rests on a precondition the kit depends on and cannot verify. And the list lives in model-facing prose inside the user-writable plugin cache, which the build's hook manifest does not cover, so an in-place cache edit could widen it with no canary and no test: the list is a convention the seat follows, not a control anything enforces. An extension to it reads the same way, as an operator decision the operator tier records, confirmed over a channel already on the list before it is treated as one.

**What no control here reaches.** Any session on this machine can write the board by resolving the path itself, which is the Principals section applying to it unchanged. Writership is wider than that machine, and the widening comes with the move: the allowlist predicate that admits the directory scopes to no machine, matching `coordinator/` followed by anything whose leaf is a `.md` and none of whose path components is transient-shaped, and the sync's inbound screen runs that same predicate, so an upstream tree carrying this machine's own board path clears the screen and is rebased into this store. One directory per machine is the seat's convention rather than something the sync enforces, and the read-as-data rule above is the only thing standing between an upstream board line and a successor reading it as its predecessor's own. The directory sits outside the `docs/` write guard because it is not inside any project's `docs/`, which is a fact about the path rather than about the allowlist, and outside the frontmatter guard's tier set because that guard covers the project, type and operator tiers alone. That second exemption is deliberate: the guard's rule is CLI-authored-only, while this directory exists for direct writes by seats today, and by a Stop hook and claim-writing subagents under the contract that adds them. What holds the contract is a writer rule stated per file plus reading after the fact, never prevention. The rule is not one blanket convention over the directory: the board and each session's registry entry are single-writer, while the heavy-process claim file and the Admin request inbox are multi-writer by design, each under its own protocol, the claim scoping a delete to the writer's own session so a completing writer cannot erase a live foreign claim, and the inbox admitting the two appending writers its own contract names, the coordinator routing an operator ask and the operator session itself, a narrowing that binds an honest writer and authenticates none, since nothing validates a write here and any session on this machine, or on any machine the sync reaches, can append a line the contract does not admit. Two destructive acts reach across that writer rule rather than sitting inside it, and both are the coordinator's: its reconciliation pass prunes a foreign `registry/<session-id>.md` where the entry's own heartbeat stamp reads exited, and it releases a foreign heavy-process claim on the claim protocol's own clock. Each destroys a record its writer never agreed to lose, and each is decided from that same record, which is an unauthenticated writer's assertion, so nothing independently attests that a session id is dead; the entry's `Started:` line and its `Heartbeat:` stamp are one writer's two fields, and one hand writing both reaches the exited reading by construction. What bounds them is visibility and recovery rather than prevention. The pass writes its own commitment line before it acts, naming the readings that established the verdict and the decider, so the act leaves a record instead of a gap; every reading that cannot be made cleanly keeps the entry rather than removing it, which is why an absent, unparseable, or future-dated stamp reads as unknown and never as stale; and a pruned entry is re-created by a living writer at its next push, the entry being that session's own account of itself rewritten each time. So the writer classes are seats, a Stop hook, claim-writing subagents, and inbox appenders, that last class being what the protocol admits rather than what the surface enforces, and the reading is weaker than attribution: the sync commits everything dirty under one fixed message and the store repository's single git identity, so the history attributes a machine and a sync window rather than a writer, and on a platform where that script does not run there is history only when someone hand-runs the store's repair path. A contested seat, meaning two sessions claiming it, freezes the board by convention and routes to the operator; convention is the whole of that mechanism, since nothing refuses the write. The stop shape the window drains through carries a residual of the same kind, and it is an availability one rather than a disclosure one: a park is taken on a request, provenance deliberately does not enter, and the messaging surface reaches cloud and remote peers, so one message can halt a leashed run for as long as it stays parked, and the run's own record reads as a legitimate park. Three things bound it rather than prevent it. Parking is the cheap direction by construction, costing time and never work, which is why the predicate is deliberately permissive. Resuming is the expensive one and is bounded separately, on the operator's own word or a closing line whose sender the resuming session names. And a park taken on a relayed request names its requester in that turn, so an unordered halt is visible to the operator rather than silent. Nothing authenticates the request itself, which is the residual as it stands. One further bound belongs on everything above. The board write, the pointer form, and the board-as-record leg of reconciliation have run; what stays reviewed prose whose failure modes are argued rather than observed is narrower, and these are the members named rather than the whole of it: the cold start against an absent board, the seat handoff, the stub forms, the contest freeze, the update window whole, its declaration, its drain round, its report, its close and its untracked degradation alike, the homing round, whose guidance ships for each seat to run over its own board, and the routed finding's own path from boarding through the ask for a missing disposition pointer to reading one that lands. The window's own case is the sharpest: the first fleet update after it lands is hand-run by design and the window serves the second onward, so nothing in it has run at all.

## What the public repository discloses

The plugin distributes from this public repository, so the tracked tree is itself a disclosure surface, and two identity classes ride in it by design rather than by accident. The operator's account name appears wherever it is design language: the three owner and author email fields and the author names across the two plugin manifests, the marketplace name, the README, and the shipped skill whose whole subject is that person's writing voice. A personally-published plugin names its author on every surface a consumer meets it through, and withholding the name there produces a worse artifact and conceals nothing, the account being the repository's own owner. Machine hostnames appear where a per-machine artifact's own name carries them: each `kaizen/notes-<machine>.md` filename, the machine column each of its note lines carries as the format's provenance field, live-document references to those filenames, because a reference reworded vaguer than the name it points at leaves the identifier public in the tree listing and only costs precision, and the same filenames where a frozen evaluation fixture quotes a real command that named one, which is the same identifier of the same class arriving through captured text rather than through prose. The two archives, `docs/archive/` and `kaizen/archive/`, keep whatever identifiers they were published with: both are append-only history, and a rewrite cannot recall what a clone already holds.

The boundary of the accepted class is provenance. An identifier reaching the shipped payload or a live document as an accident of where the work happened (the machine a measurement was taken on, an operator checkout path standing as a worked example, the account name compressed into a machine-generated 8.3 form) teaches nothing a role or a placeholder does not, so those surfaces carry roles and placeholders (`HOSTNAME`, `ACCOUN~1`, a generic path) rather than real values. The split is prose-enforced, and saying so is the point: no hook and no test screens the tracked tree for identifier shapes, so the boundary holds by review, and a surface class new to the tree joins it unguarded.

## Type-tier governance limits

The shared tier has no owner and no cross-project coordination beyond the lock:

- `memq add-type` refuses to overwrite an existing name, on the reasoning that another project may rely on it. Overwriting is reached only by asking for it, and three spellings ask: `--update` with a body flag and `--confirm-shared` replaces that record's description and body whole, `delete-type` with `--confirm-shared` removes it outright, and `memq triggers --replace` with `--confirm-shared` states the record's `triggers:` line whole, so every declaration the invocation does not name comes off a record every project reading the store sees. All three are refused under the engine store signals, for the reason the `memq-grant` paragraph above gives.
- Deletion removes the record from the store; it does not remove it from the store's history. The tiers are tracked in a git repository that replicates to whatever remote is configured for it, nothing in the kit reading that remote's visibility, so a deleted record's blob stays reachable in that history, on every machine that already pulled, and in the remote's own object history for whoever reads that repository, exactly as the storage properties above describe for any other tracked content. A record that carried a secret still needs the secret rotated after a delete.
- `memq decay-prune --archive-type` now names the projects declaring that type before it retires anything, and refuses the retirement unless `--confirm-shared` is passed whenever that scan finds more than one declaring project or cannot be run at all; `--archive-operator` requires the flag unconditionally, the operator tier belonging to every project reading the store. Only one of the two is a decision point: the operator-tier gate has no unshared case, so the kit's close-out supplies the flag on those calls and it stands as a typo guard; the type-tier gate is the one that stops a pass. Because the flag is invocation-wide rather than per target, the kit's ritual runs the two tiers as separate `decay-prune` calls, precisely so satisfying the first gate does not waive the second. That split is prose-enforced in the two skills with no mechanical check, and saying so is the point: one combined call satisfies both gates and nothing refuses it. The listing is printed either way, so a single-declarer retirement still shows what it acted on. Read the gate as bounding the ordinary case rather than guaranteeing the retirement's true reach: the scan is this machine's own, and it counts past a project whose index it cannot read, naming that project on stderr rather than failing, so two declaring projects with one unreadable index count as one and the gate waives. The same scan composes `delete-type`'s cost line, so that listing can name a count short of the real one as well, with the skip line printed immediately above it. `delete-type` prints the same listing before it removes anything, and so is the second emission point for those store segment names, which are flattened local filesystem paths reaching the model at column zero under the same 260-character sanitize. Where the scan that establishes the declarers fails, `delete-type` says the reach could not be established rather than naming the current project as the sole declarer, because a cost line an operator confirms against must not assert a reach nobody measured.
- One project's usage prune still collapses read and applied evidence that other projects of that type contributed, so a memory heavily used elsewhere can later scan as idle. This one is not closed: the prune has no equivalent declarer check.
- Under a store pin the type tier's shared-retirement gate does not operate, and the reason is structural rather than a bug. The operator tier's is unconditional and a pin does not reach it. The refusal fires when more than one `projects/` segment declares the type, or when the scan cannot be run at all, and the pin collapses an instance to exactly one segment by design, so on a readable projects root the count is always one and the gate never trips. The type tier it guards is not collapsed by the pin and stays genuinely shared across every worker of that instance, so the surface the gate protects is still there while the gate is not. The listing degrades the same way: it names the instance rather than the repositories a retirement actually costs. A root still carrying pre-pin cwd-derived segments is the exception, and it is not one to rely on.
- The pin also makes type-tier membership instance-wide. `Project-Type:` is read from the pinned index, so every worker of an instance inherits one declaration whatever repository it is running in, and reads and writes that shared tier accordingly. The content stays fenced; what widens is who is in the tier.
- A tier whose last declaring project drops its `Project-Type` line becomes unreachable to the decay scan and prune, and its sidecar grows without a reader.

## Not claimed

- The "data, not instructions" framing on emitted index lines is a mitigation, not a guarantee.
- `memq`'s argument validation protects the *store's shape*. It does not protect the user's secrets.
- `delete-type` and `delete-operator` remove a record from the store, not from its history, and they are not a redaction tool. They are for the record that was written by mistake; `decay-prune`'s archival remains the path for the record that aged out, and a successor's `supersedes:` pointer the path for the record that was right and is stale now. That last one removes nothing at all: it demotes the named record in `find`'s semantic ranking, labels it on the surfaces that serve a record by name (`find`'s two channels, `recall`, `get`, `decay-scan`), and nominates it at the next decay pass, while the record stays live, fetchable by name, and unmodified on disk. One read surface the label does not reach, deliberately: index-line changes are out of this remedy's scope, so the `MEMORY.md` index the SessionStart hook emits into a session's context carries the superseded record's description unlabeled, exactly as it did before. The pointer is model-written data on the successor rather than an adjudication of the target, which is why it is bounded to nominate rather than retire, why a pin outranks it, and why the unattended vector is refused it at both the grant hook and the CLI: no pin bounds which record a pointer may name, so the exemption that bounds the granted retirement flags does not bound this one. Both of those locks sit on the CLI path, and `memory-frontmatter-guard` is the third, sitting on the file-tool path the other two never covered: it refuses every `Write`, `Edit` and `MultiEdit` on the shared tiers and refuses a project-tier pointer naming no live same-tier record. What a worker holding file tools can still write by hand is a project-tier pointer at a real target, which is the instruction-rather-than-boundary residual the destination block above states, and every read surface honors such a pointer exactly as it honors a written one. What they guarantee is that no copy of the record's body the verb can name is left in the store's own tiers: the live record, the retired copy under `archive/`, and the repair backup beside either one all go in the same locked operation, and a name whose only copy is the retired one is a target rather than a refusal. The `.bak` of the two index files and of the usage sidecar go in that same operation, whoever wrote them, so the tier keeps no local copy of the removed record's index line that the verb can name. What they do not touch is the git history the storage properties above describe, nor the outcome journal, which no delete touches and which, unlike the backups and temps above, does replicate to the remote, nor the session transcripts and `history.jsonl` under the store root, which keep whatever a session printed or typed: a `get` of the record puts its body in a transcript and an `add-type --body` puts it on a recorded command line, so a record that carried a secret needs that secret rotated whatever this verb removed. Of a delete that completes, two things can leave a copy in the tier, both of them named in the storage properties above: a backup the sweep reported it could not remove, which deliberately does not fail the command, so a zero exit is not on its own evidence the residue is gone; and a `<file>.tmp.<pid>` stranded at one of those three paths by a rewrite killed between its write and its rename: `MEMORY.md.tmp.<pid>` at either index, holding that index as it then stood with the record's line in it, and `usage.jsonl.tmp.<pid>` at the sidecar, holding the read and applied stamps recorded against the record's name, because the sweep names the `.bak` at each path rather than the temp beside it. The second takes a hard kill to exist, and neither ever leaves the machine, `*.bak` and `*.tmp.*` both being never-sync patterns. Nor do
they touch the derived vector index at the store root
(`memory-index.jsonl`), which holds per record a name, a content hash of the
body, and the embedding built from it. That file is untracked by the store's
own `.gitignore` and never syncs, and the next semantic sweep that can read
the tier prunes the entry, so the residue is one local file until then. What
it holds is a content hash and an embedding rather than the prose, and the
bound this document rests on is the file's reach rather than the derivation's
strength: it never syncs, and the next sweep drops the entry. Embedding
inversion is an established technique against exactly this artifact class, so
treat the vector as recoverable content that happens to stay on one machine,
not as a safely irreversible derivative.
- The delete verbs are governed by the store-signal refusal and by nothing else on the agent axis. `readonly-agent-guard` is a denylist over shell verbs and tree paths and names no `memq` rule, because memq writes the external store rather than the reviewed tree, so a strict read-only agent holding Bash is refused these verbs inside a fleet worker (where the store signals are present) and is not refused them on an attended session. What stands there is the ordinary permission flow, which prompts unless a settings file grants the command. The kit ships no such grant, so the attended-session control is a prompt the operator answers rather than a guard, and a settings grant for `memq` added later would remove it without touching anything in this document.
- `decay-prune` is auditable, and reversible only in the weak sense that archiving is demotion rather than deletion: it prints everything it removed, leaves one generation of backup, durable in the project tier and not in a shared one, where the next `delete-type` or `delete-operator` sweeps it, and a retired memory keeps its description in the archive's own index and still answers `memq get` by name. The rollup is the irreversible half, discarding expired entries' prose for a tally and folding the usage sidecars' raw stamps into one rolled record per file. `--drop-malformed` rides it and is the third irreversible operation on this verb: it removes outright the unparseable usage lines every other read path and every other rewrite preserves, reaching the project tier and either shared tier the same call reaches rather than only the tier whose evidence line reported the skip, and leaving them in that one generation of backup. Its bound is that it refuses a tier where no parsed stamp would survive the drop, keeping every line and leaving that sidecar byte-unchanged, so the operation cannot empty a tier's usage evidence; a refusal on one tier does not stop the tiers where the drop is partial.
- Retention is bounded but not fixed. A memory's decay thresholds extend by 30 idle days for each distinct calendar day it was applied, capped at 365, so the most extended memory becomes an archive candidate at 425 idle days. That ceiling bounds the idle clock alone: a `supersedes: <name>` pointer on any live record of the tier makes the record it names an archive candidate whatever its clock reads, so the 425-day figure is the longest a record survives on idleness rather than the longest it survives. That pointer is authored data rather than a measurement, which is why it nominates and never retires. A `pinned:` frontmatter field exempts a memory from candidacy entirely, pointer included, and makes the prune refuse it by name. The pin binds the decay pass and not the delete verbs, deliberately: a pin is set and revoked only by editing the memory file, and no shared tier admits a hand edit, which `memory-frontmatter-guard` now enforces rather than leaving to convention, so a pin that also stopped `delete-type` and `delete-operator` would leave a pinned shared record removable by no path at all. That guard ships with no hatch of any kind for a pinned shared record, deliberately: `--update` carries a record's existing frontmatter across and so neither adds nor removes a `pinned:` line, and a content-scoped exemption would permit that delta in both directions, letting any writer silently remove a pin, which is a quieter form of what `memq-grant` withholds from an unattended worker. The delete verbs remain the path that retires a pinned shared record, and a hatch, whether a `pin`/`unpin` verb pair or an override signal the guard honors, is one verb's worth of work whenever a real case for one appears. The exemption is set only by editing the memory file and is revoked by deleting the line; a `decay-scan` that finds any pin counts the whole population and lists the first `PINNED_SHOWN` with a counted remainder, so the exempt population cannot grow unobserved. Because archived content is still served by name and by the recall digest, retiring a memory does not remove anything the storage properties above describe: a credential written into a memory persists after archiving exactly as it persisted before.
- Inside an engine worker, the store pin is effectively a single variable, because the gate it inherits is set by the engine rather than by anyone attacking it. The `KIT_MEMORY_ROOT` pair is already true on every spawn, so within that environment one repository-carried `KIT_MEMORY_PROJECT` is honored with no second signal an attacker has to supply, and a plan worker runs inside the repository it is working on. A valid-but-different value relocates that worker's whole project tier to a sibling segment under the engine's root, so its writes land where no adjudicator looks and its reads pull another segment's content into context; an unusable value denies that worker's memory subsystem outright, loudly. This is the `KIT_RUN_ID` residual below, widened from the pending tier to the project tier, and it is bounded the same way: everything stays inside the instance's own store root, which the engine allocates per instance, so the pin is never the separator between instances. The mitigation is the engine's rather than the kit's, and it is to set the variable explicitly on every spawn, which beats a value inherited from the parent environment. It does not beat configuration that runs inside the spawned session's own shells afterwards, so the mitigation is narrower than it first reads.
- Run scoping in the pending tier is not isolation. It keeps two runs from reading each other by ordinary operation, not by enforcement: the only thing selecting a run's directory is that process's own `KIT_RUN_ID`, which any session holding Bash can set to another run's value.
- The pending tier bounds what enters the *project* record without review only for a spawn that carries a run id. Under a pin, a spawn without one (the reviewer and the phone-driven shapes) is deliberately told to write memory files and their `MEMORY.md` index lines straight into the shared instance record, because a pinned project tier is that instance's ordinary adjudicated tier and those shapes are the attended half of the instance. It is a decided behavior, not an escape, and it means the quarantine covers plan-execution runs rather than every write. It does not bound the type tier: `memq add-type` inside a run still writes the shared type tier and its index directly, provenance-stamped rather than quarantined. Under the engine that store is per-instance, so the reach is that instance rather than the machine, but the write is unadjudicated. That bound is an external precondition, not something this repo enforces: it holds only while the engine points `KIT_MEMORY_ROOT` at a per-instance store, so a change to how the engine chooses that root re-opens this entry.
- Installing the optional embedding stack pulls transitive dependencies whose published advisories have no fix version at the pinned release. Accepted as a supply-chain risk of an optional, locally-installed stack rather than mitigated: the install is pinned to a reviewed version and runs with lifecycle scripts disabled, but a vulnerability with no patch available is not something a version pin closes.
- The output style's parity test bounds drift, not tampering. It holds `plugins/claude-kit/output-styles/kit.md` byte-identical with the doctrine's register core in the repository, which is a maintenance control against two copies diverging under editing. The file's security-relevant property, that it becomes system-prompt content in every main-thread session, is attested by nothing once the payload is installed, per the manifest coverage above. Its frontmatter pins are the same kind of control: `keep-coding-instructions: true` is pinned because absent or false it silently strips Claude Code's built-in coding instructions from every kit session, which is a correctness failure caught by review and by that test, not a boundary.
- Nothing here defends against an actor who already has write access to `~/.claude`. Such an actor can already execute code through hooks and settings.
