# Memory System

The kit memory store is the file-per-fact memories plus an extension layer: an outcome journal (`outcomes.jsonl`), used-tracking (`usage.jsonl`), tags, a decay lifecycle, a shared project-type tier, and an operator tier for what is true of you or of a machine, all reached through the `memq` CLI. The store syncs across machines through a private remote, and `find` answers by meaning as well as by substring where the local embedder is installed. `memq` resolves the store from the session's own filing ahead of the bare working-directory derivation, though behind two resolutions the full order below states, the store pin and the worktree fold: the harness files each session's transcript in a project directory, and where `CLAUDE_CODE_SESSION_ID` names a session exactly one transcript answers for, that directory is the store, provided the working directory sits inside the project it names. That proviso is a gate rather than a formality: a project directory's name is derived from a path, and the resolver honors the transcript only where some ancestor of the working directory (the working directory itself counted as one of its own ancestors) derives that same name, with the climb stopped at the nearest enclosing repository root, so a repository boundary is a store boundary. So a subdirectory of the directory a session was started in resolves the same store that directory does, while a session that steps into an unrelated checkout, or into an independent checkout nested inside its own project, resolves, at that checkout's root, that checkout's own store rather than dragging its own along, and from a subdirectory of that checkout the plain path derivation answers with the subdirectory's own segment. The cwd answers wherever the session does not: no session id in the environment, no transcript for it, more than one transcript of that id anywhere under the harness's own projects directory (an ambiguity is not an answer), a working directory outside the project the transcript names, or a path resolved for somewhere this process is not standing (the cross-project surfaces hand memq other directories' paths, and the filing answers only for the process's own working directory). There a plain subdirectory resolves a different, empty store. A git worktree is the exception the kit handles: memq follows the worktree's `.git` pointer, through a two-way handshake, to its main checkout's store, so a worktree resolves the same store the main checkout does, from the worktree's subdirectories too in a session the harness filed under the worktree, since a session filing that resolves to a worktree root is folded through that same handshake; a session filed under the main checkout standing in a subdirectory of a nested linked worktree stops at that worktree's own boundary and takes the plain path derivation instead, and a bare-repo worktree keeps its own store. The other exception is a session an external engine spawned with a store pin (`KIT_MEMORY_PROJECT`), where the store is fixed by the environment and the cwd does not choose it. One more state answers differently from those four, because it is a refusal rather than a resolution: an unpinned working directory naming a network share stands memq down at every verb that would resolve the project memory directory from it, before any of them reaches for `.git`, since that walk risks hanging for the SMB timeout on an unreachable host rather than failing fast. Those verbs are `log`, `find`, `get`, `recall`, `recent`, `unstamped`, `touch`, `anchor`, `triggers`, `decay-scan`, `decay-prune` and `decay-done`, twelve of the sixteen. What puts a verb on that list is that it resolves the project memory directory from the working directory, which is where the walk is, rather than anything it goes on to do with a project root: `triggers` derives no root at all and is gated all the same. Three of the twelve carry an exception inside the verb, and it is the same one at each: `get`, `touch` and `triggers` let `--operator` and `--type=<type>` past, both of which resolve their tier from the store root with no working directory in it, while every other form of those verbs, bare `--type` included, meets the refusal. The remaining four (`add-type`, `add-operator`, `delete-type`, `delete-operator`) never consult the working directory and run past the refusal untouched. `find` refuses whole rather than in part: its semantic ranking reaches every store on the machine, but its own body resolves the project segment from the working directory, so the refusal withholds the machine-wide answer along with the project-tier one, and says both were withheld rather than letting an unsearched channel read as an empty one. Every refusal says so in words on stderr, and the status behind those words splits: the six writing verbs (`log`, `touch`, `anchor`, `triggers`, `decay-prune`, `decay-done`) exit non-zero, while the six reading verbs exit 0 with empty stdout, so a caller gating on status alone cannot tell a stood-down `recall` from a clean read of an empty store and has to read the stderr line to know which it got. The store pin is an escape hatch only for a session already carrying the engine store signals named below: `KIT_MEMORY_PROJECT` on its own is ignored, with a note on stderr saying so, and the refusal then fires exactly as it would with no pin at all. That is the whole shape memq's resolver takes: a spelling refusal first, ahead of everything including the pin (and distinct from the network stand-down above, which sits behind it), throwing on a working directory the store will not name a project by, a relative path or a rooted win32 spelling opening with a single leading backslash and naming no drive, which names a different directory per process drive (a forward-slash-rooted spelling is admitted as the posix grammar's own absolute form), while a spelling opening with two separators, backslash or forward slash in any mix, is the share class above and passes, so even a pinned call from a refused spelling is refused rather than resolved; then an honored pin, a worktree's main root, this session's own filing (its transcript's project directory, folded to the main checkout where that directory is itself a worktree) where the directory being resolved is this process's own working directory and sits inside the project that filing names, a path handed in for anywhere else falling past this leg to the plain derivation, or the plain cwd standing in for its own root, tried in that order. The worktree's main root sits ahead of the session's own directory because the harness files a worktree session's transcript under the worktree while its memories belong to the main checkout, so the other order would reopen the per-worktree store split. The refusal sits behind the pin and in front of the other three, so a call reaches it only where no pin answered first, and it reaches exactly the twelve verbs named here. What the refusal reads is the working directory's spelling and nothing else: a path opening with two separators is a share, and a drive letter mapped to one is not, so a session whose cwd sits on a mapped network drive is not stood down and rides the same walk, paying the session leg's boundary screen on top where the drive's spelling diverges from its link-resolved self, the shape a resolution that reports the mapped drive's UNC target produces; whether every mapped-drive configuration resolves that way is not established, and the two outcomes differ in kind: where the spellings diverge, that leg holds the lexical climb to link-resolved parenthood at one link resolution per ancestor step, each a network round trip that can block on such a drive, and on a configuration where they come back equal the climb instead reads the path as link-free and runs with the screen down, a link on the drive crossing the ceiling unseen, the same residual the share branch above accepts by skipping resolution. That residual belongs to the predicate rather than to this refusal, and naming it is the point, since an enumeration this exact otherwise reads as though the whole hang were closed; where a mapped drive is the shape in front of you, the store pin is what avoids the walk. Two terms the rows below lean on belong here rather than at the point they first condition something. The **engine store signals** are `KIT_MEMORY_ROOT` together with `KIT_MEMORY_ROOT_ALLOW_DATA=1`, the environment an unattended fleet worker runs in; a row that withholds a verb under them is naming that worker, and the fleet section at the end owns the full rule. The **pending tier** is a fourth surface, holding the memories one run wrote that nobody has adjudicated yet; it exists only where those signals are set and a valid `KIT_RUN_ID` names the run, which is why `get` resolves it ahead of the project tier and `recall`'s budget cuts it later than any tier, why it is exempt from decay, and why `find` keeps it out of the semantic index, so one run's unadjudicated writes never surface in another session's search. If `memq` does not resolve in the shell, the shim is not installed: run the kit doctor with `-Fix` (the kit-doctor skill owns that run).

The store stands on its own, whatever Claude Code's auto-memory setting is. The kit's SessionStart hook is what puts the project index and the memory write destination in front of an ordinary session, so the index you see and the directory you write to are the kit's own statement rather than something the harness is assumed to have supplied. With auto-memory on you may see the index twice, once from each; the records are the same.

Two rules govern everything below:

- **Never hand-edit `outcomes.jsonl` or `usage.jsonl`.** They are written only through `memq` and the read-stamp hook, and rewritten by exactly two paths. `memq decay-prune` rewrites both in the project tier, under its `decay.lock`, and `usage.jsonl` in each shared tier, under that tier's own `store.lock`. The delete verbs rewrite `usage.jsonl` only, dropping the removed record's stamps under the shared tier's `store.lock`, and never touch `outcomes.jsonl`. Every rewrite on either path takes a `.bak` beside the file it touches; the decay pass leaves its backups in place, and a confirmed delete removes the `.bak` at each of its own three targets, the tier index, the archive index and the usage sidecar, whoever wrote it. The bound is the path rather than the writer, because a delete that stopped after its index rewrite leaves a backup there and no index line behind it, so a re-run bounded by what it had written itself would sweep nothing and leave the removed record's text sitting in a file no reader lists, no hand may edit, and nothing clears until some later rewrite of that same document happens to replace it. The sweep fires on any run whose removal steps all landed, which includes the run that finds no record left to remove, so a mistyped name under `--confirm-shared` spends those three backups too. Three things leave a backup- or temp-shaped copy of the removed record and nothing else does, the store's git history and this session's own transcript lying outside the verb's reach entirely, and the machine's derived vector index holding an embedding and a hash keyed by name that the next `find` sweeps out: a run that stopped before the sweep, whether refused at the record or thrown partway through a removal, where the backups are the single local recovery for a rewrite that did not land; a backup the sweep could not remove, which is reported on stderr and deliberately does not fail the delete, so a zero exit is not by itself evidence the residue is gone; and a `<file>.tmp.<pid>` a hard-killed rewrite stranded at one of those three paths, which the sweep does not name. None of those three shapes ever leaves the machine, the store's sync refusing `*.bak` and `*.tmp.*` alike. The record file is the opposite case and belongs to the stop: the delete unlinks the record last on purpose, so a run that stopped leaves the `.md` itself, and that the sync does carry. What sits beside it depends on where the stop landed, the steps running in a fixed order: the copies of the record's text, the tier index line, the archive index line, the stamps, the record files. Each rewrite lands whole or not at all, so a stop leaves every step before it done and every step after it untouched, and the failure line names exactly what the run removed, so read that rather than inferring from the order. Whatever the stop left, re-running the same delete under its consent flag finishes the remaining steps; the stop that most needs it is one in the record-file unlinks themselves, which leaves a record no index lists and no stamps describe, and only that re-run clears it. A hand edit races the hook that appends on every memory read, including yours.
- **Journal entries never enter the memory index.** `MEMORY.md` carries index lines for memory files and exactly one journal pointer line, verbatim: `Outcomes: outcomes.jsonl holds the action journal; query with memq find <term>.` The pointer deliberately does not look like a memory line (`- [Title](file.md) - description`), so index parsers ignore it.

| Command | Does |
|---|---|
| `memq log <key> pass\|fail "<summary>" [--tag t]... [--detail "..."]` | Append one outcome to the project journal. The summary caps at 120 characters and `--detail` at 500; past a cap the tail is dropped and the success line announces the cut, so compose to size, and when a cut is announced, re-log the lost tail as its own entry. Warns on an unregistered tag, never blocks. |
| `memq find <term> [--tag t] [--outcomes\|--memories\|--all] [--archived]` | Hybrid search. The lexical block first, one summary line per substring hit over this project's tiers: journal keys as `<key>  <pass>/<fail>  last <age>  <latest summary>`, memories as `<name>  [tags]  <description>`. Then, where the embedder is installed, a fenced semantic block ranking every store and archive on the machine by meaning. Retired records are ranked but withheld from that block, replaced by one line counting them and scoring the best a rerun would show; `--archived` shows them, labeled and demoted. Where this machine has a model endpoint configured, a third block sits above both: the query and the ranked candidates go to that endpoint for a judged ordering with a clause of reasoning per hit, labeled model-judged and advisory. Absent embedder: one loud line naming the remedy, then lexical results unchanged. A dead or slow endpoint: one line naming the degrade, then the other two blocks unchanged. No endpoint configured at all: silent, because a line every find printed would be noise about a channel nobody set up. | `memq get <key\|name> [--type\|--type=<type>\|--operator]` | Full journal entries for a key (newest first, capped), or a memory file's body from the first tier holding that name, a run's pending tier ahead of the project tier and a retired copy from the project, type or operator tier's `archive/` included, the pending tier having none. `--type` or `--operator` pins that tier instead of walking the precedence, which is the only spelling that reaches a shared-tier record a nearer tier shadows by name, and it is what a recognition nudge naming a tier hands you; `--type` has the `triggers` verb's two spellings, bare for the working project's own declared `Project-Type` and `--type=<type>` for a tier named outright, which is what reads back a type-tier record from a project that declares no type, and a type given twice, one spelled in another case than the store's own, or a type-tier root that could not be listed is refused, and the named spelling is refused outright under the engine store signals, at the CLI and at the grant alike, where the bare one keeps both; a flag reads no journal, a key being the bare form's namespace, and a tier with nothing behind it is refused by name rather than answered from another. One tier flag or neither, never both. Under the engine store signals the named spelling is refused outright, at the CLI and at the grant alike, the bare one keeping both: an unattended worker stamps the tier its own project declared and no other. |
| `memq anchor <name> <path>...` | Record which files a project memory is about, at the bytes they hold now: one `anchors:` frontmatter line of `<path>@<sha>` entries, spliced into the record with every other byte of it left alone. The project tier only, a run's pending tier ahead of it; `--type` in either spelling and `--operator` are refused, an anchor needing a project root and a tree. Merges into whatever the line already said, each existing path keeping its position and taking the fresh hash. Under the engine store signals this verb gets no grant at all. |
| `memq triggers <name> [<type>:<pattern>...] [--type\|--type=<type>\|--operator] [--replace [--confirm-shared]]` | Record the recognition triggers a memory should be surfaced by: one `triggers:` frontmatter line of `<type>:<pattern>` entries, spliced into the record with every other byte of it left alone. The type is one of `cmd`, `err`, `skill`, `agent`, `tool` and `glob`, and the pattern is stored verbatim. Any tier, on `touch`'s flag shape: with neither flag the project tier, a run's pending tier ahead of it, and with `--type` or `--operator` that shared tier, which a flag names outright rather than resolving by precedence. Which type tier `--type` means has two spellings and they answer different questions: bare, it is the working project's own declared `Project-Type`; `--type=<type>` names the tier outright, the way `add-type`'s positional does, and it is what reaches a type-tier record from a project that declares no type, which is most of them. The value rides on the flag word because the verb's positionals are `<name> <entry>...`, where a lookahead would read `triggers rec --type cmd:whatever` as a type named rec. One tier flag or neither, never both, and one type, never two. A pin is no obstacle here where it stops the anchor verb, a trigger being a pattern with no project root to resolve against, which is the same reason the shared tiers are reachable at all. Merges into whatever the line already said, each existing entry keeping its position and a new one appended. `--replace` writes the entries the invocation names in place of that line instead, which is the only way an entry comes off a record, and a `--replace` naming no entry at all removes the line rather than writing an empty one; a replace whose resulting line is the one the record already carries writes nothing, exactly as a merge that adds nothing does. Refuses with nothing written: an unpinned working directory that names a network share, on the shared rule above, which gates the plain form and bare `--type` and exempts `--operator` and `--type=<type>`, both of which resolve their tier without touching the working directory; a project declaring no Project-Type under bare `--type`, a type name the store holds no tier for, one outside the type-name grammar, one differing from the store's own spelling of that type in case alone, or a type-tier root this run could not list at all, which leaves whether the store spells that type that way unknown, the last three under `--type=<type>`, or a store with no operator tier under `--operator`; a name the named tier does not hold, or a pending tier it could not examine; any entry outside the grammar, every refused entry named at once, which covers a bad type, a pattern outside the charset or carrying one of the three YAML sequences a plain scalar reads as syntax, a pattern under the length floor, and a bare common token on the three types that bar reaches; a `glob:` entry under either tier flag, collected with those refusals rather than returned ahead of them, a glob naming a path under a project root the shared tiers have none of, which is why the recognition surface skips one there and why authoring one would mint a trigger nothing acts on; a record whose frontmatter block never closes or whose `triggers:` sits under a key other than `metadata:`; a line already carrying an entry it cannot read; a line already cut past what a reader reads, at the 32 entries or at the value cap, whichever it met first; and a write that would push the line past those 32 entries. Only the first of the three parts company under `--replace`: the unreadable entry is dropped and named on stderr, the refusal itself having already shown the caller that entry by text, while the already-cut line still refuses, its tail past the bound being text nothing here has read and so text no report can name, and the entry cap refuses a replacing line exactly as it refuses a merging one. Two further refusals are `--confirm-shared`'s own, each where the flag confirms nothing: the flag without `--replace`, and the flag with `--replace` but neither a tier flag nor a pinned project store. A `--replace` reaching the type or operator tier, or a project tier pinned by `KIT_MEMORY_PROJECT` to one directory every working directory of this instance shares, takes `--confirm-shared` and refuses with nothing written without it, on the bar the shared-tier repair paragraph below states; under the engine store signals that same shape is refused outright, consent or no consent, and the merge is what declares a trigger there. A pin is honored only alongside those signals, so a pinned replace meets that refusal rather than the consent demand. Under those signals this verb gets no grant at all. |

Refused under the engine store signals as well, for the reason the unattended-vector paragraph below gives. `--trigger <type>:<pattern>` declares the recognition triggers the record is born with: repeatable, written as the same top-level `triggers:` line the `triggers` verb merges into later, and validated by that verb's own grammar and both specificity bars, a `glob:` entry refused here for the reason every shared-tier glob is. A refused entry refuses the whole command with nothing written, no record and no index line, and triggers are set at creation like the tags and the pointer, so `--update` carrying one is refused. It is withheld under the engine store signals too: the standing grant an unattended worker runs under withholds the `triggers` verb on the reach of the line it writes, and a line written at a record's birth reaches that same surface. A record written with no trigger still lands, and stderr names it, so a record with no handle is visible as a debt at the moment it is incurred rather than a tier of records later. What the note offers beside the name forks on the environment: off the engine store signals it is the spelling that declares one later, `memq triggers <name> <type>:<pattern> --type=<type>`, which names this record's own tier from wherever it is run; under those signals it is the state instead, the declaration waiting for an attended session, because the standing grant a worker runs under withholds the `triggers` verb and a spelling handed over there names a command that vector cannot run. On the creation path, before the record is written, the verb prints its nearest neighbours, on stderr only so the stdout success line a caller parses is unchanged; an `--update` prints none. The block is a partial-sweep line and a persist-failure line, each where it holds, then `memq: nearest neighbours of <name>`, a provenance fence over the lines where any print, and up to `NEIGHBOURS_SHOWN` lines of name, score, tier and store, `superseded` where a live record of its tier carries `supersedes:` naming it, and a `machine:` scope where the record is scoped to another box, drawn from the live tiers of every store on the machine, `likely overlap` marking a score at or above `NEIGHBOUR_FLOOR`; retired records at or above that floor are counted on one line and never listed, the line naming the `--archived` rerun of `find` that shows them; and where any line carries the label, a closing line says a likely overlap is a candidate for `--supersedes`, a repair or a delete. It warns and never gates: each not-checked line, and that closing line, ends by saying the check does not block the write, and whether a neighbour is the same fact is the author's call. The only type-tier authoring path. |

What the verb puts on stdout for a memory hit is the record's own text, its frontmatter block included, capped at 65536 characters with a notice where the cap binds, and then one `anchors:` line per file that record anchors, or one line naming why they could not be checked, and one `triggers:` line per trigger it declares. That output is the record plus memq's additions rather than a copy of the file, and the two are easy to conflate here, because the record's own `anchors:` and `triggers:` lines sit inside its frontmatter and memq's status lines sit after the body, spelled the same way at column zero. So read a record with `get` and never copy one out of it: writing that output back would fold the status lines into the document, and a record past the cap would come back short. The status lines are memq's own voice at column zero, and what keeps a record from writing itself onto one is a reduction rather than a rule against carrying its text: an entry either grammar refuses is quoted back, capped, and stripped of every whitespace and invisible character first, so nothing a record holds can forge a line or escape the prefix. A record that anchors nothing adds none, and one that declares no trigger adds none either. Archiving is demotion, not deletion: a retired memory keeps its description in the archive's own index and still answers `get` by name. Supersession is demotion too, and lighter: the record stays live and `get` answers for it with a note naming the successor, because a replaced fact is still evidence of what was true and a pointer is model-written data rather than an adjudication.

## Recall

`memq recall` takes no search term, and that is the design rather than a missing feature. It emits the whole store as a bounded digest, one summary line per record across every surface, ordered by last sign of life, inside a fixed line budget that announces every truncation with a counted remainder. You do the ranking, reading the digest with the current task in context. That is the only scorer that understands what you are about to do; a substring match does not, and a lexical miss is silent, which is the expensive kind.

So do not reach for `find` first at effort start. `find` is the narrowing tool; `recall` is for the record you would never have thought to search for. Effort start is not the only moment the verb runs at: a seat takeover reads the digest as well, at the takeover ritual's fourth step in the role skill, which owns what that read covers.

What `find` narrows over spans the machine, not this project alone. Where the embedder is installed, it answers by meaning as well as by substring, and its semantic block ranks all three tiers, live and archived, across every project store on the machine rather than this project's tiers alone; a run's pending tier is deliberately not indexed, so a run's own unadjudicated writes never reach another session's search. Archived records are ranked but not shown by default, because a retired record among live answers is noise you must re-classify on every search. Suppression is never silent: one line at column zero counts what was withheld and scores the best of it a `--archived` rerun would actually display, so you can tell a rerun worth running from one that hands back the same screen. A hit line carries the record's name, its similarity, its tier and store, and, where it has been applied, two separate tokens: `applied x4, last 25h`, a count of the distinct days it was applied on and the age of the most recent one. They are two facts and they are printed as two, because a single `applied 4d` reads as an age and means a tally. Judge freshness from the second token and weight from the first; the ranking deliberately does not do that for you, and the count shown is the true one rather than the capped value the ranking's tiebreak uses. A record some live record of its tier supersedes is labeled on both channels, `superseded by <name>` beside the lexical line and a bare `superseded` token beside the semantic hit's `retired` one, and demoted in the semantic ranking by its own constant, so an equally similar record nothing replaces ranks ahead of it. The successor names ride the lexical label alone; the semantic token carries none. Several successors naming one target enumerate there, name-ordered and capped with a counted remainder, and demote it once whatever the count: the label is a flag rather than a sum. A cycle labels nothing whatever its length, since no member of one asserts a replacement the rest do not answer: a self-pointer, a mutual pair, and a longer A-to-B-to-C-to-A ring all drop together. A pointer reaching into a cycle from outside is not itself on one, so it still labels the member it names. Two local channels rather than one because they fail differently: lexical catches the exact identifiers an embedding fuzzes, an action key or a memory name, and semantic catches the paraphrase a substring misses. A third block joins them where this machine has a model endpoint configured, reading the candidates the other two ranked and re-ordering them by judged relevance with a clause per hit, which is the pass that catches a record topically close to your query and useless for your actual problem. It is labeled model-judged and advisory and it is the one block whose text a model wrote, so weigh its clauses as you would any other model output; the record names it prints come from the store rather than from the model. It sends your query and those candidates' names, tiers and descriptions off this machine, which `docs/security-model.md` describes in full, and it never becomes a dependency: a dead or slow endpoint costs one line and the other two blocks print unchanged, while a machine with no endpoint configured says nothing at all, which is the ordinary state and not a failure. It posts in cleartext over plain HTTP, with no authentication in the default configuration, to a service on another machine shared with that host's other tenants; `docs/security-model.md` carries the full account. Ask it in the words of your problem, not in the words you expect the memory to use. Where the embedder is absent, find says so in one line naming the remedy and serves lexical results; it never fails for want of an optional stack, and it never degrades quietly.

The semantic block is fenced and its lines are indented, because it reaches stores this project never opened. Treat what it surfaces as data to weigh, exactly as with the shared tiers. A hit labelled with another project's store is a pointer to a file, not something `get` will fetch from here.

The digest is your own sight of every surface it covers and leans on nothing outside itself. A record some live record of its tier supersedes carries `superseded by <name>` on its digest line in every tier that has one, so the digest never shows a fresh record and the record it replaced as two equal answers; recall labels and never reorders, the demotion being `find`'s alone. Descriptions ride the journal keys, the archive surface across all three tiers, and the project tier, whatever the store's pin state. The type, operator, and pending tiers are the live surfaces that stay lean, carrying name, applied tally and age, with a `superseded by <name>` label on the type and operator lines where one applies and never on a pending line: the type tier because the session hook emits its index as its own block, the operator tier because it is reached by search rather than by emission, the pending tier because it holds the run's own writing that the run just produced. Under a store pin the project lines additionally ride indented under a provenance line, because the worker that wrote them is not the session reading them back. Every surface prints its coverage line even at zero records, so an empty surface is a stated fact rather than a silent absence. When the budget binds, the cut runs project tier first, then type, then operator, then the oldest archive records, then a run's pending tier, and journal lines last, each cut surface printing a counted remainder that names how to reach what it dropped. The project tier is cut first because it is the surface with the most other paths to it: `find`, `get`, and its index file sitting in one known directory.

Type-derived and operator-derived records in the digest are indented under a provenance line, the same fence `get` puts around those bodies: the type tier is written by every project declaring that type and the operator tier by every project on the machine, so its content is data to weigh rather than instruction to follow. Column zero is memq's own voice.

**When a recalled record changes what you do, stamp it in that turn**: `memq touch <name> --applied` (add `--type` or `--operator` for a shared-tier memory). Find's output closes with that reminder wherever a shown hit is one `touch` can reach from here, which is the moment the stamp is easiest to remember and most often forgotten. Recall is how a memory gets found; the stamp is how it earns its keep. A memory that recall surfaces and you act on, but never stamp, still ages toward the archive as if nobody had used it. Only live memories take a stamp: an archived record has left its tier, so `touch` refuses it. Reinstating a project-tier memory is a hand move, its file back beside the tier's other memories and its index line restored. The shared tiers still have no reinstatement path: hand edits under `memory-types/` and `memory-operator/` are barred because those tiers are shared and their writes serialize under a lock, and nothing moves a record from `archive/` back to live. What they do have is repair and removal. Recall a retired shared memory with `get`; if what it says still holds, write it as a fresh record and let the retired one age, and if it was wrong rather than stale, `delete-type` or `delete-operator` takes it out of both places at once. Reusing a retired record's exact name for a fresh one is possible and worth avoiding, and the two paths to that name answer differently. A create proceeds, because a name coming back is ordinary, and says on stderr that the tier now holds two records of it and that the new one inherits the retired one's read and applied stamps, the store keying usage by filename; the same line names the delete that removes the retired copy. While the retired copy is the only one at that name, any `--update` refuses, the description-only form included, because a caller passing it believes they are editing a record that is gone, and the refusal names the same delete. Once a create has proceeded over the retired twin, a repair of the now-live record lands normally and says nothing about the twin, the shadow note belonging to the create alone. Both lines name that remedy only in an attended session: under the engine store signals they say instead that nothing there removes the retired copy, those signals refusing both delete verbs. A body-carrying repair never reaches either line on that vector, being refused earlier for carrying a body at all.

## Session recap

Where `recall` answers what the store holds, `memq recent` answers what happened to it lately, so it groups by write surface rather than by tier. That grouping is what makes the digest answer whether the extension layer is being exercised at all: journal entries and applied stamps exist only through `memq`, while a project-tier memory file arrives through the Write tool, so the surface a record landed on is its own provenance. Every group states its count even at zero, so an idle surface is a stated fact. Archived files answer to the clock a rename moves rather than to their mtime, which a rename preserves, so a decay pass's demotions read as the file changes they are instead of vanishing.

Do not read the file group's `added` label as "this memory is new". It reports that the file's creation time falls inside the window, and the tools that write a memory rewrite the file rather than patching it, which resets that time on every edit, so an edit to a memory written last week reports `added` too. When the recap needs to say which records are genuinely new, read the names against what the effort actually wrote rather than trusting the label.

Run it over the session's span at close-out and carry the digest into the close-out status, labeled by surface, so the report says what the store actually recorded rather than asserting that the effort banked something. `finishing-work` step 7 owns that trigger, the same way it owns the decay pass.

After recording the recap, the store syncs itself; the close-out verifies that rather than driving it. On Windows the SessionStart hook spawns a background runner (`doctor/sync-store.ps1`) that commits this machine's new and edited memory files through the allowlist gate and, where an upstream is configured, fetches, screens the incoming content against the same allowlist, rebases, and pushes. A store with no remote commits locally and stays silent. So a session's writes reach the private remote at the next session start with nothing to hand-run, and the store nags only when the sync stood down: a recorded gate (a broken allowlist, say) gets a loud line, a failure streak past a week gets one soft line, and a spawn chain that was tried but recorded no outcome (a partial update or a crashed launch, so no run ever wrote a result) gets one soft line once it goes stale; everything else, a healthy sync most of all, is silent. A repository the kit does not own gets no line at all, since it is not the kit's to sync.

The kit doctor's `-Fix` remains the repair and initialization path (it sets the store up on a fresh machine and clears a standing gate), and the way to commit this session's writes immediately rather than waiting for the next session start. It commits and never pushes: what carries a commit to the remote is the background sync runner at the next session start, or one of the two hand paths this paragraph documents below. Off Windows there is no PowerShell runner, so the sync there is this commit plus that manual push, both hand-run. Running `-Fix` from a tool shell: its consent prompt cannot reach a redirected stdin, so a bare `-Fix` always declines; tell me what it would do (a plain commit, or also an embedder install if that section needs one) and get my go-ahead, then pass `-Yes`, which consents to everything the run's flags already asked for. On its own the manual push is `git -C ~/.claude pull --rebase` (a plain `pull` refuses on a diverged branch), then `git -C ~/.claude push`, and only once its memory-sync line reads PASS or FIXED: a FAIL there is a stop, not a push. That gate is the outbound half and covers the leak probes and the store's index state, which is narrower than the pair it gates needs: that pair takes no lock against the background sync and screens no incoming tree, where `doctor/sync-store.ps1` under the kit plugin root, hand-run with an explicit `-StoreRoot`, takes both. Where PowerShell is available that script is the better of the two hand paths, and it is not without exposures of its own: a hand run inherits the invoking session's `GIT_*` environment and its ownership test is weaker than the hook's, and `docs/security-model.md` carries what each hand path leaves exposed. A WARN naming no origin remote or an origin carrying a branch this store does not track is reported only after every leak probe read clean, so it is carried into the close-out rather than treated as a gate; a WARN never means the probes went unrun, the doctor reporting an unanswerable probe as FAIL, so an allowlist it could not prove arrives as a stop already. The other WARNs it raises after a clean read (a destination branch it cannot resolve, a `push.default` advisory, an origin whose branches it cannot list) are carried the same way.

## The outcome-logging bar

Log an outcome when a future session, about to act on that key, would stop or steer differently after reading the entry. Both directions count; the norm does not.

Log:
- A failure with a cause and a countermeasure: `memq log neo.sql.openquery fail "OPENQUERY truncates NVARCHAR(MAX); stage through a temp table"`.
- A success that settled an open question: `memq log neat.deploy.appsettings pass "app-pool recycle alone picks up appsettings changes; no iisreset"`.
- An outcome that flips what the store currently believes, either direction.

Skip:
- Routine successes: a green build, a passing suite, a clean commit. The norm carries no stop/go signal.
- A failure explained by your own typo or a transient outage. Nothing for a future session to change course on.
- A durable fact with no event attached: that is a memory file, not a journal entry. The journal records what happened when you acted; the memory tier holds what is true.

**Write the summary and detail yourself; never paste raw tool output into a memq argument, and compose without embedded `"` characters.** Three reasons, all at this exact keystroke. The journal is plaintext on disk and gets read back into context, so a credential, connection string, token, API key, or personal data pasted into it is stored in the clear indefinitely: name the shape of the secret ("the connection string was missing Encrypt=True"), never its value. An embedded double quote never reaches the store's prose fields anyway: `memq` strips `"` from a log summary and detail and from a shared-tier description, which is what keeps a stored value safe to paste onto a later command line. A record body is the exception on both of its channels: it is never charset-reduced, because it is a document whose punctuation is content, so a quote composed into a body is stored and printed back, which makes a body the one thing this store hands out that is not safe to paste onto a `cmd.exe` command line. And before memq even runs, Windows PowerShell 5.1 passes an embedded `"` to a native process in a form that ends the quoted region, so one quoted argument arrives as several and the call fails its positional count while naming arguments you supplied correctly; memq prints a hint naming this cause when a failing call carries the signature. That mangling is a parsing hazard, not an injection one, and it is separate from the shim story: PowerShell resolves `memq.ps1`, which splats arguments straight onto node, and Git Bash resolves the extensionless wrapper, so neither hands your arguments to `cmd.exe`; only a caller inside `cmd.exe` itself reaches `memq.cmd`, whose `%*` forwarding `cmd.exe` parses, so on that one path an argument carrying an odd number of `"` characters ends the quoted region and anything after a `&` in that text runs as a separate command. Your own quote-free one-line prose is safe on every path.

**The no-secrets half of that rule reaches past the keystroke it names.** A shared-tier body handed to `add-type` or `add-operator` as `--body-file "<path>"` never passes through a paste at all: what lands in the record is the file's text normalized to what argv could have carried, and a file whose text plus the record's heading and frontmatter would exceed the 65536-character cap is refused whole rather than trimmed to fit, and the type and operator tiers sync to a remote every machine and every person sharing the kit can read. So the flag is for a body you composed, never a file you merely have. Do not point it at a `.env`, a settings or credentials file, or raw log or tool output, and read a file you did not write yourself before you name it.

## Applied stamps

**Applied means acted on, not merely read.** A memory is applied when it changed what you did this session: you followed its warning, reused its pattern, avoided its trap. In the turn you act on one, run `memq touch <name> --applied` (add `--type` or `--operator` when the memory lives in a shared tier). Reading, listing, or quoting a memory is not application; reads are recorded for you, by the read-stamp hook when a memory file of any of the three tiers is opened with the Read tool (direct children of the tier directory only, never `MEMORY.md`) and by `memq get` when it serves a body.

The distinction is what the decay lifecycle keys on: only `applied` stamps reset a memory's idle clock, while `read` stamps ride along as evidence for the summarize-versus-archive judgment. A memory that is read forever and applied never is a memory earning its keep in no visible way, and it will be flagged.

**When the in-turn stamp is missed, `memq unstamped` catches it by recognition.** The in-turn `touch` asks for a side action at an arbitrary mid-task moment, and a close-out sweep asks you to recall, across compaction boundaries, which of a long run's reads mattered. Both under-fire. The read stamps survive both, so `unstamped` diffs reads against applied stamps inside a window and hands back the gap: not "what did you use?" but "of these files somebody opened, which one changed what you did?", which is recognition over a list the machine already built. Executing-work runs it at every Chapter boundary, where the judgment is still fresh, and finishing-work runs a final sweep before the decay pass.

**The bar is deliberately generous: did it plausibly steer what you did, not can you prove it did.** The two errors do not cost the same. A false applied delays that memory's decay by one cycle, and nothing else. A missed applied ages a load-bearing memory toward the archive, so the store forgets a fact that was working. When in doubt, stamp.

One of the untracked-reader gaps, the `recall` digest's, stays open by design. A memory acted on straight from the digest's description, its file never opened, generates no read stamp and never enters the candidate list. Instrumenting `recall` to close it would stamp reads that are not reads. So `unstamped` is the backstop, not the replacement: the in-turn habit and find's closing reminder stay in force, and they are what covers the memory this command cannot see.

The gaps are stated rather than silent. Two paths put a read stamp in the tiers this command sweeps: `memq get` when it serves a body from the project, type, or operator tier, and the read-stamp hook when such a memory file is opened with the Read tool. Every other way of reaching a memory's text or description is an untracked reader and leaves none, which is what closes that class rather than the list below, whose members are instances of it: a body read with `cat` or any other shell reader, a description acted on from a `recall` digest or a `find` hit, an index line already sitting in your context, a Read of the tier's `MEMORY.md`, which the stamp hook refuses by name, and a `memq get` inside a run whose name the run's own pending tier answers, which stamps the pending sidecar this command does not sweep (a name resolved from a swept tier stamps that tier as always). So a window read entirely by untracked readers has no evidence to diff, and `unstamped` says so in place of the reminder: a report with no hits and no read stamp in the window names itself an absence of evidence, while one with no hits and a count behind it states that count.

Read the two the way the command states them. The zero is the strong one: no stamp anywhere in those tiers contains your own session's absence, so either your reads went untracked or the stretch read nothing, and the window rests on your own account of the stretch alone, which the paragraphs below route. The count is weaker than it looks: a stamp names a file and a time and no writer, and these sidecars are shared, the project tier with every worktree of the checkout, the shared tiers with every project on the machine, and the store syncing across machines besides, so a count can be another session's reads or reads an earlier boundary already adjudicated inside the same window. Treat it as evidence that tracking is happening in this store, never as proof that what *you* read was tracked. And lost evidence cannot buy the clean sweep: where any part of a tier's evidence went unread, a whole usage sidecar, a record listing, or a single line within a sidecar, the counted verdict names the loss and warns that a record awaiting a stamp may be hidden, in place of the clause that none is, with lost usage evidence also making the count a floor; where that loss leaves nothing counted at all, the verdict reports the zeros as an absence of evidence. The tiers state their own floors above it either way, and a floor line is a question rather than a finding: the flag behind it folds a record listing that is merely absent in with one that could not be read, and an absent project listing is the ordinary state of a store-less project on a machine that has an operator tier. The verdict is the signal built not to cry wolf, keyed on a surface that failed to read rather than one that was never there, and it prints only where no tier raised a hit, so a floor line sitting beside a list of hits has no verdict to resolve it and stays a question.

So no report is a swept window on its own, listed or empty; the report set against your own account of the stretch is. The two instruments see different ground. The report's list sees what the tracker saw, and its blind spots are at least these: the untracked readers above; a record read inside the window and archived before the sweep, which the count carries and no list can raise; and a record cleared by an applied stamp anywhere in the window, whoever wrote it and whenever, which is why widening a window drops records a narrower one would have raised. Your account sees what you actually did, untracked readers included, and the boundary's obligation reaches no further than that: the command's caller is a boundary asking which of this stretch's reads went unadjudicated, and the bar above asks what steered *you*. So walk the list and adjudicate every line on it, then set your account against it, stamping by name any use you can name that the list did not raise, and noting in the boundary's own record rather than stamping one whose record has left its tier, which `touch` refuses. A stretch whose every use is either adjudicated on the list or stamped by name discharges the boundary, whatever the report said about its own coverage, because what the report carries past that stretch is not this boundary's to adjudicate.

The hand walk is what a boundary owes when it cannot produce that account: the stretch's memory use will not come out of what the session still holds. That is settled by trying to enumerate and coming up short, never by recognising a cause, so no event decides it in advance and a compaction inside the stretch decides it least of all.

Enumerate from the store rather than from memory. Read `recall`'s digest and work its live rows, since it carries archived records too and `touch` refuses a name that has left its tier. It describes the project tier's records and merely names the shared tiers', so read the type and operator indexes directly for their descriptions, and read any tier's index directly where the digest says its budget bound. Decide from a description wherever one can decide, and spend `memq get` only where none can, because `get` stamps a read on every body it serves, archived bodies included, and a live record so stamped is a hit at the next boundary with nothing on it to say the walk was what read it, so a walk that opens everything writes use into the store that the session never had. Name in the boundary's own record the records the walk opened, so the next boundary meets those reads with the walk's account already on them. Then `touch --applied` records what steered the work, carrying `--type` or `--operator` for a record of either shared tier, since the reminder line that would name the flag prints only where the report raised a hit.

## Where a hand-written frontmatter field lands

On Claude Code, a Write into a project's memory directory is rewritten into the harness's own frontmatter shape in the same second it lands. Every key you wrote at the top level is moved into a column-0 `metadata:` map, and keys of the harness's own are added beside them, among them `type:`, `node_type:`, `originSessionId:` and `modified:`. At the top level it leaves either an empty `name:` or the record's name with a `description:` beside it. Which of those you get, and which keys ride along, varies by harness version and by which of its memory features wrote the record, so do not read any one key as the marker of the shape. The file does not read back the way you typed it, and that is the harness working rather than your write failing.

**So write every field at the top level, and expect to find it under `metadata:` afterwards.** memq reads its fields, `tags:`, `created:`, `pinned:`, `machine:`, `supersedes:`, `anchors:` and `triggers:`, at both placements: the block's top level, and inside that column-0 `metadata:` map. It keys on the map alone and never on the harness's marker keys, which is why it reads every variant. Where a file carries the same field at both, the top-level value wins. A field under any other key, or nested deeper inside the map, is a different key and is read at neither, which is what the grammar rules below hold you to. What memq writes itself, both shared tiers, emits the top-level shape and is never rewritten, and a decay pass's archive move is a rename that preserves whatever shape it found. So a store holds both shapes at once and every read surface answers the same for either.

**The rewrite sometimes quotes a multi-value scalar, and memq is indifferent to that.** `tags: gotcha, convention` may come back as `tags: "gotcha, convention"` or bare; real stores hold both. memq strips one surrounding pair off a value it reads out of the map, so either spelling matches the same tags. That strip applies to the map placement only. A `tags: "a, b"` you type at the top level and nothing rewrites is your own text, quotes included, so it matches neither `a` nor `b` while printing as `[a,b]`. Do not quote a value you write by hand.

## Tags and the registry

Tags are the cross-cutting escape hatch: an optional `tags` list on memory frontmatter and journal entries, queried with `memq find --tag <t>`. The vocabulary is controlled, not free-form, because unmanaged tags decay into synonyms that make `--tag` queries silently incomplete.

- **Frontmatter uses the inline form only**: `tags: a, b` on one line inside the `---` block, written at the top level. The YAML list form (`tags:` followed by `- a` lines) reads as no tags at all, exactly the silent incompleteness the registry guards against. The silence is what a record already on disk keeps: a Write, an Edit or a MultiEdit carrying that form into a project-tier record is refused at the write door by the frontmatter guard, whose own section below states how far that reaches. After the harness rewrite above, that same line sits under `metadata:`, sometimes wrapped as `tags: "a, b"`, and still reads as both tags; it is the inline form that matters, not which of the two placements it ends up at nor whether the serializer wrapped it. Write it unquoted: a pair of quotes you type yourself at the top level rides into the tag.
- **The registry** is `~/.claude/memory-types/tag-registry.md`: one tag per line, an optional one-phrase gloss after it, `#` comments and blank lines ignored. Add a line before minting a tag; `memq` warns on any tag outside the registry (and still writes the record).
- **Absent registry, no warnings; present registry, authoritative.** An absent file means the vocabulary is not yet established, so nothing warns. A present file, an empty one included, makes every unregistered tag warn. Creating the file is therefore the deliberate act that turns the control on.
- **Starter vocabulary**: projects (`neo`, `neat`), domains (`sql`), kinds (`gotcha`). Extend freely; the decay pass folds in tag hygiene against the registry.

## The `machine:` field

A memory frontmatter field, inline single-line form, the same line discipline and the same two placements as `tags:`: `machine: HOSTNAME`, written at the top level and read there or under `metadata:`. The value is the hostname of the machine the fact is about, exactly as `os.hostname()` reports it on that box, compared caselessly, so any other name labels the record foreign on the very machine its fact is true of. It records a fact as true of one machine rather than of the operator generally or of a project, so the fact still syncs and is still readable from another machine (useful when working against that box remotely) rather than being excluded outright. Route by this test: a fact true of one box carries the field; a fact true of the operator or of a project does not. Written by `memq add-operator --machine <name>`, and read by `find`'s semantic channel, which labels a hit whose machine is not this one. The reader re-validates the value against the same identifier gate the writer applies and drops the label when it fails, so a hand-edited or synced file cannot put free prose on a search line.

**The machine configuration epoch is a record of this kind, at a canonical name.** `machine-configuration-epoch-<hostname>`, the hostname lowercased and the record's own `machine:` field carrying that box's name in the spelling `os.hostname()` reports, is the canonical name for the record holding a machine's current configuration: its logical processor count, its physical memory, the environment settings that move a benchmark number (antivirus exclusions among them), and the date that configuration took effect. The name carries the hostname because one record per box is what the convention needs and the tier is shared by every machine, while `add-operator` refuses to overwrite an existing name, so a single fixed name would let one box's configuration stand for another's. It is authored through the CLI like every other record of this tier and never by a Write into `memory-operator/`: `memq add-operator machine-configuration-epoch-<hostname> "<description>" --body-file <path> --machine <HOSTNAME>`. Whoever observes a configuration change updates it in the turn they observe it: `memq add-operator machine-configuration-epoch-<hostname> "<description>" --body-file <path> --update --confirm-shared`, which replaces the body whole and rewrites the index description with it, the description positional being mandatory on that path as on every other, so it is passed as the description the record should keep rather than as a throwaway; `--machine` is set at creation and stays as it was, the box being the same box. Under the engine store signals the update path is closed, `--body-file` and a body-carrying `--update` both being refused there, so an unattended fleet worker that observes a configuration change on a box whose record already exists reports the change in place of writing it and leaves the write to an attended session. Creation stays open on the channel the refusal itself names: `--body` carries a body of any shape under those signals, so a fleet box holding no epoch record writes its first one rather than reporting a gap.

**A recorded measurement is read against that date before it is leaned on.** A durable figure whose value is set by the box it ran on (a suite wall clock, a lock-wait margin, any duration- or contention-sensitive reading) is valid only under the configuration it was taken on, so a session about to use one compares the moment that figure was measured against the epoch record for the machine it was measured on. A pass/fail count is not one of those and does not expire at an epoch boundary: it is a property of the tree that produced it rather than of the box that ran it, and the delta the operating doctrine requires is reported against a baseline the pre-change tree can no longer be asked for, so calling that baseline expired would make the mandatory report unproducible rather than more honest. A figure whose moment predates the epoch is expired evidence rather than a number, as is one carrying no moment at all, which cannot be placed against the epoch either way, and as is one measured on a machine no epoch record covers, which is every box until its own record is written at the canonical name. That third case obliges the same reading and one further act: the epoch is the canonical name or it is nothing, so a box whose configuration facts sit under some other name (`neo-claude-box-has-eight-cores-under-resident-load` is one such record, an ordinary operator-tier fact about a box rather than that box's epoch) has no epoch to compare against, and the session that needs the comparison writes that box's epoch record first, or states the figure unplaceable and names the epoch write as what would settle it. What expired obliges is one of two things and never a third: re-measure the figure and use the fresh reading, or state the figure as expired and unusable and name what would produce the real one. An expired figure is never quoted as current, never carried into a comparison as though both readings shared a configuration, and never repeated onward, since a figure cited from an artifact spreads the expiry to every artifact that cites it.

## The operator tier

`~/.claude/memory-operator/` holds facts true of the operator or of a machine rather than of one project or one platform. It completes the routing ladder, which runs journal, project, type, operator, doctrine, and it exists because without it such a fact strands in whichever project store happened to learn it.

**The routing test: would this fact be true in a project you have not opened yet, on any of your machines?** A fact about how you work, a tool that is absent from a box, a platform trap that is not this project's: operator tier. A fact true of every project of a type, but not beyond that type: type tier. A fact about this codebase: project tier. Where a fact is true of one machine only, it still lives here, with a `machine:` field marking which box.

Author only through `memq add-operator`, never a direct Write into `memory-operator/`: the tier is shared by concurrent sessions of every project, its writes serialize under a lock, and the Write tool cannot take one. Read the neighbours block the verb prints before the write lands: a `likely overlap` there is the store saying the fact may already be recorded, and the four-remedies paragraph below is where the remedy is chosen. `add-operator` refuses to overwrite an existing name, and refuses a description over the 120-character cap rather than truncating it. Overwriting is reached by asking for it rather than by accident: `--update` replaces the index description, `--update` with a body flag and `--confirm-shared` replaces the body whole, and `delete-operator --confirm-shared` removes the record entirely. See "Repairing and removing a shared-tier record" below.

The tier is not emitted at session start, by design. It is reached through `recall`, `find`, and `get`, which keeps every use visible to the read and applied stamps the decay clock runs on; a memory recalled through an injected index is used invisibly, and the clock ages it as though nobody had.

## The project-type tier

`~/.claude/memory-types/<type>/` holds memories shared by every project of a type, in the same file-per-fact format with its own `MEMORY.md`. A project opts in with a `Project-Type: <type>` line in the first ten lines of its own memory `MEMORY.md`; the session hook then emits the type index at session start, and `find`, `get`, `touch --type`, and the decay pass span both tiers.

**The routing rule: a fact belongs in the type tier only when it holds for every project of that type, not just the one that taught it.** The test: would a project of this type that you have never opened act on it correctly? A fact naming a specific project stays in that project's store. Starter types: `nextjs`, `dotnet`; mint new ones freely through `add-type`, named for the platform or framework that dictates the conventions.

Author only through `memq add-type`, never a direct Write into `memory-types/`: the tier is genuinely shared by concurrent sessions of different projects, its writes serialize under a lock, and the Write tool cannot take one. Read the neighbours block the verb prints before the write lands, since a duplicated type-tier fact is served to every project of the type. `add-type` refuses to overwrite an existing name, because another project may rely on it, and refuses a description over the 120-character cap rather than truncating it. Overwriting is reached by asking for it rather than by accident, in the same three shapes the operator tier's own paragraph enumerates, the last two described under "Repairing and removing a shared-tier record" below.

## Repairing and removing a shared-tier record

**A shared-tier write is not one-way.** Both shared tiers take a whole-body repair, a true delete and a recognition line stated whole (`memq triggers ... --replace`), under the same lock and the same `--confirm-shared` consent their other shared work takes. Compose carefully because the tiers are read by every project and every machine that shares them, not because a mistake is permanent. One caveat on the word consent: `--confirm-shared` is a flag rather than a prompt to a person, and on the unattended fleet vector the grant hook does not withhold it, so a worker there confirms its own shared-tier archival with nobody in the loop and no CLI path back, nothing moving a record from `archive/` to live. What bounds the flag's reach on that vector is that the delete verbs, the body repair and the `--replace` that reaches a shared tier or a pinned project store are all refused there outright, leaving it demotion only.

- **Repair** is `add-type <type> <name> "<description>" --body "..."` (or `--body-file <path>`) `--update --confirm-shared`, and the operator twin. It replaces the body whole; there is no patch grammar. The description positional is mandatory and rewrites the index line as well, so pass the description the record should keep rather than a throwaway: that line is what every project reading the tier sees. It refuses `--tag` alongside it, `--supersedes` and `--trigger` on both verbs, and `--machine` on the operator twin, which is the only one of the two commands that has that flag, so a record needing different tags, a different machine scope, or a different pointer is a delete and a fresh write. Recognition triggers are the one member of that list whose remedy is not a rewrite: they are creation-only on these two verbs and still declarable afterwards, with `memq triggers <name> <type>:<pattern> --operator`, or `--type=<type>`, which merges into whatever the record's line already carries and, under `--replace --confirm-shared`, writes that line whole in place of it. It keeps one generation of the previous body in a `.bak` beside the record, which never leaves the machine.
- **Delete** is `delete-type <type> <name> --confirm-shared`, and the operator twin. It removes the live record, the retired copy under `archive/` if one is there, both index lines, the usage stamps (on this machine only, the sidecars merging by union, which cannot express a removal, so a stamp another machine still holds returns at the next merge and a later record at that name inherits it), and every copy of the record's own text beside it, a backup a rewrite left (`<name>.md.bak`) and a temp file a killed rewrite stranded (`<name>.md.tmp.<pid>`) alike, in one locked operation, and then the three index and usage backups the never-hand-edit rule at the top of this skill describes. Check the name before you confirm: under `--confirm-shared` a name the tier does not hold is not refused, so a typo removes no record, spends those three backups anyway, exits nonzero reporting that no memory of that name exists, and names any stray copy it did sweep but never the backups. Deleting a record another machine has since modified is an ordinary git modify/delete conflict. The local delete commits; it is the rebase onto the other machine's work that stops, and the sync aborts it and leaves the checkout as it found it rather than pushing a half-merged tier, so nothing syncs in either direction until the conflict is settled. The stall surfaces as a session-start nudge once it is seven days old, and resolving it is a human's git operation in the store checkout.

**Four remedies, one per way a record goes bad, and routing between them is the whole point of holding them apart.** Delete is for the record that was **never true**: a mistake, a fact that was wrong when written, a body that says something you did not mean. Repair is for the record whose **fact is right and whose body is wrong**: the claim holds, the prose says it badly or incompletely, so the text is replaced whole and the record keeps its name and its history. Supersede is for the record that **was right and is stale now**: the fact has been overtaken, so a new record carries the answer and points back at the old one with `--supersedes`, which labels the old one on every surface that serves a record by name (`find`'s two channels, `recall`, `get`, `decay-scan`), demotes it in `find`'s semantic ranking, makes it an archive candidate at the next decay pass whatever its idle clock, and leaves it live and fetchable by name. Two surfaces it does not reach: the `MEMORY.md` index the session hook emits carries the record's description unlabeled, index-line changes being out of the remedy's scope, and a pin or usage evidence the scan could not read whole (an unreadable sidecar, or a malformed line skipped inside one) stops the nomination, as the decay-lifecycle section below states. Archive, which `decay-prune` performs, is for the record that **aged out**: nobody has needed it, so it moves to the tier's `archive/` and stops crowding the live answers, still reachable by name. The routing question is what went wrong, not how much you dislike the record. The decay scan nominates unlinked live pairs that read as one fact in its neighbour-pairs block, and the remedy is the author's: the scan names the pair and picks none of the four, since which record was never true, which is stale and which merely says it badly is a judgment over the two bodies. Reach for delete when you would be embarrassed to have another project read it, for repair when only the wording failed, for supersession when you are about to write the record that replaces it, and for archival when you simply do not need it surfaced any more. One case cuts across all four: a record carrying something it should not, a credential, a connection string, anything that needs rotating. That is a delete plus a rotation whatever else is true of the fact, because supersession, repair and archival all leave the text in the store and in its history. Supersession is the only one of the four you perform by writing the successor rather than by acting on the record itself, which is why it is the one that never needs `--confirm-shared`: the command writes only the new record, and every effect on the old one is a consequence readers draw from the pointer. That is a statement about what the command touches, not a claim that the effect is small; the unattended-vector paragraph below is where its reach is priced.

**Deletion removes a record from the store, not from its history.** The shared tiers are tracked in a git repository that replicates to a private remote, so a deleted record's content stays reachable in that history and on every machine that already pulled. A record that carried something it should not have still needs that thing rotated; the delete is not a redaction.

**The unattended vector gets a bounded subset of this CLI, and the bound has two layers.** `KIT_MEMORY_ROOT` with `KIT_MEMORY_ROOT_ALLOW_DATA=1` is the environment a fleet worker runs in, where memq runs under a prompt-free grant (`hooks/memq-grant.js`) with no operator in the loop. Twelve shapes get no grant there. Seven of them memq itself also refuses under those signals, so for those the grant is a second lock: `delete-type` and `delete-operator`, which remove a record every project reading that store reads; an `--update` carrying a body, which replaces a body whole and keeps what it replaced only in a local `.bak` the sync never carries; `--body-file`, which reads a path the caller names into a tier that syncs to a private remote; `--type=<type>`, the attached spelling of a flag whose bare word stays granted, which points a granted `get` or `touch --applied` at any type tier the store holds rather than at the one the calling project declared, so without it a worker reads an arbitrary type tier's body into its own context and stamps that tier's clocks, read and applied alike, where a stamp is a sign of life the decay pass reads; bare `--type` resolves the project's own declaration and nothing else, so what is withheld is the naming of a foreign tier, and the invariant kept is the one the store held before the spelling existed, that a stamp cannot land in a type the project has not opted into; `--trigger` on either add verb, which writes at a record's birth the same `triggers:` line the withheld `triggers` verb writes, so admitting it on a granted verb would hand back through the front door exactly the reach that verb is withheld for; and `--supersedes`, which demotes and labels a record no pin protects from it. That last one is worth its reason, because the demotion is genuinely light and the withholding still earns its place: every other way this grant lets a worker push a record down the store's answers stops at a pin, the archive flags being refused against a pinned name outright, and a pointer is not, so a worker could read the pinned population straight off `decay-scan`, which is granted and prints it by name, and demote in one further command exactly the records the operator marked as the ones not to touch. What is lost is only the pointer: the record still lands carrying every other field. Recovering it is not a later flag, though, because the field is creation-only and `--update` refuses it: the pointer has to ride the creating command, so an attended session re-runs the whole `add`, and a record that already landed without one needs a delete and a fresh write. A withheld `--trigger` costs less, because the record it writes about stays repairable: the `add` still lands with every other field and names the missing declaration on stderr, and the `triggers` verb merges one in later. What that later run needs is an operator, since the verb is itself withheld on this vector, so a record a fleet worker writes carries its recognition debt until an attended session settles it. Four are withheld at the grant alone, with nothing or almost nothing behind them: `find`, which loads an embedder out of a directory the command line does not name; `--rollup`, which discards the prose of every journal entry it folds; `anchor`, which rewrites a project-tier record in place at a name the command line gives it, where what the rewritten line buys is a claim about which files the memory is about and at which bytes, so a worker could re-anchor a record onto whatever the tree holds now and leave every drift surface reporting that memory as verified when nobody had read it; and `triggers`, which rewrites a record of any tier the same way at the record's other half, where the line it writes is what decides when that memory is put in front of a session, so a worker could aim a record's recognition wherever it liked, or crowd the line to its entry cap so the triggers somebody wrote go unread, with nothing on any surface saying the declaration changed. Its `--replace` reaches past aiming to erasure: the flag states the line whole, so one run takes off every declaration it does not name and a run naming none takes the line away, leaving a record with no recognition at all. Its tier flags are what make it the widest of the four: the same rewrite on the operator tier aims or erases recognition for every project on the machine and every machine the store syncs to, so what the withhold keeps off that vector is a fleet worker pointing a machine-wide record at whatever work it chose, or clearing what the operator pointed it at. The `--confirm-shared` the CLI asks for that replace is no second lock here, being a flag rather than a person on a vector with nobody in the loop, which is the caveat the consent paragraph above states; what is a second lock, for that one shape and no other, is memq's own refusal of a replace reaching a shared tier or a pinned project store under these signals, so the erasure has two layers where the aiming has this one. The twelfth, `--drop-malformed`, deletes malformed usage lines behind a single local `.bak`; what stands behind its screen is not a refusal of memq's but the CLI's coupling of the flag to the `--rollup` the grant already withholds, and a coupling in another file is not a lock, so the screen is what keeps a prompt-free delete withheld if that coupling is ever loosened. Withholding a grant is silence rather than a deny, and on that vector the silence is the whole outcome, since nobody is there to approve what the grant does not cover: the command is lost outright. What stays granted is the rest, `recall`, `get`, `log`, `touch`, `recent`, `unstamped` (`get` and `touch` in every spelling but the named type), both write verbs, `decay-scan`, `decay-done`, the description-only `--update`, and `decay-prune` with its archive flags and the `--confirm-shared` those flags require, archiving being demotion rather than removal.

## The `supersedes:` field

The flag on the two shared-tier verbs is one way the field is written. The other is by hand, and it is how the project tier gets it: a project memory is an ordinary file you write with the Write tool, so its `supersedes:` line is authored the same way its `tags:` and `pinned:` lines are. Every read surface treats a project-tier pointer exactly as it treats a shared-tier one.

The grammar is the one `pinned:` and `tags:` answer to, and outside the two placements it is strict on purpose, since a pointer nobody typed under a CLI's validation has nothing checking it on any read path, the frontmatter guard below screening only the Write, Edit or MultiEdit that lands one:

- Written at the top level inside the frontmatter block, which has to open on the file's first line, and read there or under the `metadata:` map the harness moves it to. A `supersedes:` under any other key is not the field, exactly as a `pinned:` under any other key is not, and it fails silently rather than erroring.
- One name, matching the record-name charset, naming a live record of the same tier. Two names point nowhere.
- Same tier only. A project memory names a project memory; there is no cross-tier pointer in this version.

A hand-written pointer gets none of the CLI's six refusals, and the frontmatter guard below sees only the ones a Write, an Edit or a MultiEdit carries, so it is still the one place a dangling pointer can be minted, and one of the two places a cycle can be, the other being a delete and a recreate through the CLI. That is why the read surfaces are built to survive one: a name no live record holds labels nothing and is inert, every member of a cycle is dropped whatever the cycle's length while a pointer reaching into one from outside still labels the member it names, and nothing on any read path retires a record on a pointer's word.

## The `anchors:` field

A memory frontmatter field naming the files a record is about, at the bytes those files held when it was written: `anchors: src/session.cs@1f0c9d3a..., docs/auth.md@8b214f60...`, one line of comma-separated `<path>@<sha>` entries, each path repo-relative and forward-slashed and each sha the 40 lowercase hex of that file's git blob name. Same line discipline and the same two placements as `tags:` and `machine:`: written at the top level of the frontmatter block, and read there or under the `metadata:` map the harness moves it to. It answers the one question no other field does, whether the code a memory describes is still the code that taught it.

**Write it with `memq anchor <name> <path>...`, never by hand.** A 40-hex value is the one field of a record whose typing a hand cannot check, so the verb hashes each named file out of the tree itself and splices a single line into the record, leaving every other byte, its body most of all, exactly where it was. The project tier only, a run's own pending tier ahead of it: `--type` and `--operator` are refused, since an anchor needs a project root to resolve its paths against and a tree to hash and neither shared tier has either. The write merges rather than replaces, so a path the line already carries keeps its position and takes the fresh hash while a path it did not carry is appended, and anchoring one file of a record that anchors four leaves the other three at the hashes they already held. The line as written goes to stdout and stderr names which paths this run hashed and which were carried over, because a carried entry was hashed whenever it was last anchored and this run says nothing about whether that file still holds those bytes. Two side effects ride the rewrite. It leaves one generation of the record's previous text in a `<name>.md.bak` beside it, unmentioned by a run that succeeded (the name rides the line a failed rewrite prints, and nothing else), swept by no listing (`.md.bak` is outside the memory-filename grammar) and carried by no sync, which makes `anchor` one of the three verbs in this CLI that spend a record's one backup generation, `triggers` being the third and taking it on the same record. And it moves the record's mtime, which the decay clock reads as a sign of life, so anchoring returns the record to zero idle days. That one is earned rather than incidental: anchoring is a verification act, and a record somebody has just checked against the tree is a record in use.

Every refusal leaves the record byte for byte as it was, and five of them are worth knowing before you run it. A name the store will not answer for: one outside the memory-filename grammar, one no record of the project or pending tier holds, or a pending tier whose entry for that name could not be examined, which is refused rather than read as an absence, since reading it as absence would rewrite the shared project-tier record of that same name and report success. That refusal covers an examination that failed and not every way the pending path can fail to be a record: something sitting there that is not a plain file, a directory at the name most of all, examines cleanly, is not a record, and sends the write to the project tier. A root that resolves to nothing: a store pin, where the records were not chosen by this working directory and no path has anything to be relative to, and a derived root that is not a directory this can resolve against. A path outside the anchor grammar, with every refused path named together rather than the first one alone, so a caller who mistyped two of four fixes both on one rerun. That grammar is narrower than the filesystem's, and two of its bars cost real files: every whitespace character is refused, so `docs/my notes.md` cannot be anchored in this version at all, and a win32 reserved device stem such as `COM1` is refused on every platform rather than only on Windows. Beside those it refuses an absolute path, a `..` segment, a backslash, a colon, a second `@`, a comma, a quote, the wildcard characters, a dots-only or trailing-dot segment, and a leading character YAML reads as an indicator. The list is what a refusal tells you rather than something to hold in your head: each one names the entry and the rule it met. A record no reader can read: a frontmatter block that opens and never closes inside the reader's line bound, an `anchors:` key sitting under something other than `metadata:`, and bytes that are not valid UTF-8, the first two being records every reader answers `not checked` for, which is the last thing a field whose whole purpose is to report drift should be minted as. And a line the merge cannot preserve whole: one already carrying an entry the reader refuses, one already longer than a reader reads, and a merge that would push the record past the 32 entries a reader takes. Those five are the ones you can compose around rather than the boundary of the set; the rest refuse the same way and name themselves when they fire, among them a malformed command line, a tier lock another writer holds, a record file that is not a plain regular file, and a rewrite this could not verify once it landed.

Four surfaces report what the field says about the tree. Three of them print per record, and each says on the record's own line that it could not check rather than answering as though it had, so no line of theirs reads as verified because nothing was said. The session line is the fourth and it works differently: it carries counts rather than per-record lines, and its absence is not one of its answers, which is the exception its own bullet below sets out. Two surfaces a reader might look for among the four are not there. The frontmatter guard reads it at the write door, to judge a record being written rather than to report on one already written, and its own section below owns that. `find` reads nothing of it: it carries no anchor label at all in this version, on either of its channels, so a hit there says nothing about drift in either direction.

- `memq decay-scan` prints the drift block on stderr after its other blocks and ahead of the neighbour-pairs block, headed by the tier it covers (`memq: anchor drift (project tier)`) and counting each class it found. A live record whose anchored file changed or is gone gets `memq: drift  <name>  changed: <path>  missing: <path>`, pinned records included, with an anchored file nobody could examine riding the same row as `unreadable:`, and a record whose frontmatter, whose own file, or whose root defeated the check gets `memq: drift  <name>  not checked (<why>)`. One further clause rides a row rather than replacing it, saying that part of the record went unchecked: `the rest of the line is unread past <n> entries`, where the parse stopped short of the line's end. This verb keeps no read budget, so no row of its block ever reports one stopping it. `memq: no anchor drift (project tier)` is reserved for a pass that checked everything and found nothing, and the heading carries a cause in its place in exactly two states: a tier that is there and could not be examined, and a store pin leaving no root. An unpinned working directory that names a network share reaches no heading at all, because `decay-scan` stands the whole command down before it resolves a memory directory and prints that stand-down in place of the block. A pinned session whose working directory also names a share does reach the heading, and what it reads there is the pin cause, because the pin and not the share is what leaves no root: moving off the share would give it none. No `decay-prune` flag acts on any of it.
- `memq get` follows the record's text on stdout with one `anchors:` line per anchor: `<path> fresh`, `<path> changed (recorded <sha7>, now <sha7>)`, `<path> missing`, or `<path> unreadable`, a `sha7` being the first seven characters of a hash. A line the parse cut adds a row of its own after the ones it did read, `the rest of the line is unread past <n> entries, so those anchors were not checked`, which is why four shapes describe the anchors a reader reached rather than every line the verb can print. A record it could not check at all gets one line naming the cause in place of those, `not checked (this record's frontmatter could not be read)`, `(this project's root could not be examined)`, or `(a store pin is in effect, so no root is derived from this working directory)`. No network cause is among them, at either end of the question. An unpinned working directory that names a network share never reaches this record at all, `get` standing the whole command down before it resolves a memory directory and printing that stand-down instead. A pinned session whose working directory also names a share does reach this line, and the pin cause is what it reads there, because the pin and not the share is what leaves no root: moving off the share would give it none. A hit on the type or operator tier is never checked whatever it declares and says so, those tiers having no root here to resolve a path against; a record that anchors nothing prints nothing.
- `memq recall` marks the digest line of a drifted live project-tier record with a `[drift]` token, in the slot the `superseded by` label takes and beside it where a record carries both, which puts it before the description rather than at the end of the line, and marks one the pass could not verify with `[drift?]`, so an unlabeled line is never a line nobody checked. Where the pass could not run at all no token is written, and the project tier's coverage line carries the cause when a store pin leaving no root is what stopped it. An unpinned working directory that names a network share reaches no coverage line at all, because `recall` stands the whole digest down before it resolves a memory directory and prints that stand-down in place of the digest. A pinned session whose working directory also names a share does reach the coverage line, and the pin cause is what it reads there, because the pin and not the share is what leaves no root. The other cause does not reach that line: a project tier nobody can examine lists no records either, and a coverage line for a tier holding none carries no clause, so it reads as a bare count of zero and `decay-scan`'s drift block is where that answer is stated in words. The coverage line also counts separately the records the digest's own listing could not examine, which have no digest line to carry a token. The type, operator, pending and archive coverage lines each carry their own not-checked clause, this digest checking the project tier alone. Read the pending tier's twice: it is the other tier `memq anchor` writes to, so it is the surface most likely to hold anchored records this digest never checked.
- The SessionStart hook prints one line last in what it emits, in a run-scoped session as much as an ordinary one, where no project index block is emitted at all. It is built from up to three sentences, because three states must not share a value: how many project memories anchor a file that has changed, how many could not be checked (`memq decay-scan says why`), and how many this check stopped short of, which names the hook's own bound (200 records, 500 anchors or 8388608 bytes read) rather than pointing at a scan that carries no budget and could not answer for them. A tier that is there and could not be examined gets its own fixed sentence, and so does a check that threw. Silence is where this surface differs from the three above, and it is read as a class rather than a list: the line is a positive statement or it is nothing, so its presence carries counts and its absence carries no claim that anything was checked. Five things produce it. Three are the check's own reasoning and are true nothings to say: every count zero, a store pin, and a memq whose exports have moved. The fourth is outside that reasoning entirely, and it is one to hold on to: the hook runs on the `startup`, `resume`, and `compact` session-start sources, so a session that began from a `clear` never runs the check at all, and a store full of drift looks exactly like a clean one. The fifth is outside it too, and it is not the drift line alone: an unpinned working directory that names a network share stands the whole hook down before the check would ever run, on a synchronous walk under that share risking the same hang the check itself refuses, so the session line's silence there is one symptom of a stand-down that also silences the decay nudge, the type index, and the destination line. Run `memq decay-scan` when you need the answer, rather than reading a quiet session start as a checked one, and read that remedy against the fifth cause rather than past it: `decay-scan` is itself one of the verbs an unpinned network working directory stands down, so in exactly the state the fifth cause names it answers with its own refusal rather than with the drift count. The way to the answer there is to move off the share or to pin the store, never to re-run the verb.

**Three limits of this version decide how far a `fresh` line can be trusted, and none of them is softer than it reads.** Nothing normalizes Unicode, so one file name spelled NFD on one filesystem and NFC on another carries different bytes: Windows and macOS resolve either form to the same file, and on Linux an anchor written under the other form reads `missing`. Normalizing the recorded text is the worse trade, since it would make the anchor name a file the author did not write. The bar on invisible characters is an enumeration of named classes rather than Unicode's whole default-ignorable set, so a character of visible width zero that the list does not name, U+3164 HANGUL FILLER among them, is admitted: a path this grammar admits is one none of the named shapes was found in, never one proved to draw everything it carries, and homoglyph confusion stays the residual either way. And the hash is the git blob name, which is SHA-1, so it gives change detection and not tamper evidence. It is taken over the file's bytes as they sit on disk, with no decode, so a checkout holding the other line ending reads `changed` on every text file a record anchors. Those three and the grammar's own costs above are instances rather than the boundary of a set, and the class they belong to is one thing: this version records bytes and text exactly as it was given them and reasons about neither.

**An anchor path resolves against the project's main root, which is where the shared store lives.** Inside a linked worktree the records come from the main checkout's store and their anchors hash the main checkout's files rather than the ones being edited there, which is the coherent pairing rather than an oversight: one shared record hashing a different tree per worktree would report drift that was only ever about which directory a session opened in. What it costs is that anchors are not a check on a worktree's own edits, so re-anchor from the main checkout once the merge has landed there.

**A drift line means the memory is unverified, not wrong.** A file the record names holds different bytes than it did when somebody wrote the record down, and that is the whole of what any of the four surfaces knows: none of them has read the record's prose or the file's, so none of them is in a position to say the fact stopped being true. Any byte counts, a reformat or a trailing-whitespace sweep included, so the ordinary drift line is a file somebody edited rather than a fact that expired. Nor is it a stop: nothing about a drift line blocks the work in front of you, so settle the one naming a memory you are about to rely on, and sweep the rest at the Chapter boundary where `memq unstamped` already runs.

Re-read the anchored source file first, then the record against it. Which remedy the record earns is the routing question the four-remedies paragraph above owns, and what a drift line adds is that the question cannot be answered until that re-read is done. Read the record itself with the Read tool whenever what comes next is a rewrite, since that is what hands back the file's exact bytes, frontmatter and all, where `get` prints the same text with memq's own lines after it under a cap that can cut a long record. That same read is what a not-checked line obliges, because a `not checked` answer on any of the four surfaces carries a cause and never a path, so the record's own `anchors:` line is the only place its paths are still written down; fix what the cause names, the record's frontmatter block, the project's root, or the record's file itself, and the surfaces answer again. The mechanics are the project tier's own, none of the shared-tier verbs reaching it. Re-anchor by running `memq anchor` over the same paths again, which restarts the record's idle clock as any other verification does. Correct the record by rewriting its file with the Write tool, to the frontmatter rules the guard section below states, and carry its whole frontmatter block across into what you write, `anchors:` along with `tags:`, `created:`, `pinned:`, `machine:`, `supersedes:` and `triggers:`, each of which loses its entire effect silently if the rewrite drops it. A Write replaces the file, so a rewrite that drops the `anchors:` line silences the drift instead of settling it. A record that anchors nothing is the one state none of the four surfaces reports: `get` prints no line for it, `recall` gives it no token, the scan skips it before it can join any class, and every count on the session line passes it by. Then run `memq anchor` over the same paths again, because correcting the prose re-hashes nothing and the drift line stands until something does. That order is also why the `<name>.md.bak` the anchor run leaves is no way back from a bad correction: the backup is taken by the anchor run and holds the record as that run found it, which is the corrected text, and nothing anywhere keeps what stood before the correction. Supersede it by writing the replacement into the same directory, the memory write destination the session hook names at every start, carrying a `supersedes: <name>` line, that name being the replaced record's filename without its `.md`, which is at most 80 characters drawn from `[A-Za-z0-9_.-]`. Retire it with `decay-prune --archive <name>`, which demotes it to the tier's `archive/` and keeps it answering `get` by name.

The project tier has no delete verb at all, so taking a record out of the store outright is a hand move, and it reaches more than the record: unlink the file, take its `MEMORY.md` index line out with it, and unlink the copies of its text beside it: any `<name>.md.bak`, which every `memq anchor` and `memq triggers` run on that record leaves holding the text the record had before that run, and any `<name>.md.tmp.<pid>` a killed rewrite stranded there. Those two are the whole of what a rewrite can leave in a tier, which is why the decay pass sweeps that same pair when it retires a record, and no listing, no reader and no later rewrite ever touches either. The record's read and applied stamps stay in `usage.jsonl` whatever you do, no project-tier path dropping one record's stamps the way the shared-tier deletes drop theirs.

Then ask whether the case also needs a rotation, because an unlink is not a redaction. The two copies beside the record are local and stay that way, the store's sync refusing `*.bak` and `*.tmp.*`. The record's own text is the opposite case: a project tier syncs under `projects/*/memory` exactly as the shared tiers sync, so a record the store has committed is in that repository's history, and on the private remote once the store has been pushed. The deletion-and-history rule above states this for the shared tiers and the project tier is no different. So for the case the four remedies route to a delete, a record carrying a credential or a connection string, the hand move takes the record out of the store's answers and out of neither its history nor the sibling copy beside it: sweep the copies, and rotate the secret.

Never delete a memory on a drift line alone. A drift line is a nomination like every other line the scan prints, no `decay-prune` flag acts on one, and a pinned record is listed among them, because a pin exempts a record from retirement and not from being unverified.

## The `triggers:` field

A memory frontmatter field naming the deterministic signals a record should be recognized by, so a session that does not know to ask still meets the memory when its work touches what the memory is about: `triggers: cmd:git stash, err:module not found, glob:plugins/claude-kit/hooks/*.js`, one line of comma-separated `<type>:<pattern>` entries. Same line discipline and the same two placements as `tags:` and `anchors:`: written at the top level of the frontmatter block, and read there or under the `metadata:` map the harness moves it to. It is the sibling of `anchors:` and not an extension of it, because an anchor names a file at the bytes it held and a trigger names a pattern, which has no bytes to hash and nothing to drift.

Six types, and the type is what says how the pattern is read: `cmd:<pattern>` against a Bash command, `err:<pattern>` against a failed call's output, `skill:<name>` for a skill invocation, `agent:<type>` for an agent dispatch, `tool:<name>` for a tool name, and `glob:<path-glob>` for a path. The pattern is stored verbatim; what a pattern means against a running session belongs to the surface that matches rather than to this field.

**Four moments are matched, not one, and which types reach each is the moment's own answer.** The recognition nudge watches two points in every tool call and two in the session's lifecycle, and a type is offered only where the moment carries something for it to be about. Before a call (`PreToolUse`): `cmd:`, `skill:`, `agent:` and `tool:`, all knowable from the request, which is where a memory about a destructive command can still be acted on. After it (`PostToolUse`): `err:` and `glob:`, plus the record's file anchors, none of which exists until the call has returned. At the prompt (`UserPromptSubmit`): `skill:`, `agent:`, `tool:`, `cmd:` and `err:` from the project tier alone, matched against the prompt's own text, which is the earliest moment anything is known about the work. At a dispatch (`SubagentStart`): `agent:` alone, that payload carrying no subject but the type of agent starting, and the pointer lands in the subagent's own context rather than the dispatcher's, except into a read-only judgment seat (a blind, adversarial, security or prose reviewer, a consultant, a blind reader, a council member, a design facilitator), which is dispatched to hold a context that inherited nothing and receives no pointer at all. So a `glob:` pattern is a tool-stream trigger and nothing else, while the other five can also be met by a prompt that merely describes the work, from the project tier alone: a prompt is prose rather than a field, so every type matched against it is a guess about what the words mean and the two specificity bars screen a pattern against a command line or a failure's output rather than against English, so a pattern a person on another machine wrote would otherwise aim at the opening prompt of every session everywhere. Under a `KIT_MEMORY_PROJECT` store pin the prompt takes no tier at all, one pinned segment serving every repository the instance runs in, so the project tier there is no more one checkout's own than a shared tier is.

**What each moment may spend, since the four moments do not share one allowance.** A tool call may carry two pointers and a prompt three, each spent out of a rolling two-minute window of its own: a prompt burst cannot silence the tool call that follows it a second later, and neither can the reverse. A dispatch has no window at all, because each dispatch delivers into a context created for it that receives exactly one such event, so what bounds it is the three pointers of that one injection. A trigger fires once per trigger per record per session in each of three classes, so a record declaring two entries that both match can carry two pointers where one entry matching twice carries one, the tool boundaries sharing one class and the prompt and the dispatch holding one each, so a prompt that merely names a command does not spend the pointer the call itself would earn; and at the dispatch the count is per dispatched agent, since a subagent inherits no memory context and shares its parent's session id byte for byte.

**Write it through the CLI, never by hand, at either of two doors: `memq triggers <name> <type>:<pattern>...` on a record that exists, and `--trigger <type>:<pattern>` on the `add-type` or `add-operator` that creates one.** The verb splices a single line into the record, leaving every other byte, its body most of all, exactly where it was; the flag writes that same line, at the frontmatter block's top level, as the record is born. One grammar is enforced at both, so a record's line reads the same whichever wrote it and the verb merges into a line the flag wrote. The rest of this paragraph is the verb's, which is the door with the wider reach and the only one that touches a record that already exists; the flag's own half is the two shared tiers alone, at creation only, refusing the whole command with nothing written where any entry fails, and refused outright under the engine store signals. The verb reaches any tier: the project tier with neither flag, a run's own pending tier ahead of it, and the type or operator tier with `--type` or `--operator`, one of them or neither. `--type` has two spellings: bare, it takes its tier from the working project's declared `Project-Type`, and `--type=<type>` names the tier outright, which is what declares a type-tier record from a project that declares no type. Five of the six types reach a shared tier; a `glob:` entry is refused under either flag, because a glob names a path relative to whatever project root the matching session is in, so one on a tier every project on the machine reads would fire one project's record on another project's files. That is the same reason `memq anchor` refuses those tiers outright, and the recognition surface skips a hand-placed shared-tier glob for it too, so nothing is minted here that nothing would act on. The write merges rather than replaces, so an entry the line already carries keeps its position and one it does not carry is appended; an entry already on the line changes nothing, a trigger being its own value whole where an anchor carries a hash that can go stale. `--replace` is the other direction and the only one there is: it writes the entries the invocation names in place of the line, and naming none removes the line, so an entry declared wrongly can be narrowed, respelled or withdrawn without deleting the record. On the type or operator tier it takes `--confirm-shared`, refusing with nothing written without it: a merge only ever adds, where a replace states the line whole, so every declaration the record carried and the invocation did not name comes off it on a tier every project on the machine reads and every machine the store syncs to. The bar is on the flag reaching a shared tier at all rather than on a run that turns out to drop something, because which entries the record carries is exactly what a caller correcting it cannot be assumed to know. Under the engine store signals that same shape is refused outright, consent or no consent, on the bar the shared-tier body repair takes there: the `.bak` a rewrite leaves is local and never syncs, so on a fleet store a correction is as final as a delete. The merge still declares a trigger there, and the refusals that would otherwise hand a fleet worker the replacing spelling name that state instead of naming a command that environment answers with a refusal. Every bar above holds under it, the grammar, the shared-tier glob refusal and the entry cap alike. The two refusals that exist because a rewrite would drop text part company here, on what the caller can see rather than on how the two writes differ: a line cut at the reader's bound still refuses, its tail being text nothing has read and so text no report can name, while an entry no reader can read is dropped and named on stderr as it comes off, the refusal that would have stood in the way having shown the caller that entry by text in the first place. That is the shape the flag most has to reach, a declaration wrong in the one way the record itself cannot state, where the alternative is a delete that costs the record its body and its applied history. The line as written goes to stdout, and a `--replace` that leaves the record carrying none writes nothing there at all, a line with no value on it being a shape no record holds; stderr is where every run says what it did, which entries arrived, which came off, which were dropped as unreadable, and whether a replace corrected a line or wrote the record's first, two outcomes a mistyped record name is all that separates. A run that adds nothing writes nothing at all: it prints the line, says every entry was already on the record, and leaves the record's bytes, its backup generation and its mtime exactly as it found them, re-declaring a trigger verifying nothing the way re-hashing an anchor does. A `--replace` whose resulting line is the one already on the record is the same answer for the same reason, and so is one naming no entry against a record that carries no line. A run that does add an entry rewrites the line, leaves one generation of the record's previous text in a `<name>.md.bak` beside it, swept by no listing and carried by no sync, and moves the record's mtime, which the decay clock reads as a sign of life. On a shared tier that deferral is not this project's alone: `lastAliveMs` reads the record's mtime, so one project declaring a trigger on a type-tier or operator-tier record postpones that record's archival for every project reading the tier and for every machine the store syncs to. Declare a trigger on a shared-tier record because the recognition is worth having, not to keep a record alive. What the shared tiers still owe is on the digest: `memq recall` counts the records of the type tier and of the operator tier that declare no trigger, on each tier's own coverage line, and a record born through an add verb with no `--trigger` says so on stderr as it lands.

**Two specificity bars, and neither one subsumes the other.** A pattern shorter than four characters is refused, and a pattern that is a bare common token is refused whatever its length, compared without regard to case: `cmd:git` fails the first and `cmd:node` fails only the second. The bar is the bare token rather than the word, so `cmd:node --test` is admitted. Both exist because a pattern loose enough to appear in unrelated work nudges on everything and is read as noise within an hour, which costs more than the memory it was pointing at. What they screen a fragment against is a command line or a failure's output, which is the whole of their reach: neither bar says anything about English, so what keeps a stored pattern off a prompt's prose is the reader's project-tier confinement instead.

**The two bars reach different types, because they are not true of the same thing.** The length floor is asked of all six. The bare-token bar is asked of `cmd:`, `err:` and `glob:` alone, those being the types whose pattern is a fragment of something longer, where a bare token means the author stopped too early and lengthening it is a remedy they can act on. A `skill:`, `agent:` or `tool:` pattern is the whole identifier and has no longer spelling, so the same bar there would not ask for a better pattern, it would make the trigger unauthorable: `tool:Bash` and `tool:Grep` name the tools they name. That is why `tool:Bash` is admitted while `cmd:Bash` is not, and why the refusal an identifier meets at the length floor says the name is too short rather than telling its author to lengthen something they do not control.

**What holds the identifier types to their names is the matcher, and it is not the same comparison at every moment.** A tool call carries the identifier in a field of its own, so `skill:`, `agent:` and `tool:` are compared to that field whole: `tool:Bash` names Bash and not BashOutput. A prompt carries no such field, only free text, so the same three are matched there on a WHOLE TOKEN, the identifier having to stand as its own word rather than merely appear inside one; the separators a qualified spelling uses are boundaries, so `agent:implementer-opus` still meets a prompt that writes `claude-kit:implementer-opus`. That is what keeps a four-character identifier honest at the boundary with no field to compare against, since bare containment would make `tool:Read` a matcher for "thread", "readme" and "spread", and a false positive there is worse than noise: a trigger fires once per trigger per record per session in the boundary's own class, so the wrong match spends that class and the right one never arrives. An above-ASCII LETTER is a token character for that reason, so an accented or CJK neighbour joins the identifier rather than bounding it, while the punctuation, separator and surrogate blocks of that range are boundaries, so a curly quote, a zero-width space, an ideographic full stop or an emoji written straight against the identifier leaves it standing as its own word. A hyphen or a dot is a token character wherever it joins two word parts, so "read-only" and `notes.bash.md` are compounds rather than the identifiers inside them while the same characters ending a sentence stay punctuation; a slash is a boundary always, so a prompt writing "Read/Write" or "Edit/MultiEdit" names both identifiers; the colon is a boundary always, which is what lets `agent:implementer-opus` meet a prompt writing `claude-kit:implementer-opus`. `cmd:` and `err:` stay containment wherever they are matched, being fragments of something longer by construction, which is the same split the bare-token bar above is drawn on. That reading of prose is tolerable only where the record reaches one checkout, which is why the prompt takes every type from the project tier alone and takes none at all where a store pin has made that tier one many repositories share.

Every refusal leaves the record byte for byte as it was, and the shapes worth knowing before you run it are these. They are the verb's list. The flag shares the grammar shapes and none of the rest, the ones from the name onward being about a record that already exists, and it carries two the verb has not in this shape, a refusal under the engine store signals reaching every entry it would write, where the verb's own refusal under those signals reaches one shape alone, a `--replace` on a shared tier or a pinned project store, and an entry count over the cap; where the flag refuses there is no record yet, so nothing at all is written, neither a record file nor an index line. An entry outside the grammar, with every refused entry named together rather than the first one alone, so a caller who mistyped two of four fixes both on one rerun: a type outside the six, a pattern past 256 characters, a comma, which is the line's own separator, an invisible character, a quote of either kind, an opening bracket, a backslash, any whitespace but the plain space, which is admitted inside a pattern and never at either end, and either specificity bar where it is asked. Three sequences ride with those, and they are the price of admitting the space at all, since the line is a YAML plain scalar and a space is what turns three ordinary characters into syntax: `": "` opens a mapping value, so a pattern carrying one writes a line no YAML reader parses and takes the record's whole frontmatter block down with it, the `pinned:` included; `" #"` opens a comment, which is worse because it parses and silently stores a shortened pattern; and a trailing `":"` is a mapping indicator wherever merge order puts that entry at the end of the line. The bars are spelled at the sequences rather than at the characters, because an error signature has colons in it by nature, so `err:Error:cannot find module` and `cmd:foo#bar` are admitted while `err:Error: cannot find module` is not. The opening bracket is barred for a different reason: `get` prints an admitted entry verbatim at column zero beside refusals annotated as `[note; note]`, so a pattern free to spell `[` could forge one of those annotations byte for byte. The backslash is barred for a third reason, and it is about the round trip rather than about any reader: a double-quoted YAML scalar spells one as a pair, and the read back takes a surrounding quote off without undoing that escape, so a pattern carrying a backslash comes back doubled and stops being the entry its author re-declares, which appends a second entry rather than matching the first and doubles again on the pass after that. A win32 path in a `cmd:` pattern is therefore spelled forward-slashed. A `glob:` pattern takes the anchor path grammar with `*` and `?` admitted, so it is relative, forward-slashed, and refuses an absolute path, a `..` segment, a backslash, a colon, a dots-only or trailing-dot segment, a win32 reserved device stem and a leading YAML indicator; the one place it is stricter than an anchor path is the single quote, which the path grammar refuses in the lead position alone and this field refuses anywhere in the pattern, on the same round-trip reason. A name the store will not answer for, or a pending tier whose entry for that name could not be examined, which is refused rather than read as an absence, since reading it as absence would rewrite the shared project-tier record of that same name and report success. A record no reader can read: a frontmatter block that opens and never closes inside the reader's line bound, a `triggers:` key sitting under something other than `metadata:`, and bytes that are not valid UTF-8. And a line the write cannot preserve whole: one already carrying an entry the reader refuses, which the merge refuses on and a `--replace` drops and names instead, one already longer than a reader reads, which refuses under both, and a write that would push the record past the 32 entries a reader takes.

Three surfaces read the field deliberately and the rest do not, which is worth stating because the anchors field's reader list is longer. `memq get` follows a record's body with one `triggers:` line per entry, and nothing at all for a record that declares none; a record whose frontmatter could not be read gets one line naming that cause, and a line cut past what a reader reads gets a row saying the rest is unread. Every tier's record is listed, unlike the anchors field beside it, whose shared-tier rung cannot be checked at all: a trigger is a pattern that resolves against nothing, so there is no project root a shared tier lacks. Where the lines sit follows the body's own framing rather than the tier, because the entries are the record's own text and not memq's: they ride wherever the body rode, at column zero for a body the reading session owns and indented two spaces under the provenance fence for a body that printed under one, which is the store-wide rule that an indented line is data and only memq writes at column zero. A cause memq states about a record it could not read is memq's own sentence and stays at column zero either way. The frontmatter guard reads it at the write door, refusing an entry outside the grammar on a Write, an Edit or a MultiEdit that lands one. `memq recall` reads it to count, not to print: each shared tier's coverage line carries how many of that tier's records declare no trigger a reader admits, and no line of the digest says what any one record recognizes. `decay-scan` reports no triggers column, because a pattern has no bytes that could have changed and so has no drift to report.

**`find` carries no trigger label on either channel, which is not the same as not reading the field.** No hit line says anything about what a record recognizes, in either direction, exactly as none carries an anchor label. What the semantic channel does with the text is separate and worth knowing before you compose a pattern: the embedder reads each record file whole, its frontmatter block included, so a `triggers:` line's text is part of what that record's vector is built from, and it keys re-embedding on a hash of those same bytes, so a `memq triggers` write changes the record's hash and the next `find` re-embeds it. A pattern is therefore a few words of search surface as well as a recognition rule, and a line of them shifts the record's vector by however much text they add.

**A `cmd:` pattern is a command line, which is where a token gets typed.** The pattern is stored verbatim, and the project tier syncs to the private remote exactly as the shared tiers do, so a pattern is in that repository's history the moment the store is pushed; the semantic index embeds the record file whole, its frontmatter included, so the pattern is in the local index too. The rule the record's body takes therefore takes the field as well: a record that carried a credential needs that credential rotated, and neither a rewrite of the line nor an unlink of the record is a redaction. Name the shape of the command rather than the invocation that carried the secret.

Under the engine store signals the verb gets no grant at all, for the reason `anchor` does not, and over a wider blast radius: it rewrites a record of any tier in place at a name the command line gives it, and the line it writes decides when that memory is put in front of a session. On the shared tiers that is recognition aimed for every project on the machine and every machine the store syncs to, rather than for the one project a worker was pointed at.

## The nudge log and the stamp-rate reading

Every nudge `memory-recognition-nudge.js` actually claims for a session also appends one line to that project's nudge log, `.kit/memory-recognition-nudges.jsonl` under the project's resolved main checkout root, so every worktree checked out from one repository shares one log rather than splitting it per checkout: gitignored, machine-local, never synced, and never read by the store or by any hook. With no store pin set that root is the same resolution `projectMemoryDir` keys the project tier on, which is what makes the reading below a join of two views of one project. Under a `KIT_MEMORY_PROJECT` pin the two part company deliberately: the pin renames the store segment the tier lives in and says nothing about where this box's working tree sits, so the tier follows the pin while the log stays at the checkout. A pin that changed between a nudge and a reading therefore joins one checkout's log against a different segment's stamps, and the honest move is to read a window across which the pin did not move. The line is `{ts, name, tier, type, pattern, boundary}`, the record named, the tier it was matched in, the trigger that fired, the moment, and the boundary the pointer was delivered at, and it is written once per record a claimed emission names, inside the same lock that claims the emission, before that lock releases, never after and never once per call. The boundary rides on the line because it is also where the pointer landed: a `SubagentStart` line reached a dispatched agent's own context and every other line reached the session's, and the reading below splits its arms on that difference. Absence of the file reads as no nudge has fired yet on this box, the same convention the store's own sidecars take for an absent `usage.jsonl`, and the log is bounded: past 1 MB it rotates to `.old`, replacing any previous one, so a window wide enough to reach past that rotation sees fewer nudges than actually fired rather than an error saying so. That is the log's one honest gap, worth stating before reading a wide window's numbers as complete.

The write lands on a claim, not on a confirmed delivery: the append happens once the marker that reserves this nudge's slot is written, before the hook's own process has emitted the line to the session's transcript. A process that dies between the marker write and the final `fs.writeSync` to the response channel can leave a logged nudge nobody actually saw, so the log is evidence of what this hook decided to show, not a certified receipt of what a session read.

This is the instrument decision 2 reads: Tier 1's deterministic recognition ships on its own merits, but a semantic tier that matches by meaning rather than by declared trigger is designed only once nudging is shown to change behavior at all, since a semantic tier with unproven nudge precision is an expensive way to get ignored. The reading is a join, done by hand or from a short script, never by a `memq` verb, because it correlates two records the store itself keeps apart: this log, which is not part of the store, and the project tier's own applied stamps, which are. `memory-recognition-nudge.js` exports the join as `nudgeStampRate(cwd, sinceMs)`, requiring cwd as the project working directory and sinceMs as the window start in epoch milliseconds, since a report with no stated window is exactly the shape this reading must not produce. It splits the project tier's live, nudgeable records (every record the index would ever consider nudging, meaning it carries at least one declared trigger or anchor) into three groups: **nudged**, every such record the log names at least once with `ts >= sinceMs` on a project-tier line delivered into the session; **dispatched**, every such record named only on lines delivered into a dispatched agent's context; and **unnudged**, every other such record. The dispatched arm is held apart because a pointer that landed in a subagent's context reached a reader that ends with the dispatch, so such a record is no fair control and is not evidence about the channel the gate asks about either: folded into the nudged arm it would grow that denominator with a population that cannot realistically earn an applied stamp. The tier filter is what keeps the join honest now that the nudge itself spans three tiers: both groups come from the project tier's own listing, so a shared-tier line naming a record whose name the project tier also holds would score that project-tier record as nudged on another tier's evidence. Widening the reading to the shared tiers is a separate question, since their applied stamps are written by every project on the machine while this log holds one project's nudges. A record that carries no trigger or anchor at all could never earn a nudge and is excluded from both groups, since it is not a fair control for one that could. A record counts as **stamped** within the nudged group when its most recent applied evidence (the same `lastMs` the decay clock itself reads) falls no earlier than that record's own first nudge in the window, within the dispatched group when it falls no earlier than that record's own first dispatch-delivered nudge in the window, and within the unnudged group when it falls no earlier than `sinceMs`, so a record nudged only near the end of the window is not charged for failing to earn a stamp in time it was never given. The answer is `{since, nudged: {total, stamped, rate}, dispatched: {total, stamped, rate}, unnudged: {total, stamped, rate}}`, with `rate` `null` rather than `NaN` where a group is empty, or `{error: <cause>}` on the same causes that leave the hook itself silent (an unloadable memq, a network-shaped working directory or store root, or a project memory directory that cannot be resolved), plus four the report alone can hit. Three of those are a bound that would shorten one side of the comparison without saying so, and each refuses rather than understate: the tier listing was cut short by this hook's own per-call cap, the trigger index was cut short by its byte bounds, or the nudge log is larger than the report's own read bound, which matters most of the three because that read fills from the front and so drops the log's newest lines, the very nudges a recent window is about. The fourth is the usage sidecar existing but not being readable, which is a different answer than the sidecar never having been written and is not folded into a zero rate.

```
node -e "console.log(require('<plugin-root>/hooks/memory-recognition-nudge.js')
  .nudgeStampRate(process.cwd(), Date.now() - 7 * 24 * 60 * 60 * 1000))"
```

Run it from the project directory the report is about. The two halves of the join are resolved by one rule: the memory tier comes from `memq`'s own resolution of that working directory, and the log root comes from the path-side half of that same resolution, so a worktree and a subdirectory the session's transcript places inside the project both read the tier and the log of the one project rather than pairing one project's records with another's log. `<plugin-root>` is `CLAUDE_PLUGIN_ROOT` where the harness supplies it and this skill's own base directory's grandparent otherwise, and it is spelled with forward slashes whatever the platform: the argument is a `require` specifier inside a JavaScript string, where a win32 backslash reads as an escape. A relative specifier is not the substitution to make. It resolves against the working directory rather than against the plugin, so it names the hook only from a checkout of the kit itself, and the reading's subject is every project's log rather than that one.

Read `nudged.rate` against `unnudged.rate` rather than either alone: the gate decision 2 names is whether a nudged record is stamped applied more often than one nothing nudged, not whether nudged records get stamped at all. `dispatched.rate` is read beside them rather than folded into either, as what the dispatch channel is worth on its own evidence. A record the tier has since retired or that decayed out between the nudge and the reading is in neither group, so the comparison is always asked of the tier as it stands at read time, and a record renamed since the nudge fired lands on the two arms unevenly, the log keying on the name it wrote at the time: the old name is gone from the tier and falls out of both arms, while the new name is live, nudgeable and named nowhere in the log, so it joins the unnudged arm and any application of it after the rename is counted as a control success. That leans the reading against the feature rather than for it, which is the safe direction for a gate, but a window spanning a rename is worth reading knowing the rename is in it.

This reading cannot, on its own, tell "the nudge caused the application" apart from "the records worth nudging are already the ones relevant to the work in front of the session, which get applied more regardless of whether they are nudged." A nudge only fires on a record whose declared trigger or anchor matched something the session just did, so the nudged group is selected for topical relevance before the comparison starts, and a materially higher nudged rate is evidence consistent with the nudge working, not proof of it: the same comparison would come out positive with the nudge text replaced by silence, if silence still let the session notice the same trigger by other means. Decision 2's gate treats this reading as one input among others for that reason, not as a number that alone justifies building the semantic tier.

## The decay lifecycle

A memory's idle clock starts at its last sign of life: the freshest of its file mtime, its optional `created:` frontmatter date, and its newest `applied` stamp. `read` stamps never reset the clock. The base thresholds are 30 idle days for a summarize candidate (condense the body, keep the index description) and 60 for an archive candidate (move to the tier's `archive/`, index line carried to the archive's own index). A summarize edit resets the mtime, so the archive threshold is reached 60 idle days plus the memory's extension after the summarize, rather than that span after its last application. A retirement takes the record's copies of its own text with it: a backup a rewrite left (`<name>.md.bak`, from a shared-tier repair or from `memq anchor` or `memq triggers` on the project tier) and any temp file a killed rewrite stranded (`<name>.md.tmp.<pid>`) move into `archive/` beside the record, in every tier, so a copy of a retired body does not sit in the live tier, where no reader lists it and no rewrite overwrites it. A copy the pass cannot move, because the archive already holds that name, because either end is not a plain file, or because the rename fails, stays where it is and is named in the report; a re-run attempts it again.

**Use extends the thresholds, and never confers permanence.** Each distinct calendar day a memory was applied pushes both thresholds out, capped:

```
extension       = min(distinctDays * 30, 365)     idle days
summarize after = 30 + extension                  idle days
archive after   = 60 + extension                  idle days
```

So six days of recorded use buys 180 extra idle days on each threshold, and the cap first binds at thirteen days: past that, more application moves nothing. Both tests are inclusive, so the most extended memory is a summarize candidate at 395 idle days and an archive candidate at 425. Linear with a cap, not doubling, deliberately: a multiplier reaches effective permanence within a handful of reinforcements, and nothing here is permanent by accumulation. Distinct days, not raw counts, so one busy afternoon is one reinforcement no matter how many times you stamped it.

Crossing a threshold nominates; it does not retire. The scan line carries the tally (`applied <date> (<n>d distinct)`) so the judgment is never blind, and the archive is recallable, so the worst case is demotion rather than amnesia.

**A superseded record is an archive candidate whatever its idle clock**, and the pointer rides the scan line as the evidence. Archive rather than summarize: the pointer short-circuits ahead of both threshold tests, so a heavily used record a fresher one replaces skips the summarize rung entirely and arrives at the pass as a retirement to judge. The applied-day extension does not hold it back: what the extension buys is time for a fact still in use, and a pointer says the store has a newer answer for that fact, so a heavily used record a fresher one replaces is nominated too. Two things outrank the nomination. A pin does, because a standing exemption granted by judgment is not overturned by a model-written pointer, and the pinned line still carries the pointer as evidence. And a tier whose usage sidecar could not be read nominates nothing, pointer included, that gate being about the pass's own blindness rather than about the record. Nomination and never retirement, for the same reason the label is a label: the pointer is hand- or model-written data, so a wrong one must cost a mislabel rather than a fact.

These numbers, and `NEIGHBOUR_FLOOR`, the similarity at which the authoring verbs' neighbours block and the scan's neighbour-pairs block read two records as one fact, are seeds rather than measurements, backed by no tally from this store, so tune them on evidence at a decay pass that has some, and do not widen them speculatively.

### Pinning

A `pinned: YYYY-MM-DD` line in a memory's frontmatter makes it never a summarize or archive candidate, and makes `decay-prune` refuse it by name. Write it at the top level; it pins there and under the `metadata:` map the harness moves it to. The date records when the judgment was made and is never parsed; presence of the field is the pin.

**A pin is a judgment act, and the tally is evidence for it, never its trigger.** Nothing about a high applied count grants a pin automatically, and nothing should: a count is a signal with no owner, and a rule keyed to it would grant standing exemptions nobody decided on. Set a pin in the turn a memory proves itself structurally load-bearing, or at a decay pass when a candidate is one you know must not age out. The case it exists for is systematic under-reporting: a memory you recognized from an index already sitting in your context passes neither reader, so its stamps undercount its true use and the formula under-extends for exactly the most ambient memories.

Revoke by deleting the line. There is no override flag, because removing the field is the override. What memq enforces is narrower than that sentence sounds: no write path emits a `pinned:` field and no path removes one, in any tier. So a shared-tier pin arrives only by an operator's own edit or by a file synced from another machine, and it leaves the same way. It happens outside the harness, in an editor or in the store's own checkout, because the frontmatter guard refuses Write, Edit and MultiEdit on both shared tiers whoever is writing, at the scope its own section below states exactly, so a session that meets that deny and retries the same tool on the same file meets it again. That edit is the one exception to the bar on hand-editing a shared tier, and it is an exception by necessity rather than by permission: the bar exists so authoring writes serialize under the tier lock, and a `pinned:` field has no authoring path to serialize. Do not reach for `delete-type` or `delete-operator` to clear one: the delete drops the record's usage stamps too, so a rewritten record starts with a zero applied tally and none of the threshold extension the old one had earned, and it meets another machine's copy as a modify/delete conflict that stalls the store's sync both ways. The delete verbs deliberately do not refuse a pinned record for exactly that reason, since refusing there would leave a pinned shared record removable by no path at all. So read a pin as binding the decay pass and nothing else. Every scan counts the whole pinned population and lists the first ten with a counted remainder, so the exempt population cannot grow unobserved even once it outgrows the listing.

Three grammar rules the scan enforces, all because a silent non-pin is the damage: the field is written at the **top level** of the frontmatter block and read there or under `metadata:`, never under another key (a `pinned:` under any key other than `metadata:` does not pin, and the scan names the memory when it sees one); the block closes with its `---` (a `pinned:` in body prose after a horizontal rule pins nothing); and that closing fence falls within the first 40 lines, which bounds the whole frontmatter walk. The opener takes the first of those lines, leaving 39 for fields, and the harness's own lines come out of the same budget. How many those are is the variant's to decide, the same variation the placement section above describes: across the records on one machine the spend runs from four lines to seven, and seven is the common case (a top-level `name:` and `description:`, the `metadata:` key, and four keys under it), which leaves a hand-written block 32 lines to work in. Budget for 32 rather than counting a particular record's header, since the harness may spend a line more at any version. Overrunning it is not a partial loss: when the closing fence lands past the bound there is no frontmatter block at all, so every field goes dark together, a `pinned:` on the block's fourth line included. The scan does not stay silent about it: it reports the record as `not classified` (the same note an unreadable file gets, since a pin sitting inside a block nothing reads is unknown either way) and names the repair the record's tier admits.

### Reading the scan's evidence line

Every `decay-scan` prints a standing usage-evidence line per tier, reporting what it actually read: a count of stamps and files, or `none` with the reason. It is unconditional rather than a warning, so a fresh store and a lost sidecar are both legible and neither alarms falsely. The line rides stderr while candidates ride stdout, so read it alongside them rather than expecting it in a captured stdout. `usage evidence: none (no usage.jsonl)` on a store you know has been used means the sidecar is gone and every memory is reading as never-applied; that is not a store full of dead memories, it is a store that lost its evidence, and the right move is to investigate rather than to archive. When a sidecar was not read whole, the file unreadable or a malformed line skipped inside it, the scan suppresses that tier's candidates entirely rather than computing them from evidence it knows it failed to read; a skipped line is the same loss at line grain, since a torn applied append is exactly where a memory's applied evidence can be hiding, and the evidence line counts the skipped lines beside the stamps that did read. The torn line itself has one sanctioned exit, because every read path and every default rewrite preserves it and hand-editing the sidecar is banned, so left in place it would suppress that tier's candidates on every future run: `decay-prune --rollup --drop-malformed` removes what the rollup rewrite otherwise preserves, under that rewrite's own `.bak`, stating its per-tier counts on stderr before anything is removed, saying each removed line, and counting the removals in the report. Preserving stays the default, and three bounds ride the flag. It is invocation-wide: the rollup rewrites the usage sidecar of every tier the pass reaches, so the drop removes malformed lines from the type and operator tiers as well, never only from the tier whose evidence line reported the skip. The removal is local hygiene rather than a redaction, the delete verbs' own caveat: the sidecars merge by union across the store's sync, which cannot express a removal, so a dropped line another machine still carries comes back at the next merge, and the shared tiers replicate to a private remote whose history keeps the bytes regardless. And it refuses any tier where no valid stamp would survive the drop: a wholly unparseable sidecar is evidence to investigate rather than growth to reclaim, so the refusal is named on stderr, that tier's file stays byte-unchanged, and the rest of the pass proceeds.

### Running the pass

Journal entries older than 30 days are rollup candidates: `decay-prune --rollup` folds them into one per-key rollup entry that preserves the pass/fail tally and the union of the entries' tags, and never re-flags its own rollups. The same flag folds each memory's `applied` stamps into one per-file record carrying its distinct-day count and its first and last application, which is what keeps the reinforcement tally computable after a prune; `read` stamps prune to the newest per file. A sidecar line the rewrite cannot parse is preserved in place by default; `--drop-malformed`, which rides `--rollup` and is an argument error without it, is the one path that removes such lines, the exit the evidence-line section above names. The rollup and the usage prunes run only under `--rollup`; an archive flag alone moves what it names and touches nothing else.

`created: YYYY-MM-DD` is an author-asserted sign of life: because the clock takes the freshest evidence, it can defer decay when file times understate recency, and can never age a memory faster than its mtime shows. Write it at the top level, like every other field here; the clock takes it there and under the `metadata:` map the harness moves it to.

The pass runs at close-out; finishing-work step 7 owns the trigger (a decay stamp older than 14 days, or absent: a store where no pass has ever run is due, not exempt) and the run: `decay-scan` reports, your judgment picks (the summarize edit is the pass's only hand edit, and a hand edit belongs to the project tier alone: a shared-tier candidate is summarized through `add-type` or `add-operator` with `--update`, a body flag and `--confirm-shared`, the same whole-body replacement under the tier lock), `decay-prune --rollup` with the archive flags mutates, `decay-done` stamps. `--confirm-shared` is one flag for the whole invocation rather than one per target, and the pass's shape follows from that. `--archive-operator` always needs it, the operator tier having no unshared case, so that gate is unconditional consent with no decision behind it: a mistyped name is caught separately, by the target check that refuses the whole pass naming the memory it could not find. The type tier's gate is the opposite, the one moment a retirement reaching past this project stops for a second look, and pre-supplying the flag waives it. Since one boolean serves both, give any operator-tier archive its own `decay-prune` call and run the type-tier archive in a separate one without the flag. `--rollup` rides exactly one of the calls, the project tier's, because a second run of it can rewrite a sidecar a lock-free stamp has touched since the first and spend that file's only backup generation on the already-pruned copy. Add `--confirm-shared` to that type-tier call only once the refusal has named the projects the retirement would reach. Where the refusal instead reports that the scan of declaring projects could not be established, the reach is genuinely unknown and confirming past it buys the retirement the gate exists to ask about, so that one is a question for the operator rather than a flag to add. Combining the two in one call waives the type tier's gate silently, which is the whole reason to split them. A pass that needed the flag and omitted it refuses having changed nothing rather than archiving what it could, so a retry costs a round and no work. Under the engine store signals the grant covers the bare `decay-prune` and its archive flags but not `--rollup`, so a pass there archives what it names and leaves the journal rollup to an attended session. The SessionStart hook nudges when the stamp is 30+ days overdue. Outside a close-out, do not run `decay-prune` unprompted.

## The frontmatter guard

A project-tier memory arrives through the Write tool, so none of the refusals the shared-tier verbs apply ever runs over it, and neither does their neighbours block: no verb sees that write, so run `memq find` in the words of the fact before the Write. Its semantic block is the substitute available here and not the same reading: the scores are the same similarity, but the block ranks by blended rank with the applied boost and the supersession demotion folded in, is capped at its own count, and carries no `likely overlap` label, so read each score against `NEIGHBOUR_FLOOR` yourself, taking the value from memq's own source; and a record the lexical block already listed is withheld from the semantic block and shows no score, so read a lexical hit as an overlap candidate on its own. `hooks/memory-frontmatter-guard.js` is the check at that door, a PreToolUse hook in front of Write, Edit and MultiEdit, and the only surface that sees a record before it exists. It computes the content the call would leave on disk (an Edit's replacement applied to the file, a MultiEdit's edits in order), and where that content carries a frontmatter block the call actually changes it holds the block to the rules stated above: a `supersedes:` naming a live record of the same directory in that exact casing, an `anchors:` entry inside the grammar and under the project root, a `triggers:` entry inside its own grammar, both specificity bars included, a `tags:` line in the inline form rather than the YAML list, a memq field at the top level or under `metadata:` and nowhere else, and a `pinned:` or `created:` value in the `YYYY-MM-DD` form. It refuses a block that opens and never closes, and one whose opening fence is not the file's first line, because memq reads either as a record declaring no fields at all: a `pinned:` inside one pins nothing and a `supersedes:` inside one points nowhere, with nothing anywhere saying so. Where a field may sit is memq's own judgment throughout, taken through its exports, so the guard and the readers it guards for cannot come to disagree about placement. That agreement is exactly as wide as the exports and no wider: the guard re-spells memq's own frontmatter read cap rather than importing it, memq exporting no name for that one, so those two bounds are held in step by maintenance rather than by construction.

**Both shared tiers refuse all three write tools, whoever is writing.** The rule is "never the Write tool" rather than "not by subagents", so the main session meets the same deny a subagent does, in one stderr line naming the memq routes that author that tier, one per thing the blocked write could have been doing. The matcher names those three tools and nothing else, so a shell redirection and an edit made outside the harness pass it untouched; the CLI-authored rule above is what governs those, and the operator's own `pinned:` edit is one of them.

**The guard answers three ways, each on the channel its reader is on, and the two allows are never one answer.** A deny exits 2 and writes one line to stderr, which is what the harness delivers to the model as the reason the call was blocked. A record checked and clean exits 0 and writes nothing on either channel. A record the guard placed inside the store and then could not check exits 0 exactly as the clean one does and says so on stdout, as the `hookSpecificOutput` object that is the one exit-0 channel the model receives, naming the tier and the cause and stating plainly that the write is going ahead unchecked. Everything else allows, and placement is what decides which of the two allows it gets. Once a target is placed inside the store, a parse error, an unreadable file, an unresolvable root and a throw out of the check itself are all the third answer, with their cause on stdout. Before placement there is no record for such a line to be about, so a target out of scope, one under an `archive/`, one that is not a memory filename, one no spelling places, a payload carrying no target, and a throw taken on the way there are the silent allow. Read this guard's silence as a statement that nothing here was its to judge, never as a judgment that came back clean.

**Read the shared-tier claim at the scope the code makes it, which is narrower than "the shared tiers refuse the Write tool".** What the guard refuses is the shared tiers of the store this session resolves, not every shared tier on the machine: under a `KIT_MEMORY_ROOT` override memq honors, the machine's real tiers sit outside the guard's root and a write to one of those is unrefused. The run-scoped pending tier is not a tier directory to memq's own resolver, so a record written there is out of scope and unvalidated. Neither is a shared tier's `archive/`: a tier directory is the tier itself and nothing nested under it, so `memory-operator/archive/` and `memory-types/<type>/archive/` place nothing, and a record written into one of those is allowed in silence, with no deny and no not-checked line, while `memq get` still serves it by name and the store still syncs it. And `MEMORY.md` is out of scope on every tier, the shared ones included, alongside the decay stamp and the sidecars, because `isMemoryFilename` is memq's own boundary for what a record is and re-deciding it in the guard would be a second grammar. Those are the members worth naming rather than the boundary of the set, which is one class: a target the guard cannot place inside the store is a target it says nothing about. Placement takes two passes before it gives up, so the class is narrower than a lexical screen would make it. The written spelling is tried first, with the extended-length and device prefixes folded off and an administrative-share UNC naming this machine rewritten to its drive form; then, for a target that is already under the store root and is not itself UNC- or device-rooted, the parent directory's resolved real path is tried, which places a short name of a component inside the store and a link or junction inside it. What survives both passes is a target that reaches the store only through an alias of the root itself, which its own header records: an administrative share by a fully qualified or aliased host name, and a mapped or substituted drive letter.

## Known limits

- A type tier is reachable only through a declaring project: when the last project drops its `Project-Type` line, the tier's files stay on disk but no scan or prune reaches them. Re-add the line in some project of that type before running a pass over it.
- The type lock can be wedged by a directory or a non-JSON-object file sitting at `~/.claude/memory-types/<type>/store.lock`; no memq command recovers that. Manual recovery: confirm no writer is live, then delete that entry by hand. The lock is availability only; store integrity does not rest on it.
- `read` stamps undercount true use. `memq get` stamps the tier it resolved a name from, so a body fetched through the CLI is the same evidence as one opened with the Read tool, but no stamp can see a memory you recognized from an index already in your context, whether the session hook put it there or the harness's own auto-memory did: that path passes neither reader. `applied` stamps carry the decay decision regardless, so `touch --applied` on a memory you act on matters more, not less, and a pin is the answer for a memory whose use is structurally invisible. This is also the boundary of `memq unstamped`: it can only offer what a read stamp saw, so a memory recognized from an index already in context never reaches its list. The command names that boundary itself at the point it bites hardest. With nothing to adjudicate, no read stamp in the window, and its usage evidence read whole, its closing verdict calls the zeros an absence of evidence rather than a clean sweep and points at this skill for the readers that leave none, which the gaps paragraph above enumerates. Where the same zero comes with unread usage evidence behind it, the verdict leads with the loss instead and names no reader, that report having no ground to say nothing reached the tracker at all.
- The archive's index grows one line per memory ever retired and has no bulk prune path; the shared-tier delete verbs are the only thing that takes a single line out of it, and the project tier has no delete verb at all. `recall` caps its read and says so when the cap binds, so the growth costs a bounded read rather than an unbounded digest, but a store archiving for years will eventually want that file trimmed by hand.
- A project store syncs across machines under its flattened path, so a project tier resolves on another machine only where that project sits at the identical path. Same-path discipline is the convention and there is no mapping layer. The type and operator tiers carry no path in their names and resolve everywhere.
- The semantic index is derived and per-machine, never synced: a vector is valid only against the embedder that produced it. Each machine builds its own on first query, so a freshly synced store answers lexically until that sweep runs.
- Two kit paths commit the store, and both go through the same leak probes that refuse a path the allowlist does not admit: the background sync runner the SessionStart hook spawns on Windows, and the kit doctor's `-Fix`. Nothing else does, which is why the close-out relies on one of those rather than a bare `git add`.
